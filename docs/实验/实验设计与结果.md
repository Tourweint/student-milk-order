# 实验设计与结果

> 本文是「周期性业务履约的状态管理与异常恢复」的**验证层**文档：用可重复的并发实验，验证
> 状态迁移、幂等、资源一致性、异常恢复这几套机制是否真的成立，并记录实验过程中暴露的缺陷与修复。
>
> 配套文档：`实验环境与运行说明.md`（如何搭建与运行）、`../基线文档/业务过程与可靠执行模型.md`（机制设计）。

## 0. 实验总览

| --- | --- | --- | --- | --- |

| 实验六 | 补偿规则引擎 | 补偿规则由规则表驱动、且仍受迁移闸门约束 | 启用 vs 停用规则；闸门放开 vs 禁止 | 停用规则即不补偿；闸门禁止则不落地（补偿不绕过可靠性层） |
| 实验七 | 跨表不变量体检 | 7 类跨表约束可被持续检出；可逆项自动修复、涉资金/终态/在途项仅告警；修复按声明依赖顺序执行 | 健康数据零误报 vs 注入 4 类违规；资金项；终态父过程下「待配送 vs 配送中」；终态订单网格缺口 | 4 类检出 4/修复 4、复检 0，订单未被误判、组合守卫零触发；资金项与在途任务只告警；终态网格缺口不补造历史 |
| 实验八 | 实时自愈与兜底双通道 | 实时通道把不可检测窗口从分钟级压到秒级；失败可退避与放弃 | 实时通道 vs 兜底通道周期；成功 vs 必然失败路径 | 实时窗口 ≈ 5.0 秒 vs 兜底 600 秒（缩短 119 倍）；超限放弃并转兜底 |
| 实验九 | 多实例部署的正确性 | 实例本地状态被消除；定时任务重复执行不产生重复效果；编号与实例解耦 | 两个组件实例只共享数据库；两个实例并发跑同一任务/批次/体检 | 跨实例确认扣款/查单/补偿全部打通；对账只落账一次；签收/体检不重复；任务号由业务键确定 |
| 实验十 | 混沌注入（事务中间故障） | 中间失败不留半截数据；被打断的业务由通道收敛 | 在扣配额/展开任务/签收事务内部注入异常；再叠加"混沌风暴" | 失败后状态/流水/任务/配额/台账全部回到原点；4 次注入全部由对账补回；风暴后零非法状态、零重复副作用 |
| 实验十一 | 长稳对账度量 | 混合负载下三通道持续收敛；检测延迟有界 | 业务负载 + 人为漂移 + 三通道并发，持续 6 秒（压缩负载） | 漂移 624 次全部收敛：兜底 543 / 体检 71 / 实时 10；检测延迟 p50 81ms、p95 216ms；最终零违规、零重复副作用 |
| 实验十二 | 性能基准（热点行争用） | 同一池子的扣减被行锁串行化；分散到多行吞吐回升 | 单池线程数扫描 1/8/32；32 线程下分散到 8/32 个池 | 热点随并发度**饱和**（8→32 线程吞吐 0.89×）而 p50 涨 9.8×；分散后吞吐 ×4；**全程零失败、零超卖、账实一致** |

## 1. 实验环境与方法

### 1.1 环境

| 项 | 值 |
| --- | --- |
| 数据库 | MariaDB 12.1.2（InnoDB），库 `student_milk_order_test` |
| 应用 | Spring Boot 2.7.18 / Java 17 / MyBatis-Plus 3.5.3.1 |
| 连接池 | HikariCP，`maximum-pool-size=64` |
| 事务隔离级别 | `READ_COMMITTED`（见第 7 节缺陷 D3） |
| 定时任务 | 全部关闭（`app.scheduler.enabled=false`），保证实验状态只由实验自身驱动 |

> 实验刻意同时覆盖 **MySQL 与 MariaDB 的行为差异**。项目文档以 MySQL 8 为目标，而实际运行环境是
> MariaDB；两者在可重复读下的语义差异本身成为实验发现之一（缺陷 D3）。

### 1.2 方法

1. **独立实验库**：实验只写 `student_milk_order_test`，不触碰开发库。库结构与开发库一致，
   并复制了 `state_transition_rule`（35 条迁移规则）、`process_reconcile_rule`（3 条补偿规则）
   与 `sys_config` 种子（状态机是白名单语义，缺规则会让所有迁移被拒）。
2. **夹具与清理**：`@BeforeEach` 建夹具（年级/班级/学生/品类/奶品），`@AfterEach` 清空业务表，
   因此实验可反复运行且结果不受历史数据影响。
3. **真实并发**：所有并发实验用固定线程池 + 双栅栏（`CountDownLatch` 就绪栅栏 + 放行栅栏），
   先把全部线程压到同一起点再同时放行，避免「先启动的线程已跑完」导致并发度虚高。
4. **数据存档**：每个实验的数据块同时打印到控制台并写入
   `target/experiment-reports/<实验类名>.txt`（UTF-8），便于复核与引用。

### 1.3 判定口径

- **承诺售出**：系统对用户返回成功的次数（用户视角「买到了」）。
- **实际消耗**：资源（配额/库存）真实被扣减的数量。
- 二者不相等即出现资源违背：承诺 > 消耗 = 超卖；承诺 < 消耗 = 少卖/泄漏。

## 2. 实验一：有限资源并发扣减（超卖）

### 2.1 验证命题

某日某品种机动配额 100 盒，200 个请求同时各买 1 盒：

- 有保护版本：成功数与配额实际消耗都应恰好等于 100，不超卖；
- 无保护版本：应能复现超卖，作为对照基线。

### 2.2 实验设计

**对照 A（无保护）**：模拟最朴素的实现——先读 `used_quota`，判断 `used+1<=total`，再写回 `used+1`。
为确定性地复现「丢失更新」，用一个 `CyclicBarrier(200)` 把所有线程卡在**已读到旧值之后、写回之前**，
使 200 个线程读到同一个初始值后再各自覆盖写回。

**对照 B（有保护）**：走 `DailyQuotaServiceImpl.deduct`，其并发语义为：

1. 事务内用 `SELECT ... FOR UPDATE` 加行锁读取保质期窗口内的配额池（先过期先出），一次性算出
   可扣总量并形成扣减计划；
2. 全部品种充足才继续，任一不足即整体抛异常（事务回滚，不留部分扣减）；
3. 按计划写回，并以 `used_quota + n <= total_quota` 作为条件更新兜底；
4. 每次扣减写 `daily_quota_usage` 台账，业务唯一键 `(order_id, product_id, quota_date)` 保证同一订单
   同一池子只扣一次。

用 200 个互不相同的订单号发起并发扣减（`FAKE_ORDER_BASE + i`）。

### 2.3 实测数据

**对照 A（无保护）**

```text
配额总量                100
并发请求数              200
系统承诺售出（成功率）    200
配额实际消耗            1
丢失更新次数            199
超卖盒数                100
```

**对照 B（有保护）**

```text
配额总量                100
并发请求数              200
扣减成功数              100
扣减失败数              100
配额实际消耗            100
超卖盒数                0
失败原因分布            100 × BusinessException: 「×××奶」2026-09-20 剩余库存 0 盒，不足本次订购的 1 盒，卖完即止
```

### 2.4 结论

- 无保护实现下，200 个请求全部被系统「承诺售出」，而配额只被消耗了 1 盒：**超卖 100 盒**
  （199 次写入被互相覆盖，即经典的丢失更新）。
- 有保护实现下，成功数恰好等于配额总量 100，配额被完整消耗且**零超卖**；失败的 100 次都拿到了
  明确的「剩余库存 0 盒」业务提示，而不是静默失败或数据错乱。
- 结论：**「加锁读 + 条件更新 + 台账唯一键」三者组合能把并发扣减收敛到确定结果**；
  单独使用条件更新（不加锁读）在 MariaDB 上会失败，见缺陷 D3。

### 2.5 实验暴露的缺陷

实验一在首次运行时**有保护版本也失败了**（成功数仅 25），失败原因是数据库异常
`Record has changed since last read in table 'daily_quota'`。根因与修复见第 7 节 D3。

## 3. 实验二：重复支付回调的幂等落账

### 3.1 验证命题

模拟微信在回调超时/抖动下重复投递同一笔支付成功通知。重复回调**不得**产生重复副作用：

1. 订单只发生一次「待支付 → 已支付」迁移；
2. 支付成功流水只有一条；
3. 迁移台账中该订单 PAY 的「已生效」记录只有一条；
4. 配送任务只展开一次；
5. 配额只扣减一次。

### 3.2 实验设计

1. 构造 1 个待支付订单（单日散订，2 盒）；
2. 组装一次成功回调报文（订单号 / 流水号 / 金额 / 支付时间 / `resultCode=SUCCESS`）；
3. 用 20 个线程**同时**投递这同一份报文（`handleWechatPayNotify`）；
4. 统计订单状态、流水条数、迁移台账条数、任务条数、配额扣减量。

### 3.3 实测数据

```text
回调投递次数                 20
回调处理成功（含幂等快速路径）   1
回调处理失败（CAS 冲突）       19
订单最终状态                 2（已支付）
支付成功流水条数              1
PAY 迁移生效条数              1
PAY 迁移冲突条数              0
配送任务条数（理论 1）          1
配额扣减盒数（理论 2）          2
失败原因分布                 19 × BusinessException: 订单状态已变更，回调处理冲突
```

### 3.4 结论

- 20 次并发回调只产生**一次**有效落账：1 条订单迁移、1 条支付流水、1 条配送任务、1 次配额扣减，
  其余 19 次都以明确的业务冲突提示结束。
- 三次迁移台账中「迁移生效」只有 1 条，说明过程层的迁移留痕与真实状态变更一致。

### 3.5 两条重要说明

**（1）为什么「迁移冲突条数」是 0？**
`ProcessTransitionExecutor.require` 在 CAS 失败时会写一条 `result=0` 的冲突台账，但随后抛出业务异常，
**同一事务整体回滚**，这条冲突台账也随之回滚。因此：
- 在「失败即中止事务」的严格路径（本实验）里，只有生效记录留痕；
- 在「失败即跳过、事务继续」的宽松路径（定时兜底、批量取消，用 `attempt`）里，冲突记录才会持久化。

这是刻意设计：台账记录的是「已提交的业务事实」，而不是内存里的尝试次数。

**（2）这个实验暴露了缺陷 D2 与 D4。** 首次运行时有 19 次回调的失败原因是「状态机规则禁止」，
而不是 CAS 冲突——根因是状态机规则缓存用了非原子的 `clear()+putAll()` 刷新（缺陷 D2）。
修掉缓存后又暴露：副作用（扣配额、写流水）发生在状态抢占之前，落败方已做副作用才失败，
并发下互相撞业务唯一键（缺陷 D4）。两处修复见第 7 节。

## 4. 实验三：并发重复展开配送任务

### 4.1 验证命题

一个覆盖 6 天、1 个品种的订单，理论应生成 6 条配送任务。并发重复展开（模拟「支付回调重复投递 +
手工补生成 + 定时展开」三者撞车）时，任务数量必须恒等于理论数量，不能出现 12 条、18 条这样的重复。

### 4.2 实验设计

1. 构造覆盖 6 天的订单（先建单日订单，再延后 `delivery_end_date`，绕过散订的「起止同日」校验）；
2. 16 个线程同时调用 `generateTasksForOrder(order)`；
3. 统计任务条数、签收记录条数、任务号去重条数、业务键组合数。

原始实现的幂等靠「先 `selectCount` 查是否已生成，再 `insert`」。该方式只在单线程下成立：并发下多个
执行者会同时查不到、再同时插入。改造后由数据库业务唯一键
`uk_order_product_date(order_id, product_id, delivery_date)` 仲裁，重复插入得到唯一键冲突并被幂等跳过。

### 4.3 实测数据

```text
并发调用次数                 16
本轮实际插入生效的线程数       1
未插入任何行的线程数（幂等跳过）  15
理论任务数                   6
实际任务条数                 6
签收记录条数（应与任务一一对应）  6
任务号去重后条数              6
业务键 (订单,品种,日期) 组合数   6
失败原因分布                 （无失败）
```

### 4.4 结论

- 16 个线程并发展开，只有 1 个线程真正插入了数据，其余 15 个全部命中唯一键冲突并被幂等跳过；
- 任务数、签收记录数、任务号去重数、业务键组合数**四者一致且等于理论值 6**，
  说明任务与签收记录严格一一对应，没有孤儿记录、没有重复任务；
- 结论：**把并发仲裁交给数据库唯一约束，比应用层「先查后插」可靠**。

## 5. 实验四：父子状态漂移的对账补偿

### 5.1 验证命题

正常路径下父订单状态由子过程驱动：

- 子任务开始配送 → 父订单进入「配送中」；
- 子任务全部到达终态 → 父订单聚合为「已完成」。

这两次推进都是普通数据库写入，一旦进程中断或异常，父状态会与子任务集合不一致，系统进入
「自洽但错误」的状态。本实验人为制造这两类漂移，验证系统能「发现不一致 → 补偿 → 回到合法状态」，
并且补偿本身幂等。

### 5.2 实验设计

1. 正常支付一个订单（订单 → 已支付，展开 1 条任务）；
2. **漂移一**：直接改库把子任务置为「配送中」，父订单仍停在「已支付」（模拟配送联动写入丢失）；
   运行 `ProcessReconcileCoordinator.reconcile(ORDER, limit)`；
3. **漂移二**：把子任务与签收记录直接置为终态，父订单仍停在「配送中」（模拟聚合写入丢失）；
   再次运行补偿；
4. **幂等验证**：状态已合法后再跑一轮补偿，统计「已生效的订单迁移条数」与「本轮探测到的漂移数」是否变化。

> 说明：补偿规则已下沉到 `process_reconcile_rule` 规则表（见实验六），本实验验证的是
> 「探测器 → 规则表决策 → 统一迁移出口」这条链路的端到端行为。

### 5.3 实测数据

```text
漂移一 · 补偿前订单状态        2（已支付）
漂移一 · 命中规则             联动丢失补偿
漂移一 · 补偿后订单状态        3（配送中）
漂移一 · 补偿生效数           1
漂移二 · 补偿前订单状态        3（配送中）
漂移二 · 命中规则             聚合丢失补偿
漂移二 · 补偿后订单状态        4（已完成）
漂移二 · 补偿生效数           1
补偿生效的订单迁移总条数        3
重复对账后再统计（应不变）      3
第三轮探测到的漂移数（应为 0）    0
```

### 5.4 结论

- 两类父状态漂移都能被对账任务发现并补偿回合法状态（2→3、3→4）；
- 补偿复用统一迁移出口与聚合出口，因此**天然幂等**：重复对账后「已生效迁移条数」不变（3 → 3），
  不会产生重复状态迁移或额外副作用；
- 结论：系统不依赖「每一步都成功」，而是具备「可检测、可恢复的最终一致性」。

## 6. 异常恢复的深化实验（实验六 ~ 八）

> 实验一~四验证了「资源一致性、过程幂等、异常恢复」的基本正确性。本组实验针对随后暴露出的
> **结构性偏薄**之处：补偿规则写死在代码里、漂移检测只能靠定时全表扫、跨表不变量从未在运行期被持续验证、
> **多实例部署从未被验证过**（而系统里藏着实例本地状态）、只在"完整失败或完整成功"的假设下验证过
> （没人验证"事务做到一半失败"）、以及**性能从未被测过**（而"一致性优先"是有代价的，代价必须被量出来）。
>
> 七组实验都带对照（启用/停用、健康/注入、实时/兜底、跨实例/并发重复执行、事务中间故障/风暴、
> 热点单池/分散多池），而不是只展示「能跑通」。

### 6.1 实验六：补偿规则引擎（规则驱动 + 迁移闸门）

**验证命题**

1. 漂移探测是**只读**的：调用探测不会改变任何业务状态；
2. 补偿由**规则表**驱动：停用规则后，同样的漂移不再被补偿；
3. 补偿仍受**迁移闸门**约束：闸门禁止时，即使命中规则也不落地。

**实验设计**

1. 制造漂移（子任务置为配送中，父订单仍为已支付）；
2. 只调用 `detect`（不执行），记录命中规则与订单状态；
3. 调用 `reconcile` 执行补偿，记录状态；
4. 把订单状态改回避分点，`UPDATE process_reconcile_rule SET enabled=0` 停用「联动丢失补偿」，
   再探测 + 执行一次，记录结果；随后恢复启用；
5. 用 `StateMachineService.updateRule` 把 `ORDER/DELIVER/2` 置为禁止（缓存立即刷新），
   再执行一次补偿，记录结果；随后恢复。

**实测数据**（`target/experiment-reports/Experiment6ReconcileRuleEngineTest.txt`）

```text
探测命中规则                    联动丢失补偿
命中子过程条件                  HAS_DISPATCHING_TASK
只探测不执行的订单状态            2（应仍为 2）
执行补偿后订单状态               3
停用规则后探测到的漂移数          0
停用规则并执行补偿后的订单状态      2（应仍为 2）
恢复规则后探测到的漂移数          1
闸门禁止时本轮补偿生效数          0
闸门禁止时的订单状态             2（应仍为 2）
闸门恢复后订单状态               3
```

**结论**

- 探测确实只读（第 1 条断言）；
- 补偿确实由数据驱动：规则停用后探测器**不再命中**，补偿自然不发生；
- **补偿不是绕过可靠性层的旁路**：闸门禁止时命中规则但补偿生效数为 0，
  这也是「配了规则 ≠ 配对了规则」的直接证据——启用一条新补偿规则时，必须同步检查
  `state_transition_rule` 是否放开了对应的迁移（种子数据里第三条示例规则就带着这条注释）。

### 6.2 实验七：跨表不变量体检

**验证命题**

1. 体检在健康数据上**零误报**；
2. 可自动修复的 4 类不变量：能被检出、能被真正修好（数据一致而非只标记记录）、
   且在下一轮体检中**复检闭环**；
3. 涉资金的不变量**只告警**：被检出、记录为未闭环、且不改动任何数据；
4. 修复动作之间的**执行顺序**按声明依赖执行，体检不会自己制造组合异常（§2.5 方案二的行为验证）。

**实验设计**

对照 A：构造 3 天订单，前两日送出并签收、第三日留作待配送（订单处于**配送中**的进行中状态），
先跑一次体检证明零误报；然后**直接改库**注入 4 类违规（不变量要防的本就是绕过业务出口的旁路写入）：

| 注入 | 手段 | 对应不变量 |
| --- | --- | --- |
| 配额账实不符 | `daily_quota.used_quota += 3` | `INV_QUOTA_LEDGER` |
| 任务已完成但记录未签收 | `delivery_record.sign_status = 2` | `INV_TASK_RECORD` |
| 已签收但营养记录丢失 | `DELETE nutrition_intake` | `INV_SIGN_INTAKE` |
| 任务网格缺一天 | `DELETE delivery_task` + 记录 | `INV_ORDER_TASK` |

> 用**进行中**订单而不是已完成订单：注入后、补网格前，三个任务里两个已是终态、第三个被删除，
> 因此若「父聚合」排在「网格补全」之前，**同一次体检**就会先把订单判成已完成（3→4）、
> 随后网格补全又补回一条待配送任务——体检自己制造出组合异常。声明依赖后顺序为
> 网格补全 → 父聚合 → 组合守卫，两者都不会发生。这是方案二的行为验证。

对照 B：制造父状态漂移（子任务已送出、订单仍为已支付）**同时**删除成功流水，
跑两轮体检，观察「自动修复」与「仅告警」两条分界线。

对照 C：构造一个已完成订单，再直接用改库把它的子任务分别置为「配送中」与「待配送」，
各跑一轮体检，验证**同一条不变量内部的等级细分**——配送中（奶已出库在途）只能告警、
待配送（奶未出库）可安全自动作废，且作废经业务取消出口执行（留痕、联动作废签收记录）。

对照 D：把已完成订单的整条任务与签收记录删掉（模拟历史被改过），验证网格缺口
**只告警、不补造历史**——因此也不会给已结束的订单造出待配送任务（即不再制造组合异常）。

  更关键的是**订单始终停在配送中**、组合守卫零触发——若不声明依赖，
  同一次体检就会先把订单误判为已完成、再补回任务，**体检自己制造组合异常**；
- 资金不一致被检出但**没有被动过一个字节**，记录保持未闭环、等级为 `ALERT_ONLY`，
  次轮仍然报出——这条对照就是「哪些该自动修、哪些不该」的分界线的实证；
- 对照 C 说明等级可以细到**每条违规**：同一条不变量下，待配送的残余任务被自动作废
  （任务→已取消、`TASK_CANCEL` 生效台账 1 条、记录闭环为 `AUTO_REPAIR`），
  配送中的残余任务保持原状、记录挂着 `ALERT_ONLY` 等人工。口径与「缺货批量取消只取消待配送任务」一致；
- 对照 D 说明"保守"的一侧：终态订单的网格缺口**只告警不补造**——
  **不为了把数字补整齐去编造历史**，这一点正是组合异常不再产生的根因。

**附带发现与其加固（诚实记录整条链路）**

对照 A 在最初实现时有一个观察项是「修复后未完成任务数 = 1」：各条修复都正确，但
**修复动作之间缺少依赖与顺序**——任务网格补齐（`INV_ORDER_TASK`）发生在父状态聚合
（`INV_ORDER_AGGREGATION`）之后，于是「已完成的订单」被补出了一个待配送任务。
**当时 6 条不变量都没有被违反**，因为没有任何一条覆盖「父过程已终态时不应存在非终态子过程」
这个组合约束。它说明：*单个机制正确 ≠ 机制组合正确*。

加固分两步（§2.5）：

1. **方案一 · 组合状态守卫** `INV_PARENT_TERMINAL_CHILD_PENDING`：把该状态变成可见、可收敛
   （当时实测守卫命中 1 条并同轮作废，未完成任务数归零）；
2. **方案二 · 声明依赖 + 拓扑序 + 根因收窄**：给 `ProcessInvariant` 增加 `dependsOn()`，
   体检器按拓扑序执行（网格补全 → 父聚合 → 组合守卫）；同时让 `INV_ORDER_TASK`
   按订单状态分级——进行中补网格、**终态只告警不补造历史**。
   于是"先补上、再作废"的绕圈过程消失，组合异常**根本不产生**，
   组合守卫退化为最后防线（只在人工改库、进程异常等真异常下才命中）。

**仍在展望里的部分（方案三）**：不变量之间的相互影响目前靠**逐对声明**依赖来消解，
本质仍是"人把关系写出来"。更远的形态是把不变量看作**约束系统**，
由约束集合推导出一个满足全部约束的修复计划（而不是逐条独立修复 + 依赖排序），
见 `../论文/后续扩展方案.md` §2.5。

### 6.3 实验八：实时自愈通道与兜底通道

**验证命题**

1. 实时通道能在「轮询间隔 + 修复耗时」量级内收敛，显著优于兜底通道的调度周期；
2. 待办按业务键去重，重复触发不会把待办表冲爆；
3. 实时通道失败时会**指数退避**，超上限后**放弃并转交兜底通道**（这正是不需要放弃实时通道的理由）。

**实验设计**

- 对照 A：制造漂移 → 入队待办 → 领取（`claimDue`）→ `reconcileEntity` → 标记完成，
  测量各步耗时，并与两个通道的调度周期对比。刻意说明：本实验直接调用消费者使用的那组方法，
  与 `ProcessPendingTaskJob` 的循环体是同一组调用，因此测得耗时真实，端到端只多一个轮询间隔；
- 对照 B：同一业务键连续入队 10 次，统计待办行数；再入队一个不同触发动作，再统计；
- 对照 C：入队一条**必然失败**的待办（未注册场景）→ 处理失败 → 观察退避期内不可再领取 →
  驱动到重试上限 → 观察状态变为「已放弃」并记录失败原因。

**实测数据**

对照 A / B / C（`Experiment8RealtimeSelfHealingTest.txt`）：

```text
【对照A】待办入队耗时(ms)                    2
         待办领取 + 补偿 + 标记完成耗时(ms)      14
         命中的补偿规则                        联动丢失补偿
         补偿后订单状态                        3（配送中）
         待办终态（1=已处理）                   1
         实时通道检测窗口上界(ms)                 5014（轮询 5000 + 修复）
         兜底通道检测窗口上界(ms)                 600000
         窗口缩短倍数                          119
【对照B】同一触发动作入队 10 次后的待办数          1
         再入队另一触发动作后的待办数             2
【对照C】首次失败后是否进入退避（退避期可领取数）     0
         尝试次数                            5
         重试上限（与生产策略同源）              5
         最终状态（2=已放弃）                   2
         最终重试次数                          5
         最近一次失败原因                       未注册场景 UNKNOWN_SCENE 的父过程探测器
```

**结论**

- 实时通道把**不可检测窗口**从兜底通道的 600 秒压到约 5.0 秒（119 倍），
  且修复本身只有十几毫秒——瓶颈是轮询间隔而不是修复；这说明「实时」的收益来自
  「发现得早」，而不是「修得快」；
- 去重键含触发动作：10 次重复入队只留 1 行待办（批量送出 78 条任务同理），
  不同触发动作各留一行；
- 失败路径完整：退避期内不可再领取 → 重试 5 次 → 状态置「已放弃」并记录原因。
  **这正是双通道不可省略的理由**：实时通道自己也会失败，必须有兜底通道兜住。

### 6.4 实验九：多实例部署的正确性

**验证命题**

多实例下出问题的从来不是算法，而是两类东西：**实例本地状态**（别的实例看不见）与
**幂等边界**（同一件事被两个实例各做一次）。五个对照分别验证：

1. 支付状态不再依赖实例内存：跨实例确认扣款、跨实例查单、跨实例补偿落账都成立；
2. 两个实例并发跑同一个支付对账任务，只落账一次；
3. 两个实例并发跑同一个自动签收批次，每条记录只签收一次；
4. 两个实例并发体检，违规记录不重复、数据最终一致；
5. 编号生成不依赖实例本地计数器（订单号带实例标识、任务号由业务键确定）。

**实验设计**

方法学说明（重要）：在单 JVM 内用 **两个组件实例 + 并发线程** 模拟两个应用实例——
它们**只共享数据库**，各自持有自己的组件对象。这覆盖的是"共享数据库、各自持有组件"的多实例语义；
不覆盖真实多进程/多主机、网络分区与负载均衡路由（见「已知局限」）。

| 对照 | 构造 | 断言要点 |
| --- | --- | --- |
| A | 构造两个 `WechatPaySimulator` 实例：A 预下单 → B 确认扣款 → A 查单；再让回调丢失，走对账补偿 | B 受理成功、A 查得到扣款、补偿落账 1 次、订单已支付、成功流水/台账/任务各一份 |
| B | 两个线程同时执行 `reconcilePendingPayments`（= 两个实例的对账任务体） | 只有一个实例报告"补偿了订单"；订单/流水/台账/任务/配额台账各一份 |
| C | 两个线程同时执行自动签收批次（逐条 `autoSignOne`） | 记录只签收一次、营养摄入只一条、任务与订单终态、SIGN 台账一条 |
| D | 两个线程同时 `invariantScanner.scan(true, …)`（注入配额账实不符） | 同一主体的违规记录**只有一行**、`used_quota` 收敛到台账合计 |
| E | 走真实下单支付路径，检查订单号/流水号与任务号的构成 | 编号含实例标识；任务号等于确定性公式 `DT{日期}-{订单}-{品种}`，且与业务键一一对应 |


```text

```

**结论**

- **本地状态是真正的杀手**：支付状态放在内存里时，跨实例的"确认扣款"与"查单"必然失败；
  其中的"查单失败"尤其危险——对账任务会把已扣款订单看作未付款，
  进而可能被超时任务取消（**钱已收、单已取消**）。落到 `wechat_pay_order` 表后，
  跨实例确认/查单/补偿三条路径全部打通（对照 A）；
- **不选主也正确**：定时任务在 N 个实例上都会跑，但每个任务的写路径都是 CAS/唯一键/幂等跳过，
  因此"重复执行只浪费算力，不产生错误"（对照 B、C、D 各证明一项）；
- **编号必须与实例解耦**：原先"时间戳 + JVM 内自增"在多实例下会撞号。任务号改为**由业务键确定性生成**
  之后，"任务号冲突 ⟺ 业务键冲突"，顺带消除了一个隐藏缺陷——**原实现会把"任务号撞了"
  误判成"业务键已存在"而静默跳过，导致一条配送任务凭空消失**；订单号则加入实例标识（对照 E）；
- **并发写入靠唯一键收口**：两个实例同时体检不会插出两条违规记录（对照 D）。

**与审计表的关系**：完整的组件级审计（哪些有本地状态、后果、处置）写在
`../基线文档/可靠性设计.md` 第十节，本节只记录可执行的验证；
未覆盖的部分（真实多进程、网络分区、回调发送仍在实例内、60 秒缓存收敛、
`retry_count` 加速前进、时钟偏移等）同样列在该节 10.3。

### 6.5 实验十：混沌注入（事务中间故障）

**验证命题**

前九个实验验证的都是"完整的坏数据"（重复回调、漂移、并发冲突）。本实验验证**中间失败**：
事务执行到一半被打断时，① 会不会留下半截数据；② 被打断的业务能否被通道收敛。

**实验设计（含方法学说明）**

注入器是**测试域 AOP**（`src/test/java/com/milk/order/chaos/ChaosInjector`），默认撤防、固定种子（可复现），
在真实事务的中间步骤**执行完之后**抛异常——这精确对应「这一步的写入已发生、整个事务尚未提交」。

> **方法学要点（一个必须写清的约束）**：注入点必须位于**某个外层事务内部**。
> 因为注入语义是"先执行、再抛"，若注入点自身就是事务边界，`proceed` 已经提交，
> "抛异常"就变成另一种现象——**调用方看到失败、实际已生效**（模糊失败/悬挂），
> 那是另一个课题，本实验不混用。

| 对照 | 注入点（事务内部的哪一步） | 断言要点 |
| --- | --- | --- |
| A | 支付落账事务里的**扣配额** | 失败后：订单仍待支付、0 流水、0 任务、配额 0、台账 0、PAY 迁移台账 0；对账查单后补偿落账 1 次 |
| B | 支付事务的**最后一步：展开任务网格** | 此前所有写入（状态抢占、配额扣减、支付流水）一并回滚；撤防后重试完整成功 |
| C | 签收事务内的**父状态聚合** | 记录/任务/营养/父状态全部回滚；重试后一次性完成，且台账恰好 1 条 |
| D | 全部注入点，60% 概率、最多 4 次（"混沌风暴"） | 4 笔被打断的支付全部被对账补回；6 处人为漂移 2 轮收敛；最终零非法状态、零重复副作用、零不变量违规 |

### 6.6 实验十一：长稳对账度量

**验证命题**

把"业务写入 + 人为漂移 + 三通道并发收敛"压在同一段时间里持续进行，度量：
① 三条通道各自做了多少工作；② 检测延迟分布；③ 持续负载后是否仍然一致。

> **与"2~24 小时长稳"的关系（必须说清）**：真实长稳需要小时级运行，单测做不到。
> 本实验用**高密度压缩**：负载压在 6 秒内持续进行，**度量口径与真实长稳一致**
> （同一批 SQL 与同一组计数器），只是时间尺度被压缩。
> 因此它能回答"机制在持续负载下是否稳定收敛"，**不能**回答
> "运行 24 小时后有没有缓慢退化（缓存/表膨胀/连接泄漏）"——那仍属后续工作。

**实验设计**

```
业务线程 ×4        把 12 个订单推进到已完成（各自负责一部分）
漂移注入线程 ×1     持续把「已完成」订单回退为「配送中」（模拟聚合写入丢失，只注入规则表覆盖得到的漂移）
实时通道线程 ×1     drainPendingTasks（连续消费待办，等价于把 5 秒轮询间隔压到 10ms）
兜底通道线程 ×1     reconcile(ORDER, 500)
体检线程 ×1         invariantScanner.scan(true, 500)
         ↓ 停机 → 再做一次收敛 → 全库体检 → 度量
```

另含一个**特征化测试**记录发现的规则覆盖盲区（见下）。

**实测数据**（`target/experiment-reports/Experiment11LongRunMetricsTest.txt`）

**结论**

- **持续负载下能稳定收敛**：624 次人为漂移全部被收掉（兜底 543 + 体检 71 + 实时 10），
  停机后只需 1 轮就无活可干，最终零违规、零重复副作用、零非法状态；
- **三条通道的分工在数据里很清楚**：
  - **兜底通道是主力**（543 次）：因为注入的是"父状态被改坏、但没有发生任何子过程事件"的漂移，
    **没有事件可驱动实时通道**；
  - **实时通道只做了 10 次**：它对应的是"子过程状态变更后父过程需要重新聚合"这一类，
    本实验里就是 12 次签收产生的待办（部分在消费时已无漂移）；
  - **体检做了 71 次**：与兜底通道同源（都覆盖父子一致性），两者互为冗余——
    这正是"一条不变量落地在多条通道上"的体现；
- **这条观察很重要**：事件驱动的实时通道**对"没有事件发生的写入丢失"无能为力**，
  所以它永远不能替代周期扫描；反过来周期扫描的检测窗口太长，所以也不能替代实时通道。
  双通道不是重复建设，而是覆盖两类不同的失效形态（**这条论证可以作为论文里的设计依据**）；
- **检测延迟有界**：待办从入队到处理完成，p50 81ms、p95 216ms、max 218ms；
  加上生产环境的 5 秒轮询间隔，即"实时通道最坏 5 秒级"（与实验八的口径一致）；
- 期间 9 次 CAS 冲突（多通道同时对同一订单补偿）全部被吸收：**冲突体现为"未生效"，而不是重复副作用**。

**同时发现一个规则覆盖盲区（当时记录，后已修复，见下）**

特征化测试构造了「订单已支付(2) + 子任务全部已签收(3)」这一状态（模拟配送联动与聚合写入同时丢失）：


原因：规则表里有 `(2, HAS_DISPATCHING_TASK → 3)` 与 `(3, ALL_TASKS_TERMINAL → 4)`，
**缺 `(2, ALL_TASKS_TERMINAL → 4)`**。

> **✅ 已修复（同日，3.4）**：新增补偿规则「已支付全终态补偿」`(2, ALL_TASKS_TERMINAL → AUTO_COMPLETE, 4)`，
> 并把迁移闸门 `ORDER/AUTO_COMPLETE/2` 从"显式禁止"改为"允许"（闸门看不见子过程，
> 安全性由聚合出口"只在全部任务终态时触发"的定义保证；管理端手动完成的 `COMPLETE/2` 仍保持禁止）。
> 该用例已翻转为回归守卫：命中规则、补偿生效 1 次、订单到已完成、体检零检出。
> 实现还顺带澄清了一个口径：**闸门该放哪一条**——最初误判为 `COMPLETE/2`（手动完成），
> 实际补偿走的是 `AUTO_COMPLETE`，两条闸门语义不同，放开哪条是独立的业务决定。

### 6.7 实验十二：性能基准（配额池热点行争用）

**验证命题**

本系统的扣减是「加行锁读剩余 → 写回已售」的读-改-写，因此**同一池子上的扣减会被行锁串行化**——
并发度再高，热点吞吐也不会线性扩展，而延迟会按并发度排队上升。这是"一致性优先"的直接代价，
必须被量出来，"单池 vs 分段池"的讨论才有依据。

**实验设计**

```text
预热 500ms（不计入指标，把 JIT 与连接池喂热）
A 组  热点单池：1 / 8 / 32 线程抢同一个池子
B 组  同为 32 线程，把配额分散到 8 / 32 个品种池（每线程绑定一个池，8 池时 4 线程共享一个）
每配置 1.5 秒；指标：TPS、p50/p95/p99/max（成功口径）、失败数、账实一致
```

> **口径与边界**：压的是**进程内服务调用**（`DailyQuotaService.deduct`），不含 HTTP 与序列化
> ——目的是单独暴露"行锁串行化"这一个因素；池容量给足，测吞吐而非失败路径（超卖拒绝已在实验一验证）；
> 本项目配额池唯一键是 `(quota_date, product_id)`，**没有"按班级分段"这一维**，
> 所以"分段池"用**多品种池**做等价代理（同为"把热点分散到多行"），真按班级分段需要改配额维度（后续工作）。

**实测数据**（`target/experiment-reports/Experiment12QuotaHotspotBenchmarkTest.txt`；
单机开发环境，多次运行波动约 ±20%，以下为其中一轮）

```text
场景                         [线程/池]   成功次数   TPS      p50     p95     p99    max(ms)
热点单池 · 1 线程             [1 / 1]      313    208.27    4.63    6.35    7.31    8.57
热点单池 · 8 线程             [8 / 1]     1146    758.55   10.29   13.81   15.65   19.55
热点单池 · 32 线程            [32 / 1]    1036    672.01   45.27   60.67   96.01   98.72
分散 8 池 · 32 线程           [32 / 8]    4067   2686.84   11.34   16.73   20.82   50.53
分散 32 池 · 32 线程          [32 / 32]   4028   2669.65   10.71   19.69   29.11   82.32

热点 32 线程 / 单线程 TPS：      3.23 ×（并发度 32× ⇒ 远非线性）
热点 8 → 32 线程吞吐增幅：      0.89 ×（并发度 4× ⇒ 已饱和，甚至略降）
热点 32 线程 p50 / 单线程 p50：  9.78 ×（并发度 32× ⇒ 排队而非变慢）
分散 32 池 / 热点 32 线程：      3.97 ×
分散 8 池 → 32 池吞吐增幅：      0.99 ×（收益递减：已接近锁外瓶颈）
全部配置失败数：0；账实一致：池已售合计 == 成功扣减数 == 台账行数，零超卖
```

**结论**

- **热点池确实被行锁串行化**：32 线程的吞吐（672 TPS）甚至**低于** 8 线程（758 TPS）——
  并发度提高 4 倍、吞吐反而下降，p50 却从 10.3ms 涨到 45.3ms（4.4×）、相对单线程涨 9.8×。
  **吞吐不涨、延迟线性涨**，这就是串行化瓶颈的标准特征；
- **分散到多行后吞吐回升约 4 倍**（672 → 2670 TPS），p50 回落到 10.7ms——
  同一份代码、同一份数据规模，唯一的差别是热点不在一行上；
- **两个修正了直觉的发现**：
  1. **"单线程 TPS = 吞吐上限"是错的**：单线程 TPS（208）是"单次端到端耗时的倒数"，
     它把连接获取、幂等查询、提交等**锁外开销**也算进去了；多线程可以把这些开销与锁内临界区
     **流水重叠**，所以热点并发吞吐（672）高于单线程 TPS（约 3.2×），但仍远低于 32× 的线性——
     临界区吞吐 ≈ 670 ops/s（≈1.5ms/次），这才是该行锁的真实服务能力；
  2. **分散的收益在 8 个池就到顶**（8 池 → 32 池只有 0.99×）：说明行锁之外还有第二个瓶颈
     （每笔扣减要执行 3 次保质期窗口加锁读 + 1 次条件更新 + 1 次台账插入，共 5 条 SQL，
     再加连接与 ORM 开销）。**要再上一个量级，得减少每笔扣减的 SQL 次数**（例如先做一次范围读
     确定窗口内实际存在的池，再逐池加锁），而不是继续分散；
- **正确性在压力下没有松动**：五个配置共约 10600 次并发扣减，全部成功、零失败、零超卖，
  且每个配置结束后"池已售合计 == 成功扣减数 == 台账行数"——**性能实验同样断言不变量**；
- **"按班级分段"的代价（推论，未实测）**：分段能解决热点，但不同班级不能互相借用余量，
  会降低配额利用率（某班卖完另一班还有货）。所以这是**一致性-吞吐-利用率**的三方权衡，
  而不是"分段一定更好"。

### 6.8 契约矩阵测试（结构性回归守卫）

**验证命题**：状态机的三条结构性约束在任何改动后都不能被悄悄破坏。

| 矩阵 | 断言内容 |
| --- | --- |
| A · 规则覆盖 | 白名单语义下漏配一行 = 该迁移**静默被禁止**（无报错），因此每个场景/动作必须覆盖全部可达来源状态 |
| B · 安全关键禁止 | 已完成任务不可回退、已退订订单不可再流转、配送中订单不可退订等；未配置组合同样默认禁止 |
| C · 台账可回放 | 用迁移台账重放一遍，必须得到与真实状态一致的结果（无缝隙、无跳跃） |
| D · 不变量执行顺序 | 每条声明依赖都排在本项之前（拓扑性）、关键序对成立、顺序确定可复现，**且不是字典序的巧合** |

**实测数据**（`target/experiment-reports/StateMachineContractTest.txt`、`InvariantDependencyOrderTest.txt`）

```text
【A】订单动作数 5 / 任务动作数 5
     应覆盖的（场景/动作/来源状态）组合数   35
     实际缺失组合数                    0
【C】台账条数                          3
     回放路径                          1 → 2 → 3 → 4
     回放得到的状态                      4（与实际状态一致）
【D】执行顺序     INV_ORDER_TASK → INV_ORDER_AGGREGATION → INV_PARENT_TERMINAL_CHILD_PENDING
                 → INV_PAYMENT_CONSISTENCY → INV_QUOTA_LEDGER → INV_SIGN_INTAKE → INV_TASK_RECORD
     字典序（对照） INV_ORDER_AGGREGATION → INV_ORDER_TASK → …（前两项相反）
     网格补全 位于父聚合之前                0 < 1
     父聚合 位于组合守卫之前                1 < 2
     两次解析结果一致（确定性）              true
     违反声明依赖的项（应无）                （无）
```

**结论**

- 规则覆盖矩阵是**白名单语义的必要配套**：漏配一行不会报错，只会让某个迁移在某天突然被拒——
  这个测试把它变成编译期内（执行期）可见的失败；
- 台账可回放矩阵把「过程可观测」从口号变成断言：`process_transition_log` 足以完整重放订单的
  每一次状态变化，且每一步首尾相接。

## 7. 缺陷台账与回归验证

这是本轮实验最有价值的部分：**实验的目的不是证明设计有效，而是把设计里的洞挖出来**。

| 编号 | 现象 | 根因 | 修复 | 回归守卫 |
| --- | --- | --- | --- | --- |
| D1 | 并发展开任务会重复生成（理论 6 条可能变 12 条） | 幂等靠应用层「先 `selectCount` 再 `insert`」，并发下双双查不到再双双插入 | 配送任务加业务唯一键 `uk_order_product_date`；`IdempotencyGuard` 把唯一键冲突翻译为「已存在」并幂等跳过；配额台账同理加 `uk_order_product_pool` | 实验三（任务数恒等于理论数） |
| D2 | 并发回调被「状态机规则禁止」误拒（19/20） | `StateMachineServiceImpl.refresh()` 用 `cache.clear()` + `putAll()` 刷新；并发读取方在「已清空、未填完」窗口内读到空规则表，白名单语义下等于**瞬时全禁** | 改为「先构造完整新表，再一次性替换 volatile 引用」；并加 `@PostConstruct` 启动预热，消除首批请求落在空缓存上的可能 | 实验二新增断言：失败必须是 CAS 冲突抛异常，不能是规则表静默拒绝 |
| D3 | 并发扣减报 `Record has changed since last read in table 'daily_quota'`（有保护版本只成功 25/200） | 同一事务内先对某行做**一致性快照读**、再对该行做**加锁读/更新**。MariaDB 在 REPEATABLE READ 下会直接拒绝，MySQL 则静默改读最新版本——同一份代码在两种数据库上行为不一致 | ① 扣减改为一次性 `SELECT ... FOR UPDATE` 行锁读，不再混用「快照读校验 + 加锁写回」；② 统一数据源隔离级别为 `READ_COMMITTED`（本系统并发安全全部由条件更新/行锁/唯一键显式保证，不依赖可重复读语义） | 实验一对照 B（成功数恰好等于配额、零超卖） |
| D4 | 修复 D2 后，19 次并发回调改为撞业务唯一键 `uk_order_product_pool` | 副作用（扣配额、写支付流水）发生在状态抢占（CAS）**之前**：落败方已经做了副作用才失败，只能靠回滚收场，并发下互相撞唯一键 | 调整为**先抢占状态、再执行副作用**：`payOrder` / `handleWechatPayNotify` 都先做 CAS，落败方立即中止，配额扣减/流水写入/任务展开只由胜出者执行一次 | 实验二（失败原因全部为「订单状态已变更，回调处理冲突」） |
| D5 | 「每一次状态迁移都写入台账」存在空洞：退订/缺货取消联动作废签收记录时无台账记录 | `markRecordRejected` 绕过统一出口，直接 `deliveryRecordMapper.update` 改 `sign_status`，未经过执行器 | 改为按任务查询未签收记录后**逐条经执行器 `attempt` 提交**（宽松迁移 + 留痕） | 实验五（订单/任务/签收记录每一步迁移的台账条数均为 1） |
| D6 | 订单头与明细**并非原子写入**：`doCreateOrder` 上的 `@Transactional` 实际不生效 | `doCreateOrder` 是 public 却被同类 `createOrder` 内部直调，Spring AOP 代理被绕过，注解形同虚设——明细插入失败会留下「订单存在但明细不完整」的半截数据 | 事务边界上移到外部入口 `createOrder`，`doCreateOrder` 降为 `private` | ⚠️ 暂无自动化守卫（由清理审计发现，建议后续补 JUnit 用例） |

D1–D4 由实验一~四暴露；D5 是在"统一论文与代码表述"时逐条核对不变量发现的——**不变量只在被验证时才成立**。

**共同规律**：D1/D2/D4 都是「检查与动作之间存在时间窗」导致的竞态——检查时条件成立、动作时条件已变。
三者分别用 **数据库唯一键**、**原子替换不可变快照**、**先抢占状态再动作** 三种手段消除窗口。
D3 是数据库语义差异问题，用 **显式行锁 + 统一隔离级别** 消除。
D5 是另一类问题：**不变量被"绕过统一出口"的旁路悄悄破坏**——它不会报错、不会丢数据，
只会让「可回溯」这个承诺悄悄失效。

### 7.1 补充用例（实验五）：状态迁移留痕完整性

「每一次状态迁移都写入台账」是过程可观测性的前提，但极易被破坏：只要有一条路径绕过统一出口
直接改状态，台账就会出现空洞。本用例走一条跨三张表、跨两级状态的完整链路（支付 → 退订联动），
逐项核对「最终状态 / 台账条数 / 资源回补」是否三方一致。

实测数据（`target/experiment-reports/Experiment5TransitionLedgerTest.txt`）：

```text
订单最终状态（期望 5 已退订）                   5
任务最终状态（期望 4 已取消）                   4
签收记录最终状态（期望 3 拒收）                 3
台账 ORDER/PAY 生效条数（期望 1）               1
台账 ORDER/CANCEL 生效条数（期望 1）            1
台账 DELIVERY_TASK/TASK_CANCEL 条数（期望 1）   1
台账 DELIVERY_RECORD/REJECT 条数（期望 1）      1
配额剩余（期望回补到 0）                        0
有效扣减台账行数（期望 0）                      0
已逻辑删除的台账行数（保留审计痕迹）             1
```

**判定**：三张表的每一次状态变更对应且仅对应一条「已生效」台账记录；配额按台账精确回补
（`used_quota` 归零、有效台账行归零）。

**附带发现（台账行的删除语义）**：`restore` 的「回补后删除台账行」实际是**逻辑删除**
（`DailyQuotaUsage` 带 `@TableLogic`），因此业务查询不可见、重复回补自然跳过，
但物理行仍存在并占用业务唯一键 `uk_order_product_pool`。当前业务路径不会触发问题
（同一订单同一池子不会二次扣减），但若将来出现该场景，必须先物理清理或调整键策略。
这一约束已记入 `../基线文档/可靠性设计.md`。

## 8. 结论

1. **资源一致性**：并发扣减在「行锁读 + 条件更新 + 台账唯一键」下零超卖，且资源被完整消耗；
   去掉保护后同样的负载会超卖 100 盒，证明该机制不是装饰。
2. **过程幂等**：同一动作重复执行（重复回调、重复展开）只产生一次有效副作用，
   且由数据库约束而非应用层判断保证，因而在并发下依然成立。
3. **异常恢复可配置**：父状态漂移的补偿规则已下沉到规则表，可在线启停；
   停用即不补偿、闸门禁止即不落地（实验六），说明「能力可配」没有换来「约束可绕」。
4. **恢复是持续发生的，而不是一次的**：7 类跨表不变量被周期求值，可逆项自动修复并复检闭环，
   涉资金项、终态项与在途任务只告警（实验七）；而且它连"机制组合"这一层都盖住了——
   实验七发现的组合异常先被组合守卫收敛，再通过**声明依赖 + 拓扑序 + 根因收窄**做到根本不产生；
   实时通道把不一致的不可检测窗口从 10 分钟压到约 5 秒，
   并在自身失败时退避、放弃、由兜底通道兜住（实验八）。
5. **过程可观测**：每次状态迁移都落入 `process_transition_log`，成功与冲突可区分；
   而且台账足以**完整回放**订单的每一次状态变化（契约矩阵 C）。
6. **多实例不再依赖任何实例本地状态**：支付状态落库后，跨实例确认扣款/查单/补偿全部打通；
   定时任务不选主也正确（写路径全是 CAS/唯一键/幂等跳过，"重复执行只浪费不犯错"）；
   编号与实例解耦（任务号由业务键确定、订单号带实例标识）——其中还顺手消除了一个隐藏缺陷：
   原实现会把"任务号撞了"误判成"业务键已存在"而静默跳过，**导致一条配送任务凭空消失**（实验九）。
7. **事务中间失败不留半截数据**：在支付事务的中间/末尾与签收事务的末尾注入异常，
   状态、流水、任务、配额、台账全部回到原点；被打断的 4 笔支付全部由对账补回，
   且补回后仍然只有一份副作用（实验十）。这说明"原子性靠事务，收敛靠通道"两条腿都要有。
8. **持续负载下三通道稳定收敛且延迟有界**：624 次人为漂移全部收掉（兜底 543 / 体检 71 / 实时 10），
   检测延迟 p95 216ms，最终零违规、零重复副作用（实验十一）。数据同时说明了双通道的必要性：
   **事件驱动的实时通道对"没有事件发生的写入丢失"无能为力**，而周期扫描的窗口又太长。
9. **"一致性优先"的代价被量出来了**：同一池子的并发扣减被行锁串行化——32 线程吞吐甚至低于
   8 线程（0.89×），p50 却涨到单线程的 9.8 倍；分散到多行后吞吐回升 4 倍（实验十二）。
   而且压力下正确性没有松动：约 10600 次并发扣减零失败、零超卖、账实一致。
   **性能实验同样断言不变量，这是本项目"性能不能让一致性妥协"主张的证据。**
6. **实验的副产品**：共 6 个真实缺陷被暴露并修复——D1~D4 由并发实验暴露（其中 D2、D4 只在并发下
   才可能出现，靠代码评审很难发现），D5 由「逐条核对不变量」发现，D6 由「清理死代码时的审计」发现
   （自调用导致 `@Transactional` 失效，订单头与明细非原子写入）。这本身就是「为什么需要验证层」
   的最好论据：**不变量只在被验证时才成立**。

## 9. 已知局限与后续工作

| 局限 | 说明 | 后续方向 |
| --- | --- | --- |
| 多实例验证是"单 JVM 内的多实例模拟" | 实验九用「两个组件实例 + 并发线程」覆盖了"共享数据库、各自持有组件"的多实例语义；**未覆盖**真实多进程/多主机、网络分区、负载均衡路由、进程崩溃恢复、数据库主从延迟 | 真实多节点环境下用混沌工具复测（见后续扩展方案 3.2）；其余不确定项逐条列在 `../基线文档/可靠性设计.md` 10.3 |
| 异步回调的发送仍在实例内 | 支付状态已落库，但**回调的发送**由处理"确认扣款"的实例用内存线程池完成；该实例在重试期间崩溃则该次回调丢失（由对账补偿兜住）。多实例下 `notifyUrl` 需指向负载均衡地址 | 若要求回调不丢，应改为持久化投递（事件表 + 消费者），与 3.2 一起考虑 |
| 缓存类配置变更最长 60 秒收敛 | 状态机规则与系统参数是每实例 60 秒 TTL 缓存，管理端改完在另一实例上可能最长 60 秒后生效 | 需要"即刻全局生效"则引入版本号或失效广播 |
| 长稳是"高密度压缩"而非小时级 | 实验十一把 6 秒当作长稳的压缩代理，覆盖"持续负载下是否稳定收敛"，**不覆盖**运行数小时后的缓慢退化（缓存膨胀、表膨胀、连接泄漏） | 真实长稳需要小时级运行与资源曲线采集（后续扩展方案 3.2 的剩余部分） |
| 混沌注入是白盒的 | 注入点在代码里预先选定（扣配额/展开任务/签收聚合），覆盖"事务中间故障"这一类；**未覆盖**进程被杀、网络分区、数据库不可用、磁盘满、时钟跳变等黑盒故障 | 引入进程级/网络级故障工具后补齐；其中"进程被杀"与多实例部分重合 |
| 检测延迟"先执行后抛"的语义边界 | 注入点若自身就是事务边界，"抛异常"会变成"调用方看到失败、实际已生效"（模糊失败/悬挂），本实验刻意不混用该形态 | 若要验证模糊失败语义，应单独设计（幂等查询 + 用户可重试的提示） |
| ~~补偿规则存在覆盖盲区~~ | **已修复（3.4）**：补 `(2, ALL_TASKS_TERMINAL → 4)` 规则并放开 `AUTO_COMPLETE/2` 闸门；原用例已翻转为回归守卫。遗留一个语义边界：**子任务全部取消时也会被补为已完成**，"全部取消→已退订"的区分依赖退款设计（`全取消补偿` 规则仍默认停用） | 明确退款/已退订与"全部取消"的关系后启用相应规则与条件 |
| 度量精度依赖时间列类型 | 检测延迟最初只能落在 0ms / 1000ms 两档，因为过程层时间列是秒精度 `DATETIME`；已把 `process_pending_task` 的时间列改为 `DATETIME(3)` 后得到 p50 81ms / p95 216ms。**时间列精度也是可观测性的一部分** | 其余过程层表（体检记录、迁移台账）仍是秒精度；需要更细的度量时按同样方式升级 |
| 数据库单一 | 部署目标为 MariaDB 12.1，已在其实测；MySQL 8 未实测（`mysql-connector-j` 与 SQL 语法均兼容，不是必需项） | 若需在 MySQL 8 部署，跑同一套实验复测即可（统一 `READ_COMMITTED` 后预期与 MariaDB 行为一致） |
| 支付为模拟实现 | `WechatPaySimulator` 为内存实现，重启丢失预支付单；这也是**唯一的本地状态依赖**（多实例下回调可能落到没有该预支付单的实例） | 接入真实支付、或把预支付单落到 `payment_record` 后重做实验二 |
| 修复动作之间的相互影响靠"逐对声明"消解 | 实验七对照 A 发现的组合异常已按方案一（组合守卫）+ 方案二（声明依赖 + 拓扑序 + 根因收窄）加固：异常从"一轮内收敛"变为**根本不产生**（实测订单未被误判、守卫零触发） | 但依赖关系仍需人工逐对写出；更远的方向是把不变量看作约束系统、由约束集合求解一致状态（方案三，见后续扩展方案 §2.5） |
| 缺长时间稳定性测试 | 未做数小时级的连续压测与对账命中率统计（实验十一是秒级压缩负载） | 小时级运行 + 资源曲线（内存/连接/表增长）采集 |
| ~~缺性能基线~~ | **已补**（实验十二）：热点行争用的 TPS/延迟与"单池 vs 分散多池"对比已量化；但口径是**进程内服务调用**，且为**单机**环境 | HTTP 全链路（JMeter/k6）与多机部署下的复测；分段池的"利用率损失"未实测（目前是推论） |
| 性能数据波动较大 | 单机开发环境（与 IDE/数据库同机），多轮运行 TPS 波动约 ±20%；**结论依赖的是比值（饱和/倍数），不是绝对值** | 独立压测机 + 固定资源配额后复测 |
| 台账写入为「尽力而为」 | 迁移台账写失败只告警，不阻塞业务 | 如需强审计，改为同事务强一致并接受写放大 |
