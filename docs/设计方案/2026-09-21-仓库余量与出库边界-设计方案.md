## 1. 背景与目标

**业务事实（2026-09-21 确认）**：配送站是**学校自己的**，不是奶企的。业务链为：奶企 → 学校配送站（收货、按班分类）→ 公共领取点 → 班级/学生 → 班主任签收（见 `../基线文档/业务边界与责任域.md` §二）。仓库在校园内，收货点数本来就是配送站每天的人工动作。

**缺口**：配额池建模的是"供货计划"，与物理世界之间没有对账通道。三个具体表现：

1. **多出来的奶没有归宿**：企业多送（要 500 到 504）、家长退订后未送的奶、拒收退回的奶——这些实物在学校仓库里，系统里没有任何账目承载它们；
2. **短交发现太晚**：企业少送（要 500 到 480）要到家长支付扣减失败或缺货取消时才暴露，此时已触发退款整条链路；
3. **配额发行无物理依据**：管理员设 100 盒配额，仓库里有没有 100 盒，系统不知道。

**设计主张**：**仓库余量是机动配额的唯一合法来源**。配额池继续作为并发控制闸门（行锁、条件更新、台账、守恒全部不动），唯一的变化是**额度的发行被仓库实物封顶**。出入库全自动，唯一日常人工步骤 = 收货点数时登记一行。

**目标**：一条进出账台账 + 到货登记接口 + 出库/退回自动挂钩 + 配额发行校验 + 短交预警。让"多出来的奶"进余量池（不浪费）、"短交"在收货时暴露（缺货取消+退款链路几乎不再触发）、"应送 vs 实到"差异可查。

**非目标（明确不做）**：效期预警、先进先出的物理管理、盘点、库位管理（这些是 ERP 的职责，本方案是"一条进出账"，不是库存系统）；采购订货与奶企结算（商务域）；学期套餐的供货计划管理（走合同，套餐实物占账但不占机动额度）。

## 2. 业务规则（拍板结论）

| # | 规则 | 说明 |
| --- | --- | --- |
| R1 | **台账四类账目** | `IN 到货`（人工登记，每日一品种一行，可挂批次）/ `OUT 送出`（自动，挂任务号）/ `IN_BACK 退回`（自动，拒收触发）/ `ADJ 修正`（人工，管理员+必填原因，含期初 INIT）。▶§11.2-4：**`INIT` 是独立 `biz_type`**，不并入 `ADJ`；▶§11.2-5：`ADJ` 的 `quantity` **带符号** |
| R2 | **出库时点 = "今日已送出"** | 物理移动发生在仓库 → 领取点，即 `batch-start`（今日已送出）时刻，**不是签收**。签收是消费确认，出库是物流事实，两者分开。套餐任务与机动任务送出走同一条 OUT 账（实物不分来源） |
| R3 | **退回 = 拒收自动入账** | `rejectRecord` 时同事务记 `IN_BACK`（奶被带回学校即入账）；破损无法回卖的走 `ADJ` 冲销（两条留痕，账实对齐）。次日补送的新奶走正常 OUT |
| R4 | **余量恒等式** | `W(品种) = ΣIN + ΣIN_BACK + ΣINIT − ΣOUT − ΣADJ`。任何时刻 W ≥ 0（不变量，见 §6）。▶§11.2-5：**`ΣADJ` 为带符号求和**（原文的"−ΣADJ"使"反向 ADJ 冲销"无法实现） |
| R5 | **配额发行封顶** | 设置配额时校验：**窗口内机动剩余额度合计（Σ(total−used)）+ 套餐待送出量合计（任务 status∈{1,2} 的 quantity）≤ W**。不满足则拒绝设置（提示"仓库余量不足，请先登记到货"）。**支付扣减路径零改动**——额度发行时已被封顶，扣减时无需再查仓库（不新增热点行）。▶**本行口径已被 §11.2 的 R5′ 取代**（原文既漏"已售未送出"又重复计入 `status=2`，可超发） |
| R6 | **到货登记必经** | 不登记到货则 W=0，机动配额设不了——显式失败优于静默。这是每天收货点数的线上化，不是新增负担。首次上线需一次性期初登记（INIT 行），使 W ≥ 窗口内剩余额度合计，否则全部设配额操作会被 R5 拒绝 |
| R7 | **台账只读** | 台账是事实记录，禁止修改删除（与 `process_transition_log` 同一原则）；记错走反向 `ADJ` 冲销，两条留痕 |
| R8 | **多到货的归宿** | IN 记实到数（504），比计划多的 4 盒自动成为余量 → 次日机动配额上限自然 +4。**"多出来的奶"的处理方式 = 进余量池继续卖**，这正是业务方确认的口径 |
| R9 | **短交预警（不阻断）** | 登记到货时对照当日应到计划（口径见 §7），差异 > 0 给出预警消息，**不阻断登记**（企业可能分批到货）；管理员据此下调配额或提前安排 |
| R10 | **权限** | 到货登记/查询：配送站 + 管理员；修正：仅管理员；家长/班主任不接触仓库 |

## 3. 数据模型

```text
warehouse_ledger（仓库台账）
  id
  biz_type    VARCHAR(12)  -- IN / OUT / IN_BACK / ADJ / INIT
  biz_date    DATE         -- 业务日期（IN=到货日，OUT=送出日；▶§11.2-2：OUT 取 task.delivery_date）
  product_id  BIGINT       -- 品种（不混账）
  quantity    INT          -- 恒为正数，方向由 biz_type 表达（▶§11.2-5：ADJ 例外，带符号）
  ref_type    VARCHAR(30)  -- OUT=delivery_task / IN_BACK=delivery_record / 其他=NULL
  ref_id      BIGINT       -- 关联对象 id（OUT 幂等键、IN_BACK 幂等键）
  receipt_no  VARCHAR(64)  -- ▶§11.2-3 新增：到货凭证号（IN 默认 MAIN、第二车填送货单号；INIT 填 INIT）
  batch_no    VARCHAR(64)  -- 可选，IN 时挂批次（后续扩展方案 §4.7 的数据来源）
  reason      VARCHAR(255) -- ADJ / IN_BACK 必填；IN 可填供应商/送货单号
  operator    VARCHAR(64)
  deleted, create_time, update_time
  唯一键（▶§11 修订后：uk_out/uk_back 合并为 uk_biz_ref，uk_in 换成 uk_in_receipt）：
    uk_biz_ref     (biz_type, ref_id)                            -- OUT/IN_BACK 幂等（NULL 不互相约束）
    uk_in_receipt  (biz_type, biz_date, product_id, receipt_no)  -- IN/INIT 幂等（双击、迁移重跑）
```

- 单表多类型（`SUM(CASE)` 即得 W），不建"到货单""出库单"多张表——一条进出账，管理端一页看全；
- 台账行与既有台账同原则：只增不改；`ADJ` 是唯一的纠错通道（留痕冲销）；
- 期初：`INIT` 行每人一品种一行（实施迁移步骤，R6）。

## 5. 服务层设计与可靠性约束

**钩子点（共 3 处，全部复用既有事务边界）**：

1. `DeliveryTaskServiceImpl.batchStart`（今日已送出）：同事务逐任务写 OUT（唯一键幂等，重复 batch-start 靠 CAS + `uk_out` 双重挡住）；套餐与机动任务同一钩子；
   ▶**§11 P0-4：实际方法名为 `batchStartDelivery`，且单条 `startDelivery` 与批量共用同一个 `casDispatch`——
   钩子必须挂在两者共用的收口（各自 CAS 成功后调用同一私有落账方法），只挂批量会漏记全部单条送出**；
2. `DeliveryTaskServiceImpl.rejectRecord`：同事务写 IN_BACK（挂 record_id）；
   ▶**§11.2-6：钩子只能挂在这个用户入口，禁止挂共享助手 `markRecordRejected`**；
3. `DailyQuotaServiceImpl.setQuotaBatch`：设置前校验 R5（一次 SUM 查 W + 一次 SUM 查套餐待送量——低频路径，无热点问题）。
   ▶**§11.2 R5′：判据换成「D 日实物需求 ≤ W」，并在事务内先锁 `product` 行（原描述漏了校验-动作竞态）**。

**可靠性约束（逐条对齐检查清单）**：

1. **台账写入与业务动作同事务**：OUT/IN_BACK 与任务状态迁移在同一事务，"奶送出了但账没记"不可能发生（与自愈待办同款约束）；
2. **幂等靠唯一键**：OUT/IN_BACK/IN 都有业务唯一键，应用层用 `IdempotencyGuard` 翻译冲突，禁止"先查再插"；
3. **多实例**：batch-start 双实例并发 → CAS 只一方赢 + `uk_biz_ref` 兜底；到货登记双击 → `uk_in_receipt` 仲裁；
4. **配额池零改动**：deduct/restore/结转/先过期先出全部不动——发行校验只加在 setQuotaBatch 入口，**并新增一条 `product` 行锁使同品种发行串行**；
5. **无新定时任务**：预警在登记时同步计算返回，不需要扫描任务。

## 6. 不变量清单

| 编码 | 不变量 | 处置 | 说明 |
| --- | --- | --- | --- |
| `INV_WAREHOUSE_NONNEG` | 任意时点 W(品种) ≥ 0 | **ALERT_ONLY** | W<0 意味着账错（OUT 多记 / IN 漏记 / ADJ 误操作），修复需人工对账，不自动改 |
| `INV_LEDGER_OUT_TASK` | 按任务：**`dispatch_time IS NOT NULL`** 的任务必须恰有一条 OUT（`biz_type='OUT' AND ref_id=task.id`）；反之 OUT 行必须对应已送出任务 | **AUTO_REPAIR** | ▶**§11 P0-3：原判据「status∈{2,3,4}」会把大量 1→4 未送出任务误判为漏记并自动补写入台账（补完 W 变负）**。改判据后：漏记可幂等补写（唯一键仲裁，`biz_date = DATE(dispatch_time)`）；多记不可能。**逐任务行级探测**，不用合计相等 |
| `INV_LEDGER_REFUND_LINK` | 按记录：真拒收（`sign_status=3 AND reject_reason_code IS NOT NULL`）的记录必须恰有一条 IN_BACK（`biz_type='IN_BACK' AND ref_id=record.id`） | **ALERT_ONLY** | 口径与 `INV_TASK_COMPENSATION` 同源；退回是否可回卖涉实物状态（破损），只告警。**逐记录行级探测**（合计相等会被两处反向错误抵消） |
| `INV_WAREHOUSE_COVERAGE` | 发行封顶关系式恒成立：`Σ池剩余 + Σ(status=1 且 delivery_date ≤ today 的任务 quantity) ≤ W` | **ALERT_ONLY** | ▶**§11 新增（第 4 条）**：R5′ 是发行时的**闸门**（只在设配额那一刻生效）；并发竞态/规则停用/直接改库都可能绕过闸门。本条目把同一关系式升级为**持续验证**，把"绕过闸门"暴露出来。只告警不自动改（自动改意味着自动下调他人配额 = 业务决策） |

## 7. 短交预警口径

登记到货时计算"应到 vs 实到"：

```text
应到(品种, 当日) = 当日机动配额 total 合计 + 窗口内未售额度合计（结转池）+ 套餐当日待送出量
实到 = 本次登记 quantity
差异 = 应到 − 实到 > 0 → 预警消息（不阻断）
```

> ▶**§11.2：上式已作废**——「当日 total 合计」与「窗口内未售额度合计（含当日池）」把当日池算了两遍，
> 且漏掉「已售未送出的零散任务」（原 R5 的同一处错误）。**短交预警与 R5′ 共用 §11.2 的统一公式**，
> 基准日 D = 当日。

口径要点：应到的主体是**当日计划**（配额+结转+套餐），不是"历史累计欠货"——分批到货时第二车实到会使累计追平，管理员看当日消息即可；预警是提示不是闸门（R9），真正的闸门是 R5 发行校验。

## 8. 边界与异常情况

| 情况 | 处置 |
| --- | --- |
| 忘记登记到货就直接设配额 | R5 显式拒绝："仓库余量不足，请先登记到货"——显式失败优于静默（与周末停送开关同一设计哲学） |
| 到货登记数字错了 | 反向 ADJ 冲销 + 重新登记，历史行不改（R7） |
| 企业分批到货 | 一日一品种一行挡住了第二车——同日补登走 ADJ（+增量，备注"第二车"）或放宽 `uk_in` 为允许多行（实施时二选一，默认 ADJ 简单）。▶**§11.2-3 已裁定：唯一键加 `receipt_no`**（第二车填送货单号，配送站可自助补登；`ADJ` 仅管理员，会让收货人无法当场补登） |
| 拒收的奶已破损 | IN_BACK 照记（回到学校即入账），破损走 ADJ 减（两条留痕，账实对齐） |
| 退订/平移/缺货取消（未送出） | 实物未动，**不动账**——奶自然留在余量里，明天额度重设时继续可用 ✓ |
| 退订作废已送出任务（`status=2`） | ▶**§11.2-7**：`cancelPendingTasksForOrder`（`:1166`）**可取消配送中任务**；已送出即已记 OUT，实物到校不回来 → **不回补、不记 IN_BACK**（避免与"退回"混同） |
| 多到货 4 盒 | IN 记实到，余量自动 +4，次日配额上限自然提高 ✓（R8） |
| 拒收后补送 | 次日新奶走 OUT；被拒的原奶在 IN_BACK 里——两笔账互不干扰 |
| 系统上线时仓库已有存量、且有未完成订单 | 期初 INIT 登记（R6），W 必须 ≥ 窗口内剩余额度合计，否则 R5 拒绝一切设配额——实施检查清单必含此项 |
| 学生转班/班级调整 | 台账按品种记账、OUT 按任务记账，与班级无关——无交叉影响 |
| 双实例并发 batch-start | CAS 只一方胜 + `uk_out` 兜底，OUT 只记一次 |

**实验二十（对齐实验系列规范：对照组 + 归档 + 数据写入实验文档）**：

| 用例 | 验证命题 |
| --- | --- |
| ① 守恒 | 混合负载（下单支付+送出+拒收+修正）后，W == ΣIN+ΣIN_BACK+INIT−ΣOUT−ΣADJ，逐品种断言 |
| ② 出库幂等 | 并发 batch-start（16 线程）→ 每任务恰一条 OUT |
| ③ 发行封顶 | W=50 时设配额 100 → 拒绝；登记到货 60 后 → 通过 |
| ④ 短交预警 | 应到 100、实到 80 → 预警消息 + 登记成功 + 余量 80 |
| ⑤ 退回闭环 | 拒收 → IN_BACK 1 条 → W 恢复 → 次日补送 OUT 正常 |
| ⑥ 多实例 | 双组件并发登记/并发送出 → 台账不重复（唯一键仲裁） |

## 10. 决策记录（2026-09-21）

| # | 议题 | 决策 | 理由 |
| --- | --- | --- | --- |
| 1 | 仓库余量是否进系统 | **进**（业务方确认"只有余量才能卖"） | 配送站是学校自己的，仓库在履约链起点（边界文档 §二）；不做则履约链从半截开始 |
| 2 | 到货登记是否必经 | **必经**（不登记 W=0，配额设不了） | 显式失败优于静默；收货点数本就是人工必做动作，线上化非新增负担 |
| 3 | 出库时点 | **送出（batch-start），非签收** | 物理移动在仓库→领取点；签收是消费确认。两者分开才对得上"奶去哪了" |
| 4 | 套餐与台账关系 | **占实物、不占机动额度** | 套餐走合同不占配额池（既有规则）；但实物同仓同账，OUT 同记，R5 校验含套餐待送量 |
| 5 | 台账形态 | **单表多类型一条账** | SUM(CASE) 即余量；不建多张单据表；管理端一页看全 |
| 6 | 效期/先进先出/盘点 | **仍不做** | 台账是"一条进出账"不是 ERP；批次钩子（§4.7）已由 IN 的 batch_no 预留 |
| 7 | 与"计划模型"的关系 | **双模型各得其所** | 学期套餐的地基=合同（学期初锁定量）；机动配额的地基=仓库（卖之前先看库）——不再是权宜之分 |

**被明确排除的做法**：① 全量库存系统（入库单/出库单/效期预警/盘点/库位）——超出"一条进出账"，属 ERP 职责；② 出库时点放签收——把物流事实和消费确认混同，拒收退回的账无法解释；③ 出库放支付——支付时奶没动，出库会凭空扣实物；④ 配额扣减时实时查仓库——新增热点行，且额度发行已封顶、无需二次校验。

## 11. 评审修订（2026-09-21，实施前置）

> 本节由 2026-09-21 的方案评审产出：把 §2~§9 的口径逐条对照代码
> （`DeliveryTaskServiceImpl`、`DailyQuotaServiceImpl`、`ProcessInvariant*`、实验包与实验库）核对后，
> 发现 **4 处会导致"账算错"的硬缺陷**与 **8 条必须钉死的口径**。
> **凡本节与上文冲突，一律以本节为准**；上文保留原文作为设计期证据（评审前的问题记录在案，便于论文引用）。

### 11.1 P0 硬缺陷（不修则必然算错账）

| # | 缺陷 | 代码证据 | 修订 |
| --- | --- | --- | --- |
| P0-1 | **R5 公式算错需求**：任务在**支付事务内**就展开（扣配额与展开任务同事务），而 OUT 在**送出**时才记 —— 「已售未送出」的零散任务既不在 `Σ(total−used)`（已被扣走）也不在原公式里 → **可超发**；同时 `status∈{1,2}` 中的 2 已 OUT、W 已扣过，再计一次是**重复** → 误拒合法设置 | `OrderInfoServiceImpl`（支付：扣配额 + 展开任务）、`DailyQuotaServiceImpl.deduct`、`DeliveryTaskServiceImpl.casDispatch` | 统一为 §11.2 的 **R5′**：任务口径 `status=1 且 delivery_date ≤ D`，池口径 `quota_date ∈ [D−2, D]` |
| P0-2 | **发行校验是 check-then-act**：`setQuotaBatch` 只对目标池 `selectForUpdate`，W 的聚合读无锁 → 同品种并发发行两个日期时各自都读到旧 W → **双双通过** | `DailyQuotaServiceImpl.setQuotaBatch` | 发行事务内先锁 `product` 行（同品种发行串行化）。`deduct` 只锁池行、且加锁顺序为 product→quota，无环 |
| P0-3 | **`INV_LEDGER_OUT_TASK` 判据错**：`status∈{2,3,4}` 中的 4 绝大多数**从未送出**（缺货取消 / 家长豁免 / 平移作废 / 期末摊平全部是 1→4）→ 大面积误报，且处置是 AUTO_REPAIR → **自动补造假 OUT 行，W 变负** | `DeliveryTaskServiceImpl`（1→4 四处 CAS） | 判据改为 **`dispatch_time IS NOT NULL`**（与 CAS 同事务写入），补写时 `biz_date = DATE(dispatch_time)` |
| P0-4 | **出库钩子漏了单条路径**：§5 只写 `batch-start`，但单条 `startDelivery` 与批量走**同一个 `casDispatch`** | `DeliveryTaskServiceImpl.startDelivery` / `batchStartDelivery` / `casDispatch` | 钩子挂在共享收口（两处 CAS 成功后调用同一私有落账方法），否则单条送出全部漏账 |

### 11.2 权威口径（替代 §2 R4/R5 与 §7）

**统一公式（R5′ 发行封顶 = §7 短交预警，同一个 helper）**：

```text
需求(品种 p, 基准日 D)
  = Σ_{池: quota_date ∈ [D−2, D]} GREATEST(total_quota − used_quota, 0)   -- D 当天可卖（含结转池）
  + Σ_{任务: product_id=p, status=1, delivery_date ≤ D} quantity            -- D 当天及逾期未送出（不分套餐/零散）
判定：需求 ≤ W(p) → 通过；否则设配额时拒绝（R5′）／到货登记时给短交预警（§7，不阻断）
```

三点必须一起看，缺一条就失衡：

1. **任务必须算 `≤ D`，不只是 `= D`**：池口径含结转（`D−2`、`D−1` 的未售），若任务只算当天，
   结转池与「早先已售未送出」会**对同一批实物重复计入可卖额度** → 实测可超发（原稿算术漏洞正属此类）；
2. **任务必须算全部类型**：套餐不经配额池，但**实物同仓**；只算套餐会漏掉「已售未送出的零散」（P0-1）；
3. **不能算 `status=2`**：已 OUT、W 已扣，再计即重复（原稿 `{1,2}`）。

**需业务知悉的后果**：W 是"今天仓库里的实物"，因此**提前为远期日期设池会被拒绝**（那天的货还没到），
即系统**不做远期预售**（本方案无 MRP、无预计到货，明确不做）。管理员操作次序固定为
**当日到货登记 → 当日/次日配额设置**，与 §8「忘记登记到货就直接设配额 → 显式拒绝」自洽。

**其余口径**：

| # | 口径 | 结论 |
| --- | --- | --- |
| 1 | **「窗口」定义** | 复用既有 `SHELF_DAYS=3`（池子 `D` 可用于配送日 `D..D+2`）；池口径 = `quota_date ∈ [D−2, D]`，**不得另立窗口** |
| 2 | **OUT 的 `biz_date`** | `= task.delivery_date`（业务日账，日账与短交预警口径一致）；实际送出时刻查 `dispatch_time`（`batch-start` 支持补登过去日期，用 today 会错位） |
| 3 | **分批到货（第二车）** | 唯一键加 `receipt_no`：`uk_in_receipt(biz_type, biz_date, product_id, receipt_no)`；首行默认 `MAIN`、第二车填送货单号 → 配送站**可自助补登**，双击仍撞键（`ADJ` 仅管理员，会让收货人无法当场补登） |
| 4 | **`INIT` 是独立 `biz_type`** | §2 R1「ADJ 修正（含期初 INIT）」表述作废；`INIT` 行 `receipt_no='INIT'`，同样受 `uk_in_receipt` 约束（迁移可安全重跑） |
| 5 | **`ADJ` 带符号** | 原文 `−ΣADJ` 使"反向 ADJ 冲销"不可实现。改为：`quantity` 对 `IN/OUT/IN_BACK/INIT` 恒正（方向由 `biz_type` 表达），**`ADJ` 带符号**（正=增加余量，负=减少余量）；恒等式 `W = Σ(IN, IN_BACK, INIT) + Σ(ADJ 带符号) − Σ(OUT)` |
| 6 | **IN_BACK 钩子位置（禁令）** | 只能挂用户入口 `rejectRecord`；**禁止**挂共享助手 `markRecordRejected` —— 它是「任务作废时把未签收记录置 `sign_status=3`」的公用方法，缺货取消与退订也在调用它，挂错会**凭空多记退回**（`INV_TASK_COMPENSATION` 用 `sign_status=3 AND reject_reason_code IS NOT NULL` 区分这两类，正是同一原因） |
| 7 | **退订作废已送出任务** | `cancelPendingTasksForOrder` 可取消 `status=2`（配送中）：已送出即已记 OUT，实物到校不回来 → **不回补、不记 IN_BACK**（§8 的"未送出不动账"按此补全） |
| 8 | **期初 `INIT` 下界** | 不只"窗口内剩余额度"：须 `W ≥ Σ_{池 ∈ [today−2, today]} (total−used) + Σ_{status=1 任务, delivery_date ≤ today} quantity`，否则首次 `batch-start` 即把 W 打成负数 |

### 11.4 实施期与设计期的偏差（2026-09-21 落地后回填）

| 项 | 设计 | 实施 | 原因 |
| --- | --- | --- | --- |
| 到货日期 | §4 只写"date" | **不得晚于今天**（显式拒绝） | 到货登记记的是既成事实；允许登记未来日期等于允许"凭空增加余量"，封顶会失去物理依据 |
