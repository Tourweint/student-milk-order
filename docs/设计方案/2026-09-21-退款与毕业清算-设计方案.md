## 1. 背景与目标

**业务事实与缺口**：

1. 钱与履约的粒度不齐：订单一笔 `pay_amount` 挂全程，履约按"任务（订单×品种×日）"逐期进行。学期中"这个月剩 15 天别送了，退 15 盒的钱"在当前系统里无法表达——配送中禁止退订，只能引导线下。
2. 现存审计缺口：已支付未配送退订（`ORDER/CANCEL/2`）会回补配额、作废任务，但**不产生任何退款记录**——资金台账断链（模拟场景钱是模拟的，台账完整性仍是过程可观测的一部分）。
3. 毕业时学生名下可能挂着未走完的订单（待支付/已支付/配送中），需要一次性的清算出口。

**设计主张（评审要点）**：退款域是**继支付域之后，"长期、多阶段、可失败过程"抽象的第二个业务落点**——退款单（父过程）→ 退款执行（子动作）→ 回调丢失（对账）→ 重复退款（幂等），与支付域完全同构（《业务过程与可靠执行模型》§1.3 的"抽象可迁移"由本方案兑现）。因此退款域**复用四层模型与全部既有可靠性机制，不新造第二套**。

**目标**：家长可对已支付/配送中订单申请按期次退款；管理员审核后执行，模拟通道即时到账；毕业时一键清算名下全部未完成订单；退订联动补齐全额退款记录；全程走统一迁移出口（CAS + 规则闸门 + 台账留痕），金额守恒。

**非目标（明确不做，见 §10 决策记录）**：真实微信退款联调（T+1、退款回调、原路退回）——模拟通道同步完成，对账任务留扩展接口；稀缺公平分配策略（维持先到先得）；转班归属；跨学期衔接。

## 2. 业务规则（拍板结论）

| # | 规则 | 说明 |
| --- | --- | --- |
| R1 | **退款基数 = 执行时刻的"可退期次"，显式排除已退订订单** | 可退期次 = 该订单 `delivery_task.status=1`（待配送）的任务 ∪ 缺货取消任务（任务 status=4 且关联 `delivery_record.sign_status=3 AND reject_reason_code IS NULL`，与 `INV_TASK_COMPENSATION` 同判据——缺货取消没送奶，钱应退）。**已退订（订单 status=5）联动作废的任务不计入**：其同样 sign=3、无 reason_code，与缺货取消同形，若计入会与 R4 全额退款重复退钱。配送中、已完成、真拒收（有 reason_code，已补送）的期次不退 |
| R2 | **金额口径：按盒均摊，累计制防尾差；分母用合同总盒数快照** | 零散任务金额 = 明细快照单价 × quantity（精确）；套餐任务单价 = `payAmount / 合同总盒数` 均摊。**分母「合同总盒数」在下单/支付时快照落库（order_info 增列 `contract_total_boxes`，任务生成处写入），退款公式固定取快照，不实时 `SUM(delivery_task)`**——平移/重排 CAS 作废行不删、拒收补送加量、期末摊平重写 quantity，SUM 会漂移。**分子只算本次 attempt 实际作废成功的盒数，且排除补送产生的增量**。退款金额 = `payAmount × 累计退盒数 / contract_total_boxes − 该订单已退累计`（BigDecimal 2 位），保证 **Σ(全部退款) ≤ payAmount 恒成立、多笔退款之和与按比例计算一致**，无逐笔舍入漂移。**已知偏差**：多品种套餐贵价奶与便宜奶按均价同价退款（精确需逐品种累计已退盒数，≈ refund_record，已被明确排除），维持均价并记为已知偏差，不留暗坑 |
| R3 | **订单状态不新增** | 退款执行时把可退任务经 `attempt(TASK_CANCEL, 1→4)` CAS 作废 → 子任务全终态 → 既有聚合出口 `completeOrderIfAllTasksDone`（已放开 2/3→4）把订单自然推向"已完成"。**退款是挂在订单旁侧的资金过程，不侵入订单状态机**；部分退款后订单继续配送剩余期次，状态不变 |
| R4 | **退订联动补台账** | 已支付未配送退订（2→5）在**同一事务**创建一张全额、即时的退款记录（状态 3 已退款），补齐资金台账；流程不变，只补记录。原子性用 `@Lazy` 自注入（OrderInfoServiceImpl 现有先例）在同一事务内完成，退款侧**不反向依赖 OrderInfoService**（依赖环见 §5.8） |
| R5 | **退款单状态机** | `1 待审核 → 2 已审核待退款 → 3 已退款`；`1 待审核 → 4 已拒绝`（可重新申请）；迁移全部经 `ProcessTransitionExecutor`，场景 `REFUND`，规则种子见 §7 |
| R6 | **申请幂等（DB 唯一约束，非"先查再插"）** | 同一订单存在进行中退款单（状态 1/2）时拒绝新申请；状态 4/5 的历史单不阻塞。实现：**生成列 + 唯一索引**（status∈(1,2) 时生成列取 order_id，否则 NULL，`uk_refund_active`），冲突由 `IdempotencyGuard` 翻译为"已存在"；**不做应用层"先 selectCount 再 insert"**（AGENTS.md 禁令） |
| R7 | **金额以执行时刻为准，preview/execute 共用口径** | 申请时记录申请盒数（仅参考），**退款金额在执行时刻按 R1/R2 计算**——申请与执行之间任务可能继续配送（窗口期用"执行时计算"消除，而不是冻结任务）；执行前置校验可退盒数 > 0，否则拒绝执行。**preview 与 execute 必须调用同一个计算方法（同一私有方法）**，家长预览"可退 15 盒"与实际退款盒数必须一致 |
| R8 | **毕业清算（专属路径，不复用超时取消）** | 对学生名下全部 `status ∈ {1,2,3}` 订单逐单处理：待支付 → **清算专属路径**（`attempt(CANCEL, 1→5)` + 作废待支付流水），**不调用 `cancelTimeoutOrder`**——其"未超时直接 return false"会导致待支付单清不掉，"查单对账"会把"已扣款未回调"订单补成已支付，与真实资金状态不符；已支付/配送中 → 按整单可退期次生成并执行退款。清算幂等：重复执行只会得到"无可清算订单"。学生是否从班级移除由管理员另行操作（转班/归属暂缓，不在本方案） |
| R9 | **权限** | 家长：对本人孩子订单申请退款、查看本人退款单；管理员：审核、执行、查看全部；班主任/配送站：不接触退款 |
| R10 | **执行退款必须回补配额** | 对本次**实际作废成功**的零散单任务（`packageId == null`）逐任务调 `dailyQuotaService.restoreForOrderProductDate(orderId, productId, date)` 回补配额（缺货取消同款方法）；**缺货取消任务在取消时已回补过配额，不重复回补**。注意该方法忽略 quotaDate 入参、按"订单+品种"整份回补，不能按天部分回补。套餐任务不涉及每日配额。漏回补 = "钱退了、库存没回来" |

## 3. 数据模型

```text
order_info 增列（R2 分母快照）：
  contract_total_boxes    # 合同总盒数，下单/支付任务生成时一次性写入（generateTasksForOrder），此后不变

refund_order（退款单）
  id, refund_no（uk_refund_no，退款单号：RF+时间戳+InstanceIdentity.TAG+序列，跨实例唯一）
  order_id（idx_refund_order；进行中单唯一性由生成列 uk_refund_active 约束，见 R6）, order_no, student_id, user_id（申请人）
  apply_box_count（申请盒数，参考值）, refunded_boxes（累计已退盒数）
  refund_amount（退款金额，执行时回填）, status（1待审核/2已审核/3已退款/4已拒绝/5已取消）
  apply_reason, audit_user_id, audit_time, audit_remark
  refund_channel（1 模拟微信）, refund_time
  deleted, create_time, update_time
```

- 一张退款单即一条资金记录，**不另建 refund_record**（一单一行，无多次部分执行——部分退款是"多张单"，不是"一张单多次执行"）。
- 退款单号带 `InstanceIdentity.TAG`（与订单号/流水号同规则，多实例不撞 `uk_refund_no`）。
- 不新建任务侧表：退款与任务的关联通过执行时刻的实时查询（R1 口径）建立，不落"退款-任务"明细——避免申请快照与执行现实的窗口漂移。
- R2 分母不落 refund_order：执行时读 `order_info.contract_total_boxes`（支付后不可变），语义与"金额以执行时刻为准"一致，且天然不漂移。

## 5. 服务层设计与可靠性约束

**执行链（`RefundOrderService.executeRefund`，事务边界在外部入口）**：

```text
读取退款单（校验 status=2）→ 计算 R1 候选可退任务（含订单非 5 校验）
→ 逐条 attempt(TASK_CANCEL, 1→4) 作废待配送任务（CAS 即幂等闸门，落败=已被并发处理，剔除、不参与计价）；
  已是 4 的缺货取消任务直接计入可退集（本就处于终态，无需再作废）
→ 按【实际作废成功集合】计算 R2 金额（分母=order_info.contract_total_boxes 快照；分子=本次成功作废盒数，排除补送增量）
→ 零散单逐任务回补配额（R10，packageId==null；缺货取消任务不重复回补）
→ 若成功集合为空（全部被并发配送/取消）→ 拒绝执行（转 4 已拒绝，见 §7 台账）
→ CAS 推进退款单 2→3（REFUND/EXECUTE，统一出口，**require**：规则禁止/并发冲突抛业务异常整体回滚，不留静默失败）
→ 回填 refund_amount / refunded_boxes / refund_time
→ 事务内 enqueue 父过程自愈待办（任务批量作废 → 订单聚合）——与配送送出同款双通道语义
→ 聚合出口自然收敛订单状态（R3，不手写"订单改成什么"）
```

**可靠性约束（逐条对齐《可靠性设计》检查清单）**：

1. **顺序硬约束：先抢履约、再计价、后动资金**：候选集 → 逐条 attempt 作废（履约侧抢占，只认返回 true）→ 按实际成功集合计价 → 配额回补 → 退款单 CAS 2→3（资金侧，用 **require**）→ 回填，全部同事务，任一失败整体回滚。**禁止先计价后作废**（并发输掉的任务也会被计价 → 多退钱）。
2. **任务作废走统一出口**：`attempt(TASK_CANCEL)`，禁止直改 status；平移/重排的预检天然兼容（作废后任务 status=4 不在候选集）。
3. **金额守恒靠累计制**（R2）：`Σ已退金额 ≤ payAmount` 由公式结构保证，不靠事后体检兜底；`INV_REFUND_AMOUNT` 仅作告警级复核（涉资金不自动修）。
4. **与配送并发竞争**：执行时刻计算（R7）——执行事务内逐条 CAS 作废，已被配送的任务拿不到（CAS 失败即剔除），金额按实际作废集合结算。**不存在"退了钱又把奶送了"的窗口**：作废成功 ⇔ 钱按它结算；作废失败 ⇔ 奶照送、钱不退它。
5. **申请幂等靠 DB 唯一约束**（R6）：生成列（status∈(1,2) 时取 order_id，否则 NULL）+ 唯一索引 `uk_refund_active`，冲突由 `IdempotencyGuard` 翻译为"已存在"；**不做应用层"先 selectCount 再 insert"**（AGENTS.md 明令禁止的路径；低频不构成理由，多实例下会重复插）。
6. **毕业清算幂等**（R8）：逐单 CAS/attempt（清算专属路径，不调 `cancelTimeoutOrder`），重复执行零效果；单笔失败不阻塞其余（逐条 try/catch + 结果清单返回）。
7. **对账扩展点（不在本期）**：真实微信退款为 T+1 异步，届时 refund_order 2→3 由回调驱动、`RefundReconcileJob` 对账超时未回调的 2 状态单——与 `PaymentReconcileJob` 完全同构，接口与状态机已预留，只加一个 Job 与一个查单方法。
8. **依赖环约束**：退款要读订单、作废任务、回补配额、触发父聚合，R4 又要求 cancelOrder 同事务创建退款单——order ↔ refund 成环。**拆法：父聚合只走 `pendingTaskService.enqueue(ORDER, ...)` 实时通道（OrderInfoServiceImpl 现有写法），退款侧不依赖 OrderInfoService；R4 的原子性用 `@Lazy` 自注入（OrderInfoServiceImpl:86-88 现有先例）在同一事务内完成；不引入事件总线（仓库目前零事件基础设施）**。

## 6. 不变量清单

| 编码 | 不变量 | 处置 | 说明 |
| --- | --- | --- | --- |
| `INV_REFUND_AMOUNT` | 订单累计已退金额 ≤ payAmount；已退款单必有 refund_amount>0 | **ALERT_ONLY** | 涉资金，只告警人工核处（对齐 INV_PAYMENT_CONSISTENCY 分级原则） |
| `INV_REFUND_TERMINAL` | 已退款(3)退款单的订单不应存在"退款单覆盖盒数"范围内的非终态任务 | **ALERT_ONLY** | 弱关联校验（执行时计算口径），防人工改库把作废任务改回来 |

不新增自动修复项：资金与履约历史不自动改（终态保守原则）。

## 8. 边界与异常情况（对照《边界与异常全景》）

| 情况 | 处置 |
| --- | --- |
| 申请后、执行前，家长又想少退点 | 取消进行中单（新增 `CANCEL 1→5`?）——**M1 不做**，拒绝后重新申请（R6 状态 4 不阻塞）；列为实施时可选 |
| 执行时订单恰好被并发退订（2→5） | **前置校验改为「订单状态非 5 且可退集合非空」，不再硬校验 ∈ {2,3}**——订单可能因全部任务终态被聚合为 4 已完成，但其中仍有缺货取消任务应可退（家长没喝到奶），硬门禁会吞掉合法退款；退订侧同事务创建的全额退款单（R4）与本单并存由 `INV_REFUND_AMOUNT` 兜底告警（双保险） |
| 套餐总盒数极小（1 盒）除法精度 | BigDecimal 2 位 + 累计制，最后一笔自然找平 |
| 清算时学生有待支付订单 | **清算专属路径**：待支付 → `attempt(CANCEL, 1→5)` + 作废待支付流水；**不调用 `cancelTimeoutOrder`**（未超时 return false → 清不掉；查单对账会把"已扣款未回调"补成已支付，与真实资金不符） |
| 已退订订单的任务混入可退集 | R1 显式排除订单 status=5 的任务（联动作废任务 sign=3、无 reason_code，与缺货取消同形）；R4 已全额退款，避免同一批盒数退两次 |
| preview 与 execute 口径不一致 | 二者必须调用同一计算方法（同一私有方法，R7）；预览只读不落库，金额以执行时刻计算 |
| 平移/摊平与执行退款同批操作同一订单 | 执行前预检可退集，作废 CAS 天然互斥；摊平基准= `1+补送量` 不含已作废任务，无交叉污染 |

### 10.1 评审修订决策（2026-09-21，评审意见并入）

| # | 议题 | 决策 | 理由 |
| --- | --- | --- | --- |
| 1 | R2 分母 | 合同总盒数支付时快照落库（order_info 增列 contract_total_boxes），不实时 SUM 任务表 | 平移/补送/摊平会改任务表数量，分母漂移导致退款比例错 |
| 2 | 执行链顺序 | 先逐条 attempt 作废，再按实际成功集合计价，最后 CAS 2→3 | 并发输掉的任务不应计价，避免多退 |
| 3 | 资金侧 CAS 语义 | 退款单 2→3 用 require（失败抛错回滚），任务作废用 attempt | attempt 在规则停用时静默失败且不写台账 |
| 4 | 退款门禁 | 订单非 5 且可退集合非空，替代 ∈ {2,3} 硬校验 | 全部任务终态自动完成（4）的订单仍可能有缺货取消可退期次 |
| 5 | 毕业清算 | 专属路径，不复用 cancelTimeoutOrder | 其未超时 return false、查单对账会补支付状态 |
| 6 | 退订边界 | R1 显式排除订单 5 的任务 | 联动作废任务与缺货取消同形，避免与 R4 重复退 |
| 7 | 配额回补 | 新增 R10：零散单逐任务 restoreForOrderProductDate，缺货取消任务不重复回补 | 漏回补 = 钱退了、库存没回来 |
| 8 | 依赖环 | 退款侧不依赖 OrderInfoService；R4 用 @Lazy 自注入；聚合走 enqueue 实时通道 | 避免 order↔refund 环形依赖；不引事件总线 |
| 9 | 盒均摊偏差 | 维持均价并记为已知偏差 | 多品种贵贱同价；精确需逐品种累计（≈refund_record，已排除） |
| 10 | R6 幂等 | 生成列 + 唯一索引，冲突交 IdempotencyGuard | 不做应用层"先查再插"（多实例会重复插） |
