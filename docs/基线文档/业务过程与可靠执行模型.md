# 业务过程与可靠执行模型

> 本文是项目的**核心抽象文档**：说明本项目真正要解决的问题不是「做一个订奶系统」，而是
> 「一个现实业务对象进入系统后，会经历长期、多阶段、异步、可失败的执行过程；
> 系统需要让这个过程在并发、重复、超时和局部失败下仍然可控」。
>
> 校园乳品配送只是**验证场景**，研究对象是**周期性业务履约的状态管理与异常恢复**。
> 本文同时给出抽象在代码中的落点，避免抽象停留在文档层面。
>
> 相关文档：`系统架构.md`（技术栈与模块）、`可靠性设计.md`（机制细节与判定口径）、
> `../实验/实验设计与结果.md`（验证）。

## 一、问题定义

### 1.1 现实流程 vs 理想流程

把「牛奶」拿掉之后，业务可以抽象成：

```text
现实业务需求
     ↓
业务订单
     ↓
执行计划
     ↓
多个执行任务
     ↓
任务逐个完成
     ↓
业务对象最终完成
```

但现实世界不是理想流程，执行过程会遭遇：

```text
                    ┌── 重复
                    ├── 并发
业务执行 ───────────┼── 超时
                    ├── 失败
                    ├── 部分成功
                    └── 数据不一致
```

因此系统真正要解决的是两个问题：

| 问题 | 内容 |
| --- | --- |
| **A. 过程如何被建模？** | 复杂业务过程如何从一个业务对象分解成多个可执行状态和任务？ |
| **B. 过程如何保证可靠？** | 出现重复、并发、超时、失败、部分成功时，如何保证系统不会进入不可控状态？ |

### 1.2 核心主张

> 系统真正想保证的不是「每一步都成功」——现实系统做不到；
> 而是**即使中间发生异常，系统最终也能识别问题，并把业务过程恢复到一个可解释、可继续执行的合法状态**。

### 1.3 为什么这不是一个普通订单系统

这一节是全文最需要讲清楚的地方。**「普通订单系统」与「本系统」的差别不在功能多少，
而在难点来源不同**：普通订单系统的难点通常在吞吐量、部署规模与数据量；本系统的难点在
**业务过程的长期性与异常性**。

| 维度 | 普通订单系统 | 本系统 |
| --- | --- | --- |
| **状态** | 订单一个 `status` 字段：创建 → 支付 → 完成 | 订单**宏观状态** + N 个配送任务**微观状态**；父状态由子过程**聚合**决定 |
| **生命周期** | 短：一次交易，结束即终止 | 长：学期套餐约 5 个月，逐日展开为数十上百个任务 |
| **执行方式** | 同步、单次、一次性交付 | **异步、逐日、多任务**，允许部分成功、允许个别期次取消 |
| **状态迁移** | `if/else` 硬编码在 Service 里 | **规则表驱动**（`state_transition_rule` 白名单，管理端在线调整），每次迁移**留痕** |
| **失败处理** | 依赖事务回滚：要么全成功、要么全失败 | 承认「每一步都成功」做不到，改为**可检测、可恢复的最终一致性**：对账 + 补偿 + 定时兜底 |
| **资源模型** | 库存是一个数字，下单即扣 | 按品种 × 按日的**配额池** + 保质期结转 + 先过期先出 + **台账精确回补到原池** |
| **幂等** | 通常不考虑 | 重复支付回调、重复任务展开、重复配额扣减都必须幂等，由**数据库唯一键 + CAS** 保证 |
| **顺序约束** | 无 | **先抢占状态、再执行副作用**（顺序颠倒会产生重复副作用并互撞唯一键） |
| **目标** | 「每一步都成功」 | 「即使中间异常，也能恢复到合法状态」 |
| **验证方式** | 功能点测试 | **并发/幂等/恢复实验 + 无保护对照 + 契约矩阵**，量化证明机制有效（并暴露了 6 个真实缺陷） |

一句话概括差异：

> 普通订单系统关心**一次交易能否成功**；本系统关心**一个长期过程在被反复中断、重复触发、
> 并发执行之后，能否仍然收敛到一个合法状态**。

**因此本系统不通过引入 AI 推荐、消息队列、Redis、微服务、容器编排来「显得高级」——
这些能力与本项目要解决的问题没有因果关系。** 本项目的复杂度来自业务过程本身。

> 术语对照（论文用词 ↔ 代码符号）见 `../论文/术语与代码对照表.md`，
> 用于确保论文表述与代码实现严格对应。

## 二、四层模型

```text
┌─────────────────────────────────────┐
│             业务层                   │  订单 / 支付 / 配送 / 配额 / 营养
│    （校园乳品配送：验证场景）          │
├─────────────────────────────────────┤
│             过程层                   │  状态定义 / 任务分解 / 状态聚合 / 迁移留痕
│                                      │  漂移探测 / 补偿决策 / 自愈待办 / 不变量体检
│                                      │  → com.milk.order.process
├─────────────────────────────────────┤
│             可靠性层                 │  幂等 / CAS / 行锁 / 台账 / 对账 / 补偿
│                                      │  → com.milk.order.reliability
├─────────────────────────────────────┤
│             兜底层                   │  超时检测 / 定时任务 / 自动恢复
│                                      │  → module/**/job + process/job
└─────────────────────────────────────┘
```

**这四层是问题抽象，代码只是它的实现。** 其中过程层与可靠性层是真正的横切关注点，
因此独立成顶层包（见第七节的映射表）。

> 本轮的深化重点：**把「异常恢复」也做成过程层的一等能力**。重构前补偿规则是订单服务里的两个
> `if`、漂移检测靠定时全表扫；现在探测（探测器）/ 决策（补偿规则表）/ 执行（统一迁移出口）
> 三层分离，并补上「实时自愈通道 + 兜底通道」的双通道与「跨表不变量体检」。
> 见 §3.6–§3.8。

## 三、过程层

### 3.1 一个订单不是一个状态

普通订单是 `创建 → 支付 → 完成`。本项目不是：

```text
创建
 ↓
支付
 ↓
生成 N 个执行任务（学期套餐按整个配送周期逐日展开）
 ↓
任务逐个执行（待配送 → 配送中 → 已完成 / 已取消 / 拒收）
 ↓
任务状态不断变化
 ↓
最终聚合
 ↓
订单完成
```

由此得到第一个关键区分：

> **订单状态是长期过程的宏观状态，配送任务状态是过程执行的微观状态。两者不能混在一起。**

### 3.2 层级化业务状态管理（父子状态机）

```text
                 Order
                   │
        ┌──────────┼──────────┐
        ↓          ↓          ↓
      Task 1     Task 2     Task 3 ...
        ↓          ↓          ↓
      完成        完成        配送中
                                 
                   ↓
        全部终态 → Order = 配送中 / 已完成
```

父状态**不由某个子任务直接改写**，而由子过程整体聚合决定。代码落点：

| 能力 | 实现 |
| --- | --- |
| 父→子分解（过程展开） | `DeliveryTaskService.generateTasksForOrder` |
| 子→父联动（开始执行） | `OrderInfoService.markDeliveringIfPaid` |
| 子→父聚合（全部终态） | `OrderInfoService.completeOrderIfAllTasksDone` |
| 候选检索与子过程条件求值 | `OrderProcessProbe`（实现 `ParentProcessProbe`） |
| 补偿动作落地 | `OrderProcessAggregator`（实现 `ParentProcessAggregator`） |
| 父子一致性探测与补偿 | `ProcessReconcileEngine` + `ProcessReconcileCoordinator` |

其中后两个「聚合出口」在实现上都通过**统一迁移出口**（见 3.3）完成，因此规则校验、CAS、留痕三者一致；
补偿同样只能经聚合出口落地，不允许自己拼 SQL 改状态——**否则修复本身就会成为绕过可靠性层的旁路**。

### 3.3 统一迁移出口：`ProcessTransitionExecutor`

这是过程层的核心，也是把散落在各 Service 里的 `if (status == X)` + 条件更新收口的地方：

```java
public interface ProcessTransitionExecutor {
    /** 严格迁移：规则禁止或 CAS 冲突都抛业务异常（用户直接发起、失败必须告知的操作） */
    void require(TransitionSpec spec, BooleanSupplier casUpdate);

    /** 宽松迁移：规则禁止或 CAS 冲突返回 false，不抛异常（批量流转、定时兜底、对账补偿） */
    boolean attempt(TransitionSpec spec, BooleanSupplier casUpdate);

    /** 只查规则（用于回调幂等分支等需要自行分流的场景） */
    boolean allowed(String scene, String action, Integer fromStatus);

    /** 只断言规则（批量操作的前置一次性校验） */
    void requireAllowed(String scene, String action, Integer fromStatus, String sceneText);
}
```

一次迁移把三件事收在一处：

1. **规则校验**：迁移是否允许由 `state_transition_rule` 规则表（白名单）驱动，管理端可在线调整；
2. **CAS 条件更新**：调用方以「原状态」为条件更新目标状态，并发下只有一个执行者成功；
3. **迁移留痕**：成功与冲突都写入 `process_transition_log` 迁移台账。

迁移的输入是显式规格 `TransitionSpec`（场景 / 动作 / 主体 / 起止状态 / 冲突提示 / 是否受规则管控），
因此「状态迁移」从一段散落的语句变成了一个可校验、可留痕、可测试的**过程定义**。

> **不变量**：业务对象的 `status` 字段只能经本执行器迁移；禁止在 Controller 或业务 Service 中
> 以非条件更新方式直接改状态。

两个方法对应两类语义，这是刻意的：

- `require` 用于**用户直接发起**的操作（支付、退订、手动完成、任务取消）：失败必须明确告知；
- `attempt` 用于**批量/兜底/补偿**：本轮不生效即跳过，天然幂等，重复执行无副作用。

### 3.4 状态迁移规则数据驱动

```text
传统写法：                        本项目：
代码                              状态 + 操作 + 来源状态
 ↓                                     ↓
if (status == X) 允许 Y              规则表（state_transition_rule）
                                       ↓
                                  状态机执行器
                                       ↓
                                  管理端在线调整，无需重新发布
```

规则表语义是**白名单**：未配置的组合一律视为禁止。因此新增状态迁移时必须同步补规则种子
（`src/main/resources/sql/data.sql`），否则该迁移会被拒绝。

### 3.5 迁移台账 `process_transition_log`

每次迁移落一行：场景、动作、主体、业务单号、起止状态、结果（1 生效 / 0 CAS 冲突）、操作人、备注。

- 台账是**过程可观测**的基础：支撑过程回放、问题回溯、父子状态对账与实验取证；
- 台账写入是「尽力而为」：写失败只告警，不改变业务迁移结果；
- 台账记录的是**已提交的业务事实**：在事务内因异常中止时，冲突记录随事务一起回滚。

**管理端查询入口**：`GET /api/system/transition-log/list`（仅管理员），支持按场景、动作、主体表、
业务单号（模糊）、结果、时间范围分页筛选；页面入口为「系统管理 → 过程迁移台账」。
台账**只读**，不提供修改与删除——删改会破坏可追溯性。

### 3.6 补偿规则引擎：探测 / 决策 / 执行三层分离

重构前的异常恢复是「代码里的两个 `if`」：想改补偿目标、想临时停止补偿、想新增一类漂移，
都必须改代码重新发布，且与状态迁移的数据驱动形成明显不对称。

现在把它拆成三层，每层职责单一、可单独验证：

```text
┌──────────────────────────────────────────────────────────────┐
│ 探测层  ProcessReconcileEngine                                │
│   按规则表的 parent_status 取候选 → 逐条求值子过程条件 → 产出决策 │
│   只读：不修改任何业务状态，可随时调用（体检 / 预览 / 实验）      │
│   业务侧提供：ParentProcessProbe（候选怎么查、条件怎么判）        │
├──────────────────────────────────────────────────────────────┤
│ 决策层  process_reconcile_rule（规则表）                       │
│   「父过程状态 + 子过程条件 → 补偿动作 + 目标状态」，可在线启停    │
├──────────────────────────────────────────────────────────────┤
│ 执行层  ParentProcessAggregator → 统一迁移出口                  │
│   仍要过 state_transition_rule 闸门，仍走 CAS，仍写迁移台账        │
└──────────────────────────────────────────────────────────────┘
```

规则种子（`sql/data.sql`）：

| 规则名 | 父状态 | 子过程条件 | 动作 | 目标状态 | 默认 |
| --- | --- | --- | --- | --- | --- |
| 联动丢失补偿 | 2 已支付 | `HAS_DISPATCHING_TASK` | `DELIVER` | 3 配送中 | 启用 |
| 聚合丢失补偿 | 3 配送中 | `ALL_TASKS_TERMINAL` | `AUTO_COMPLETE` | 4 已完成 | 启用 |
| 全取消补偿 | 3 配送中 | `ALL_TASKS_CANCELLED` | `CANCEL` | 5 已退订 | **停用（示例）** |

前两条与重构前行为等价（默认启用，保证不改变语义），第三条是「用配置表达新补偿」的示例，
默认停用并附注：**启用它还需要同步放开 `state_transition_rule` 的 `ORDER/CANCEL/3`**，
否则统一出口会以「规则禁止」拒绝该补偿。这条注释本身就是配置化规则的代价：
**规则之间存在依赖，配了规则不等于配对了规则**（实验六专门验证了这一点）。

两个刻意的边界：

1. **只配置「用哪个条件、补偿到什么状态」，不配置条件本身的语义**。
   条件（`HAS_DISPATCHING_TASK` 等）是显式枚举 + 业务侧实现，因为「什么算全部终态」涉及业务边界，
   允许任意表达式会让规则表无法审阅、无法测试；
2. **同一主体一轮只补偿一次**（按规则 id 取首个命中）。允许叠加会让一次探测连跳两个状态，
   使补偿范围超出单条规则的可审阅边界。

### 3.7 双通道：实时自愈 + 定时兜底

补偿能力有了，还要解决**什么时候发现**。重构前是纯拉模式：兜底任务每 10 分钟全表扫一轮，
因此漂移的**不可检测窗口最长 10 分钟**。

> 关键认识：「实时」的价值不是界面更快，而是**把系统「处于错误状态而不自知」的窗口缩短**。
> 但自愈本身也会失败，所以实时通道**不能替代**兜底——两者必须是双通道。

```text
子过程状态变更成功（同一事务内）
        │  ① 写一条自愈待办 process_pending_task（唯一键去重）
        ↓
秒级消费者 ProcessPendingTaskJob（每 5 秒）
        │  ② 按父过程最新状态重新探测 → 补偿
   ┌────┴─────┐
 成功         失败
   │            │
 置已处理    指数退避重试；超 5 次置「已放弃」并告警
                │
                ↓
        ③ 兜底通道 OrderProcessReconcileJob（每 10 分钟）最后防线
```

三个设计要点：

- **入队在事务内**：子状态已变与父过程待聚合「要么一起提交、要么一起回滚」，待办本身不会成为新的不一致来源；
- **它把隐式约定变成显式数据**：父过程聚合不再依赖「调用方记得调用聚合出口」，
  即使某条路径漏掉同步调用、或同步调用被规则表临时挡住，待办仍在，秒级消费者会补上；
- **去重键含触发动作** `(scene, entityId, triggerAction, status)`：一次批量送出 78 条任务也只产生一行待办。

两条通道的失败策略不同，且是刻意的：兜底通道「单条失败只记录并继续」（本轮尽可能多修），
实时通道「异常向上抛」（失败必须被看见并重试）。

### 3.8 不变量体检：从一次性验证到运行期持续验证

这是本轮最核心的一条设计主张：

> **不变量只在被验证时才成立。** 实验能证明它在某一次运行中成立过，但业务过程是持续的。

系统里存在一批**跨表约束**，它们不是主键外键能表达的，只能靠代码自觉维护。现在把每条约束
写成可注册的检查项 `ProcessInvariant`（探测只读 + 修复分级），由体检任务周期求值：

| 编码 | 不变量 | 处置 | 检测口径要点 |
| --- | --- | --- | --- |
| `INV_QUOTA_LEDGER` | 配额已售数 = 台账合计 | 自动修复 | 台账回补是**逻辑删除**，求和必须限定 `deleted = 0` |
| `INV_TASK_RECORD` | 任务已完成 ⇒ 签收记录已签收 | 自动修复 | — |
| `INV_SIGN_INTAKE` | 已签收 ⇒ 存在营养摄入记录 | 自动修复 | 一个记录最多一条摄入（`uk_delivery_record` 仲裁） |
| `INV_ORDER_TASK` | 订单的任务覆盖「品种 × 配送日」全网格 | **按情况分下**：进行中自动补网格 / 终态只告警不补造历史 | 比组合数而非行数：合并不误报，取消不误报 |
| `INV_ORDER_AGGREGATION` | 父订单状态与子任务集合一致 | 自动修复 | 复用补偿探测器，与兜底通道同一套判定口径 |
| `INV_PARENT_TERMINAL_CHILD_PENDING` | 父过程终态 ⇒ 不存在非终态子过程 | **按情况分下**：待配送自动作废 / 配送中仅告警 | **组合约束**：由实验发现（单条机制都正确、组合起来说不过去） |
| `INV_PAYMENT_CONSISTENCY` | 订单状态与支付流水互证 | **仅告警** | 涉资金，两端都可能是“对的”，必须人工核处 |

**分级的判断标准是修复的可逆性与影响面**：能由既有台账唯一推导出正确值、且重算幂等的才允许自动修复；
涉及资金流向或需要业务判断的一律只告警。实验七的对照 B 专门验证了这条分界线。

**等级还可以按"同一条不变量的具体情况"再分**：`INV_PARENT_TERMINAL_CHILD_PENDING` 中，
残余子任务处于「待配送」时奶尚未出库，自动作废是安全的；处于「配送中」时奶已出库在途，
自动作废等于把已送出的奶从记录里抹掉——只能告警。`INV_ORDER_TASK` 同理：
订单进行中时网格缺口必须补回来，订单已终态时缺口属于"历史被改过"，
**补造历史是错的**（会给已结束的订单造出待配送任务），只能报出来让人核。
因此体检框架的修复判定以**每条违规的实际等级**为准，不变量声明的等级只是默认值
（未声明时回退到默认，且回退方向是"不自动修"）。
这条设计同时保证了：**探测可以比修复更激进，修复永远比探测更保守**。

**修复的执行顺序由声明决定**：不变量之间不是彼此独立的——补网格会改变"子任务是否全部终态"，
而这正是父聚合的判定依据。因此 `ProcessInvariant.dependsOn()` 显式声明依赖，
体检器按拓扑序执行：

```text
INV_ORDER_TASK（补网格） → INV_ORDER_AGGREGATION（判父聚合） → INV_PARENT_TERMINAL_CHILD_PENDING（判组合）
```

若顺序反了，**体检自己就会制造**「已完成订单 + 待配送任务」这种组合异常。
依赖引用未注册编码或成环时直接失败——配置错误不能静默退化成任意顺序。
这条依赖是实验七发现问题的产物：单条机制都正确，组合起来却说不通（见实验七「附带发现与其加固」）。

体检记录（`process_invariant_violation`）**每个（不变量 × 主体）保留一行当前一致性状态**，
而不是每次检出追加一行：否则同一主体反复漂移会堆出多行，反而看不出「它现在到底一致不一致」。
重复漂移用 `reopen_count` 计数表达——它同时是衡量自愈有效性的指标。
一轮体检还会做**复检闭环**：上轮未闭环、本轮未再检出的记录自动闭环（问题真的消失了，而不是被忽略）。

## 四、可靠性层

可靠性层的原语集中在 `com.milk.order.reliability`，并配合过程层的执行器与数据库约束使用。
各机制的详细判定口径与实现见 `可靠性设计.md`，此处只列职责边界。

| 机制 | 解决的问题 | 落点 |
| --- | --- | --- |
| 业务唯一键 + 幂等守卫 | 同一动作执行多次怎么办 | `IdempotencyGuard`、`uk_order_product_date`、`uk_order_product_pool`、`uk_delivery_record` |
| CAS 条件更新 | 两个执行者同时改同一状态 | `ProcessTransitionExecutor` 内的条件更新 |
| 悲观行锁读 | 读-改-写之间被并发插入 | `DailyQuotaMapper.selectForUpdate` |
| 资源台账 | 资源从哪个池子扣、回补到哪 | `daily_quota_usage` + `DailyQuotaService.restore*` |
| 先抢占状态再执行副作用 | 落败方也做了副作用 | `payOrder` / `handleWechatPayNotify` 的顺序约定 |
| 支付对账 + 补偿落账 | 支付这一侧跨系统边界的不一致 | `OrderInfoService.reconcilePendingPayments` + `PaymentReconcileJob` |
| 补偿规则数据驱动 | 漂移补偿规则写死在代码里 | `process_reconcile_rule` + `ProcessReconcileEngine`（§3.6） |
| 自愈待办（实时通道） | 父过程聚合依赖调用方自觉、检测窗口过长 | `process_pending_task` + `ProcessPendingTaskService`（§3.7） |
| 跨表不变量体检 | 跨表约束只在实验里被验证过一次 | `ProcessInvariant` × 6 + `ProcessInvariantJob`（§3.8） |

## 五、兜底层

> 可靠系统不能假设所有执行机会都会正常发生。

正常路径（人工 / API / 回调）之外，必须存在兜底路径：**定时扫描 → 发现异常状态 → 执行恢复**。

| 任务 | 周期 | 通道 | 兜底/恢复内容 | 开关 |
| --- | --- | --- | --- | --- |
| `OrderTimeoutCancelJob` | 5 分钟 | 兜底 | 待支付超时自动取消；取消前先查单对账，已扣款则转补偿落账而非取消 | `order.pay.timeout.minutes` |
| `PaymentReconcileJob` | 5 分钟 | 兜底 | 在途待支付流水主动查单，回调丢失时补偿落账 | `order.pay.reconcile.enabled` |
| `ProcessPendingTaskJob` | **5 秒** | **实时** | 消费自愈待办，按父过程最新状态立即探测并补偿（失败退避，超 5 次放弃） | `process.pending.enabled` |
| `OrderProcessReconcileJob` | 10 分钟 | 兜底 | 按补偿规则表批量探测并修复父子状态漂移（实时通道的最后防线） | `order.process.reconcile.enabled` |
| `ProcessInvariantJob` | 30 分钟 | 兜底 | 跨表不变量体检：检出未闭环项、自动修复可逆项、复检闭环 | `process.invariant.scan.enabled` |
| `DeliveryAutoSignJob` | 每天 00:30 | 兜底 | 超时未签收自动签收（复用人工签收流程：CAS + 营养摄入 + 聚合完成） | — |

所有定时任务可用 `app.scheduler.enabled=false` 整体关闭（实验与测试环境使用）。

**通道分层的口径**（这是本轮最需要讲清的设计）：

| | 实时通道 | 兜底通道 |
| --- | --- | --- |
| 触发 | 子过程状态变更（事件驱动，同事务入队） | 周期扫描（拉模式） |
| 检测窗口 | ≈ 轮询间隔 5 秒 + 修复耗时（实验八实测约 5.0 秒） | ≤ 调度周期 10 分钟 |
| 失败处理 | 指数退避重试，超限放弃并告警 | 下一轮继续，天然幂等 |
| 职责 | **收敛速度** | **最终一致（保证）** |

两者缺一不可：只有实时通道，自愈失败就没人管；只有兜底通道，不可检测窗口太长（实验八量化对比）。

## 七、代码落点映射

| 抽象层 | 包/位置 | 关键类 |
| --- | --- | --- |
| 过程层 · 迁移 | `com.milk.order.process` | `ProcessTransitionExecutor`、`TransitionSpec`、`ProcessTransitionLog` |
| 过程层 · 补偿 | `com.milk.order.process.reconcile` | `ProcessReconcileEngine`、`ProcessReconcileCoordinator`、`ProcessReconcileRule`、`ParentProcessProbe`、`ParentProcessAggregator` |
| 过程层 · 实时通道 | `com.milk.order.process.pending` | `ProcessPendingTaskService`（+`ProcessPendingTask`） |
| 过程层 · 体检 | `com.milk.order.process.invariant` | `ProcessInvariant`、`ProcessInvariantScanner`、`InvariantScanReport` |
| 过程层 · 调度 | `com.milk.order.process.job` | `ProcessPendingTaskJob`（实时）、`ProcessInvariantJob`（体检） |
| 过程层 · 数据访问 | `com.milk.order.process.mapper` | 4 张过程层表的 Mapper |
| 可靠性层 | `com.milk.order.reliability` | `IdempotencyGuard` |
| 兜底层 | `com.milk.order.module.*.job`、`process.job` | 6 个定时任务（见第五节） |
| 业务层 | `com.milk.order.module.*` | order / delivery / product / nutrition / stats ... |
| 业务侧的父过程实现 | `module.order.process`、`module.*.invariant` | `OrderProcessProbe`、`OrderProcessAggregator`、6 个不变量检查项 |

依赖方向：

```text
业务模块（module.*） ──→ 过程层（process） ──→ { 状态规则服务, 过程层 Mapper }
业务模块（module.*） ──→ 可靠性层（reliability）
业务模块实现过程层接口：ParentProcessProbe / ParentProcessAggregator / ProcessInvariant
兜底层（module.*.job、process.job） ──→ 业务模块的 Service + 过程层协调器
```

**为什么探测器与聚合器由业务侧实现**：过程层因此不认识 `order_info`、`delivery_task` 任何一张表，
「父过程」对过程层只是一个接口。新增一类父过程（如续订计划）只需新增一个探测器 + 一个聚合器，
过程层零改动。

过程层与可靠性层**不反向依赖任何业务 Service**，因此可被订单、配送等模块共同复用。

## 八、不变量清单（改动时必须保持）

1. **状态只能经统一出口迁移**：`status` 字段的变更必须经 `ProcessTransitionExecutor`，
   且必须是「以原状态为条件」的条件更新；禁止读状态后无条件下全量更新。
2. **父子状态只由聚合决定**：父订单状态不得由某个子任务直接改写，必须经聚合出口
   （`completeOrderIfAllTasksDone` / `markDeliveringIfPaid`）。
3. **先抢占状态、再执行副作用**：同一业务动作涉及状态迁移与副作用（扣资源、写流水、展开任务）时，
   必须先做状态抢占，落败方立即中止；否则会出现重复副作用并互撞业务唯一键。
4. **资源变更必须留台账**：配额/资源扣减必须写台账并记录到具体池子，回补必须按台账回到原池子。
5. **幂等由数据库约束保证**：需要「同一业务键只存在一行」的记录必须建唯一约束，
   应用层只负责把唯一键冲突翻译为「已存在」。
6. **扣减必须行锁读**：涉及「读剩余 → 写已售」的路径必须先 `SELECT ... FOR UPDATE`，
   禁止先做一致性快照读再更新同一行（MariaDB 会直接拒绝，MySQL 会静默改读最新版本）。
7. **台账「尽力而为」**：迁移台账写入失败不得影响业务结果。
8. **补偿不得绕过闸门与出口**：补偿动作只能经 `ProcessTransitionExecutor` 落地，
   不得自己拼 SQL 改状态；因此补偿同样受 `state_transition_rule` 约束（实验六验证）。
9. **探测只读**：`ProcessReconcileEngine` 与 `ProcessInvariant.detect` 必须是只读的，
   可以被随时调用而不产生副作用。探测与执行分离是「可随时体检、可预览」的前提。
10. **自愈待办必须与子过程状态变更同事务入队**：否则待办会成为新的不一致来源；
    去重键为 `(scene, entity_id, trigger_action, status)`，且 `status` 必须参与唯一键
    （否则逻辑删除的已处理行会阻塞同一业务键的新待办）。
11. **修复必须经业务出口**：不变量修复只能调用业务侧的既有出口（迁移出口、配额回算、任务展开），
    不得直接改状态字段；涉及资金的不变量必须保持 `ALERT_ONLY`，不得自动改。
12. **规则覆盖面靠契约测试守住**：白名单语义下漏配一行等于该迁移**静默被禁止**，
    因此 `StateMachineContractTest` 矩阵 A 断言全部可达来源状态都有规则行；新增迁移必须同步补种子。

## 九、与实验的对应

| 抽象能力 | 验证实验 |
| --- | --- |
| 资源一致性与行锁 | 实验一（并发扣减，含无保护对照） |
| 幂等落账与先抢占再动作 | 实验二（重复支付回调） |
| 过程展开的幂等 | 实验三（并发重复生成任务） |
| 父子聚合与异常恢复 | 实验四（父状态漂移对账补偿） |
| 统一出口与迁移留痕 | 实验五（迁移台账完整性） |
| 补偿规则数据驱动 + 迁移闸门 | 实验六（规则引擎：停用规则即不补偿、闸门禁止即不落地） |
| 跨表不变量体检与处置分级 | 实验七（7 类不变量：注入 → 检出 / 自动修复 / 仅告警 / 复检闭环；含终态父过程残余子任务、终态订单网格缺口的等级细分） |
| 修复顺序依赖与拓扑执行 | 契约矩阵 D（执行顺序满足声明依赖、关键序对成立、非字典序巧合）；实验七对照 A 的行为验证 |
| 双通道自愈与失败退避放弃 | 实验八（实时通道 vs 兜底通道、待办去重、超限放弃） |
| 契约不回归 | `StateMachineContractTest`（规则覆盖矩阵、安全关键禁止、台账可回放） |

实验还反向暴露了 6 个真实缺陷（弱幂等、规则缓存非原子刷新、快照读与加锁读混用、
副作用先于状态抢占、联动路径绕过统一出口导致台账空洞、自调用导致事务边界失效），
修复与回归守卫详见 `../实验/实验设计与结果.md` 第 7 节。

另有一项**由实验七主动发现、并已按方案一加固**的问题（诚实记录整条链路）：
同时注入多条不相关的违规时，各自修复正确，但**修复动作之间缺少依赖与顺序**，
产生了新的、当时未被任何不变量覆盖的组合异常——「任务网格被补齐后，已完成的订单重新出现了待配送任务」。
处理分两步：先加**组合状态守卫** `INV_PARENT_TERMINAL_CHILD_PENDING` 让异常一轮内收敛；
再把根因去掉——`ProcessInvariant.dependsOn()` 声明依赖并**按拓扑序**执行（补网格 → 判父聚合 → 判组合），
同时让 `INV_ORDER_TASK` 对终态订单**只告警、不补造历史**。
于是组合异常**根本不产生**（实测对照 A：订单未被误判为已完成、组合守卫零触发），
守卫退化为"最后防线"。仍需人工逐对声明依赖这一点，以及更远的"由约束集合求解一致状态"，
见 `../论文/后续扩展方案.md` §2.5。
