## 1. 事实基线（现状）

| 项 | 现状 | 依据 |
|---|---|---|
| 接口 | `GET /api/delivery/task/pending-quantity`（返回整数）；`GET /api/delivery/task/parent-home`（聚合：剩余 + 下次配送日 + 近期拒收） | `DeliveryController` |
| 口径 | 绑定学生名下 `delivery_task.status ∈ {1 待配送, 2 配送中}` 的 `quantity` 合计 | `DeliveryTaskServiceImpl.pendingQuantityForCurrentStudent` |
| 实现 | **库内 `SUM(quantity)` 下沉**（走 `idx_student_status`），只回传一个数 | `DeliveryTaskMapper.sumPendingQuantityByStudent` |
| 数据范围 | 每次请求按 `username` **查库**取 `user.studentId`（JWT 只带 username，不带 studentId） | `DataScopeResolver` |
| 网关 | 仅 `PARENT` 可访问 | `SecurityConfig` |
| 任务产生 | 支付事务内按「配送日 × 品种」**逐条** insert，业务唯一键 `uk_order_product_date` 幂等 | `DeliveryTaskServiceImpl` |
| 前端 | 小程序首页独立加载，失败只记日志、卡片不渲染 | `miniprogram/pages/index/index.js` |
| 兜底调度 | 实时自愈待办 5s；父子对账 10min；不变量体检 30min；自动签收每日 00:30 | `process/job/*`、`module/*/job/*` |

### 1.1 两处与直觉不符，先纠正

1. **「JWT 不刷新 Token，家长解绑孩子后仍能查到孩子 A 的数据」——不成立。**
   JWT 里没有 `studentId`，数据范围每次请求都从库里读 `sys_user.student_id`。解绑/换绑后**下一次请求立即生效**。
   真正会残留旧数据的是**前端本地缓存**（见 §3.2），不是鉴权。

2. **「系统数据每日核对」表述不准确。**
   实际周期是：不变量体检 **每 30 分钟**、父子对账每 10 分钟、自动签收每日 00:30。没有"每日核对"这个周期。
   文案若要写核对频率，应写"系统定期核对"或直接不写频率。

## 4. 不要改（明确保留）

| # | 项 | 理由 |
|---|---|---|
| 4.1 | **任务展开从"逐条 insert"改成批量 insert** | 逐条 insert 才能用唯一键逐条仲裁幂等；改批量要重做幂等逻辑、更难。当前并发表现正常，容量也够。**仅记录，不改** |
| 4.2 | （续 4.1）权衡记录 | 逐条：实现简单、幂等天然、事务稍长；批量：事务更短，但要重新设计"批量插入中哪几条已存在"的幂等，且丢失"逐条跳过"的简洁性。结论：**保留逐条**，到"单学期百万行 + 高频全表统计"再评估 |
| 4.3 | 一个家长多个孩子的"切换孩子" | 属新功能（当前 `sys_user.student_id` 是单值），需改账号模型、接口契约与小程序 UI。**移入 `../TODO.md` A1** |
| 4.4 | ~~放假/暂停期间的处置~~ | **已解决（2026-09-20）**：不新增"暂停"状态，用配送日平移解决，见 `../变更记录/2026-09-20-配送日平移与拒收补送.md` |

## 5. 必须保持不能改（不变量）

1. **口径只读、不得有写副作用**：本接口只读 `delivery_task`，绝不允许为了"把数字补整齐"去改任务状态或补造历史。
2. **数据范围只能来自服务端解析**：`studentId` 必须经 `DataScopeResolver` 从库里的当前用户记录解析，
   不得改为信任前端传参、也不得改为从 JWT 里取。
3. **拒收、取消、退订必须让任务离开 `{1,2}`**：
   - 拒收：任务 `配送中(2) → 已取消(4)`，因此拒收**自然从"剩余"里减一**；
   - 退订：同事务作废未完成任务；
   - 这三条是"剩余数会自动变化"的**唯一依据**，不能被改成"把拒收也计入剩余"。
   （若业务要求"拒收后补送"，则**新增补偿**，而不是改本接口口径——补送已实现，见变更记录）
4. **接口失败不得导致首页白屏，也不得显示会误导的 0**：空态与异常态必须可区分。
5. **计数不得以实例内存状态为唯一真相**：若将来引入缓存，缓存只能是可回退的加速层
   （TTL 内允许不一致、到期/丢失必须回源），并须在 `可靠性设计.md` 记录为显式例外。
6. **前端不做强一致承诺**：家长看到的是"有延迟的真相"（实时待办 5s / 对账 10min / 体检 30min 收敛）。
   文案与交互不得承诺"实时精确"。
