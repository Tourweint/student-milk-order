# 可靠性设计

> 本文说明「业务过程可靠执行」用到的具体机制：每个机制解决什么问题、在代码哪里、判定口径是什么、
> 以及改动时必须守住的不变量。
>
> 抽象与层次划分见 `业务过程与可靠执行模型.md`；验证数据见 `../实验/实验设计与结果.md`。

## 一、机制总览

| 机制 | 解决的问题 | 实现位置 |
| --- | --- | --- |
| 业务唯一键 + 幂等守卫 | 同一个动作执行多次 | `uk_order_product_date`、`uk_order_product_pool`、`uk_delivery_record`、`IdempotencyGuard` |
| CAS 条件更新 | 两个执行者同时改同一状态 | `ProcessTransitionExecutor` 的 `casUpdate` |
| 悲观行锁读 | 读-改-写之间被并发插入 | `DailyQuotaMapper.selectForUpdate` |
| 资源台账 + 精确回补 | 资源从哪个池子扣、回到哪里 | `daily_quota_usage`、`DailyQuotaService.restore/restoreForOrderProductDate` |
| 先抢占状态、再执行副作用 | 落败方重复执行副作用 | `payOrder`、`handleWechatPayNotify` |
| 状态迁移留痕 | 过程不可观测 / 无法回溯 | `process_transition_log`、`ProcessTransitionExecutor` |
| 支付对账 + 补偿落账 | 支付侧跨系统边界不一致 | `reconcilePendingPayments` |
| **补偿规则表 + 补偿协调器** | 补偿规则写死在代码里 | `process_reconcile_rule`、`ProcessReconcileEngine`、`ProcessReconcileCoordinator`（§7.2） |
| **自愈待办（实时通道）** | 父过程聚合靠调用方自觉、检测窗口过长 | `process_pending_task`、`ProcessPendingTaskService`（§7.3） |
| **跨表不变量体检** | 跨表约束只在实验里被验证过一次 | `ProcessInvariant` × 6、`ProcessInvariantScanner`（§7.4） |
| 定时兜底 / 实时通道 | 执行机会根本没发生 | 6 个 `*Job`（5 个兜底 + 1 个实时消费） |

## 二、幂等：把并发仲裁交给数据库

### 2.1 为什么不能用「先查再写」

应用层幂等的常见写法是「先 `selectCount` 判断是否已存在，不存在再 `insert`」。该写法**只在单线程下成立**：
并发下多个执行者会同时查不到，再同时插入，于是产生重复数据。实验三即复现了这一点
（理论 6 条配送任务，16 线程并发展开）。

### 2.2 正确写法

1. 给业务键建**唯一约束**，由数据库承担并发仲裁；
2. 应用层只负责把唯一键冲突翻译成「已存在」并幂等跳过。

代码落点 `com.milk.order.reliability.IdempotencyGuard`：

```java
/** 执行一次「写入并忽略重复」的操作；返回 true=插入成功，false=唯一键冲突（判定为已存在并跳过） */
public boolean insertIgnoringDuplicate(Runnable insert)
```

已有业务唯一键：

| 表 | 唯一键 | 语义 |
| --- | --- | --- |
| `delivery_task` | `uk_order_product_date (order_id, product_id, delivery_date)` | 同一订单同一奶品同一配送日只允许一条任务 |
| `daily_quota_usage` | `uk_order_product_pool (order_id, product_id, quota_date)` | 同一订单同一品种同一配额池只允许扣减一行 |
| `nutrition_intake` | `uk_delivery_record (delivery_record_id)` | 一个签收记录最多生成一条摄入记录（正常签收与体检补写两条路径都由数据库仲裁） |
| `process_pending_task` | `uk_pending (scene, entity_id, trigger_action, status)` | 同一主体同一触发动作只保留一条待处理自愈待办 |

> 注意：MySQL/MariaDB 下唯一键冲突只回滚该条语句，事务可继续提交其余写入，因此
> 「冲突即跳过」在同一事务内是安全的。

### 2.3 幂等还需要的第二层：先抢占状态

唯一键能防「重复插入」，但防不住「重复副作用」。
`handleWechatPayNotify` / `payOrder` 里的顺序是刻意的：

```text
先 CAS 抢占状态（待支付→已支付）  ← 只有一个执行者能过
        ↓
再做副作用：扣配额 → 写流水 → 展开任务   ← 只执行一次
```

若反过来「先做副作用、再 CAS」，落败方已经扣了配额、写了流水才失败，只能靠回滚收场，
并发下还会互相撞业务唯一键（实验二暴露的 D4）。

## 三、CAS 条件更新

**解决的问题**：「两个执行者同时试图改变同一状态」。

```sql
UPDATE order_info SET status = 2 WHERE id = ? AND status = 1
```

只有一方能更新成功（受影响行数 1），另一方得到 0 行，据此判定冲突。

**代码落点**：所有状态迁移经 `ProcessTransitionExecutor`，由调用方传入以原状态为条件的更新动作。
`require` 在冲突时抛业务异常并回滚；`attempt` 在冲突时返回 false 并跳过。

**为什么不用 `@Version` 乐观锁**：项目状态变更天然是「按状态机从一个合法状态推进到下一个」，
用「状态本身作为版本」比额外版本号更贴合语义，也避免为每个实体加冗余字段。

## 四、悲观行锁读

**解决的问题**：「读剩余 → 写已售」这类读-改-写之间，行被并发修改。

**代码落点**：`DailyQuotaMapper.selectForUpdate`

```sql
SELECT * FROM daily_quota WHERE quota_date = ? AND product_id = ? AND deleted = 0 FOR UPDATE
```

配额扣减的三遍结构（`DailyQuotaServiceImpl.deduct`）：

1. **加锁读**：一次性把保质期窗口内的池子（先过期先出）读进来，得到权威可扣量并形成扣减计划；
2. **充足校验**：全部品种都充足才继续，任一不足即整体抛异常 → 事务回滚，不会留下部分扣减；
3. **写回**：按计划更新，并以 `used_quota + n <= total_quota` 作为最后一道防御。

### 4.1 为什么必须用行锁读（重要）

同一事务内若**先对某行做一致性快照读、再对该行做加锁读或更新**，不同数据库行为不一致：

| 数据库 | 行为 |
| --- | --- |
| MySQL 8 | UPDATE 自动读到最新已提交版本，静默成功 |
| MariaDB（REPEATABLE READ） | 直接拒绝：`Record has changed since last read in table 'xxx'` |

这是实验一在并发扣减下暴露的真实缺陷（有保护版本只成功 25/200）。

## 五、事务隔离级别

**本项目的选择：统一使用 `READ_COMMITTED`**（`spring.datasource.hikari.transaction-isolation`）。

理由：

1. 本系统的并发安全**全部由「条件更新 / 行锁 / 唯一键」显式保证**，不依赖 REPEATABLE READ 的
   可重复读语义；
2. REPEATABLE READ 下 MariaDB 与 MySQL 对「快照建立后被并发修改的行」行为不一致（见 4.1），
   会造成「同一份代码、两种数据库、两种结果」；
3. 显式统一后，行为可预期，也消除了「读快照、写最新」的语义撕裂。

> 若将来确需 REPEATABLE READ 的语义（例如报表需要事务内稳定快照），应把**报表类只读事务**
> 单独标注隔离级别，而不是把写路径改回 REPEATABLE READ。

## 六、资源台账与精确回补

**台账不是「库存表」，而是「资源变动的可追踪记录」。**

| 能力 | 实现 |
| --- | --- |
| 扣减按池子记账（含保质期结转池，先过期先出） | `deduct` 写 `daily_quota_usage`（订单×品种×池子日期×盒数） |
| 退订回补：精确回到原池子 | `restore(orderId)`：按台账逐行回补后删除台账行 |
| 缺货单期取消：只回补该订单该品种 | `restoreForOrderProductDate(orderId, productId, date)` |
| 防御：不允许把 `used_quota` 减成负数 | 回补使用条件更新 `used_quota >= n` |

回补到**原池子**而不是简单 `stock++`，是为了避免「从 A 池子扣、补到 B 池子」造成的账实不符。

**台账行的删除语义（重要约束）**：回补时执行的「删除台账行」实际是**逻辑删除**（实体带 `@TableLogic`），
因此业务查询不可见、重复回补自然跳过（幂等），但**物理行仍然存在**，并继续占用业务唯一键
`uk_order_product_pool`。这意味着：*同一订单同一品种同一池子若需要二次扣减，会直接撞唯一键*。
当前所有扣减都只发生一次（支付成功时），不会触发；若将来引入「退款后重新扣减」「配额重算」等场景，
必须先物理清理旧台账行或调整键策略。该约束由实验五（见 `../实验/实验设计与结果.md` 第 7.1 节）发现。

**同一个坑的第二次出现（已规避）**：自愈待办表 `process_pending_task` 的去重键里**必须**包含 `status`——
否则「已处理」行被逻辑删除后，其物理行仍占用唯一键，会让同一业务键的新待办**静默入队失败**。
把 `status` 放进唯一键后，待处理(0)/已处理(1)/已放弃(2) 各自独立成键，逻辑删除已处理行不再阻塞新待办。
设计时先识别出该陷阱，因此未在运行中暴露——这类「上一轮踩过的坑在新表上的复现」是必须主动检查的。

## 七、对账、补偿与持续验证

**核心思想：从「绝对原子性」转向「可检测、可恢复的最终一致性」。**

```text
发现不一致 → 对账 → 决策 → 补偿 → 恢复合法状态 → 复检
```

### 7.1 支付侧对账

支付系统成功、而订单系统没更新，就会出现跨边界状态不一致（支付 = 成功，订单 = 待支付）。
系统不追求「所有事情必须同时成功」，而是主动查单补偿：

| 对账类型 | 检测「什么不一致」 | 补偿动作 | 落点 |
| --- | --- | --- | --- |
| 支付对账 | 存在在途待支付流水，但微信侧已扣款 | 走回调同一路径补偿落账（扣配额 + 写流水 + 改状态 + 展开任务） | `OrderInfoService.reconcilePendingPayments` |
| 超时对账 | 待支付超时 | 取消前先查单：已扣款则转补偿落账，**绝不取消已付款订单** | `OrderInfoService.cancelTimeoutOrder` |

### 7.2 过程侧补偿：探测 / 决策 / 执行三层

过程侧的不一致形态是「父过程状态与子过程集合不匹配」。这类补偿**曾经硬编码在订单服务里**
（两个 `if`），现已下沉为规则驱动：

| 层 | 职责 | 落点 |
| --- | --- | --- |
| 探测 | 按规则表的 `parent_status` 取候选，逐条求值子过程条件，产出决策（**只读**） | `ProcessReconcileEngine`、`ParentProcessProbe` |
| 决策 | 「父状态 + 子条件 → 补偿动作 + 目标状态」，可在线启停 | `process_reconcile_rule` |
| 执行 | 复用统一迁移出口做条件更新并留痕 | `ParentProcessAggregator` → `ProcessTransitionExecutor` |

补偿的幂等性来自「复用统一迁移出口 + 聚合出口」：补偿本身也是一次带条件的状态迁移，
状态已合法时不会产生新的迁移（实验四验证：重复对账后已生效迁移条数不变）。

**两条必须守住的边界**：

1. **补偿也是迁移，也要过闸门**。启用一条新补偿规则时，必须确认 `state_transition_rule`
   放开了对应迁移，否则统一出口会以「规则禁止」拒绝补偿（实验六实测：命中规则但补偿生效数为 0）。
   种子里的第三条示例规则（全取消补偿）默认停用，并在描述里写明了这一依赖。
2. **条件不配置化**。规则表可配的是「用哪个条件、补偿到什么状态」；条件本身的语义
   （什么算「全部终态」）由枚举 + 业务侧实现，因为允许任意表达式会让规则表无法审阅、无法测试。

### 7.3 双通道：实时自愈 + 定时兜底

| | 实时通道 | 兜底通道 |
| --- | --- | --- |
| 触发 | 子过程状态变更（同事务入队 `process_pending_task`） | 周期扫描（`OrderProcessReconcileJob`） |
| 检测窗口 | ≈ 轮询间隔 5 秒 + 修复耗时（实测约 5.0 秒） | ≤ 调度周期 10 分钟 |
| 失败处理 | 指数退避重试，超 5 次置「已放弃」并告警 | 下一轮继续（幂等） |
| 职责 | 收敛速度 | 最终一致（保证） |

为什么要双通道（这是设计论证，不是功能堆砌）：

- **只有兜底通道**：不可检测窗口是分钟级，且全表扫随数据量增长而变慢；
- **只有实时通道**：自愈本身会失败（实测：重试 5 次后放弃），失败后没人管。

另外，待办把「父过程需要重新聚合」从**隐式约定**（调用方记得调用聚合出口）变成**显式数据**：
即使某条路径漏掉同步聚合、或同步聚合被规则表临时挡住，待办仍在，秒级消费者会按最新状态补上。
入队必须在子过程状态变更的**同一事务内**，否则待办本身会成为新的不一致来源。

### 7.4 跨表不变量体检

这是本轮最核心的主张：**不变量只在被验证时才成立**。

| 编码 | 不变量 | 处置 |
| --- | --- | --- |
| `INV_QUOTA_LEDGER` | `daily_quota.used_quota` = 台账合计（`deleted = 0`） | 自动修复（以台账为准重算） |
| `INV_TASK_RECORD` | 任务已完成 ⇒ 签收记录已签收 | 自动修复（经统一出口补签收） |
| `INV_SIGN_INTAKE` | 已签收 ⇒ 存在营养摄入记录 | 自动修复（复用签收时的生成逻辑） |
| `INV_ORDER_TASK` | 任务覆盖「品种 × 配送日」全网格 | 自动修复（经任务展开出口补生成） |
| `INV_ORDER_AGGREGATION` | 父订单状态与子任务集合一致 | 自动修复（复用 §7.2 的探测与聚合出口） |
| `INV_PAYMENT_CONSISTENCY` | 订单状态与支付流水互证 | **仅告警**（涉资金，人工核处） |

**分级的判断标准**：能由既有台账唯一推导出正确值、且重算幂等的才允许自动修复；涉及资金流向
或需要业务判断的一律只告警（实验七对照 B 验证：资金不一致被检出但数据一个字节都没动）。

**假阳性控制**：`INV_PAYMENT_CONSISTENCY` 的「流水成功但订单未落账」方向只检出自成功时间
超过 5 分钟的记录，避免把支付对账任务的正常工作窗口误报成不一致——**判定口径必须考虑
「系统本来就在处理中」这件事**。

**记录语义**：每个（不变量 × 主体）保留一行当前状态，重复漂移用 `reopen_count` 累加；
一轮体检对上轮未闭环、本轮未再检出的记录做**复检闭环**（问题真的消失了，而不是被忽略）。

## 八、定时任务与调度

正常路径是「人工 / API / 回调」；异常路径是「事件驱动自愈（实时）+ 定时扫描（兜底）」。

| 任务 | 周期 | 通道 | 内容 | 开关 |
| --- | --- | --- | --- | --- |
| `OrderTimeoutCancelJob` | 5 分钟 | 兜底 | 待支付超时自动取消（先查单对账，防误杀已付款） | `order.pay.timeout.minutes`（默认 15） |
| `PaymentReconcileJob` | 5 分钟 | 兜底 | 在途待支付流水的回调丢失补偿 | `order.pay.reconcile.enabled` |
| `ProcessPendingTaskJob` | **5 秒** | **实时** | 消费自愈待办，立即探测并补偿（失败退避，超 5 次放弃） | `process.pending.enabled` |
| `OrderProcessReconcileJob` | 10 分钟 | 兜底 | 按补偿规则表批量修复父子状态漂移（实时通道的最后防线） | `order.process.reconcile.enabled` |
| `ProcessInvariantJob` | 30 分钟 | 兜底 | 跨表不变量体检 + 自动修复可逆项 | `process.invariant.scan.enabled` |
| `DeliveryAutoSignJob` | 每天 00:30 | 兜底 | 超时未签收自动签收 | — |

设计口径：

- 兜底任务一律**幂等可重复执行**：本轮处理不了就留给下一轮，不追求一次做完；
- 单条失败不影响其余（逐条 try/catch），并有单批处理上限防止历史脏数据拖死任务；
- 实时通道的失败**必须可见**：退避重试 + 超限放弃 + 告警，绝不静默吞掉；
- 全部任务可用 `app.scheduler.enabled=false` 关闭（实验/测试环境使用）。

## 九、改动时的检查清单

涉及状态、资源、支付、配送的改动，提交前逐条确认：

1. 状态迁移是否经 `ProcessTransitionExecutor`，且条件更新以原状态为准？
2. 新增状态/动作是否补了 `state_transition_rule` 规则种子？（白名单语义，缺规则=全禁）
3. 是否需要「同一业务键只存在一行」？需要就建唯一约束，不要用「先查后插」。
4. 涉及「读剩余 → 写已售」的路径，是否用了 `SELECT ... FOR UPDATE`？
5. 状态迁移与副作用的顺序是否为「先抢占状态、再执行副作用」？
6. 资源扣减是否写了台账，回补是否回到原池子？
7. 新增的异步/异常路径，是否考虑了「执行机会没发生」时的兜底与补偿？
8. 兜底任务是否幂等？是否有单批上限？是否有开关？
9. **是否新增了绕过统一出口的旁路**？逐条核对：所有 `set(…::getStatus)` / `set(…::getSignStatus)`
   类的写入是否都经 `ProcessTransitionExecutor`——旁路不会报错，
   但会让「每一次状态迁移都留痕」这一不变量悄悄失效（缺陷 D5 即此类问题，守卫为实验五）。
10. **新增/调整补偿规则时**：`state_transition_rule` 是否放开了该补偿要执行的迁移？（否则补偿会被闸门拒绝）
    规则默认值是否安全（新规则默认停用、行为等价的老规则才默认启用）？
11. **新增子过程状态变更路径时**：是否在同一事务内 `enqueue` 了父过程自愈待办？
    触发动作是否唯一（决定去重粒度）？
