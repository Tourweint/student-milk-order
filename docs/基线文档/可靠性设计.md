# 可靠性设计

> 本文说明「业务过程可靠执行」用到的具体机制：每个机制解决什么问题、在代码哪里、判定口径是什么、
> 以及改动时必须守住的不变量。
>
> 抽象与层次划分见 `业务过程与可靠执行模型.md`；验证数据见 `../实验/实验设计与结果.md`。

## 一、机制总览

| 机制 | 解决的问题 | 实现位置 |
| --- | --- | --- |
| 业务唯一键 + 幂等守卫 | 同一个动作执行多次 | `uk_order_product_date`、`uk_order_product_pool`、`uk_delivery_record`、`IdempotencyGuard` |
| CAS 条件更新 | 两个执行者同时改同一状态 | `ProcessTransitionExecutor` 的 `casUpdate` |
| 悲观行锁读 | 读-改-写之间被并发插入 | `DailyQuotaMapper.selectForUpdate` |
| 资源台账 + 精确回补 | 资源从哪个池子扣、回到哪里 | `daily_quota_usage`、`DailyQuotaService.restore/restoreForOrderProductDate` |
| 先抢占状态、再执行副作用 | 落败方重复执行副作用 | `payOrder`、`handleWechatPayNotify` |
| 状态迁移留痕 | 过程不可观测 / 无法回溯 | `process_transition_log`、`ProcessTransitionExecutor` |
| 支付对账 + 补偿落账 | 支付侧跨系统边界不一致 | `reconcilePendingPayments` |
| **补偿规则表 + 补偿协调器** | 补偿规则写死在代码里 | `process_reconcile_rule`、`ProcessReconcileEngine`、`ProcessReconcileCoordinator`（§7.2） |
| **自愈待办（实时通道）** | 父过程聚合靠调用方自觉、检测窗口过长 | `process_pending_task`、`ProcessPendingTaskService`（§7.3） |
| **跨表不变量体检** | 跨表约束只在实验里被验证过一次 | `ProcessInvariant` × 7、`ProcessInvariantScanner`（§7.4） |
| 定时兜底 / 实时通道 | 执行机会根本没发生 | 6 个 `*Job`（5 个兜底 + 1 个实时消费） |

## 二、幂等：把并发仲裁交给数据库

### 2.1 为什么不能用「先查再写」

应用层幂等的常见写法是「先 `selectCount` 判断是否已存在，不存在再 `insert`」。该写法**只在单线程下成立**：
并发下多个执行者会同时查不到，再同时插入，于是产生重复数据。实验三即复现了这一点
（理论 6 条配送任务，16 线程并发展开）。

### 2.2 正确写法

1. 给业务键建**唯一约束**，由数据库承担并发仲裁；
2. 应用层只负责把唯一键冲突翻译成「已存在」并幂等跳过。

代码落点 `com.milk.order.reliability.IdempotencyGuard`：

```java
/** 执行一次「写入并忽略重复」的操作；返回 true=插入成功，false=唯一键冲突（判定为已存在并跳过） */
public boolean insertIgnoringDuplicate(Runnable insert)
```

已有业务唯一键：

| 表 | 唯一键 | 语义 |
| --- | --- | --- |
| `delivery_task` | `uk_order_product_date (order_id, product_id, delivery_date)` | 同一订单同一奶品同一配送日只允许一条任务 |
| `daily_quota_usage` | `uk_order_product_pool (order_id, product_id, quota_date)` | 同一订单同一品种同一配额池只允许扣减一行 |
| `nutrition_intake` | `uk_delivery_record (delivery_record_id)` | 一个签收记录最多生成一条摄入记录（正常签收与体检补写两条路径都由数据库仲裁） |
| `process_pending_task` | `uk_pending (scene, entity_id, trigger_action, status)` | 同一主体同一触发动作只保留一条待处理自愈待办 |

> 注意：MySQL/MariaDB 下唯一键冲突只回滚该条语句，事务可继续提交其余写入，因此
> 「冲突即跳过」在同一事务内是安全的。

### 2.3 幂等还需要的第二层：先抢占状态

唯一键能防「重复插入」，但防不住「重复副作用」。
`handleWechatPayNotify` / `payOrder` 里的顺序是刻意的：

```text
先 CAS 抢占状态（待支付→已支付）  ← 只有一个执行者能过
        ↓
再做副作用：扣配额 → 写流水 → 展开任务   ← 只执行一次
```

若反过来「先做副作用、再 CAS」，落败方已经扣了配额、写了流水才失败，只能靠回滚收场，
并发下还会互相撞业务唯一键（实验二暴露的 D4）。

## 三、CAS 条件更新

**解决的问题**：「两个执行者同时试图改变同一状态」。

```sql
UPDATE order_info SET status = 2 WHERE id = ? AND status = 1
```

只有一方能更新成功（受影响行数 1），另一方得到 0 行，据此判定冲突。

**代码落点**：所有状态迁移经 `ProcessTransitionExecutor`，由调用方传入以原状态为条件的更新动作。
`require` 在冲突时抛业务异常并回滚；`attempt` 在冲突时返回 false 并跳过。

**为什么不用 `@Version` 乐观锁**：项目状态变更天然是「按状态机从一个合法状态推进到下一个」，
用「状态本身作为版本」比额外版本号更贴合语义，也避免为每个实体加冗余字段。

## 四、悲观行锁读

**解决的问题**：「读剩余 → 写已售」这类读-改-写之间，行被并发修改。

**代码落点**：`DailyQuotaMapper.selectForUpdate`

```sql
SELECT * FROM daily_quota WHERE quota_date = ? AND product_id = ? AND deleted = 0 FOR UPDATE
```

配额扣减的三遍结构（`DailyQuotaServiceImpl.deduct`）：

1. **加锁读**：一次性把保质期窗口内的池子（先过期先出）读进来，得到权威可扣量并形成扣减计划；
2. **充足校验**：全部品种都充足才继续，任一不足即整体抛异常 → 事务回滚，不会留下部分扣减；
3. **写回**：按计划更新，并以 `used_quota + n <= total_quota` 作为最后一道防御。

### 4.1 为什么必须用行锁读（重要）

同一事务内若**先对某行做一致性快照读、再对该行做加锁读或更新**，不同数据库行为不一致：

| 数据库 | 行为 |
| --- | --- |
| MySQL 8 | UPDATE 自动读到最新已提交版本，静默成功 |
| MariaDB（REPEATABLE READ） | 直接拒绝：`Record has changed since last read in table 'xxx'` |

这是实验一在并发扣减下暴露的真实缺陷（有保护版本只成功 25/200）。

## 五、事务隔离级别

**本项目的选择：统一使用 `READ_COMMITTED`**（`spring.datasource.hikari.transaction-isolation`）。

理由：

1. 本系统的并发安全**全部由「条件更新 / 行锁 / 唯一键」显式保证**，不依赖 REPEATABLE READ 的
   可重复读语义；
2. REPEATABLE READ 下 MariaDB 与 MySQL 对「快照建立后被并发修改的行」行为不一致（见 4.1），
   会造成「同一份代码、两种数据库、两种结果」；
3. 显式统一后，行为可预期，也消除了「读快照、写最新」的语义撕裂。

> 若将来确需 REPEATABLE READ 的语义（例如报表需要事务内稳定快照），应把**报表类只读事务**
> 单独标注隔离级别，而不是把写路径改回 REPEATABLE READ。

## 六、资源台账与精确回补

**台账不是「库存表」，而是「资源变动的可追踪记录」。**

| 能力 | 实现 |
| --- | --- |
| 扣减按池子记账（含保质期结转池，先过期先出） | `deduct` 写 `daily_quota_usage`（订单×品种×池子日期×盒数） |
| 退订回补：精确回到原池子 | `restore(orderId)`：按台账逐行回补后删除台账行 |
| 缺货单期取消：只回补该订单该品种 | `restoreForOrderProductDate(orderId, productId, date)` |
| 防御：不允许把 `used_quota` 减成负数 | 回补使用条件更新 `used_quota >= n` |

回补到**原池子**而不是简单 `stock++`，是为了避免「从 A 池子扣、补到 B 池子」造成的账实不符。

**台账行的删除语义（重要约束）**：回补时执行的「删除台账行」实际是**逻辑删除**（实体带 `@TableLogic`），
因此业务查询不可见、重复回补自然跳过（幂等），但**物理行仍然存在**，并继续占用业务唯一键
`uk_order_product_pool`。这意味着：*同一订单同一品种同一池子若需要二次扣减，会直接撞唯一键*。
当前所有扣减都只发生一次（支付成功时），不会触发；若将来引入「退款后重新扣减」「配额重算」等场景，
必须先物理清理旧台账行或调整键策略。该约束由实验五（见 `../实验/实验设计与结果.md` 第 7.1 节）发现。

**同一个坑的第二次出现（已规避）**：自愈待办表 `process_pending_task` 的去重键里**必须**包含 `status`——
否则「已处理」行被逻辑删除后，其物理行仍占用唯一键，会让同一业务键的新待办**静默入队失败**。
把 `status` 放进唯一键后，待处理(0)/已处理(1)/已放弃(2) 各自独立成键，逻辑删除已处理行不再阻塞新待办。
设计时先识别出该陷阱，因此未在运行中暴露——这类「上一轮踩过的坑在新表上的复现」是必须主动检查的。

## 七、对账、补偿与持续验证

**核心思想：从「绝对原子性」转向「可检测、可恢复的最终一致性」。**

```text
发现不一致 → 对账 → 决策 → 补偿 → 恢复合法状态 → 复检
```

### 7.1 支付侧对账

支付系统成功、而订单系统没更新，就会出现跨边界状态不一致（支付 = 成功，订单 = 待支付）。
系统不追求「所有事情必须同时成功」，而是主动查单补偿：

| 对账类型 | 检测「什么不一致」 | 补偿动作 | 落点 |
| --- | --- | --- | --- |
| 支付对账 | 存在在途待支付流水，但微信侧已扣款 | 走回调同一路径补偿落账（扣配额 + 写流水 + 改状态 + 展开任务） | `OrderInfoService.reconcilePendingPayments` |
| 超时对账 | 待支付超时 | 取消前先查单：已扣款则转补偿落账，**绝不取消已付款订单** | `OrderInfoService.cancelTimeoutOrder` |

### 7.2 过程侧补偿：探测 / 决策 / 执行三层

过程侧的不一致形态是「父过程状态与子过程集合不匹配」。这类补偿**曾经硬编码在订单服务里**
（两个 `if`），现已下沉为规则驱动：

| 层 | 职责 | 落点 |
| --- | --- | --- |
| 探测 | 按规则表的 `parent_status` 取候选，逐条求值子过程条件，产出决策（**只读**） | `ProcessReconcileEngine`、`ParentProcessProbe` |
| 决策 | 「父状态 + 子条件 → 补偿动作 + 目标状态」，可在线启停 | `process_reconcile_rule` |
| 执行 | 复用统一迁移出口做条件更新并留痕 | `ParentProcessAggregator` → `ProcessTransitionExecutor` |

补偿的幂等性来自「复用统一迁移出口 + 聚合出口」：补偿本身也是一次带条件的状态迁移，
状态已合法时不会产生新的迁移（实验四验证：重复对账后已生效迁移条数不变）。

**两条必须守住的边界**：

1. **补偿也是迁移，也要过闸门**。启用一条新补偿规则时，必须确认 `state_transition_rule`
   放开了对应迁移，否则统一出口会以「规则禁止」拒绝补偿（实验六实测：命中规则但补偿生效数为 0）。
   种子里的第三条示例规则（全取消补偿）默认停用，并在描述里写明了这一依赖。
2. **条件不配置化**。规则表可配的是「用哪个条件、补偿到什么状态」；条件本身的语义
   （什么算「全部终态」）由枚举 + 业务侧实现，因为允许任意表达式会让规则表无法审阅、无法测试。

**覆盖盲区（实验十一的特征化测试发现，3.4 已补齐）**：规则表原本有
`(已支付, HAS_DISPATCHING_TASK → 配送中)` 与 `(配送中, ALL_TASKS_TERMINAL → 已完成)`，
但**缺 `(已支付, ALL_TASKS_TERMINAL → 已完成)`**——「订单已支付 + 子任务已全部签收」
（配送联动与聚合写入同时丢失）既不会被补偿、也不被现有不变量判为违规，静默停在已支付。

补齐（3.4）做了三件事，每件都体现"配了规则 ≠ 配对了规则"：

1. 新增规则「已支付全终态补偿」`(2, ALL_TASKS_TERMINAL → AUTO_COMPLETE, 4)`，默认启用；
2. **放开闸门 `ORDER/AUTO_COMPLETE/2`**（原为显式禁止"已支付订单未开始配送不自动完成"）。
   安全性论证：闸门看不见子过程，因此"不跳过未完成配送"这层约束**不由闸门保证**，
   而由聚合出口的定义保证——只有全部任务终态才会走到 AUTO_COMPLETE；
   管理端手动完成的 `COMPLETE/2` **仍保持禁止**（放开哪条闸门是独立的业务决定，最初曾误判为它）；
3. 聚合出口 `completeOrderIfAllTasksDone` 从"仅配送中"放开为"已支付/配送中"，
   CAS 以**实际父状态**为条件（同一出口服务正常路径与补偿路径，天然幂等留痕）。

这再次说明：**规则表的覆盖面必须被主动审视，而不是等出了问题才发现**——
这次是长稳实验的特征化用例把它暴露出来的。遗留语义边界：**子任务全部取消时也会被补为已完成**，
"全部取消 → 已退订"的区分依赖退款设计（`全取消补偿` 规则仍默认停用）。

### 7.3 双通道：实时自愈 + 定时兜底

| | 实时通道 | 兜底通道 |
| --- | --- | --- |
| 触发 | 子过程状态变更（同事务入队 `process_pending_task`） | 周期扫描（`OrderProcessReconcileJob`） |
| 检测窗口 | ≈ 轮询间隔 5 秒 + 修复耗时（实测约 5.0 秒） | ≤ 调度周期 10 分钟 |
| 失败处理 | 指数退避重试，超 5 次置「已放弃」并告警 | 下一轮继续（幂等） |
| 职责 | 收敛速度 | 最终一致（保证） |

为什么要双通道（这是设计论证，不是功能堆砌）：

- **只有兜底通道**：不可检测窗口是分钟级，且全表扫随数据量增长而变慢；
- **只有实时通道**：自愈本身会失败（实测：重试 5 次后放弃），失败后没人管。

另外，待办把「父过程需要重新聚合」从**隐式约定**（调用方记得调用聚合出口）变成**显式数据**：
即使某条路径漏掉同步聚合、或同步聚合被规则表临时挡住，待办仍在，秒级消费者会按最新状态补上。
入队必须在子过程状态变更的**同一事务内**，否则待办本身会成为新的不一致来源。

### 7.4 跨表不变量体检

这是本轮最核心的主张：**不变量只在被验证时才成立**。

| 编码 | 不变量 | 处置 |
| --- | --- | --- |
| `INV_QUOTA_LEDGER` | `daily_quota.used_quota` = 台账合计（`deleted = 0`） | 自动修复（以台账为准重算） |
| `INV_TASK_RECORD` | 任务已完成 ⇒ 签收记录已签收 | 自动修复（经统一出口补签收） |
| `INV_SIGN_INTAKE` | 已签收 ⇒ 存在营养摄入记录 | 自动修复（复用签收时的生成逻辑） |
| `INV_ORDER_TASK` | 任务覆盖「品种 × 配送日」全网格 | **按情况分级**：订单进行中（已支付/配送中）自动补生成；订单已终态**只告警、不补造历史**（补造反而会制造组合异常） |
| `INV_ORDER_AGGREGATION` | 父订单状态与子任务集合一致 | 自动修复（复用 §7.2 的探测与聚合出口） |
| `INV_PARENT_TERMINAL_CHILD_PENDING` | 父过程终态 ⇒ 不存在非终态子过程 | **按情况分级**：待配送自动作废（经业务取消出口）/ 配送中仅告警（奶已出库在途） |
| `INV_PAYMENT_CONSISTENCY` | 订单状态与支付流水互证 | **仅告警**（涉资金，人工核处） |

**分级的判断标准**：能由既有台账唯一推导出正确值、且重算幂等的才允许自动修复；涉及资金流向
或需要业务判断的一律只告警（实验七对照 B 验证：资金不一致被检出但数据一个字节都没动）。

**等级可以细到"每条违规"**：修复判定以 `InvariantViolation.severity` 为准，不变量声明的等级只是默认值
（未声明时回退到默认，回退方向是"不自动修"）。因此同一条约束下可以"有的情况自动修、有的只能告警"。
原则是：**探测可以比修复更激进，修复永远比探测更保守**。

**执行顺序由声明依赖决定**：`ProcessInvariant.dependsOn()` 声明「本项必须在哪些编码之后执行」，
体检器按**拓扑序**执行（同层按编码升序打破平局，因此确定可复现）；引用未注册编码或依赖成环时**直接失败**
（配置错误不能静默退化成任意顺序）。当前声明两条：

```text
INV_ORDER_TASK（补网格） → INV_ORDER_AGGREGATION（判父聚合） → INV_PARENT_TERMINAL_CHILD_PENDING（判组合）
```

为什么必须这样：父聚合的判定依据是"子任务是否全部终态"。若先判父、再补子，
**体检自己就会制造**「已完成订单 + 待配送任务」这种组合异常。顺序本身是设计的一部分，
因此 `resolvedExecutionOrder()` 把它暴露出来可测、可审阅（守卫矩阵 D）。
更强的形态是把不变量当约束系统求解（见后续扩展方案 §2.5 方案三）。

**假阳性控制**：`INV_PAYMENT_CONSISTENCY` 的「流水成功但订单未落账」方向只检出自成功时间
超过 5 分钟的记录，避免把支付对账任务的正常工作窗口误报成不一致——**判定口径必须考虑
「系统本来就在处理中」这件事**。

**记录语义**：每个（不变量 × 主体）保留一行当前状态，重复漂移用 `reopen_count` 累加；
一轮体检对上轮未闭环、本轮未再检出的记录做**复检闭环**（问题真的消失了，而不是被忽略）。

## 八、定时任务与调度

正常路径是「人工 / API / 回调」；异常路径是「事件驱动自愈（实时）+ 定时扫描（兜底）」。

| 任务 | 周期 | 通道 | 内容 | 开关 |
| --- | --- | --- | --- | --- |
| `OrderTimeoutCancelJob` | 5 分钟 | 兜底 | 待支付超时自动取消（先查单对账，防误杀已付款） | `order.pay.timeout.minutes`（默认 15） |
| `PaymentReconcileJob` | 5 分钟 | 兜底 | 在途待支付流水的回调丢失补偿 | `order.pay.reconcile.enabled` |
| `ProcessPendingTaskJob` | **5 秒** | **实时** | 消费自愈待办，立即探测并补偿（失败退避，超 5 次放弃） | `process.pending.enabled` |
| `OrderProcessReconcileJob` | 10 分钟 | 兜底 | 按补偿规则表批量修复父子状态漂移（实时通道的最后防线） | `order.process.reconcile.enabled` |
| `ProcessInvariantJob` | 30 分钟 | 兜底 | 跨表不变量体检 + 自动修复可逆项 | `process.invariant.scan.enabled` |
| `DeliveryAutoSignJob` | 每天 00:30 | 兜底 | 超时未签收自动签收 | — |

设计口径：

- 兜底任务一律**幂等可重复执行**：本轮处理不了就留给下一轮，不追求一次做完；
- 单条失败不影响其余（逐条 try/catch），并有单批处理上限防止历史脏数据拖死任务；
- 实时通道的失败**必须可见**：退避重试 + 超限放弃 + 告警，绝不静默吞掉；
- 全部任务可用 `app.scheduler.enabled=false` 关闭（实验/测试环境使用）。

## 九、改动时的检查清单

涉及状态、资源、支付、配送的改动，提交前逐条确认：

1. 状态迁移是否经 `ProcessTransitionExecutor`，且条件更新以原状态为准？
2. 新增状态/动作是否补了 `state_transition_rule` 规则种子？（白名单语义，缺规则=全禁）
3. 是否需要「同一业务键只存在一行」？需要就建唯一约束，不要用「先查后插」。
4. 涉及「读剩余 → 写已售」的路径，是否用了 `SELECT ... FOR UPDATE`？
5. 状态迁移与副作用的顺序是否为「先抢占状态、再执行副作用」？
6. 资源扣减是否写了台账，回补是否回到原池子？
7. 新增的异步/异常路径，是否考虑了「执行机会没发生」时的兜底与补偿？
8. 兜底任务是否幂等？是否有单批上限？是否有开关？
9. **是否新增了绕过统一出口的旁路**？逐条核对：所有 `set(…::getStatus)` / `set(…::getSignStatus)`
   类的写入是否都经 `ProcessTransitionExecutor`——旁路不会报错，
   但会让「每一次状态迁移都留痕」这一不变量悄悄失效（缺陷 D5 即此类问题，守卫为实验五）。
10. **新增/调整补偿规则时**：`state_transition_rule` 是否放开了该补偿要执行的迁移？（否则补偿会被闸门拒绝）
    规则默认值是否安全（新规则默认停用、行为等价的老规则才默认启用）？
11. **新增子过程状态变更路径时**：是否在同一事务内 `enqueue` 了父过程自愈待办？
    触发动作是否唯一（决定去重粒度）？
12. **新增跨表约束时**：是否登记为 `ProcessInvariant`？处置等级是 `AUTO_REPAIR` 还是 `ALERT_ONLY`
    （涉资金/需业务判断/终态历史的一律 `ALERT_ONLY`；同一约束内可按情况逐条覆写等级）？
    检测口径是否考虑了「系统本来就在处理中」这类中间态？
    修复是否与已有不变量冲突（会不会产生新的组合异常）？**会不会"为了把数字补整齐"去补造历史**？
13. **新增不变量时是否要声明 `dependsOn()`**：本项的修复会不会改变其它检查项的判定依据？
    （典型：补子任务会改变"子任务是否全部终态"）需要就声明依赖，不要依赖编码字典序碰巧排对。
13. **新增带逻辑删除的表且需要幂等去重时**：唯一键是否包含会变化的状态列？
    否则逻辑删除的历史行会永久占用业务键，使新写入**静默失败**（`process_pending_task` 的设计即为此）。
14. **新增状态/动作后**：`StateMachineContractTest` 矩阵 A 会失败——这是有意的，
    必须同步补 `data.sql` 的规则种子，而不是放宽测试。
15. **是否引入了新的实例本地状态**（内存 Map / 静态计数器 / 本地缓存）？
    见第十节：多实例下的问题几乎全部来自"本地状态"与"幂等边界"这两类。

## 十、多实例部署的正确性

多实例下出问题的从来不是算法，而是两类东西：**实例本地状态**（别的实例看不见）与
**幂等边界**（同一件事被两个实例各做一次）。本节记录一次完整审计的结果与处置。

### 10.1 审计结论一览

| 组件 | 原先的本地状态 / 幂等边界 | 多实例下的后果 | 处置 |
| --- | --- | --- | --- |
| `WechatPaySimulator` 预支付单 | 内存 `Map<prepayId, 预支付单>` | 用户在实例 A 预下单、确认扣款落到实例 B → **付不了款** | **已持久化**到 `wechat_pay_order`（状态由数据库共享） |
| `WechatPaySimulator` 已扣款单 | 内存 `Map<outTradeNo, 支付结果>` | 实例 B 的对账任务查不到扣款 → **已付款订单被当作未付款**，轻则漏补偿、重则被超时任务取消 | 同上（查单读库） |
| 配送任务号 | JVM 内 `static AtomicLong` | 两个实例同一秒生成同一个任务号 → 撞 `uk_task_no`，而幂等守卫会把"号撞了"误判成"业务键已存在"并**静默跳过** → **一条配送任务凭空消失** | **改为由业务键确定性生成**（`DT{日期}-{订单}-{品种}`）：号冲突 ⟺ 业务键冲突，两者不可能再背离 |
| 订单号 / 支付流水号 | JVM 内 `static AtomicLong` | 两个实例同一秒生成同一订单号 → 撞 `uk_order_no` → **下单失败** | 编号中加入**实例标识** `InstanceIdentity.TAG`（5 位随机，进程启动时确定） |
| 体检违规记录写入 | 应用层"先查再插" | 两个实例同时体检 → 同一主体插出两条违规记录 | 唯一键 `uk_violation` + `IdempotencyGuard` 幂等插入 |
| 6 个定时任务 | 无选主，**每个实例都会跑** | 同一批数据被多个实例并发处理 | **不作为缺陷修复**：逐个审计后确认幂等（见 10.2）；重复执行只浪费算力，不产生错误 |
| `StateMachineServiceImpl` / `SysConfigServiceImpl` 缓存 | 每实例一份，60 秒 TTL | 管理端在实例 A 改了规则/参数，实例 B 最长 60 秒后才生效 | **记录为有界延迟**（不是错误）：规则/参数变更的收敛上界 = 60 秒 |
| `RegisterRateLimiter` | 内存滑动窗口（按 IP） | N 个实例下等效阈值放大 N 倍 | **记录为有界削弱**：该限频只用于拦截脚本批量注册，非安全边界 |
| JWT 会话、`DataScopeResolver`、`IdempotencyGuard`、`MyMetaObjectHandler` | 无状态 | 无影响 | 无需改动 |

### 10.2 为什么可以"不选主"

定时任务在 N 个实例上都会触发，是否必须选主？本项目选择**不选主，而是把幂等做实**：

| 任务 | 重复执行时谁"赢" | 结论 |
| --- | --- | --- |
| `OrderTimeoutCancelJob` | 逐单 CAS 取消（`eq(status, 待支付)`） | 幂等 ✔ |
| `PaymentReconcileJob` | 落账经统一迁移出口 CAS（`待支付 → 已支付`） | 幂等 ✔（实验九对照 B） |
| `ProcessPendingTaskJob` | 待办可能被两个实例同时领取；补偿本身是 CAS/`attempt` | 幂等 ✔（见 10.3 的注意点） |
| `OrderProcessReconcileJob` | 补偿动作经统一迁移出口 CAS | 幂等 ✔ |
| `ProcessInvariantJob` | 修复经业务出口 CAS；违规记录由唯一键仲裁 | 幂等 ✔（实验九对照 D） |
| `DeliveryAutoSignJob` | 逐条 CAS 签收，不满足前置条件静默跳过 | 幂等 ✔（实验九对照 C） |

选主会引入新的分布式协调（锁、租约、脑裂处理），而**幂等本身已经能保证正确性**；
选主只能省下重复执行的算力，属于优化而非正确性需求。因此本项目不做选主，
并在文档里写清"重复执行只浪费不犯错"。

### 10.3 仍留在实例内、以及未被覆盖的部分（不确定项，必须写清）

1. **异步回调的发送仍是实例内的**：处理"确认扣款"的那个实例用内存线程池做指数退避重试；
   该实例若在重试期间崩溃，这次回调尝试就丢了。**支付单已落库为「已扣款」，对账任务（任意实例）
   查单即可补偿**——即"回调是尽力而为，对账才是保证"。这是有意设计，但意味着
   *回调送达的及时性依赖实例存活*。
2. **`notifyUrl` 在多实例下必须指向负载均衡地址**。当前默认值是 `http://127.0.0.1:8090/...`，
   只适合单实例。因为支付状态已持久化，回调**落到哪个实例都能正确处理**（这正是本次加固的意义），
   但指向一个不存在的实例端口时回调会全部失败、退化为纯对账补偿。
3. **`ProcessPendingTaskJob` 的重复消费会让 `retry_count` 前进得更快**：两个实例同时领取同一条待办，
   失败时会各记一次重试，因此"重试 5 次即放弃"在多实例下可能更早触发。
   后果是待办更早转交兜底通道（正确性不受影响，只是收敛路径变了）。
   若要严格单次消费，需要引入 CAS 认领（新增"处理中"状态 + 超时回收），当前未做。
4. **体检闭环标记在并发下可能被覆盖为"未闭环"（假阴性）**：两个实例的修复一个成功一个失败时，
   "已闭环/未闭环"的最终标记取决于写入顺序。下一轮体检会通过"复检通过"自动闭合，属自愈范围。
   实验九对照 D 的实测值为 1（已闭环），但**这不是可保证的结果**，因此测试只断言
   "记录不重复 + 数据一致"，不把该标记作为断言。
5. **系统参数与状态机规则变更的收敛延迟为 60 秒**（每实例 TTL 缓存）：管理端改完规则后，
   另一实例上仍可能按旧规则处理最长 60 秒。如果将来需要"变更即刻全局生效"，
   需要引入版本号/失效广播，当前未做。
6. **实例间时钟偏移未处理**：超时判定（`order.pay.timeout.minutes`）、在途窗口（2 分钟）、
   自动签收的"配送日期早于当天"都依赖 `LocalDateTime.now()`。若实例时钟不一致，
   边界行为会随之偏移。**部署要求：多实例必须校时（NTP）。**
7. **本节的验证方式是在单 JVM 内用「多组件实例 + 并发线程」模拟多实例**
   （实验九）。它覆盖"共享数据库、各自持有组件"的多实例语义，
   但**不覆盖**：真实多进程/多主机、网络分区、负载均衡路由、进程崩溃恢复、数据库主从延迟。
   这几项需要真实的多节点环境与混沌工具，列入后续工作。
8. **`wechat_pay_order` 表会持续增长**（演示规模的支付单全量保留）。
   它同时是对账依据，因此不能随意清理；若长期运行需要按"已对账 + 超过保留期"清理，当前未做。

## 十一、混沌注入与度量口径

验证层除了"构造坏数据"，还需要"在中间时刻打断"。本节记录注入的方法学约束与度量口径，
实验数据见 `../实验/实验设计与结果.md` §6.5–6.6。

### 11.1 注入语义：为什么必须"先执行、再抛"

注入器（测试域 AOP）在事务的中间步骤**执行完之后**抛异常，精确对应
「这一步的写入已发生、外层事务尚未提交」。因此：

- **注入点必须位于某个外层事务内部**。若注入点自身就是事务边界，`proceed` 已经提交，
  "抛异常"就变成另一种现象——**调用方看到失败、实际已生效**（模糊失败/悬挂）。
  这是另一个课题（需要幂等查询 + 可重试提示），不能与"事务中间故障"混在一起验证；
- 由此得出的两条工程结论（本项目都做到了）：
  ① 一次业务动作涉及的多张表写入必须放在**同一事务**；
  ② 事务边界必须落在**外部调用入口**（历史缺陷 D6：同类内部直调导致 `@Transactional` 失效）。

### 11.2 度量口径（与长稳一致，可复现）

| 指标 | 口径 |
| --- | --- |
| 三通道工作量 | 实时通道：消费待办并补偿生效条数；兜底通道：`reconcile` 返回的生效条数；体检：报告中的 `totalRepaired` |
| 检测延迟 | `process_pending_task` 的 `update_time - create_time`（入队 → 处理完成），取 p50/p95/max；**需加上消费者的轮询间隔**（生产为 5 秒）才是端到端窗口 |
| 重复漂移 | 体检记录的 `reopen_count` 合计（同一主体被反复检出的次数） |
| 冲突可见性 | 迁移台账中 `result = 0` 的条数（补偿/并发竞争落败，体现为"未生效"而非重复副作用） |
| 最终一致 | 停机后收敛 + 全库体检零检出 + 每主体仅一份副作用（成功流水 / PAY 台账 / 任务 / 摄入） |

> **时间列精度也是可观测性的一部分**：检测延迟最初只能落在 0ms / 1000ms 两档，
> 因为时间列是秒精度 `DATETIME`。把 `process_pending_task` 的时间列改为 `DATETIME(3)` 后
> 才得到有意义的 p50/p95。若需要更细的度量，其余过程层表应按同样方式升级。

### 11.3 双通道分工的实测结论（设计依据）

实验十一里 624 次"父状态被改坏"的漂移中：**兜底通道收掉 543 次、体检 71 次、实时通道 10 次**。
原因是注入的漂移**没有发生任何子过程事件**，事件驱动的实时通道无从触发。

结论：**实时通道对"没有事件发生的写入丢失"无能为力，周期扫描的检测窗口又太长**——
两者覆盖的是两类不同失效形态，因此双通道不是重复建设。
这也是本项目把"实时通道"定位为**收敛速度**、把"兜底通道"定位为**最终一致保证**的原因。

## 十二、性能：一致性优先的代价（热点行争用）

可靠性设计的核心手段——行锁读 + 条件更新 + 台账唯一键——是有代价的。
实验十二把它量了出来（数据见 `../实验/实验设计与结果.md` §6.7）：

| 观察 | 数据 | 含义 |
| --- | --- | --- |
| 热点池串行化 | 32 线程吞吐 672 TPS **低于** 8 线程的 758（0.89×），p50 从 10.3ms 涨到 45.3ms | 吞吐不随并发度提升，延迟按并发度排队——串行化瓶颈的标准特征 |
| 单线程 TPS ≠ 上限 | 单线程 208 TPS，热点并发 672 TPS（3.2×），远低于 32× 线性 | 单线程 TPS 把锁外开销也算进去了；多线程可把锁外开销与锁内临界区**流水重叠**，临界区真实服务能力 ≈ 670 ops/s |
| 分散多行有效 | 32 池 2670 TPS（×4），p50 回落到 10.7ms | 同一份代码，只是热点不在一行上 |
| 分散收益 8 池即到顶 | 8 池 → 32 池仅 0.99× | 行锁之外还有第二个瓶颈：每笔扣减 5 条 SQL（3 次窗口加锁读 + 1 次条件更新 + 1 次台账插入）+ 连接/ORM 开销 |
| 压力下正确性不变 | 约 10600 次并发扣减：零失败、零超卖、账实一致 | **性能实验同样断言不变量** |

### 12.1 为什么要写这一节（判断依据）

1. **"不超卖"不是免费的**。行锁串行化意味着**单个热门品种池的吞吐上限 ≈ 临界区服务能力**，
   与部署多少实例无关（池子行在数据库里，实例再多也要排队）。
   这是答辩时最容易被追问的一点，现在有数据。
2. **出路及其代价要一起说**。分段池（按班级/批次）能把热点分散开（实测多品种池 ×4），
   但**分段后各段不能互相借用余量**，配额利用率会下降（某班卖完、另一班还有货）——
   这是**一致性-吞吐-利用率**的三方权衡，不是"分段一定更好"。
   而且本项目配额唯一键是 `(quota_date, product_id)`，没有班级这一维，
   真要分段需要改配额维度与分配算法（后续工作 §3.3）。
3. **下一个量级的瓶颈不在锁，在每笔扣减的 SQL 次数**。保质期窗口 3 天导致每笔扣减最多 3 次
   加锁读；先做一次范围读确定窗口内实际存在的池再逐池加锁，可以省掉空读——
   但必须保持"读最新版本再写回"（READ_COMMITTED，见 §5），不能改成快照读预判后再加锁。
