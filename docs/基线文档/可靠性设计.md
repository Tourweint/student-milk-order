# 可靠性设计

> 本文说明「业务过程可靠执行」用到的具体机制：每个机制解决什么问题、在代码哪里、判定口径是什么、
> 以及改动时必须守住的不变量。
>
> 抽象与层次划分见 `业务过程与可靠执行模型.md`；验证数据见 `../实验/实验设计与结果.md`。

## 一、机制总览

| 机制 | 解决的问题 | 实现位置 |
| --- | --- | --- |
| 业务唯一键 + 幂等守卫 | 同一个动作执行多次 | `uk_order_product_date`、`uk_order_product_pool`、`uk_delivery_record`、`IdempotencyGuard` |
| CAS 条件更新 | 两个执行者同时改同一状态 | `ProcessTransitionExecutor` 的 `casUpdate` |
| 悲观行锁读 | 读-改-写之间被并发插入 | `DailyQuotaMapper.selectForUpdate` |
| 资源台账 + 精确回补 | 资源从哪个池子扣、回到哪里 | `daily_quota_usage`、`DailyQuotaService.restore/restoreForOrderProductDate` |
| 先抢占状态、再执行副作用 | 落败方重复执行副作用 | `payOrder`、`handleWechatPayNotify` |
| 状态迁移留痕 | 过程不可观测 / 无法回溯 | `process_transition_log`、`ProcessTransitionExecutor` |
| 支付对账 + 补偿落账 | 支付侧跨系统边界不一致 | `reconcilePendingPayments` |
| **补偿规则表 + 补偿协调器** | 补偿规则写死在代码里 | `process_reconcile_rule`、`ProcessReconcileEngine`、`ProcessReconcileCoordinator`（§7.2） |
| **自愈待办（实时通道）** | 父过程聚合靠调用方自觉、检测窗口过长 | `process_pending_task`、`ProcessPendingTaskService`（§7.3） |
| **跨表不变量体检** | 跨表约束只在实验里被验证过一次 | `ProcessInvariant` × 7、`ProcessInvariantScanner`（§7.4） |
| 定时兜底 / 实时通道 | 执行机会根本没发生 | 6 个 `*Job`（5 个兜底 + 1 个实时消费） |

## 二、幂等：把并发仲裁交给数据库

### 2.1 为什么不能用「先查再写」

应用层幂等的常见写法是「先 `selectCount` 判断是否已存在，不存在再 `insert`」。该写法**只在单线程下成立**：
并发下多个执行者会同时查不到，再同时插入，于是产生重复数据。实验三即复现了这一点
（理论 6 条配送任务，16 线程并发展开）。

### 2.2 正确写法

1. 给业务键建**唯一约束**，由数据库承担并发仲裁；
2. 应用层只负责把唯一键冲突翻译成「已存在」并幂等跳过。

代码落点 `com.milk.order.reliability.IdempotencyGuard`：

```java
/** 执行一次「写入并忽略重复」的操作；返回 true=插入成功，false=唯一键冲突（判定为已存在并跳过） */
public boolean insertIgnoringDuplicate(Runnable insert)
```

已有业务唯一键：

| 表 | 唯一键 | 语义 |
| --- | --- | --- |
| `delivery_task` | `uk_order_product_date (order_id, product_id, delivery_date)` | 同一订单同一奶品同一配送日只允许一条任务 |
| `daily_quota_usage` | `uk_order_product_pool (order_id, product_id, quota_date)` | 同一订单同一品种同一配额池只允许扣减一行 |
| `nutrition_intake` | `uk_delivery_record (delivery_record_id)` | 一个签收记录最多生成一条摄入记录（正常签收与体检补写两条路径都由数据库仲裁） |
| `process_pending_task` | `uk_pending (scene, entity_id, trigger_action, status)` | 同一主体同一触发动作只保留一条待处理自愈待办 |

> 注意：MySQL/MariaDB 下唯一键冲突只回滚该条语句，事务可继续提交其余写入，因此
> 「冲突即跳过」在同一事务内是安全的。

### 2.3 幂等还需要的第二层：先抢占状态

唯一键能防「重复插入」，但防不住「重复副作用」。
`handleWechatPayNotify` / `payOrder` 里的顺序是刻意的：

```text
先 CAS 抢占状态（待支付→已支付）  ← 只有一个执行者能过
        ↓
再做副作用：扣配额 → 写流水 → 展开任务   ← 只执行一次
```

若反过来「先做副作用、再 CAS」，落败方已经扣了配额、写了流水才失败，只能靠回滚收场，
并发下还会互相撞业务唯一键（实验二暴露的 D4）。

## 三、CAS 条件更新

**解决的问题**：「两个执行者同时试图改变同一状态」。

```sql
UPDATE order_info SET status = 2 WHERE id = ? AND status = 1
```

只有一方能更新成功（受影响行数 1），另一方得到 0 行，据此判定冲突。

**代码落点**：所有状态迁移经 `ProcessTransitionExecutor`，由调用方传入以原状态为条件的更新动作。
`require` 在冲突时抛业务异常并回滚；`attempt` 在冲突时返回 false 并跳过。

**为什么不用 `@Version` 乐观锁**：项目状态变更天然是「按状态机从一个合法状态推进到下一个」，
用「状态本身作为版本」比额外版本号更贴合语义，也避免为每个实体加冗余字段。

## 四、悲观行锁读

**解决的问题**：「读剩余 → 写已售」这类读-改-写之间，行被并发修改。

**代码落点**：`DailyQuotaMapper.selectForUpdate`

```sql
SELECT * FROM daily_quota WHERE quota_date = ? AND product_id = ? AND deleted = 0 FOR UPDATE
```

配额扣减的三遍结构（`DailyQuotaServiceImpl.deduct`）：

1. **加锁读**：一次性把保质期窗口内的池子（先过期先出）读进来，得到权威可扣量并形成扣减计划；
2. **充足校验**：全部品种都充足才继续，任一不足即整体抛异常 → 事务回滚，不会留下部分扣减；
3. **写回**：按计划更新，并以 `used_quota + n <= total_quota` 作为最后一道防御。

### 4.1 为什么必须用行锁读（重要）

同一事务内若**先对某行做一致性快照读、再对该行做加锁读或更新**，不同数据库行为不一致：

| 数据库 | 行为 |
| --- | --- |
| MySQL 8 | UPDATE 自动读到最新已提交版本，静默成功 |
| MariaDB（REPEATABLE READ） | 直接拒绝：`Record has changed since last read in table 'xxx'` |

这是实验一在并发扣减下暴露的真实缺陷（有保护版本只成功 25/200）。

## 五、事务隔离级别

**本项目的选择：统一使用 `READ_COMMITTED`**（`spring.datasource.hikari.transaction-isolation`）。

理由：

1. 本系统的并发安全**全部由「条件更新 / 行锁 / 唯一键」显式保证**，不依赖 REPEATABLE READ 的
   可重复读语义；
2. REPEATABLE READ 下 MariaDB 与 MySQL 对「快照建立后被并发修改的行」行为不一致（见 4.1），
   会造成「同一份代码、两种数据库、两种结果」；
3. 显式统一后，行为可预期，也消除了「读快照、写最新」的语义撕裂。

> 若将来确需 REPEATABLE READ 的语义（例如报表需要事务内稳定快照），应把**报表类只读事务**
> 单独标注隔离级别，而不是把写路径改回 REPEATABLE READ。

## 六、资源台账与精确回补

**台账不是「库存表」，而是「资源变动的可追踪记录」。**

| 能力 | 实现 |
| --- | --- |
| 扣减按池子记账（含保质期结转池，先过期先出） | `deduct` 写 `daily_quota_usage`（订单×品种×池子日期×盒数） |
| 退订回补：精确回到原池子 | `restore(orderId)`：按台账逐行回补后删除台账行 |
| 缺货单期取消：只回补该订单该品种 | `restoreForOrderProductDate(orderId, productId, date)` |
| 防御：不允许把 `used_quota` 减成负数 | 回补使用条件更新 `used_quota >= n` |

回补到**原池子**而不是简单 `stock++`，是为了避免「从 A 池子扣、补到 B 池子」造成的账实不符。

**台账行的删除语义（重要约束）**：回补时执行的「删除台账行」实际是**逻辑删除**（实体带 `@TableLogic`），
因此业务查询不可见、重复回补自然跳过（幂等），但**物理行仍然存在**，并继续占用业务唯一键
`uk_order_product_pool`。这意味着：*同一订单同一品种同一池子若需要二次扣减，会直接撞唯一键*。
当前所有扣减都只发生一次（支付成功时），不会触发；若将来引入「退款后重新扣减」「配额重算」等场景，
必须先物理清理旧台账行或调整键策略。该约束由实验五（见 `../实验/实验设计与结果.md` 第 7.1 节）发现。

**同一个坑的第二次出现（已规避）**：自愈待办表 `process_pending_task` 的去重键里**必须**包含 `status`——
否则「已处理」行被逻辑删除后，其物理行仍占用唯一键，会让同一业务键的新待办**静默入队失败**。
把 `status` 放进唯一键后，待处理(0)/已处理(1)/已放弃(2) 各自独立成键，逻辑删除已处理行不再阻塞新待办。
设计时先识别出该陷阱，因此未在运行中暴露——这类「上一轮踩过的坑在新表上的复现」是必须主动检查的。

## 七、对账、补偿与持续验证

**核心思想：从「绝对原子性」转向「可检测、可恢复的最终一致性」。**

```text
发现不一致 → 对账 → 决策 → 补偿 → 恢复合法状态 → 复检
```

### 7.1 支付侧对账

支付系统成功、而订单系统没更新，就会出现跨边界状态不一致（支付 = 成功，订单 = 待支付）。
系统不追求「所有事情必须同时成功」，而是主动查单补偿：

| 对账类型 | 检测「什么不一致」 | 补偿动作 | 落点 |
| --- | --- | --- | --- |
| 支付对账 | 存在在途待支付流水，但微信侧已扣款 | 走回调同一路径补偿落账（扣配额 + 写流水 + 改状态 + 展开任务） | `OrderInfoService.reconcilePendingPayments` |
| 超时对账 | 待支付超时 | 取消前先查单：已扣款则转补偿落账，**绝不取消已付款订单** | `OrderInfoService.cancelTimeoutOrder` |

### 7.2 过程侧补偿：探测 / 决策 / 执行三层

过程侧的不一致形态是「父过程状态与子过程集合不匹配」。这类补偿**曾经硬编码在订单服务里**
（两个 `if`），现已下沉为规则驱动：

| 层 | 职责 | 落点 |
| --- | --- | --- |
| 探测 | 按规则表的 `parent_status` 取候选，逐条求值子过程条件，产出决策（**只读**） | `ProcessReconcileEngine`、`ParentProcessProbe` |
| 决策 | 「父状态 + 子条件 → 补偿动作 + 目标状态」，可在线启停 | `process_reconcile_rule` |
| 执行 | 复用统一迁移出口做条件更新并留痕 | `ParentProcessAggregator` → `ProcessTransitionExecutor` |

补偿的幂等性来自「复用统一迁移出口 + 聚合出口」：补偿本身也是一次带条件的状态迁移，
状态已合法时不会产生新的迁移（实验四验证：重复对账后已生效迁移条数不变）。

**两条必须守住的边界**：

1. **补偿也是迁移，也要过闸门**。启用一条新补偿规则时，必须确认 `state_transition_rule`
   放开了对应迁移，否则统一出口会以「规则禁止」拒绝补偿（实验六实测：命中规则但补偿生效数为 0）。
   种子里的第三条示例规则（全取消补偿）默认停用，并在描述里写明了这一依赖。
2. **条件不配置化**。规则表可配的是「用哪个条件、补偿到什么状态」；条件本身的语义
   （什么算「全部终态」）由枚举 + 业务侧实现，因为允许任意表达式会让规则表无法审阅、无法测试。

**覆盖盲区（实验十一的特征化测试发现，3.4 已补齐）**：规则表原本有
`(已支付, HAS_DISPATCHING_TASK → 配送中)` 与 `(配送中, ALL_TASKS_TERMINAL → 已完成)`，
但**缺 `(已支付, ALL_TASKS_TERMINAL → 已完成)`**——「订单已支付 + 子任务已全部签收」
（配送联动与聚合写入同时丢失）既不会被补偿、也不被现有不变量判为违规，静默停在已支付。

补齐（3.4）做了三件事，每件都体现"配了规则 ≠ 配对了规则"：

1. 新增规则「已支付全终态补偿」`(2, ALL_TASKS_TERMINAL → AUTO_COMPLETE, 4)`，默认启用；
2. **放开闸门 `ORDER/AUTO_COMPLETE/2`**（原为显式禁止"已支付订单未开始配送不自动完成"）。
   安全性论证：闸门看不见子过程，因此"不跳过未完成配送"这层约束**不由闸门保证**，
   而由聚合出口的定义保证——只有全部任务终态才会走到 AUTO_COMPLETE；
   管理端手动完成的 `COMPLETE/2` **仍保持禁止**（放开哪条闸门是独立的业务决定，最初曾误判为它）；
3. 聚合出口 `completeOrderIfAllTasksDone` 从"仅配送中"放开为"已支付/配送中"，
   CAS 以**实际父状态**为条件（同一出口服务正常路径与补偿路径，天然幂等留痕）。

这再次说明：**规则表的覆盖面必须被主动审视，而不是等出了问题才发现**——
这次是长稳实验的特征化用例把它暴露出来的。遗留语义边界：**子任务全部取消时也会被补为已完成**，
"全部取消 → 已退订"的区分依赖退款设计（`全取消补偿` 规则仍默认停用）。

### 7.3 双通道：实时自愈 + 定时兜底

| | 实时通道 | 兜底通道 |
| --- | --- | --- |
| 触发 | 子过程状态变更（同事务入队 `process_pending_task`） | 周期扫描（`OrderProcessReconcileJob`） |
| 检测窗口 | ≈ 轮询间隔 5 秒 + 修复耗时（实测约 5.0 秒） | ≤ 调度周期 10 分钟 |
| 失败处理 | 指数退避重试，超 5 次置「已放弃」并告警 | 下一轮继续（幂等） |
| 职责 | 收敛速度 | 最终一致（保证） |

为什么要双通道（这是设计论证，不是功能堆砌）：

- **只有兜底通道**：不可检测窗口是分钟级，且全表扫随数据量增长而变慢；
- **只有实时通道**：自愈本身会失败（实测：重试 5 次后放弃），失败后没人管。

另外，待办把「父过程需要重新聚合」从**隐式约定**（调用方记得调用聚合出口）变成**显式数据**：
即使某条路径漏掉同步聚合、或同步聚合被规则表临时挡住，待办仍在，秒级消费者会按最新状态补上。
入队必须在子过程状态变更的**同一事务内**，否则待办本身会成为新的不一致来源。

### 7.4 跨表不变量体检

这是本轮最核心的主张：**不变量只在被验证时才成立**。

| 编码 | 不变量 | 处置 |
| --- | --- | --- |
| `INV_QUOTA_LEDGER` | `daily_quota.used_quota` = 台账合计（`deleted = 0`） | 自动修复（以台账为准重算） |
| `INV_TASK_RECORD` | 任务已完成 ⇒ 签收记录已签收 | 自动修复（经统一出口补签收） |
| `INV_SIGN_INTAKE` | 已签收 ⇒ 存在营养摄入记录 | 自动修复（复用签收时的生成逻辑） |
| `INV_ORDER_TASK` | 任务覆盖「品种 × 配送日」全网格 | **按情况分级**：订单进行中（已支付/配送中）自动补生成；订单已终态**只告警、不补造历史**（补造反而会制造组合异常） |
| `INV_ORDER_AGGREGATION` | 父订单状态与子任务集合一致 | 自动修复（复用 §7.2 的探测与聚合出口） |
| `INV_PARENT_TERMINAL_CHILD_PENDING` | 父过程终态 ⇒ 不存在非终态子过程 | **按情况分级**：待配送自动作废（经业务取消出口）/ 配送中仅告警（奶已出库在途） |
| `INV_PAYMENT_CONSISTENCY` | 订单状态与支付流水互证 | **仅告警**（涉资金，人工核处） |
| `INV_TASK_COMPENSATION` | 真拒收（`sign_status=3 AND reject_reason_code IS NOT NULL`）⇒ 存在 `delivery_compensation` 补偿记录 | **仅告警**（补送涉配额与业务判断，人工核处） |

**分级的判断标准**：能由既有台账唯一推导出正确值、且重算幂等的才允许自动修复；涉及资金流向
或需要业务判断的一律只告警（实验七对照 B 验证：资金不一致被检出但数据一个字节都没动）。

**等级可以细到"每条违规"**：修复判定以 `InvariantViolation.severity` 为准，不变量声明的等级只是默认值
（未声明时回退到默认，回退方向是"不自动修"）。因此同一条约束下可以"有的情况自动修、有的只能告警"。
原则是：**探测可以比修复更激进，修复永远比探测更保守**。

**执行顺序由声明依赖决定**：`ProcessInvariant.dependsOn()` 声明「本项必须在哪些编码之后执行」，
体检器按**拓扑序**执行（同层按编码升序打破平局，因此确定可复现）；引用未注册编码或依赖成环时**直接失败**
（配置错误不能静默退化成任意顺序）。当前声明两条：

```text
INV_ORDER_TASK（补网格） → INV_ORDER_AGGREGATION（判父聚合） → INV_PARENT_TERMINAL_CHILD_PENDING（判组合）
```

为什么必须这样：父聚合的判定依据是"子任务是否全部终态"。若先判父、再补子，
**体检自己就会制造**「已完成订单 + 待配送任务」这种组合异常。顺序本身是设计的一部分，
因此 `resolvedExecutionOrder()` 把它暴露出来可测、可审阅（守卫矩阵 D）。
更强的形态是把不变量当约束系统求解（见后续扩展方案 §2.5 方案三）。

**假阳性控制**：`INV_PAYMENT_CONSISTENCY` 的「流水成功但订单未落账」方向只检出自成功时间
超过 5 分钟的记录，避免把支付对账任务的正常工作窗口误报成不一致——**判定口径必须考虑
「系统本来就在处理中」这件事**。

**记录语义**：每个（不变量 × 主体）保留一行当前状态，重复漂移用 `reopen_count` 累加；
一轮体检对上轮未闭环、本轮未再检出的记录做**复检闭环**（问题真的消失了，而不是被忽略）。

## 八、定时任务与调度

正常路径是「人工 / API / 回调」；异常路径是「事件驱动自愈（实时）+ 定时扫描（兜底）」。

| 任务 | 周期 | 通道 | 内容 | 开关 |
| --- | --- | --- | --- | --- |
| `OrderTimeoutCancelJob` | 5 分钟 | 兜底 | 待支付超时自动取消（先查单对账，防误杀已付款） | `order.pay.timeout.minutes`（默认 15） |
| `PaymentReconcileJob` | 5 分钟 | 兜底 | 在途待支付流水的回调丢失补偿 | `order.pay.reconcile.enabled` |
| `ProcessPendingTaskJob` | **5 秒** | **实时** | 消费自愈待办，立即探测并补偿（失败退避，超 5 次放弃） | `process.pending.enabled` |
| `OrderProcessReconcileJob` | 10 分钟 | 兜底 | 按补偿规则表批量修复父子状态漂移（实时通道的最后防线） | `order.process.reconcile.enabled` |
| `ProcessInvariantJob` | 30 分钟 | 兜底 | 跨表不变量体检 + 自动修复可逆项 | `process.invariant.scan.enabled` |
| `DeliveryAutoSignJob` | 每天 00:30 | 兜底 | 超时未签收自动签收（**排除奶站已申报「未送达」的任务**，见第十六节） | — |

设计口径：

- 兜底任务一律**幂等可重复执行**：本轮处理不了就留给下一轮，不追求一次做完；
- 单条失败不影响其余（逐条 try/catch），并有单批处理上限防止历史脏数据拖死任务；
- 实时通道的失败**必须可见**：退避重试 + 超限放弃 + 告警，绝不静默吞掉；
- 全部任务可用 `app.scheduler.enabled=false` 关闭（实验/测试环境使用）。

## 九、改动时的检查清单

涉及状态、资源、支付、配送的改动，提交前逐条确认：

1. 状态迁移是否经 `ProcessTransitionExecutor`，且条件更新以原状态为准？
2. 新增状态/动作是否补了 `state_transition_rule` 规则种子？（白名单语义，缺规则=全禁）
3. 是否需要「同一业务键只存在一行」？需要就建唯一约束，不要用「先查后插」。
4. 涉及「读剩余 → 写已售」的路径，是否用了 `SELECT ... FOR UPDATE`？
5. 状态迁移与副作用的顺序是否为「先抢占状态、再执行副作用」？
6. 资源扣减是否写了台账，回补是否回到原池子？
7. 新增的异步/异常路径，是否考虑了「执行机会没发生」时的兜底与补偿？
8. 兜底任务是否幂等？是否有单批上限？是否有开关？
9. **是否新增了绕过统一出口的旁路**？逐条核对：所有 `set(…::getStatus)` / `set(…::getSignStatus)`
   类的写入是否都经 `ProcessTransitionExecutor`——旁路不会报错，
   但会让「每一次状态迁移都留痕」这一不变量悄悄失效（缺陷 D5 即此类问题，守卫为实验五）。
10. **新增/调整补偿规则时**：`state_transition_rule` 是否放开了该补偿要执行的迁移？（否则补偿会被闸门拒绝）
    规则默认值是否安全（新规则默认停用、行为等价的老规则才默认启用）？
11. **新增子过程状态变更路径时**：是否在同一事务内 `enqueue` 了父过程自愈待办？
    触发动作是否唯一（决定去重粒度）？
12. **新增跨表约束时**：是否登记为 `ProcessInvariant`？处置等级是 `AUTO_REPAIR` 还是 `ALERT_ONLY`
    （涉资金/需业务判断/终态历史的一律 `ALERT_ONLY`；同一约束内可按情况逐条覆写等级）？
    检测口径是否考虑了「系统本来就在处理中」这类中间态？
    修复是否与已有不变量冲突（会不会产生新的组合异常）？**会不会"为了把数字补整齐"去补造历史**？
13. **新增不变量时是否要声明 `dependsOn()`**：本项的修复会不会改变其它检查项的判定依据？
    （典型：补子任务会改变"子任务是否全部终态"）需要就声明依赖，不要依赖编码字典序碰巧排对。
13. **新增带逻辑删除的表且需要幂等去重时**：唯一键是否包含会变化的状态列？
    否则逻辑删除的历史行会永久占用业务键，使新写入**静默失败**（`process_pending_task` 的设计即为此）。
14. **新增状态/动作后**：`StateMachineContractTest` 矩阵 A 会失败——这是有意的，
    必须同步补 `data.sql` 的规则种子，而不是放宽测试。
15. **是否引入了新的实例本地状态**（内存 Map / 静态计数器 / 本地缓存）？
    见第十节：多实例下的问题几乎全部来自"本地状态"与"幂等边界"这两类。
16. **新增"批量改期/改量"能力时**（平移、日历重排、摊平等）：是否复用既有落账骨架 `relocateTask`
    而不是另写一套「作废 + 合并/新建」？三条硬约束是否保持（不更新 `deliveryEndDate`、
    合并/加量 0 行抛异常回滚、CAS 即幂等闸门）？涉及日历规则（周末/停送日）时，
    默认开关是否为"不生效"，且关闭时是**拒绝执行**而不是静默不改（见第十四节）？
17. **新增自动兜底（"系统替人做决定"）能力时**：判定条件用的是**信息态**还是**物理态**？
    凡是"系统自己补出业务事实"（自动签收、自动完成、自动补单）的兜底，都要问一句
    "有没有一种情况，记录上看着该动作成立、但实际上那件事没发生"——有，就必须留一个
    **业务侧可声明的例外**（如奶站「未送达申报」），并且**候选集与单条入口都要挡**
    （候选集分批取，两次取之间可能新增例外；只在候选集过滤会漏，见第十六节）。

## 十、多实例部署的正确性

多实例下出问题的从来不是算法，而是两类东西：**实例本地状态**（别的实例看不见）与
**幂等边界**（同一件事被两个实例各做一次）。本节记录一次完整审计的结果与处置。

### 10.1 审计结论一览

| 组件 | 原先的本地状态 / 幂等边界 | 多实例下的后果 | 处置 |
| --- | --- | --- | --- |
| `WechatPaySimulator` 预支付单 | 内存 `Map<prepayId, 预支付单>` | 用户在实例 A 预下单、确认扣款落到实例 B → **付不了款** | **已持久化**到 `wechat_pay_order`（状态由数据库共享） |
| `WechatPaySimulator` 已扣款单 | 内存 `Map<outTradeNo, 支付结果>` | 实例 B 的对账任务查不到扣款 → **已付款订单被当作未付款**，轻则漏补偿、重则被超时任务取消 | 同上（查单读库） |
| 配送任务号 | JVM 内 `static AtomicLong` | 两个实例同一秒生成同一个任务号 → 撞 `uk_task_no`，而幂等守卫会把"号撞了"误判成"业务键已存在"并**静默跳过** → **一条配送任务凭空消失** | **改为由业务键确定性生成**（`DT{日期}-{订单}-{品种}`）：号冲突 ⟺ 业务键冲突，两者不可能再背离 |
| 订单号 / 支付流水号 | JVM 内 `static AtomicLong` | 两个实例同一秒生成同一订单号 → 撞 `uk_order_no` → **下单失败** | 编号中加入**实例标识** `InstanceIdentity.TAG`（5 位随机，进程启动时确定） |
| 体检违规记录写入 | 应用层"先查再插" | 两个实例同时体检 → 同一主体插出两条违规记录 | 唯一键 `uk_violation` + `IdempotencyGuard` 幂等插入 |
| 6 个定时任务 | 无选主，**每个实例都会跑** | 同一批数据被多个实例并发处理 | **不作为缺陷修复**：逐个审计后确认幂等（见 10.2）；重复执行只浪费算力，不产生错误 |
| `StateMachineServiceImpl` / `SysConfigServiceImpl` 缓存 | 每实例一份，60 秒 TTL | 管理端在实例 A 改了规则/参数，实例 B 最长 60 秒后才生效 | **记录为有界延迟**（不是错误）：规则/参数变更的收敛上界 = 60 秒 |
| `RegisterRateLimiter` | 内存滑动窗口（按 IP） | N 个实例下等效阈值放大 N 倍 | **记录为有界削弱**：该限频只用于拦截脚本批量注册，非安全边界 |
| JWT 会话、`DataScopeResolver`、`IdempotencyGuard`、`MyMetaObjectHandler` | 无状态 | 无影响 | 无需改动 |

### 10.2 为什么可以"不选主"

定时任务在 N 个实例上都会触发，是否必须选主？本项目选择**不选主，而是把幂等做实**：

| 任务 | 重复执行时谁"赢" | 结论 |
| --- | --- | --- |
| `OrderTimeoutCancelJob` | 逐单 CAS 取消（`eq(status, 待支付)`） | 幂等 ✔ |
| `PaymentReconcileJob` | 落账经统一迁移出口 CAS（`待支付 → 已支付`） | 幂等 ✔（实验九对照 B） |
| `ProcessPendingTaskJob` | 待办可能被两个实例同时领取；补偿本身是 CAS/`attempt` | 幂等 ✔（见 10.3 的注意点） |
| `OrderProcessReconcileJob` | 补偿动作经统一迁移出口 CAS | 幂等 ✔ |
| `ProcessInvariantJob` | 修复经业务出口 CAS；违规记录由唯一键仲裁 | 幂等 ✔（实验九对照 D） |
| `DeliveryAutoSignJob` | 逐条 CAS 签收，不满足前置条件静默跳过 | 幂等 ✔（实验九对照 C） |

选主会引入新的分布式协调（锁、租约、脑裂处理），而**幂等本身已经能保证正确性**；
选主只能省下重复执行的算力，属于优化而非正确性需求。因此本项目不做选主，
并在文档里写清"重复执行只浪费不犯错"。

### 10.3 仍留在实例内、以及未被覆盖的部分（不确定项，必须写清）

1. **异步回调的发送仍是实例内的**：处理"确认扣款"的那个实例用内存线程池做指数退避重试；
   该实例若在重试期间崩溃，这次回调尝试就丢了。**支付单已落库为「已扣款」，对账任务（任意实例）
   查单即可补偿**——即"回调是尽力而为，对账才是保证"。这是有意设计，但意味着
   *回调送达的及时性依赖实例存活*。
2. **`notifyUrl` 在多实例下必须指向负载均衡地址**。当前默认值是 `http://127.0.0.1:8090/...`，
   只适合单实例。因为支付状态已持久化，回调**落到哪个实例都能正确处理**（这正是本次加固的意义），
   但指向一个不存在的实例端口时回调会全部失败、退化为纯对账补偿。
3. **`ProcessPendingTaskJob` 的重复消费会让 `retry_count` 前进得更快**：两个实例同时领取同一条待办，
   失败时会各记一次重试，因此"重试 5 次即放弃"在多实例下可能更早触发。
   后果是待办更早转交兜底通道（正确性不受影响，只是收敛路径变了）。
   若要严格单次消费，需要引入 CAS 认领（新增"处理中"状态 + 超时回收），当前未做。
4. **体检闭环标记在并发下可能被覆盖为"未闭环"（假阴性）**：两个实例的修复一个成功一个失败时，
   "已闭环/未闭环"的最终标记取决于写入顺序。下一轮体检会通过"复检通过"自动闭合，属自愈范围。
   实验九对照 D 的实测值为 1（已闭环），但**这不是可保证的结果**，因此测试只断言
   "记录不重复 + 数据一致"，不把该标记作为断言。
5. **系统参数与状态机规则变更的收敛延迟为 60 秒**（每实例 TTL 缓存）：管理端改完规则后，
   另一实例上仍可能按旧规则处理最长 60 秒。如果将来需要"变更即刻全局生效"，
   需要引入版本号/失效广播，当前未做。
6. **实例间时钟偏移未处理**：超时判定（`order.pay.timeout.minutes`）、在途窗口（2 分钟）、
   自动签收的"配送日期早于当天"都依赖 `LocalDateTime.now()`。若实例时钟不一致，
   边界行为会随之偏移。**部署要求：多实例必须校时（NTP）。**
7. **本节的验证方式是在单 JVM 内用「多组件实例 + 并发线程」模拟多实例**
   （实验九）。它覆盖"共享数据库、各自持有组件"的多实例语义，
   但**不覆盖**：真实多进程/多主机、网络分区、负载均衡路由、进程崩溃恢复、数据库主从延迟。
   这几项需要真实的多节点环境与混沌工具，列入后续工作。
8. **`wechat_pay_order` 表会持续增长**（演示规模的支付单全量保留）。
   它同时是对账依据，因此不能随意清理；若长期运行需要按"已对账 + 超过保留期"清理，当前未做。

## 十一、混沌注入与度量口径

验证层除了"构造坏数据"，还需要"在中间时刻打断"。本节记录注入的方法学约束与度量口径，
实验数据见 `../实验/实验设计与结果.md` §6.5–6.6。

### 11.1 注入语义：为什么必须"先执行、再抛"

注入器（测试域 AOP）在事务的中间步骤**执行完之后**抛异常，精确对应
「这一步的写入已发生、外层事务尚未提交」。因此：

- **注入点必须位于某个外层事务内部**。若注入点自身就是事务边界，`proceed` 已经提交，
  "抛异常"就变成另一种现象——**调用方看到失败、实际已生效**（模糊失败/悬挂）。
  这是另一个课题（需要幂等查询 + 可重试提示），不能与"事务中间故障"混在一起验证；
- 由此得出的两条工程结论（本项目都做到了）：
  ① 一次业务动作涉及的多张表写入必须放在**同一事务**；
  ② 事务边界必须落在**外部调用入口**（历史缺陷 D6：同类内部直调导致 `@Transactional` 失效）。

### 11.2 度量口径（与长稳一致，可复现）

| 指标 | 口径 |
| --- | --- |
| 三通道工作量 | 实时通道：消费待办并补偿生效条数；兜底通道：`reconcile` 返回的生效条数；体检：报告中的 `totalRepaired` |
| 检测延迟 | `process_pending_task` 的 `update_time - create_time`（入队 → 处理完成），取 p50/p95/max；**需加上消费者的轮询间隔**（生产为 5 秒）才是端到端窗口 |
| 重复漂移 | 体检记录的 `reopen_count` 合计（同一主体被反复检出的次数） |
| 冲突可见性 | 迁移台账中 `result = 0` 的条数（补偿/并发竞争落败，体现为"未生效"而非重复副作用） |
| 最终一致 | 停机后收敛 + 全库体检零检出 + 每主体仅一份副作用（成功流水 / PAY 台账 / 任务 / 摄入） |

> **时间列精度也是可观测性的一部分**：检测延迟最初只能落在 0ms / 1000ms 两档，
> 因为时间列是秒精度 `DATETIME`。把 `process_pending_task` 的时间列改为 `DATETIME(3)` 后
> 才得到有意义的 p50/p95。若需要更细的度量，其余过程层表应按同样方式升级。

### 11.3 双通道分工的实测结论（设计依据）

实验十一里 624 次"父状态被改坏"的漂移中：**兜底通道收掉 543 次、体检 71 次、实时通道 10 次**。
原因是注入的漂移**没有发生任何子过程事件**，事件驱动的实时通道无从触发。

结论：**实时通道对"没有事件发生的写入丢失"无能为力，周期扫描的检测窗口又太长**——
两者覆盖的是两类不同失效形态，因此双通道不是重复建设。
这也是本项目把"实时通道"定位为**收敛速度**、把"兜底通道"定位为**最终一致保证**的原因。

## 十二、性能：一致性优先的代价（热点行争用）

可靠性设计的核心手段——行锁读 + 条件更新 + 台账唯一键——是有代价的。
实验十二把它量了出来（数据见 `../实验/实验设计与结果.md` §6.7）：

| 观察 | 数据 | 含义 |
| --- | --- | --- |
| 热点池串行化 | 32 线程吞吐 672 TPS **低于** 8 线程的 758（0.89×），p50 从 10.3ms 涨到 45.3ms | 吞吐不随并发度提升，延迟按并发度排队——串行化瓶颈的标准特征 |
| 单线程 TPS ≠ 上限 | 单线程 208 TPS，热点并发 672 TPS（3.2×），远低于 32× 线性 | 单线程 TPS 把锁外开销也算进去了；多线程可把锁外开销与锁内临界区**流水重叠**，临界区真实服务能力 ≈ 670 ops/s |
| 分散多行有效 | 32 池 2670 TPS（×4），p50 回落到 10.7ms | 同一份代码，只是热点不在一行上 |
| 分散收益 8 池即到顶 | 8 池 → 32 池仅 0.99× | 行锁之外还有第二个瓶颈：每笔扣减 5 条 SQL（3 次窗口加锁读 + 1 次条件更新 + 1 次台账插入）+ 连接/ORM 开销 |
| 压力下正确性不变 | 约 10600 次并发扣减：零失败、零超卖、账实一致 | **性能实验同样断言不变量** |

### 12.1 为什么要写这一节（判断依据）

1. **"不超卖"不是免费的**。行锁串行化意味着**单个热门品种池的吞吐上限 ≈ 临界区服务能力**，
   与部署多少实例无关（池子行在数据库里，实例再多也要排队）。
   这是答辩时最容易被追问的一点，现在有数据。
2. **出路及其代价要一起说**。分段池（按班级/批次）能把热点分散开（实测多品种池 ×4），
   但**分段后各段不能互相借用余量**，配额利用率会下降（某班卖完、另一班还有货）——
   这是**一致性-吞吐-利用率**的三方权衡，不是"分段一定更好"。
   而且本项目配额唯一键是 `(quota_date, product_id)`，没有班级这一维，
   真要分段需要改配额维度与分配算法（后续工作 §3.3）。
3. **下一个量级的瓶颈不在锁，在每笔扣减的 SQL 次数**。保质期窗口 3 天导致每笔扣减最多 3 次
   加锁读；先做一次范围读确定窗口内实际存在的池再逐池加锁，可以省掉空读——
   但必须保持"读最新版本再写回"（READ_COMMITTED，见 §5），不能改成快照读预判后再加锁。

## 十三、配送日平移与拒收补送的可靠性约束

> 落地记录见 `../变更记录/2026-09-20-配送日平移与拒收补送.md`。该方案**不新增状态、不新增迁移动作**，
> 规则种子零新增；可靠性约束集中在"幂等闸门、预检、顺序、配额口径"四点。

**1. 平移（`DeliveryTaskService.shiftTasksToDate`）**

- **CAS 即幂等闸门**：第 1 步 `attempt(TASK_CANCEL, 1→4)` 作废原任务；重试时原任务已是 4、CAS 失败即整条跳过，
  因此随后的"合并 quantity（`quantity = quantity + n`）"不会重复执行，**不需要批次表或额外幂等键**。
- **两级预检**（执行前，命中即拒绝整批）：① 源任务存在 `status=2`（奶已出库在途，不能改期）；
  ② 目标日同订单同品种任务存在 `status≠1`（已开始配送，无法安全合并）。
  预检拦下的正是"合并阶段条件更新 0 行"，避免整批因一条失败而回滚。
- **合并失败不得静默跳过**：`UPDATE ... WHERE id=? AND status=1` 影响 0 行必须抛异常回滚；
  静默跳过会得到"原任务已作废、目标日未加量"的静默丢盒。
- **不改 `deliveryEndDate`**：`INV_ORDER_TASK` 按 `(end-start+1)×品种数` 算期望；改 end 会让平移产生的空档日
  被判为缺失、被 `AUTO_REPAIR` 补造任务（凭空多送）。作废行 `deleted=0` 仍占网格组合，
  因此**不改 end 时 `actual ≥ expected`（只报缺失、不报多余）**。
- 原 `delivery_record` 保持未签收、仅改 remark：自动签收兜底按 `task.status=2` 过滤候选集，
  平移后 task=4 不在候选集，不会被误处理；`INV_TASK_RECORD` 只查"任务已完成"，也不受影响。

**2. 期末摊平（`DeliveryTaskService.adjustQuantitiesBeforeDeadline`）**

- **重置而非叠加**：每次重算目标量再条件更新（无变更则跳过），可重复执行且幂等。
- **重置基准 = `1 + 补送量`**（补送量按 `delivery_compensation.target_task_id` 汇总），
  否则会把拒收补送的 +1 抹掉；摊平后量 = `min(基准 + 分配量, 3)`。
- **剩余量 M 的口径**：M = 该订单从今天起 `status ∈ {1,2}` 的 quantity 合计（**含截止日之后的任务**）；
  K = 截止日当天及之前仍待配送的任务数；`M > 2K` 提示延后截止日、`M < K` 提示缩短。
  **截止日之后的待配送任务作废**（盒数提前并入窗口，总数守恒）；不改 end（同上，网格安全）。

**3. 拒收补送（`DeliveryTaskService.rejectRecord` → `generateCompensation`）**

- **顺序是硬约束**：CAS 2→4 → 定位/新建 target → 写补偿台账 → 加量 → 配额 → `enqueue` →
  `completeOrderIfAllTasksDone` **放最后**。零散订单只有 1 个任务，拒收后即全终态；若补送未落库就触发完成判定，
  订单会被判为已完成，30 分钟内被 `INV_PARENT_TERMINAL_CHILD_PENDING` 的 `AUTO_REPAIR` 调 `cancelTask`
  自动作废——补送再次静默丢失。
- **补偿台账唯一键 = 幂等键**：`delivery_compensation.source_task_id` 唯一；撞键必须**抛异常回滚**
  （`@Transactional` 中 `return` 是正常提交，会留下"原任务已取消但无补偿"的静默丢盒）。
- **补送目标日 = 原任务日 + 1**：目标日已有同订单同品种待配送任务则合并 quantity，否则新建。
  若"改期"却不合并而直接新建，会撞 `uk_order_product_date` + `uk_task_no` 并被 `IdempotencyGuard` 静默跳过。
- **配额按订单类型分叉**：仅 `packageId == null`（零散）调 `addCompensationBox`；套餐不占机动池，调了会污染。
  `addCompensationBox` **不校验 `used + boxes <= total`**——补送成本由商家承担，池子已满也允许追加（可能超池）；
  `INV_QUOTA_LEDGER` 只校验 `used == 台账合计`，不受影响。
- **不变量 `INV_TASK_COMPENSATION`（`ALERT_ONLY`）**：判据为 `sign_status=3 AND reject_reason_code IS NOT NULL`。
  退订/缺货取消经 `markRecordRejected` 也把记录置为 `sign_status=3`，但**不写** `reject_reason_code`，
  故不能只按状态判，否则会把它们误报成"拒收未补送"。

## 十四、周末停送与调休例外（配送日历重排）的可靠性约束

> 业务规则见 `../研发规范/项目开发规范.md` §5.4.2（配送日调整），接口见 `接口文档.md` §6，
> 落地与实测见 `../变更记录/2026-09-20-周末停送与调休例外.md` 与 `../实验/实验设计与结果.md` §6.10。
> 本方案**不新增状态、不新增迁移动作**，
> `state_transition_rule` 零新增；约束集中在"落账复用、闸门、上限前推、幂等、例外表权威"五点。

**1. 与平移共用同一套落账骨架（`relocateTask`）**

- 重排**不得另写一套落账逻辑**：`shiftTasksToDate` 与 `calendarRebalance` 都调用私有方法 `relocateTask`，
  顺序固定为「`attempt(TASK_CANCEL, 1→4)` CAS 作废 → 同步 `delivery_record` remark → 合并/新建目标日 →
  `enqueue` 父过程自愈待办」。两套逻辑各自演化必然漂移——上一轮 D7（摊平重复计入补送量）就是算法分叉的产物。
- 平移原有的两条硬约束原样保留：**合并/加量条件更新影响 0 行必须抛异常回滚**（否则"原任务作废 + 目标日未加量"
  会静默丢盒）、**不得更新 `deliveryEndDate`**（改 end 会让 `INV_ORDER_TASK` 把空档日 `AUTO_REPAIR` 补造任务）。

**2. 闸门：开关关闭时必须拒绝，而不是静默不改**

- `sys_config.delivery.weekend.stop` 默认 `false`。为 `false` 时 `calendarRebalance` **直接抛业务异常**。
  若只是"什么都不做"，调用方会以为自己重排成功；拒绝执行让"未生效"对管理员显式可见。

**3. 上限是"继续向前找"而不是"拒绝该条"**

- 首选目标日（周末提前 2 天、停送日提前 1 天）若**不是有效配送日**（停送日 / 未调休的周末）、
  **已有任务非待配送**、或**该订单该品种合并后 > 3 盒**，则继续向前（更早）找，直到满足或超出回溯边界
  （30 天 / 早于今天）才跳过并计入 `messages`。
- 边界必须同时挡住"改到已过去的日期"（`target < today` 直接返回 null）：把奶排到过去的配送日等于静默丢盒。
- 容量判定按 `(订单, 品种)` 维度（合并键即 `uk_order_product_date`），且**合并结果就地写回目标日缓存**，
  否则同一批次内后续同键任务会看不到已并入的盒数而重复新建（撞唯一键 → `createTaskReturning` 返回 null → 抛异常回滚）。

**4. 幂等与守恒**

- 源任务 CAS 作废（1→4）后不再是 `status=1`，重排的候选集自然为空 → 重复执行 `requested` 归零，
  与平移同源（**CAS 本身就是幂等闸门**，不需要批次表）。
- 盒数与任务数守恒：作废只改状态不删行 + 目标日合并/新建一条 → `status∈{1,2}` 的 quantity 合计不变
  （实验十四实测 15 → 15）。
- `delivery_exception` 的唯一键 `uk_exception_date` 由 `IdempotencyGuard.isDuplicate` 翻译为「该日期已存在」，
  **禁止"先查再插"**（多实例下会重复插入）。

**5. 例外表是唯一权威**

- 系统**不做**官方节假日的任何自动推算（各地不同、每年发布、存在连放 13 天等极端情况）；
  管理员维护什么就是什么，不校验"官方日历"。补课日（type=2）当天照常配送，停送日（type=1）并入前一工作日。
- 例外表只允许维护**今天及以后**：历史已配送/已签收的日期属"已提交业务事实"，不可改。

**6. 顺序硬约束**

- 例外维护 → 日历重排 → 期末摊平。摊平晚于重排是硬约束：摊平会把窗口内的待配送量按 `min(基准+分配, 3)`
  重新分配，重排若在其后执行会与摊平结果互相覆盖（设计依据见
  `../设计方案/2026-09-20-周末停送与调休例外-设计方案.md` §6）。

## 十五、退款域（退款单父过程）的可靠性约束

> 业务规则见 `../研发规范/项目开发规范.md` §5.7，接口见 `接口文档.md` §10，
> 设计取舍与备选见 `../设计方案/2026-09-21-退款与毕业清算-设计方案.md`，
> 实现与实测见 `../变更记录/2026-09-21-退款与毕业清算.md` 与 `../实验/实验设计与结果.md` §6.11。
> 退款域是**继支付域之后"长期、多阶段、可失败过程"抽象的第二落点**：复用四层模型与全部既有机制
> （统一迁移出口、规则闸门、CAS、台账、幂等守卫、双通道父聚合、配额台账），不新造第二套。

**1. 顺序硬约束：先抢履约、再计价、后动资金**

执行链固定为：读退款单（校验 2）→ 取 R1 候选期次 → **逐条 `attempt(TASK_CANCEL, 1→4)` 作废，只认返回 true**
→ 按**实际作废成功集合**计价 → 零散单回补配额 → **`require` 推进退款单 2→3** → 回填金额 → `enqueue` 父聚合待办。

- 反过来"先按候选集计价、再作废"会把并发输掉的任务也退钱（候选集是**意图**，作废返回 true 才是**事实**）。
- 与"开始配送"并发时只有一方能在同一任务上成功：作废成功 ⇔ 钱按它结算；作废失败 ⇔ 奶照送、钱不退它。
  **不存在"退了钱又把奶送了"的窗口**（实验十五用例四实测：作废 2 盒 + 已送出 2 盒 = 合同 4 盒，金额 6.00）。

**2. 资金侧必须用 `require`，不能用 `attempt`**

`attempt` 在"规则被管理端停用"时直接返回 false 且**不写台账**（见 §3.2 的短路分支），调用方无法区分
"规则禁止"与"CAS 冲突"。退款单推进（2→3）是资金动作，用 `require`：规则禁止/并发冲突一律抛业务异常、
整体回滚，"没退款"对管理员显式可见。任务作废仍用 `attempt`（跳过 = 已被并发处理，属正常）。

**3. 金额守恒靠公式结构，不靠事后体检**

- **分母是快照不是实时汇总**：`order_info.contract_total_boxes` 在支付展开任务时写入一次、此后不变。
  平移/重排会 CAS 作废但保留任务行、拒收补送会加量或新建任务（**免费盒**）、期末摊平会重写 `quantity`
  ——实时 `SUM(delivery_task.quantity)` 必然漂移，分母一变退款比例就算错。
- **分子只算实际作废成功的盒数，并扣除该任务上的补送盒数**（补送是商家免费补偿、不额外收费，
  计入分子会多退钱；纯补送任务可退 0 盒，直接不进候选集）。
- **累计制防尾差**：套餐单 `本笔 = 实付 × (已退累计盒数 + 本笔盒数) / 合同总盒数 − 已退累计金额`，
  最后再以 `实付 − 已退金额` 为硬上限。实测 10.00 元 3 盒：退 2 盒 = 6.67，与已配送 1 盒的四舍五入值 3.33
  相加恰为 10.00（逐笔独立四舍五入会漂移）。零散单按明细单价精确计价（`pay_amount` 即明细小计之和、无优惠）。
- 金额为 0 时**抛异常回滚**，不允许"任务作废了但没退钱"的静默结果。

**4. 申请幂等靠生成列唯一索引，不靠"先查再插"**

`refund_order.active_order_id` 为生成列：`deleted = 0 AND status IN (1,2)` 时取 `order_id`，否则 `NULL`，
配 `uk_refund_active` 唯一索引 → **同一订单最多一张进行中退款单**，冲突由 `IdempotencyGuard` 翻译为
"已有进行中的退款单"。三个细节：

- 表达式**必须含 `deleted = 0`**：否则被逻辑删除的进行中单会永久占死唯一键（§6 已记录过同类陷阱）；
- `NULL` 不参与唯一键比较 → 终态/删除后自动释放该键，"历史单不阻塞新申请"（已拒绝(4) 可重新申请）；
- 不用"先 `selectCount` 再 `insert`"：多实例下会双双查不到、再双双插入（实验十五用例一实测 8 线程并发申请 → 1 张）。

**5. 可退期次判据的边界（R1）**

"待配送(1) ∪ 缺货取消"。缺货取消的识别必须与 `INV_TASK_COMPENSATION` 同判据
（`task.status=4 AND record.sign_status=3 AND reject_reason_code IS NULL`），因此：

- **平移/重排作废的任务不置记录为拒收**（只改 remark、保持未签收）→ 不会被误判为"没送奶"；
- **退款自己作废的任务同样不置拒收**（否则下次退款会把它当"缺货取消"再退一遍）；
- **真拒收**写了 `reject_reason_code` → 不计入（奶已补送）；
- **已退订(5) 订单整体排除**：退订联动作废的任务与缺货取消同形，计入会与退订的全额退款（R4）重复退钱。

**6. 订单状态零新增，父聚合只走待办通道**

退款不引入"部分退款中"这类中间状态（会污染主状态机与契约矩阵）：作废期次后子任务全部终态，
由 `ProcessPendingTaskJob`（实时）按 `process_reconcile_rule` 的 `ALL_TASKS_TERMINAL → AUTO_COMPLETE`
把 `已支付(2)/配送中(3)` 收敛为 `已完成(4)`；实验关闭定时任务时由实验显式驱动同一入口（实测收敛到 4）。

**7. 退订联动（R4）与依赖方向**

已支付未配送退订在同一事务内补一张**全额、即时（状态 3）**的退款记录：规则表只描述 `1→2→3` 的合法路径，
不存在"无状态→已退款"的迁移，故该记录**建单即终态、不经迁移出口**（退订本身的 `ORDER/CANCEL` 迁移已留痕）。

依赖方向：`order → refund`（退订联动，`@Lazy` 字段注入打破构造期环路），**refund 不反向依赖
`OrderInfoService`**（订单数据经 `OrderInfoMapper`/`PaymentRecordMapper` 读取，父聚合只 `enqueue` 待办），
避免 order ↔ refund 环形依赖。

**8. 毕业清算（R8）**

逐单**独立事务**（经自代理调用 `self.settleOneOrder`，同类内部直调会让 `@Transactional` 失效），
单笔失败不阻塞其余、失败原因回填结果清单。待支付单走专属取消路径（见 §10.1 拒绝"未超时 return false"
与"查单对账补支付"两种副作用）。重复执行只会得到"无可清算订单"（实验十五用例六：第二轮 totalOrders=0）。

**9. 不变量（均为 ALERT_ONLY，涉资金不自动修）**

| 编码 | 判据 | 说明 |
| --- | --- | --- |
| `INV_REFUND_AMOUNT` | 订单 `Σ(refund_amount of status=3) ≤ pay_amount`，且每张已退款单金额 > 0 | 公式结构已保证，本项是"人工改库/旁路写入"的最后防线 |
| `INV_REFUND_TERMINAL` | 已退款单作废的任务（按任务 `remark` 中的退款单号关联）必须保持已取消(4) | 退款域**不落**"退款-任务"明细表，关联靠执行时刻写入任务 remark 的单号，用于发现"作废任务被改回非终态" |

**10. 未做（明确预留）**：真实微信退款（T+1 异步、退款回调、原路退回）不在本期——模拟通道同步完成；
届时 `2→3` 改由回调驱动，并新增 `RefundReconcileJob` 对账超时未回调的 `2` 状态单，与支付侧
`PaymentReconcileJob`（§7.1）完全同构，接口与状态机已预留、只加不改。

## 十六、奶站「当日未送达申报」的可靠性约束

> 业务规则见 `../研发规范/项目开发规范.md` §5.4.1，接口见 `接口文档.md` §6，
> 实现与实测见 `../变更记录/2026-09-21-奶站当日未送达申报.md` 与
> `../实验/实验设计与结果.md` §6.14。

**这一节要解决的问题是"自动兜底把信息态当成了物理态"**，也是全项目里唯一一处
**"系统替人补出业务事实"必须留业务侧例外**的地方：

**1. 问题定义（为什么必须留例外）**

`DeliveryAutoSignJob` 的判定条件是「配送日期 &lt; 今天 + 任务配送中 + 记录未签收」，其中"任务配送中"
来自配送站的**按钮**（信息态），而"奶有没有到校"是**物理态**。两者不一致时（车坏了、路断了、奶没备齐），
兜底会替老师签收，并**同一事务内生成营养摄入记录**——一条虚假签收 + 一份虚假摄入，二者都是
"已提交业务事实"，只能人工清理。

**2. 例外通道：只声明、不改状态**

`delivery_undelivered_report`（`uk_task` 唯一键）：奶站申报"该任务已点已送出，但实际没送到"。
申报**只做标记与待办**：任务保持「配送中」，不新增状态、不写任何状态迁移台账、不触发补偿，
避免"用新状态机解决一个信息缺口"。

**3. 两道闸门（候选集 + 单条入口），缺一不可**

- `listExpiredAutoSignRecordIds` 在候选集里剔除已申报任务（`selectReportedTaskIds`，任务 ID 白名单 IN）；
- `autoSignOne` **再判一次**：候选集是分批取的（每批 ≤200、下一批下一轮），两次取之间可能新增申报
  （奶站在 00:30 前补报），只在候选集过滤会漏——**"兜底一定不会签掉未送达任务"的保证来自单条入口这一判**。

**4. 前置守卫与幂等**

- 只允许「配送中」且配送日不晚于今天的任务申报：待配送的任务本就不在候选集（不会产生虚假签收），
  终态任务兜底不碰，放宽只会把申报变成"随便打标签"；
- 一条任务只允许一条申报，重复申报由唯一键仲裁 → 业务提示（不是"先查再插"）。

**5. 人工处置仍走既有出口**

跟进只写 `handle_status/handle_remark/handle_by/handle_time`，**不改任务与订单状态**；
实际处置必须走签收 / 拒收 / 取消，从而照旧经过统一迁移出口与台账。这是本机制的边界：
**它解决的是"不要自动签"，不解决"该怎么处置"**——后者若需要自动化，属于"人工介入通道"（`4.3`）的范畴，
当前刻意不做，由配送站面板的待跟进列表与顶部提醒条承接。

**6. 已知边界**：申报影响的是**自动签收**这一条兜底路径；任务仍停在「配送中」时，
`INV_ORDER_AGGREGATION` 等不变量看到的是"子任务未终态"（合法中间态），不会误报；
但若长期无人处置，该订单会一直停在「配送中」——**这是刻意接受的代价**（比制造虚假签收更可取），
后续可用体检项或告警把它变成"可见的待办"。

## 十七、家长端「当日豁免」的可靠性约束

> 业务规则见 `../研发规范/项目开发规范.md` §5.4.1，接口见 `接口文档.md` §6，
> 实现与实测见 `../变更记录/2026-09-21-家长端当日豁免.md` 与 `../实验/实验设计与结果.md` §6.15。

**1. 次数上限是"资源"，所以它按配额池那一套写**

`delivery_parent_exemption`（学生 × 自然月一行 `used_count`）。判定用
`SELECT ... FOR UPDATE` + `used_count + 1 <= limit` 条件更新，**不是** `COUNT(明细) < N`——
后者在并发下必然超限（读-改-写），这与 §4 的配额扣减是同一类问题、同一套解法。
计数行不存在时先插入，撞 `uk_student_month` 由唯一键仲裁，再回读行锁累加。

**2. 次数与动作同事务 ⇒ 失败自动回退**

`parentExemptToday` 是唯一事务边界：抢次数 → 逐条 `doCancelTask` → 回补配额。
任何一步抛异常（含并发下某个任务已被送出、CAS 失败）都会整体回滚，**不会出现"次数扣了但没豁免"**。
家长重试即可——这是"宁可让他再点一次，也不要留下对不上账的次数"。

**3. 复用取消出口，不新写第二套**

豁免调用的是 `cancelTask` 与平移/补送共用的 `doCancelTask`（规则闸门 + CAS + 迁移台账 + 父过程自愈待办 +
签收记录联动置拒收）。因此豁免**天然留痕、天然不绕过状态机**，且契约矩阵/实验五的"每次迁移都留痕"
不变量对它自动成立。若将来新增第三种"取消"入口，仍应走这个私有出口。

**4. 口径与边界（必须写清）**

- 只豁免「**今天 + 待配送(1)**」：已送出(2) 的奶在途（取消等于抹掉已出库记录），终态无需豁免；
- 配额回补按「订单 × 品种」整份（`restoreForOrderProductDate`，与缺货取消同一口径）。零散订购是单日订单，
  因此等于该日份额；**若该订单此前发生过拒收补送加量，回补额会包含补送盒数**——这是既有的台账口径限制
  （台账键是 `(订单, 品种, 池子日期)`，不含任务），已如实记录，不在本次改动里扩大台账维度；
- 学期套餐不占配额，回补为 no-op；
- 上限配成 `0` 即**关闭该能力**（管理端可随时关停，不需要发版）。

**5. 未做（明确边界）**：豁免不产生任何"补送"义务，也不自动退款——家长放弃的是当天这一份；
若家长要求退钱，走既有的退款域（`/api/refund/**`）。**也不做"撤回豁免"**（豁免后当天任务已作废，
让家长撤回答易与配送站动作打架）。

## 十八、仓库余量台账（供给侧）的可靠性约束

> 业务规则见 `../研发规范/项目开发规范.md` §5.9，接口见 `接口文档.md` §11，
> 设计取舍与评审修订见 `../设计方案/2026-09-21-仓库余量与出库边界-设计方案.md`（口径以该文 §11 为准）。

**1. 台账恒等式与"只增不改"**

`W(品种) = ΣIN + ΣIN_BACK + ΣINIT + ΣADJ(带符号) − ΣOUT`，任何时刻 `W ≥ 0`。
台账与 `process_transition_log` 同一原则：**只允许新增与查询**，业务代码不得更新或删除；
记错走反向 `ADJ` 冲销（两条留痕）。因此本模块**不提供**修改/删除接口，`ADJ` 是唯一纠错通道。

> `ADJ` 的 `quantity` **带符号**：若按"恒为正向、方向由类型表达"建模，"反向 ADJ 冲销"
> 在数学上无解（原设计 `−ΣADJ` 即有此漏洞，见设计方案 §11.2-5）。

**2. 三条写入路径的事务边界：与业务动作同事务**

| 路径 | 挂载点 | 幂等键 |
|---|---|---|
| `OUT` 送出 | "开始配送"的同一事务：`startDelivery` 与 `batchStartDelivery` **共用收口** `recordOutStock` | `uk_biz_ref(biz_type, ref_id)`：一个任务只出一次库 |
| `IN_BACK` 退回 | `rejectRecord`（**用户入口**）的同一事务 | `uk_biz_ref`：一条签收记录只退回一次 |
| `IN` 到货 | `receipt`（人工登记） | `uk_in_receipt(biz_type, biz_date, product_id, receipt_no)`：双击与脚本重跑都只落一行 |

- **钩子只能挂"开始配送"的共享收口，不能只挂批量**：单条与批量走同一个 `casDispatch`（1→2），
  只挂批量会漏记全部单条送出。
- **`IN_BACK` 钩子只能挂 `rejectRecord`，禁止挂 `markRecordRejected`**：
  后者是"任务作废时把未签收记录置 `sign_status=3`"的共享助手，缺货取消（`:1138`）与退订（`:1192`）
  都在调用它——挂错会让"奶根本没被拒收"的作废动作凭空多记退回。
- 顺序遵循既有约束：**先 CAS 抢占状态，再做副作用（写台账）**，落败方不会入账。

**3. 发行封顶（R5′）是一个 check-then-act，必须加锁**

设配额走 `DailyQuotaServiceImpl.setQuotaBatch` → `WarehouseService.requireIssuanceCoverage`：

```text
需求(p, D) = Σ_{池: quota_date ∈ [D−2, D]} GREATEST(total−used, 0)
           + Σ_{任务: status=1, delivery_date ≤ D} quantity        ≤  W(p)
```

- **W 的聚合读是无锁的**，两个并发请求给同品种不同日期设池会各自读到旧 W 后**双双通过**；
  因此在同一事务内先 `SELECT ... FOR UPDATE` 锁 `product` 行，把同品种发行串行化。
  **加锁顺序固定 `product → daily_quota`**（扣减路径只锁 `daily_quota` 行），不会成环。
- **任务口径必须含逾期**（`delivery_date ≤ D`）且**含全部订单类型**，但**不含 `status=2`**：
  池口径含结转池（D−2、D−1 的未售），只算当天会让"早先已售未送出"与结转池对同一批实物重复计数
  （实测可超发）；套餐不经配额池但实物同仓，只算套餐会漏掉"已售未送出的零散"（设计与评审见 §11.2）。
- 窗口复用 `QuotaConstants.SHELF_DAYS`（**唯一来源**）：仓库侧另立窗口会造成
  "扣减说能卖、封顶说不能"的静默错账。
- **额度发行时已封顶 ⇒ 支付扣减路径零改动**，不新增热点行（见 §4、§12 的代价讨论）。

**4. 四条不变量（`module/warehouse/invariant/`）**

| 编码 | 探测口径 | 处置 | 为什么是这个等级 |
|---|---|---|---|
| `INV_LEDGER_OUT_TASK` | 双向：① `dispatch_time IS NOT NULL` 的任务缺 OUT 行；② OUT 行对应的任务无 `dispatch_time` | ① `AUTO_REPAIR`；② `ALERT_ONLY` | ①漏记可逆且由既有事实（`dispatch_time`）唯一推导，补写 `biz_date = DATE(dispatch_time)`；②多做一条出库的方向取决于真实对账结果，属人工判断 |
| `INV_WAREHOUSE_NONNEG` | 每品种 `W < 0` | `ALERT_ONLY` | 方向不确定（可能该补 IN、也可能该冲销 ADJ），自动补账＝凭空造事实 |
| `INV_LEDGER_REFUND_LINK` | 真拒收（`sign_status=3 AND reject_reason_code IS NOT NULL`）的记录缺 IN_BACK | `ALERT_ONLY` | 退回是否可回仓涉实物状态（破损/变质），属业务判断 |
| `INV_WAREHOUSE_COVERAGE` | 每品种 `W < 当期可卖额度 + 待送出任务` | `ALERT_ONLY` | 自动修＝自动下调他人已设配额，属业务决策；且与"已售出的额度"冲突 |

- **判据必须是 `dispatch_time` 而不是任务状态**：`4-已取消` 是多来源终态，
  缺货取消 / 家长豁免 / 平移作废 / 期末摊平**全是 1→4 且从未送出**——按 `status ∈ {2,3,4}`
  判"应已出库"会让体检**自己补写出大批假出库行并把 W 打成负数**。
- **`INV_LEDGER_REFUND_LINK` 必须带 `reject_reason_code`**：与 §7 的 `INV_TASK_COMPENSATION`
  同源（任务作废联动置 `sign_status=3` 时不写原因分类），否则会把"缺货取消/退订"误报成"拒收未入账"。
- **依赖声明（`dependsOn`）**：`INV_WAREHOUSE_NONNEG` 与 `INV_WAREHOUSE_COVERAGE` 都依赖
  `INV_LEDGER_OUT_TASK` —— 补记 OUT 会**降低** W，覆盖不足必须在"出库账补全之后"判定，
  否则会拿虚高的余量去比对需求而漏报（这是 §7.2"修复改变他人判定依据必须声明依赖"的第三个实例）。
- 同时**持续验证**与**发行闸门**并存不是重复：闸门只在发行那一刻生效，
  并发绕过、规则停用、直接改库、发行后任务才生成等路径都不会被闸门看到。

**5. 多实例**

台账写入一律靠唯一键仲裁（`uk_biz_ref` / `uk_in_receipt`）+ 应用层 `IdempotencyGuard` 翻译冲突，
**不引入实例本地状态**；`batch-start` 在多实例并发下：CAS 只一方赢（另一方不写 OUT），
即使两方都写，`uk_biz_ref` 也保证一个任务只出一行。到货登记双击/双实例 → `uk_in_receipt` 仲裁。
不变量修复（`AUTO_REPAIR` 补 OUT）本身幂等，多实例重复体检只多花算力。

**6. 上线与变更检查清单**

1. `schema.sql` §11 / `sql/2026-09-21-warehouse-ledger.sql` 建表；实验库同步重建（见
   `../实验/实验环境与运行说明.md` §3.4）；
2. 逐品种登记上线时的实物存量（走「到货登记」界面，凭证号填「期初」；见
   `../使用说明/管理员操作手册.md` §3.8）；
3. 跑增量脚本 §3 的只读核查（逐池日确认 `W ≥ 需求`；确认无品种 `W < 0`）；
4. 改动词及台账口径时，必须同步：`WarehouseService.requiredStock`/`requireIssuanceCoverage`、
   `INV_WAREHOUSE_COVERAGE` 的 SQL、`sql/2026-09-21-warehouse-ledger.sql` 的核查 SQL——
   三处是同一公式的三份落地，任一处漂移都会造成"闸门放过、体检报错"或反之。

**7. 未做（明确边界）**：效期预警、先进先出、盘点、库位、采购订货与结算（属 ERP 责任域）；
**出库不做余额校验**（送出是物流事实：缺货只体现为 W 变小与告警，不由系统拒绝配送）；
`OUT` 的 `biz_date` 取任务配送日期、`IN_BACK` 取拒收日，与实例时钟无关。
