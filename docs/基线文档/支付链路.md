# 支付链路说明

本文档描述学生奶订购系统的支付链路。家长端（小程序）走**微信支付模拟链路**（预下单 → 确认扣款 → 微信异步回调 → 前端轮询），管理端与定时续订走**同步模拟支付**。两条链路的订单状态流转与库存/流水约束完全一致。

## 1. 链路一：微信支付模拟链路（小程序家长端）

模拟微信支付平台的三个角色：**商户后端**（本系统）、**微信支付平台**（`WechatPaySimulator`，内存预支付单 + 签名）、**用户微信客户端**（小程序弹窗 + 模拟确认接口）。

```text
小程序                      商户后端                         模拟微信支付平台
  │ ① POST /api/order/prepay/{id}                              │
  │ ────────────────────▶ 校验归属/状态/金额                    │
  │                          作废旧待支付流水，写新待支付流水    │
  │                          ──── 统一下单 ────────────────────▶│ 签发 prepayId
  │ ◀──── 返回调起凭证（prepayId/金额/订单号/签名参数）──────────│
  │                                                             │
  │ ② 弹出「微信支付（模拟）」确认框                             │
  │ ③ POST /api/mock/wechat/pay-confirm {prepayId}              │
  │ ─────────────────────────────────────────────────────────▶ │ 用户确认扣款
  │                                                             │ ④ 异步 POST 签名报文
  │                          ◀──── ⑤ POST /api/pay/wechat/notify（带 Wechatpay-Signature）────
  │                          验签 → 幂等校验（状态/金额）        │
  │                          扣库存+流水 → 支付流水置成功        │
  │                          订单 1→2（payTime/transactionId）  │
  │                          应答 200 "SUCCESS" ──────────────▶ │
  │ ⑥ 轮询 GET /api/order/{id}（1s×10次）                       │
  │ ────────────────────▶ status=2 → 展示支付成功               │
```

涉及代码：

| 环节 | 文件 |
| --- | --- |
| 小程序支付流程 | `miniprogram/utils/pay.js`（`requestWechatPay`）、`miniprogram/api/pay.js` |
| 预下单接口 | `OrderController.prepay` → `OrderInfoService.prepayOrder` |
| 微信支付平台模拟器 | `module/order/pay/WechatPaySimulator`、`WechatPayMockProperties`（`wxpay.mock.*` 配置） |
| 用户确认扣款（模拟） | `MockWechatPayController`（`/api/mock/wechat/pay-confirm`） |
| 微信回调通知 | `WechatPayNotifyController`（`/api/pay/wechat/notify`）→ `OrderInfoService.handleWechatPayNotify` |
| 前端页面入口 | 订单详情/订单列表/下单确认页（order-detail / order-list / order-create） |

### 关键机制

- **签名**：模拟微信用 `wxpay.mock.api-key` 对报文做 HMAC-SHA256；回调报文放在 `Wechatpay-Signature` 头，商户端先验签再处理，验签失败直接拒绝。
- **回调异步化**：确认扣款后由模拟器线程延迟（默认 500ms）POST 通知地址，真实体现「微信主动回调」；通知地址为 `wxpay.mock.notify-url`（默认 `http://127.0.0.1:8090/...`）。
- **幂等**：回调处理前检查订单状态——已支付及之后的状态直接返回 SUCCESS（微信重试通知不会重复扣库存/重复写流水）。
- **金额核对**：回调金额必须与订单应付金额一致，不一致拒绝处理。
- **重复发起支付**：每次预下单把该订单旧的「待支付」流水作废（置为 3-失败），再写新待支付流水；用户取消支付弹窗后订单保持待支付，可从订单列表/详情重新支付。
- **取消支付**：待支付订单可在小程序订单列表/详情「取消支付」，复用 `cancelOrder`（状态 → 5-已退订，取消原因记「用户取消支付」），同时作废待支付流水；若回调在取消后才到达，`handleWechatPayNotify` 对已取消订单拒绝处理（返回 FAIL），不会把已取消订单置为已支付。
- **鉴权**：notify 与 mock 接口在 `SecurityConfig` 中免 JWT（微信服务器无登录态），可信性由验签保证。
- **预支付单存储**：保存在模拟器内存中，后端重启后未完成支付的预支付单失效，重新发起支付即可。

## 2. 链路二：同步模拟支付（管理端 + 定时续订）

`POST /api/order/pay/{id}` → `OrderInfoService.payOrder`（`@Transactional`）：

1. 数据范围校验（家长仅本人孩子、班主任仅本班、管理员不限）+ 状态机校验（仅「待支付」可支付）+ 金额非空校验；
2. 逐明细扣库存（`InventoryService.deductForOrder`，写 `inventory_record` 出库流水）；
3. 写 `payment_record`（status=2，流水号 `MOCK+时间戳+随机数`）；
4. 订单状态 1→2（`markOrderPaid`：status/payTime/payType/transactionId）。

适用场景：Web 管理端「支付」按钮（管理员操作）、定时续订任务创建新订单后的自动支付。小程序端已不再调用该接口。

## 3. 两条链路共同的不变量（改动时必须保持）

1. 订单状态只能经 `OrderInfoService` 流转，支付仅允许 1→2，取消（待支付/已支付）只允许 →5；`markOrderPaid` 是「置为已支付」的统一出口。
2. 扣库存、写/更新支付流水、更新订单状态必须在同一事务内完成。
3. 库存变更必须经 `InventoryService` 并保留 `inventory_record` 流水。
4. 支付流水金额不允许为 `NULL`；回调金额必须与订单应付金额一致。
5. 回调处理必须幂等（重复通知不产生重复扣库存/重复流水）。

## 4. 已知风险与改进建议

| 风险 | 说明 | 级别 | 建议 |
| --- | --- | --- | --- |
| 并发竞态 | 「查状态 → 更新」非原子：两个并发回调/支付请求理论上可同时读到「待支付」。 | 低（模拟环境单用户） | 状态更新改条件更新（`UPDATE ... WHERE status=1`）或乐观锁；`payment_record` 对 `order_id + status=2` 加唯一约束兜底。 |
| 模拟链路上线风险 | `/api/mock/wechat/**` 与模拟器仅适用于本地演示。 | 提醒 | 对接真实微信支付时移除模拟链路，替换为微信支付 SDK + 商户证书 + 平台证书验签。 |
| 预支付单在内存 | 后端重启丢失未完成预支付单（重新发起支付即可恢复）。 | 低 | 可持久化到表或 Redis。 |
| 支付不锁库存 | 待支付订单不占库存，支付时才扣减，库存不足则回调失败、订单保持待支付。 | 设计如此 | 如需改善可在下单时预占/超时释放。 |
