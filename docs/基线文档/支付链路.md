# 支付链路说明

本文档描述学生奶订购系统的支付链路。家长端（小程序）走**微信支付模拟链路**（预下单 → 确认扣款 → 微信异步回调 → 前端轮询），Web 管理端走**同步模拟支付**。两条链路的订单状态流转与配额/流水约束完全一致。

## 1. 链路一：微信支付模拟链路（小程序家长端）

模拟微信支付平台的三个角色：**商户后端**（本系统）、**微信支付平台**（`WechatPaySimulator`，内存预支付单 + 签名）、**用户微信客户端**（小程序弹窗 + 模拟确认接口）。

```text
小程序                      商户后端                         模拟微信支付平台
  │ ① POST /api/order/prepay/{id}                              │
  │ ────────────────────▶ 校验归属/状态/金额                    │
  │                          作废旧待支付流水，写新待支付流水    │
  │                          ──── 统一下单 ────────────────────▶│ 签发 prepayId
  │ ◀──── 返回调起凭证（prepayId/金额/订单号/签名参数）──────────│
  │                                                             │
  │ ② 弹出「微信支付（模拟）」确认框                             │
  │ ③ POST /api/mock/wechat/pay-confirm {prepayId}              │
  │ ─────────────────────────────────────────────────────────▶ │ 用户确认扣款
  │                                                             │ ④ 异步 POST 签名报文
  │                          ◀──── ⑤ POST /api/pay/wechat/notify（带 Wechatpay-Signature）────
  │                          验签 → 幂等校验（状态/金额）        │
  │                          抢占订单状态 1→2（CAS，落败方回滚） │
  │                          扣配额 + 支付流水置成功             │
  │                          应答 200 "SUCCESS" ──────────────▶ │
  │ ⑥ 轮询 GET /api/order/{id}（1s×10次）                       │
  │ ────────────────────▶ status=2 → 展示支付成功               │
```

涉及代码：

| 环节 | 文件 |
| --- | --- |
| 小程序支付流程 | `miniprogram/utils/pay.js`（`requestWechatPay`）、`miniprogram/api/pay.js` |
| 预下单接口 | `OrderController.prepay` → `OrderInfoService.prepayOrder` |
| 微信支付平台模拟器 | `module/order/pay/WechatPaySimulator`、`WechatPayMockProperties`（`wxpay.mock.*` 配置） |
| 用户确认扣款（模拟） | `MockWechatPayController`（`/api/mock/wechat/pay-confirm`） |
| 微信回调通知 | `WechatPayNotifyController`（`/api/pay/wechat/notify`）→ `OrderInfoService.handleWechatPayNotify` |
| 前端页面入口 | 订单详情/订单列表/下单确认页（order-detail / order-list / order-create） |

### 关键机制

- **签名**：模拟微信用 `wxpay.mock.api-key` 对报文做 HMAC-SHA256；回调报文放在 `Wechatpay-Signature` 头，商户端先验签再处理，验签失败直接拒绝。
- **回调失败重试（2026-09-14）**：非 HTTP 200 或应答非 `SUCCESS` 一律视为失败，按指数退避自动重试（1s/2s/4s/8s/16s，`wxpay.mock.notify-max-retries` 默认 5 次、`notify-retry-base-ms` 基数 1s），对齐微信重试节奏；重试耗尽后支付单仍保留在微信侧存储，等待商户查单补偿。
- **主动查单（2026-09-14）**：`GET /api/order/{id}/pay-result`——待支付订单向模拟微信侧查单，用户已扣款但回调丢失时走回调同路径补偿落账；前端支付轮询超时的兜底入口。
- **对账补偿任务（2026-09-14）**：`PaymentReconcileJob` 每 5 分钟扫描「存在待支付流水且已过 2 分钟在途窗口」的订单逐单查单补偿；系统参数 `order.pay.reconcile.enabled` 可关闭。
- **支付超时自动取消（2026-09-14）**：`OrderTimeoutCancelJob` 每 5 分钟扫描超时候选订单，超时锚点取最近一次待支付流水时间（防误杀刚重新发起支付的订单）；取消前先查单——已扣款转补偿落账，绝不取消已付款订单；阈值 `order.pay.timeout.minutes`（默认 15 分钟，管理端在线可改）。
- **CAS 幂等落账（2026-09-14）**：`markOrderPaid` 改为条件更新（`WHERE status=待支付`），并发双回调/回调与取消竞争仅一方成功；失败方回滚本轮全部写入（含配额扣减），由微信重试走幂等快速路径收口。
- **状态迁移规则表（2026-09-14）**：全部订单状态迁移经 `state_transition_rule` 白名单校验（管理端「系统管理-状态机规则」在线配置，未配置的迁移一律禁止），支付/取消/配送联动/完成均可在线启停。
- **回调异步化**：确认扣款后由模拟器线程延迟（默认 500ms）POST 通知地址，真实体现「微信主动回调」；通知地址为 `wxpay.mock.notify-url`（默认 `http://127.0.0.1:8090/...`）。
- **幂等**：回调处理前检查订单状态——已支付及之后的状态直接返回 SUCCESS（微信重试通知不会重复扣配额/重复写流水/重复展开任务）；未支付的并发回调则由「先 CAS 抢占状态」保证只有一个执行者进入副作用阶段。
- **金额核对**：回调金额必须与订单应付金额一致，不一致拒绝处理。
- **重复发起支付**：每次预下单把该订单旧的「待支付」流水作废（置为 3-失败），再写新待支付流水；用户取消支付弹窗后订单保持待支付，可从订单列表/详情重新支付。
- **取消支付**：待支付订单可在小程序订单列表/详情「取消支付」，复用 `cancelOrder`（状态 → 5-已退订，取消原因记「用户取消支付」），同时作废待支付流水；若回调在取消后才到达，`handleWechatPayNotify` 对已取消订单拒绝处理（返回 FAIL），不会把已取消订单置为已支付。
- **鉴权**：notify 与 mock 接口在 `SecurityConfig` 中免 JWT（微信服务器无登录态），可信性由验签保证。
- **预支付单存储**：保存在模拟器内存中，后端重启后未完成支付的预支付单失效，重新发起支付即可。

## 2. 链路二：同步模拟支付（Web 管理端）

`POST /api/order/pay/{id}` → `OrderInfoService.payOrder`（`@Transactional`）：

1. 数据范围校验（家长仅本人孩子、班主任仅本班、管理员不限）+ 状态机规则校验（仅「待支付」可支付）+ 金额非空校验；
2. **先抢占状态**：经过程层统一出口做 CAS（`待支付 → 已支付`）并写迁移台账，落败方立即中止；
3. 零散订购按品种扣减当日机动配额（`DailyQuotaService.deduct`：行锁读 + 条件更新，并写 `daily_quota_usage` 台账；学期套餐不占配额）；
4. 写 `payment_record`（status=2，流水号 `MOCK+时间戳+单调序列号`）；
5. 展开整个配送周期的配送任务与签收记录（幂等）。

> 第 2 步必须在第 3、4 步之前：并发下只有一个执行者能抢占到状态，配额扣减与流水写入因而只发生一次。
> 反过来「先做副作用、再 CAS」会让落败方已经扣了配额、写了流水才失败，并发下还会互相撞业务唯一键
> （实验二暴露，见 `../实验/实验设计与结果.md` 缺陷 D4）。

适用场景：Web 管理端「支付」按钮（管理员操作）。小程序端走链路一（微信支付模拟链路），不调用该接口。

## 3. 两条链路共同的不变量（改动时必须保持）

1. 订单状态只能经过程层统一出口 `ProcessTransitionExecutor` 迁移：支付仅允许 1→2，取消（待支付/已支付）只允许 →5；迁移必须是以原状态为条件的 CAS 条件更新。
2. 状态抢占、配额扣减、写/更新支付流水、展开配送任务必须在同一事务内完成，且**先抢占状态、再执行副作用**。
3. 资源变更只能经 `DailyQuotaService`：扣减必须「行锁读配额池 + 条件更新 + 写 `daily_quota_usage` 台账」，退订回补必须按台账回到原池子。
   （历史说明：早期版本的 `InventoryService` / `inventory_record` 已于 2026-09-12 随订购模式重构删除，现由「每日机动配额 + 扣减台账」承担，见 `../变更记录/2026-09-12-订购模式重构（学期套餐与每日机动配额）.md`。）
4. 支付流水金额不允许为 `NULL`；回调金额必须与订单应付金额一致。
5. 回调处理必须幂等：已支付走幂等快速路径直接应答，「迁移落账」由 CAS 保证只成功一次；重复通知不产生重复扣配额、重复流水或重复任务。
6. 每次状态迁移都写入 `process_transition_log` 迁移台账，成功与 CAS 冲突可区分（台账为「尽力而为」的可观测记录，写入失败不影响业务结果）。

## 4. 已知风险与改进建议

| 风险 | 说明 | 级别 | 建议 |
| --- | --- | --- | --- |
| 并发竞态 | ~~「查状态 → 更新」非原子~~ **已于 2026-09-14 修复**：订单状态迁移全部改为 CAS 条件更新（`UPDATE ... WHERE status=原状态`），并发双回调/回调与取消仅一方成功，失败方整体回滚。 | 已修复 | 后续可为 `payment_record` 增加 `order_id + transaction_id` 唯一约束进一步兜底。 |
| 取消后回调到达 | 订单被取消（用户取消/超时取消）后回调才到：拒绝处理，模拟微信按退避重试直至耗尽。真实链路对应「关单+退款」。 | 低（模拟环境无资金流） | 对接真实支付时在此路径触发退款流程。 |
| 模拟器内存态与对账 | 支付单存模拟器内存：进程存活期间查单/对账可靠；重启后丢失（未完成预支付单本就失效，订单交由超时任务正常取消）。 | 低 | 可持久化到表或 Redis。 |
| 模拟链路上线风险 | `/api/mock/wechat/**` 与模拟器仅适用于本地演示。 | 提醒 | 对接真实微信支付时移除模拟链路，替换为微信支付 SDK + 商户证书 + 平台证书验签。 |
| 预支付单在内存 | 后端重启丢失未完成预支付单（重新发起支付即可恢复）。 | 低 | 可持久化到表或 Redis。 |
| 支付不锁库存 | 待支付订单不占库存（配额），支付时才扣减，配额不足则回调失败、订单保持待支付。 | 设计如此 | 如需改善可在下单时预占/超时释放。 |

## 5. 过程层留痕与对账补偿

支付是「状态迁移 + 副作用」最密集的一条链路，因此它的可靠性由过程层与兜底层共同保证：

| 能力 | 说明 | 落点 |
| --- | --- | --- |
| 统一迁移出口 | 所有订单状态迁移收口到 `ProcessTransitionExecutor`：规则校验（`state_transition_rule` 白名单）+ CAS 条件更新 + 迁移留痕 | `com.milk.order.process` |
| 迁移台账 | 每次迁移写 `process_transition_log`（场景/动作/主体/起止状态/结果/操作人）。台账记录的是**已提交的业务事实**：在事务内因异常中止时，冲突记录随事务一起回滚 | 同上 |
| 支付对账补偿 | 每 5 分钟扫在途待支付流水，主动查单；回调丢失时走回调同一路径补偿落账 | `PaymentReconcileJob`、`reconcilePendingPayments` |
| 超时兜底对账 | 超时取消前先查单：已扣款则转补偿落账，**绝不取消已付款订单**；超时锚点取最近一次待支付流水时间，防误杀刚重新发起支付的订单 | `OrderTimeoutCancelJob`、`cancelTimeoutOrder` |
| 过程聚合对账 | 每 10 分钟修复「父订单状态与子任务集合不一致」的漂移（支付后任务展开与状态联动可能的写入丢失） | `OrderProcessReconcileJob`、`reconcileOrderAggregation` |

可靠性机制的设计口径与不变量见 `可靠性设计.md`；量化验证（20 次并发重复回调只落账一次等）见
`../实验/实验设计与结果.md`。
