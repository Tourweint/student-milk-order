# 系统架构

## 技术栈

### 后端
- Java 17
- Spring Boot 2.7.18
- Spring Security（认证授权）
- MyBatis-Plus 3.5.3（数据访问）
- MySQL 8 / MariaDB 10.6+（数据库，实测环境为 MariaDB 12.1）
- 事务隔离级别：`READ_COMMITTED`（显式统一，见 `可靠性设计.md` 第五节）
- JWT（无状态认证）
- Apache POI（Excel 导入导出）
- Spring Scheduler（定时任务）

### 前端（Web 管理端）
- Vue 3 + TypeScript
- Vite（构建工具）
- Element Plus（UI 组件库）
- ECharts（数据可视化）
- Axios（HTTP 客户端）
- Pinia（状态管理）
- Vue Router（路由）

### 移动端（微信小程序，后续开发）
- 微信小程序原生或 uni-app
- 共用后端 RESTful API

## 系统分层

```
┌─────────────────────────────────────────────┐
│              表现层 (Presentation)            │
│  Web 管理端 (Vue3)  │  微信小程序             │
├─────────────────────────────────────────────┤
│              控制层 (Controller)              │
│         Spring Boot RESTful API              │
├─────────────────────────────────────────────┤
│              业务层 (Service)                 │
│     10 大业务模块的业务逻辑处理               │
├─────────────────────────────────────────────┤
│              持久层 (Mapper)                  │
│         MyBatis-Plus + MySQL/MariaDB         │
└─────────────────────────────────────────────┘
```

在业务层之下，还存在一组**横切关注点**（业务过程建模与可靠执行）。它们不是业务模块，
而是被多个业务模块共同依赖的机制层，因此独立成顶层包：

```
┌─────────────────────────────────────────────┐
│             业务层                           │  订单 / 配送 / 配额 / 营养 ...
├─────────────────────────────────────────────┤
│             过程层     com.milk.order.process │  状态机 / 迁移规格 / 迁移台账
├─────────────────────────────────────────────┤
│             可靠性层   com.milk.order.reliability │ 幂等守卫（业务唯一键）
├─────────────────────────────────────────────┤
│             兜底层     module.*.job           │  超时检测 / 定时任务 / 自动恢复
└─────────────────────────────────────────────┘
```

设计动机、四层模型与代码落点见 `业务过程与可靠执行模型.md`；机制细节见 `可靠性设计.md`。

**状态迁移不变量**：业务对象的 `status` 字段只能经 `ProcessTransitionExecutor` 迁移，
且必须是「以原状态为条件」的 CAS 条件更新；禁止读状态后无条件下全量更新。

## 订单状态机

```
待支付 ──支付──→ 已支付 ──开始配送──→ 配送中 ──签收完成──→ 已完成
  │                │（退款闸门：开始配送后不可自助退订）      ↑
  └──取消/超时──→ 已退订 ←────────退订（仅未开始配送可退）──┘
```

配送任务开始配送（配送站"今日已送出"或单条开始）会联动订单进入配送中，作为退款闸门；开始配送后的退费走线下处理。

### 状态迁移的合法性

订单与配送任务两套状态机的迁移是否允许，由 `state_transition_rule` 规则表（**白名单语义**）
驱动，管理端可在线调整而无需重新发布；未配置的组合一律禁止。所有迁移经
`ProcessTransitionExecutor` 执行（规则校验 + CAS 条件更新 + 迁移留痕），详见
`业务过程与可靠执行模型.md`。此外，配送记录（`delivery_record.sign_status`）作为任务下挂的子状态机，
只做 CAS 与留痕、不纳入规则表（判定标准：是否可被外部独立发起）。

新增状态或动作时**必须同步补规则种子**（`src/main/resources/sql/data.sql`），否则该迁移会被拒绝。

### 父子状态聚合

订单的宏观状态由子过程（配送任务）聚合决定，而不是由某个子任务直接改写：

| 子过程 | 父状态推进 | 落点 |
| --- | --- | --- |
| 任务开始配送 | 已支付 → 配送中 | `OrderInfoService.markDeliveringIfPaid` |
| 任务全部到达终态 | 配送中 → 已完成 | `OrderInfoService.completeOrderIfAllTasksDone` |
| 父子状态不一致 | 对账补偿修复 | `OrderProcessReconcileJob` → `reconcileOrderAggregation` |

### 定时兜底任务

| 任务 | 周期 | 作用 |
| --- | --- | --- |
| `OrderTimeoutCancelJob` | 5 分钟 | 待支付超时自动取消（取消前先查单对账，绝不取消已付款订单） |
| `PaymentReconcileJob` | 5 分钟 | 在途待支付流水主动查单，回调丢失时补偿落账 |
| `OrderProcessReconcileJob` | 10 分钟 | 修复父订单状态与子任务集合不一致的漂移 |
| `DeliveryAutoSignJob` | 每天 00:30 | 超时未签收自动签收（复用人工签收流程） |

全部任务可用 `app.scheduler.enabled=false` 整体关闭（实验与测试环境使用）。
