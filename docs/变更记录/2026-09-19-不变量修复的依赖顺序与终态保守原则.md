# 2026-09-19 不变量修复的依赖顺序（方案二）与「终态不补造历史」原则

## 背景

同日《组合状态守卫》按方案一加固了「修复动作之间缺少顺序」的缺口：新增组合状态守卫、
让组合异常一轮体检内收敛。当时明确留了一个边界：

> 这是"把问题变可见并收敛"，不是"消除根因"——修复动作之间的顺序依赖仍未声明，
> 仍可能出现"先补上、再作废"绕一圈才收敛的过程。

本次实施 `docs/论文/后续扩展方案.md` §2.5 的**方案二**，把根因去掉；
方案三（由约束集合求解一致状态）继续保留为展望。

## 主要改动

### 1. 不变量声明依赖，体检按拓扑序执行

- `ProcessInvariant.dependsOn()`：声明「本项必须在哪些编码之后执行」（默认无依赖）；
- `ProcessInvariantScanner.orderedInvariants()` 由"按编码字典序"改为**按声明依赖的拓扑序**
  （Kahn 式逐轮选取：每轮取"依赖已满足"的最小编码，因此**确定且可复现**）；
  依赖引用未注册编码、编码重复、依赖成环三种情况全部**直接失败**——
  配置错误不能静默退化成任意顺序，否则体检结果不可解释；
- 新增 `resolvedExecutionOrder()` 暴露当前顺序：**顺序本身是设计的一部分**，
  不应该只存在于一次运行的日志里，因此要可测、可审阅。

声明了两条依赖：

```text
INV_ORDER_TASK（补子过程网格）
    → INV_ORDER_AGGREGATION（判父过程聚合）
        → INV_PARENT_TERMINAL_CHILD_PENDING（判组合：父终态不应有非终态子过程）
```

理由：父聚合的判定依据是「子任务是否全部终态」，而这个集合会被"补网格"改变。
顺序反了，**体检自己就会制造**「已完成订单 + 待配送任务」。

### 2. `INV_ORDER_TASK` 按订单状态分级：终态只告警、不补造历史

| 订单状态 | 处置 | 理由 |
| --- | --- | --- |
| 已支付 / 配送中（进行中） | `AUTO_REPAIR`：补全网格 | 网格缺口会直接影响后续配送与聚合 |
| 已完成 / 已退订（终态） | `ALERT_ONLY`：只报出来 | 缺口属于"历史被改过"；**补造历史是错的**——它会给一个已结束的订单造出待配送任务，正是组合异常的产生源 |

同时探测范围由 `status IN (2,3)` 扩到 `(2,3,4,5)`：
终态订单的网格也纳入**检测**（覆盖面不减），只是**不自动修**。
`repair()` 里再加一层兜底（终态直接返回 false），避免调用方绕过等级直接调用修复时补造历史。

**这是本项目的"保守原则"的第二次体现**：第一次是涉资金不修改，这次是**不为了把数字补整齐去编造历史**。

### 3. 契约矩阵新增第四项：执行顺序

`src/test/java/com/milk/order/contract/InvariantDependencyOrderTest.java`：

| 断言 | 内容 |
| --- | --- |
| 拓扑性 | 每条声明依赖都必须排在本项之前（逐项校验，失败列出明细） |
| 关键序对 | 网格补全 < 父聚合 < 组合守卫 |
| 确定性 | 两次解析结果一致 |
| **不是字典序巧合** | 字典序下 `INV_ORDER_AGGREGATION` 排在 `INV_ORDER_TASK` 之前，因此"顺序正确"本身就证明依赖声明在起作用 |

## 测试与实测数据

### 实验七（4 个对照，全部通过）

| 对照 | 内容 | 关键结果 |
| --- | --- | --- |
| A（改造） | **进行中**订单注入 4 类违规 | 4 检出 / 4 修复 / 次轮 0；**订单始终为配送中（未被误判为已完成）、组合守卫零触发** → 方案二的行为验证 |
| B | 父状态漂移 vs 资金不一致 | 漂移 1/1 修复；资金项 1 检出 / 0 修复、未闭环 `ALERT_ONLY` |
| C | 终态父过程残余子任务 | 配送中：1 检出 / 0 修复 / 1 告警，任务保持原状；待配送：1 检出 / 1 修复，`TASK_CANCEL` 台账 1 条 |
| D（新增） | **终态订单网格缺口** | 1 检出 / **0 修复** / 1 告警；**任务数 0（没有补造历史）**；组合守卫 0 触发 |

> 对照 A 的设计要点：注入后、补网格前，"三个任务里两个已终态、第三个被删除"，
> 因此**若父聚合先于网格补全执行，同一次体检就会把订单判成已完成再补回任务**。
> 实测订单保持配送中——这条断言就是方案二的行为证据。

## 尚存不确定性

1. **依赖关系仍需人工逐对声明**：新增不变量时若没意识到"我的修复会改变别人的判定依据"，
   依赖就漏了。当前用契约矩阵 D 兜住"声明了就必须满足"，但**漏声明**目前测不出来——
   这需要"约束求解"式的思路（方案三）才能真正解决。
2. 拓扑序只解决**修复动作**的顺序，不解决"修复与并发业务路径"的交错
   （那由既有的 CAS/幂等机制保证，见实验一~三）。
3. `INV_ORDER_TASK` 对终态订单只告警后，**终态订单的历史缺口需要人工响应**——
   目前只有体检记录（`process_invariant_violation`）承载，尚无管理端页面（第三档 4.3 人工介入通道）。
