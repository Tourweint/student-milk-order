# 2026-09-19 补偿规则覆盖补齐（已支付 + 子任务全终态）

## 背景

后续扩展方案 3.4，修复实验十一特征化测试发现的规则覆盖盲区：

「订单已支付(2) + 子任务已全部签收(3)」（配送联动与聚合写入同时丢失）——
既没有补偿规则覆盖（规则表有 `(2,HAS_DISPATCHING_TASK→3)` 与 `(3,ALL_TASKS_TERMINAL→4)`，
缺 `(2,ALL_TASKS_TERMINAL→4)`），也不被现有不变量判为违规，订单静默停在"已支付"。

## 改动（3 处代码/数据 + 1 处测试翻转）

| 内容 | 落点 |
| --- | --- |
| 新增补偿规则「已支付全终态补偿」`(2, ALL_TASKS_TERMINAL → AUTO_COMPLETE, 4)`，默认启用 | `sql/data.sql` + 开发库/实验库 |
| 放开迁移闸门 `ORDER/AUTO_COMPLETE/2`（显式禁止 → 允许） | `sql/data.sql` + 开发库/实验库 |
| 聚合出口从"仅配送中"放开为"已支付/配送中"，CAS 以实际父状态为条件 | `OrderInfoServiceImpl.completeOrderIfAllTasksDone` |
| 特征化用例翻转为回归守卫 | `Experiment11LongRunMetricsTest.paidOrderWithAllTasksTerminalIsCompensated` |

### 修正了方案里的一个误判（值得记录）

原方案写的是放开 `ORDER/COMPLETE/2`。核对闸门种子后发现**补偿动作走的是 `AUTO_COMPLETE`**，
而 `COMPLETE/2` 是**管理端手动完成**的闸门——必须保持禁止（否则管理员可以手动"完成"一笔
还有待配送任务的已支付订单）。

教训加深了一层：**"配了规则 ≠ 配对了规则"，连"该放开哪条闸门"都要先核对动作码**——
规则表的 `action` 与迁移闸门的 `action` 是同一个编码空间，但语义上"自动聚合"与"人工操作"
是两类入口，放开哪条是独立的业务决定。

### 显式确认过的两个安全边界

1. **"已支付 + 零任务"不会被误补**：`ALL_TASKS_TERMINAL` 的求值含"至少一条任务"守卫。
   应付了钱却没生成任务属于更严重的漂移，应由 `INV_ORDER_TASK` 补生成任务，
   若被补偿"完成"掉反而会抹掉配送义务（收了钱没有奶）。
2. **子任务全部取消时也会被补为已完成**：与状态 3 的现有语义一致（`聚合丢失补偿` 同样如此）。
   "全部取消 → 已退订"的区分依赖退款设计，`全取消补偿` 规则仍默认停用——已写入规则描述与文档。

### 闸门放开的安全性论证（已写入代码注释与文档）

闸门**看不见子过程**，因此"不跳过未完成配送"这层约束不由闸门保证，
而由聚合出口的定义保证——只有全部任务终态才会走到 `AUTO_COMPLETE`。
这正是规则/闸门分工的边界：**闸门管"这个动作允许从哪个状态发起"，规则管"发现漂移后该做什么"**。

## 实现过程中发现并修正的测试设计问题

翻转后的断言最初有两个错误，都是"探测与收敛的时序"问题：

1. **先收敛后探测**导致命中规则为空（漂移已被修掉，探测自然为空）——已改为先 `detectEntity` 再收敛；
2. **AUTO_COMPLETE 台账计数口径**：同一条订单会有两条生效台账——签收时的正常聚合（3→4）
   与补偿聚合（2→4）。断言口径收窄为 `from_status = 2` 的那条，并注明原因。

## 尚存不确定性

1. **"全部取消 → 已完成"还是"已退订"**：本规则沿用了状态 3 的现有语义（全部取消也算终态，
   补为已完成）；若业务要求"全部取消应转已退订并发起退款"，需要先做退款设计，
   再启用 `全取消补偿` 规则并处理两条规则同时命中的优先级问题。
2. **闸门放开的影响面**：`AUTO_COMPLETE/2` 对所有调用方生效（聚合出口、补偿引擎）。
   目前 `AUTO_COMPLETE` 的唯一入口是聚合出口（受"全部任务终态"守卫），风险可控；
   若未来新增直接发起 `AUTO_COMPLETE` 的入口，需重新评估该闸门。
3. **运行中的开发服务**需重启后才会按新闸门工作（缓存 TTL 60 秒或重启）。
