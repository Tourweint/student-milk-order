# 2026-09-19 性能基准（配额池热点行争用）

## 背景

第二档的最后一项（后续扩展方案 3.3）。系统的核心卖点是"绝对不超卖"（行锁读 + 条件更新 + 台账唯一键），
但这个机制是有代价的：**同一个池子上的扣减会被行锁串行化**。本次把它量出来，
让"单池 vs 分段池"的讨论有数据依据——这也是答辩时"吞吐呢？扛得住多少人抢？"的答案。

### 实验设计

```text
预热 500ms（不计入指标，把 JIT 与连接池喂热）
A 组  热点单池：1 / 8 / 32 线程抢同一个池子
B 组  同为 32 线程，把配额分散到 8 / 32 个品种池（每线程绑定一个池）
每配置 1.5 秒；指标：TPS、p50/p95/p99/max（成功口径）、失败数、账实一致
```

**两个与原方案的差异（及原因）**：

1. **进程内基准代替 JMeter/k6**：压 `DailyQuotaService.deduct` 服务调用，不含 HTTP/序列化——
   目的是单独暴露"行锁串行化"这一个因素，掺入 HTTP 只会稀释结论；
   且数据照常归档到 `target/experiment-reports/`，`mvn test` 可复现。HTTP 全链路冒烟保留在
   `docs/测试/系统测试用例.md` §4.2（未测）。
2. **"分段池"用多品种池做等价代理**：配额唯一键是 `(quota_date, product_id)`，没有班级这一维；
   两者同为"把热点分散到多行"，行锁争用形态相同。真按班级分段需要改配额维度与分配算法（后续工作）。

## 实测数据（单机，多轮波动约 ±20%；结论依赖比值，不依赖绝对值）

```text
场景                         [线程/池]   成功次数   TPS      p50     p95     p99    max(ms)
热点单池 · 1 线程             [1 / 1]      313    208.27    4.63    6.35    7.31    8.57
热点单池 · 8 线程             [8 / 1]     1146    758.55   10.29   13.81   15.65   19.55
热点单池 · 32 线程            [32 / 1]    1036    672.01   45.27   60.67   96.01   98.72
分散 8 池 · 32 线程           [32 / 8]    4067   2686.84   11.34   16.73   20.82   50.53
分散 32 池 · 32 线程          [32 / 32]   4028   2669.65   10.71   19.69   29.11   82.32

热点 32 线程 / 单线程 TPS：      3.23 ×（并发度 32× ⇒ 远非线性）
热点 8 → 32 线程吞吐增幅：      0.89 ×（并发度 4× ⇒ 已饱和，甚至略降）
热点 32 线程 p50 / 单线程 p50：  9.78 ×（并发度 32× ⇒ 排队而非变慢）
分散 32 池 / 热点 32 线程：      3.97 ×
分散 8 池 → 32 池吞吐增幅：      0.99 ×（收益递减：已接近锁外瓶颈）
全部配置失败数：0；账实一致：池已售合计 == 成功扣减数 == 台账行数，零超卖
```

## 结论

1. **热点池确实被行锁串行化**：32 线程吞吐（672 TPS）甚至低于 8 线程（758 TPS），
   而 p50 从 10.3ms 涨到 45.3ms——**吞吐不涨、延迟线性涨**，串行化瓶颈的标准特征；
2. **分散到多行后吞吐回升约 4 倍**，p50 回落到 10.7ms：同一份代码、同一份数据规模，
   唯一差别是热点不在一行上；
3. **修正了一个直觉**：**"单线程 TPS = 吞吐上限"是错的**。单线程 TPS（208）是"单次端到端耗时的倒数"，
   把连接获取、幂等查询、提交等锁外开销也算进去了；多线程可以把锁外开销与锁内临界区**流水重叠**，
   所以热点并发吞吐（672）是单线程的 3.2×——但远低于 32× 的线性。
   临界区真实服务能力 ≈ 670 ops/s（≈1.5ms/次）；
4. **分散的收益在 8 个池就到顶**（8 → 32 池仅 0.99×）：行锁之外还有第二个瓶颈——
   每笔扣减 5 条 SQL（3 次保质期窗口加锁读 + 1 次条件更新 + 1 次台账插入）+ 连接/ORM 开销。
   **要再上一个量级得减少每笔扣减的 SQL 次数**（如先范围读确定窗口内实际存在的池再逐池加锁），
   而不是继续分散；
5. **正确性在压力下没有松动**：约 10600 次并发扣减零失败、零超卖、账实一致。
   **性能实验同样断言不变量**——"性能不能让一致性妥协"是可验证的主张；
6. **"按班级分段"的代价（推论，未实测）**：分段后各段不能互相借用余量，配额利用率会下降
   （某班卖完、另一班还有货）→ **一致性-吞吐-利用率**三方权衡，不是"分段一定更好"。

本轮还发现并处理了一个**断言设计问题**（值得记录）：最初断言"分散后 p99 应低于热点单池"，
全量回归时偶发失败——分散配置吞吐更高、样本更多，尾部更容易撞上 GC 停顿，
**p99 的跨配置比较不可靠**。已移除该断言，保留吞吐对比与热点内部的排队上升
（同配置内比较），并在代码注释与实验文档中写明原因。

## 尚存不确定性

1. **HTTP 全链路未测**：本基准压的是进程内服务调用；HTTP/序列化/网关层的吞吐与延迟仍空缺
   （`系统测试用例.md` §4.2 保留为待办）。
2. **单机环境**：应用与数据库同机，多轮 TPS 波动约 ±20%；断言只依赖比值，但绝对数值不具备外推性，
   需独立压测机复测。
3. **"分段池的利用率损失"是推论**：没有做"分段后卖不完余量作废率"的实测；引入班级分段时需补测。
4. **生产语义差异**：基准用合成订单号（台账唯一键无外键约束），未包含订单头/支付流水的写入；
   真实支付事务的临界区更长，热点吞吐会低于本基准的数值（方向不变，数值偏乐观）。
5. **未实现真正的班级分段**：如需实施，要改配额唯一键维度、分配算法与回补口径（后续工作）。
