## 一、背景

`家长端剩余配送盒数-边界与异常处理.md` §6 的两项口径问题落地：

1. **放假/停课**：不新增"暂停"状态，用 `delivery_date` 平移解决（每个配送日本来就有任务）；
2. **拒收补送**：挂原订单补送，不新开 0 元散装订单。

方案在 4 轮代码审查中修正了若干"照字面实现会坏"的点，最终定稿 v5。

## 二、变更内容

### 1. Schema（`schema.sql` + 增量脚本 `sql/2026-09-20-delivery-shift-and-compensation.sql`）

- `delivery_record` 新增 `reject_reason_code`、`reject_reason_detail`（结构化拒收原因）。
- 新表 `delivery_compensation`：`source_task_id`(UNIQUE)、`target_task_id`、`order_id`、`product_id`、`boxes`、`compensation_date`、`remark` + 标准字段。

### 2. 后端

- `DeliveryTaskService.shiftTasksToDate(taskIds, targetDate)`：配送日平移。
  - 两级预检（源任务存在配送中 → 拒绝整批；目标日同订单同品种任务非待配送 → 拒绝整批）。
  - 逐条 `attempt` CAS 作废原任务（1→4，幂等闸门），成功后再合并（`quantity += n`，条件更新 status=1，0 行即抛异常回滚）/新建到目标日。
  - **不更新 `deliveryEndDate`**（改 end 会让网格不变量的空档日被 AUTO_REPAIR 补造）。
  - 原 `delivery_record` 不置拒收，仅 remark 标注、保持未签收。
- `DeliveryTaskService.adjustQuantitiesBeforeDeadline(orderId, deadline)`：期末摊平。
  - 剩余量 M = 该订单从今天起 `status∈{1,2}` 的 quantity 合计（**含截止日之后的任务**）。
  - 窗口 K = 截止日当天及之前仍待配送的任务数；`M-fixed > 2K` 提示延后、`< K` 提示缩短。
  - 重置基准 = `1 + 该任务补送量`（从 `delivery_compensation` 汇总），**避免抹掉拒收补送**；摊平后量 = `min(基准+分配, 3)`。
  - 截止日之后的待配送任务作废（盒数已提前并入窗口）；可重复执行且幂等。
- `DeliveryTaskService.rejectRecord(recordId, reasonCode, reasonDetail, reason)`（保留旧签名兼容）：
  - 2→4 CAS 抢占 → 记录 2→3 并写结构化原因 → **同事务内落拒收补送** → enqueue → `completeOrderIfAllTasksDone`（**放最后**，否则零散订单会被先判完成、补送任务被组合守卫自动作废）。
  - 补送：次日同订单同品种待配送任务存在则合并 `quantity += 1`，否则新建；写 `delivery_compensation`（撞键抛异常回滚）；**仅零散订单**（`packageId == null`）追加次日机动配额。
- `DailyQuotaService.addCompensationBox(orderId, productId, quotaDate, boxes)`：补送配额追加（行锁 + 条件更新 + 台账）；池子不存在抛异常；**不校验 `used + boxes <= total`**（补送成本商家承担，允许超池）。
- 不变量 `INV_TASK_COMPENSATION`（`ALERT_ONLY`）：真拒收（`sign_status=3 AND reject_reason_code IS NOT NULL`）但无补偿记录 → 告警。
- `DeliveryController` 新增 `POST /api/delivery/task/shift`、`POST /api/delivery/task/rebalance`；`POST /api/delivery/record/reject` 增加 `reasonCode`/`reasonDetail` 可选参数。
- `SecurityConfig`：平移/摊平仅 `ADMIN`。
- `DeliveryRecordVO` 增加 `rejectReasonCode`/`rejectReasonDetail`。

## 五、关键设计决策（原方案逐轮代码审查的结论）

方案在实现前经 4 轮"是否照着写会坏"的审查，逐条推翻了几个"看起来对但会静默丢数据"的设计：

1. **补送不新建任务、改为合并 quantity**。
   任务本就逐日展开（含周末），除周期最后一天外，**次日必然已有同订单同品种任务**；
   新建会同时撞 `uk_order_product_date` 与 `uk_task_no`，被 `IdempotencyGuard` 当作"已存在"**静默跳过** →
   学生少一盒且系统毫无感知。改为 `quantity += 1` 后不再撞键。
   （零散订单为单日、次日无任务，才是"新建"的正当场景；两类订单因此分叉。）
2. **补送落库必须在 `completeOrderIfAllTasksDone` 之前**。
   零散订单只有 1 个任务，拒收后即全终态；若先判完成，订单当场变"已完成"，补送任务会成为
   "已完成订单 + 待配送任务"，30 分钟内被 `INV_PARENT_TERMINAL_CHILD_PENDING` 的自动修复 `cancelTask` 抹掉。
3. **平移不更新 `deliveryEndDate`**。
   `INV_ORDER_TASK` 用 `(end-start+1)×品种数` 算期望；改 end 会让平移留下的空档日被判为缺失并被自动补造任务（凭空多送）。
4. **平移"先 CAS 作废、再合并"**（而不是先合并）。
   新路径不复用 `cancelTask`（它会把签收记录置为拒收、并触发父聚合完成判定）；顺序反过来后，
   CAS 天然成为幂等闸门，**不需要批次表**，重试不会重复加量。
5. **合并/加量的条件更新影响 0 行必须抛异常回滚**，不能静默跳过——否则又是"原任务已作废、目标日未加量"的静默丢盒。
6. **摊平的重置基准 = `1 + 该任务补送量`**。
   若一律重置回 1，会把拒收补送的 +1 抹掉；M 的口径含截止日之后的任务、并作废窗口外待配送任务，否则算法恒为无操作。
7. **补送配额允许超池**（不校验 `used + boxes <= total`）：破损/变质是商家责任，补送成本商家承担；
   校验反而会因"池子满"导致补送失败。
8. **平移/摊平都不引入新状态、新动作**：规则种子零新增，契约矩阵无需大改。

> 以上 1–8 就是原方案文档里真正有价值的部分；其余"酒店房间类比"等解释性内容属于讨论过程，随方案文档一并删除。
