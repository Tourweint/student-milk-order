# 2026-09-21 奶站「当日未送达申报」（自动签收的例外通道）

## 一、背景：一个"物理/信息混同"造成的虚假业务事实

`DeliveryAutoSignJob` 的兜底判定是「配送日期 < 今天 + 任务配送中 + 记录未签收」，其中"任务配送中"
来自配送站点的**按钮**（**信息态**），而"奶有没有到校"是**物理态**。两者不一致时（车辆故障、道路中断、
奶未备齐），兜底会替老师签收，并在**同一事务内生成营养摄入记录**——一条虚假签收 + 一份虚假摄入，
两者都是"已提交业务事实"，只能人工清理，且 `process_transition_log` 里还留下一条 SIGN 台账。

本变更给这条兜底路径加一个**业务侧可声明的例外通道**：奶站申报"已点已送出、物理上没送到"。

## 二、变更内容

### 1. Schema（`schema.sql` + 增量脚本 `sql/2026-09-21-undelivered-report.sql`）

- 新表 `delivery_undelivered_report`：`task_id`(UNIQUE `uk_task`)、`order_id`、`product_id`、`class_id`、
  `delivery_date`、`reason`、`report_by`、`handle_status`(0-待跟进 / 1-已跟进)、`handle_remark`、
  `handle_by`、`handle_time` + 标准字段；索引 `idx_date_status`。
- `class_id` 是**冗余列**（与 `delivery_task` 一致），用于班主任数据范围过滤，避免"先捞全班任务 ID 再 IN"。
- ⚠️ schema 变更：实验库与开发库均须同步（本会话已给实验库补建；开发库执行上述增量脚本，幂等可重复）。

### 2. 后端（delivery 模块）

| 文件 | 改动 |
| --- | --- |
| `entity/DeliveryUndeliveredReport` | 新增实体；类注释写明问题定义与"只标记、不改状态"的边界 |
| `mapper/DeliveryUndeliveredReportMapper` | 新增；`selectReportedTaskIds(taskIds)` 用「任务 ID 白名单 IN」返回已申报任务，规模有上界（每批 ≤200） |
| `dto/UndeliveredReportRequest` | `taskId` + `reason`（@NotBlank，≤255） |
| `vo/UndeliveredReportVO` | 待办列表行：任务号/订单号/学生/班级/奶品/盒数/原因/申报人/跟进人与时间 + **任务当前状态** |
| `service/DeliveryUndeliveredReportService` + impl | `report`（前置守卫 + 唯一键幂等）、`pageReports`（数据范围 + 回显）、`handle`（只登记） |
| `service/impl/DeliveryTaskServiceImpl` | **两道闸门**：`listExpiredAutoSignRecordIds` 候选集剔除已申报任务；`autoSignOne` 单条入口再判一次 |
| `job/DeliveryAutoSignJob` | 类注释补"必须显式排除的例外"及理由 |
| `config/SecurityConfig` | `POST /api/delivery/task/undelivered-report` → ADMIN/DELIVERY（申报）；`PUT …/undelivered-report/**` → ADMIN（跟进）；列表 GET 落 `/task/**` → ADMIN/TEACHER/DELIVERY |

**四个关键判断**：

1. **两道闸门，缺一不可**：候选集是分批取的（每批 ≤200、下一批下一轮），两次取之间奶站仍可能补报；
   只在候选集过滤会漏。**"兜底一定签不掉未送达任务"的保证来自 `autoSignOne` 的单条判断**。
2. **只允许「配送中」的任务申报**：待配送(1) 本就不在兜底候选集（不会产生虚假签收），
   已完成/已取消(3/4) 是终态（兜底不碰）；放宽只会让申报变成"随便给任务打标签"。
   同时拒绝"尚未到来的配送日"。
3. **申报与处置分离**：`handle` 只写 `handle_status/handle_remark/handle_by/handle_time`，
   **不改任务与订单状态**；实际处置必须走签收/拒收/取消，从而照旧经过统一迁移出口并留痕。
4. **幂等靠唯一键**：一条任务一条申报（`uk_task`），重复申报由 `IdempotencyGuard` 翻译为业务提示；
   没有用"先 `selectCount` 再 `insert`"。

## 四、边界与已知限制

1. 申报**不新增状态、不自动改任何状态**，也不写任何迁移台账；跟进同样不改状态。
2. **长期无人处置的代价**：任务会一直停在「配送中」，其订单停在「配送中」——这是刻意接受的
   （比制造虚假签收可取）。当前只靠面板待办 + 顶部提醒让它"可见"，**没有自动升级/告警落点**；
   若需要，属"人工介入通道"（`后续扩展方案.md` §4.3）的范畴。
3. 申报只挡**自动签收**这一条路径；人工签收/批量签收仍可正常执行（人工看到的是真实情况）。
4. **未覆盖**：实验为单线程构造，未验证"申报与自动签收真并发"的竞争（
   两者都在同一任务上做条件更新/唯一键，方向上安全，但未实测）。
