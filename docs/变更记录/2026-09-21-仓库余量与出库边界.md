# 2026-09-21 仓库余量与出库边界（供给侧台账）

## 一、背景

履约链的**起点**原先不在系统里：业务事实是"奶企 → 学校配送站（收货、按班分类）→ 公共领取点 →
班级/学生 → 班主任签收"，而配送站是**学校自己的**（不是奶企的），仓库就在校园内。但系统里
`daily_quota` 建模的是"**供货计划**"，与物理世界之间没有对账通道，于是有三个具体缺口：

1. **多出来的奶没有归宿**：企业多送（要 500 到 504）、退订后未送的奶、拒收退回的奶——
   实物在学校仓库里，系统里没有任何账目承载它们；
2. **短交发现太晚**：企业少送（要 500 到 480）要到家长支付扣减失败或缺货取消时才暴露，
   此时已触发退款整条链路；
3. **配额发行没有物理依据**：管理员设 100 盒配额，仓库里有没有 100 盒，系统不知道。

**设计主张**：**仓库余量是机动配额发行的唯一合法来源**（"只有仓库余量才能卖"）。
配额池继续作为并发控制闸门（行锁、条件更新、台账、守恒**全部不动**），唯一的变化是
**额度发行被仓库实物封顶**。

> 设计取舍、备选与明确排除的做法见 `../设计方案/2026-09-21-仓库余量与出库边界-设计方案.md`；
> 该文 §11 是本次评审的修订记录（**4 处硬缺陷 + 8 条口径**），本记录只写"实际做了什么"。

## 二、设计评审先行（本轮的第一个动作）

本轮按项目约定"先文档、后实现"，但在写代码**之前**先把设计方案逐条对着代码核对了一遍，
结果发现 4 处"照着写一定会算错账"的缺陷（详见设计方案 §11 与
`../实验/实验设计与结果.md` 第 7 节 **D8**）：

| # | 缺陷 | 后果 |
| --- | --- | --- |
| P0-1 | 发行封顶公式把"已售未送出的零散任务"漏掉、又重复计入已送出（`status=2`）的任务 | **可超发**（实测反例：W=100 时仍能放出 120 盒的额度） |
| P0-2 | 发行校验是 check-then-act（W 的聚合读无锁） | 同品种并发发行两个日期会**双双通过** |
| P0-3 | 出库不变量用"任务状态 ∈ {2,3,4}"判"应已出库" | `1→4` 的取消任务被成批误判，且处置是 AUTO_REPAIR → **体检补写出假出库行、W 变负** |
| P0-4 | 出库钩子只写了 `batch-start` | 单条 `startDelivery` 与批量走同一个 `casDispatch` → **单条送出全部漏账** |

这四处都不是"实现走样"，而是设计公式与真实数据模型不符（例如"已售未送出"这一状态在业务上不存在，
只有"任务 status=1 且配额已扣"这一事实组合）。**结论先改文档再改代码**，并把两条最关键的
落成实验二十的断言（③⑦）作为回归守卫。

## 三、变更内容

### 1. Schema（`schema.sql` + 增量脚本 `sql/2026-09-21-warehouse-ledger.sql`）

- 新表 `warehouse_ledger`（**一条进出账**，不是库存系统）：
  `biz_type`(IN/OUT/IN_BACK/ADJ/INIT) / `biz_date` / `product_id` / `quantity` / `ref_type` / `ref_id` /
  `receipt_no` / `batch_no` / `reason` / `operator`；
- 唯一键 **`uk_biz_ref(biz_type, ref_id)`**（OUT/IN_BACK 幂等：一个任务只出一次库、一条记录只退回一次）与
  **`uk_in_receipt(biz_type, biz_date, product_id, receipt_no)`**（IN/INIT 幂等：双击与脚本重跑只落一行，
  同日第二车用不同凭证号合法新增）；
- `ADJ` 的 `quantity` **带符号**（正=增加余量，负=减少余量）——否则"反向 ADJ 冲销"在数学上无解；
- ⚠️ schema 变更：开发库与实验库均已同步（开发库执行了增量脚本、实验库复制了表结构）；
  实验库须按 `../实验/实验环境与运行说明.md` §3.4 同步，否则实验会失败。

**四条不变量**（`module/warehouse/invariant/`）：

| 编码 | 判据 | 处置 |
| --- | --- | --- |
| `INV_LEDGER_OUT_TASK` | 双向：已送出（`dispatch_time` 非空）缺 OUT 行 → 可补写；OUT 行对应任务未送出 → 告警 | ① AUTO_REPAIR ② ALERT_ONLY |
| `INV_WAREHOUSE_NONNEG` | 每品种 `W < 0` | ALERT_ONLY（方向不确定，人工对账后走反向 ADJ） |
| `INV_LEDGER_REFUND_LINK` | 真拒收（`sign_status=3 AND reject_reason_code IS NOT NULL`，与 `INV_TASK_COMPENSATION` 同源）缺 IN_BACK | ALERT_ONLY |
| `INV_WAREHOUSE_COVERAGE` | 每品种 `W < 当期可卖额度 + 待送出任务`（把发行闸门升级为**持续验证**） | ALERT_ONLY |

`INV_WAREHOUSE_NONNEG` 与 `INV_WAREHOUSE_COVERAGE` 用 `dependsOn()` 声明依赖 `INV_LEDGER_OUT_TASK`：
补记 OUT 会**降低** W，必须在"出库账补全之后"判定（这是"AUTO_REPAIR 改变他人判定依据必须声明依赖"的第三个实例）。

## 五、边界与已知限制

1. **不是库存系统**：不做效期预警、先进先出、盘点、库位、采购订货与奶企结算——那些属奶站/学校 ERP
   责任域（`业务边界与责任域.md` §六 第 3 条"责任域边界"）。
2. **出库不做余额校验**：送出是**物流事实**，缺货只体现为 W 变小与 `INV_WAREHOUSE_NONNEG`/
   `INV_WAREHOUSE_COVERAGE` 告警，系统不拒绝配送（否则等于用一份可能滞后的账阻断现场作业）。
3. **不做远期预售（需业务知悉）**：封顶比的是"今天的实物"，因此**提前为远期日期设池会被拒绝**——
   本方案无 MRP、无预计到货。管理员操作次序固定为**当日到货登记 → 当日/次日配额设置**。
4. **台账只增不改**：不提供修改/删除接口；记错走反向 `ADJ` 冲销（两条留痕），
   减记不得使余量变负（服务层拦截，超出的差异应先去核对到货/送出/退回）。
5. **一个品种一天一行的"主凭证"**：同日第二车必须显式填送货单号；不填会与第一车撞唯一键被判重
   （这是刻意的——静默追加会让"当日到底到了几车"不可知）。
6. **批次仍是可选标注**：`batch_no` 与既有 `daily_quota.batch_no` 并存，召回反查链目前仍以配额池为入口
   （台账侧的迁移是后续工作，见 `../论文/后续扩展方案.md` §4.7 的"载体升级"说明）。
7. **并发正确性未做真实多机验证**：与全项目一致——正确性来自唯一键 + 条件更新 + 行锁，
   不依赖分布式协调；`requireIssuanceCoverage` 的 `product` 行锁只保证**同库内**串行。
