# 2026-09-19 多实例部署的正确性：本地状态审计与消除

## 背景

第二档的第一项（后续扩展方案 3.1）：验证并保证多实例部署的正确性。

多实例下出问题的从来不是算法，而是两类东西：**实例本地状态**（别的实例看不见）与
**幂等边界**（同一件事被两个实例各做一次）。因此本次先做一遍完整审计，再按审计结论修，
最后用可复现的方式验证（实验九）。

审计**比预想的多挖出两个问题**：原先只看到"定时任务无协调"和"预支付单在内存"两个障碍，
实际还发现**编号生成依赖实例本地计数器**——其中任务号撞号的后果是**静默丢数据**。

## 审计结论与处置

| 组件 | 原先的本地状态 / 幂等边界 | 多实例下的后果 | 处置 |
| --- | --- | --- | --- |
| 预支付单 | 内存 `Map<prepayId, …>` | 在实例 A 预下单、确认扣款落到实例 B → **付不了款** | 持久化到 `wechat_pay_order` |
| 已扣款单 | 内存 `Map<outTradeNo, …>` | 实例 B 的对账查不到扣款 → **已付款订单被当作未付款**，可能被超时任务取消（钱已收、单已取消） | 同上（查单读库） |
| 配送任务号 | `static AtomicLong` | 两实例同一秒生成同一任务号 → 撞 `uk_task_no`，而幂等守卫把"号撞了"误判成"业务键已存在"→ **一条配送任务凭空消失** | 改为由业务键确定性生成：`DT{日期}-{订单}-{品种}` |
| 订单号 / 流水号 | `static AtomicLong` | 两实例同一秒生成同一订单号 → 撞 `uk_order_no` → **下单失败** | 编号加入 `InstanceIdentity.TAG`（5 位随机，进程启动确定） |
| 体检违规记录写入 | 应用层"先查再插" | 并发体检给同一主体插出两条记录 | 唯一键 `uk_violation` + `IdempotencyGuard` |
| 6 个定时任务 | 无选主，每实例都跑 | 同一批数据被并发处理 | **判定为不需要修**：逐个审计后确认幂等（见下） |
| 规则/参数缓存 | 每实例 60 秒 TTL | 管理端改动最长 60 秒后才在另一实例生效 | 记录为**有界延迟**（非错误） |
| 注册限频 | 内存滑动窗口 | N 实例下等效阈值放大 N 倍 | 记录为**有界削弱**（仅拦脚本注册，非安全边界） |
| JWT / `IdempotencyGuard` / `DataScopeResolver` | 无状态 | 无影响 | 无需改动 |

**为什么可以不选主**：6 个定时任务的写路径全部是"逐条 CAS 取消/落账/签收、
统一迁移出口 `attempt`、唯一键仲裁"，因此重复执行只会浪费算力。
选主需要引入锁/租约/脑裂处理，属于算力优化而非正确性需求，本项目不做。

## 主要改动

1. **新增表 `wechat_pay_order`**（模拟微信侧支付单）+ 实体/Mapper；
   `WechatPaySimulator` 由"读内存 Map"改为"读库"：
   - 统一下单：作废该订单旧的待确认预支付单，插入新预支付单；
   - 确认扣款：`status 1→2` 的**条件更新**（并发/重复确认只有一个成功，不会重复扣款或重复发回调），
     再异步回调；
   - 查单：按 `out_trade_no` 读最新已扣款行。
   - 顺带消除了原实现的"重启后预支付单失效"限制（现在重启不丢）。
2. **任务号改为由业务键确定性生成**（`DeliveryTaskServiceImpl.buildTaskNo`）：
   任务号冲突 ⟺ 业务键冲突，两者不可能再背离；静态计数器随之删除（消除唯一的跨实例本地状态）。
3. **新增 `InstanceIdentity`**：进程启动时随机 5 位标识，用于订单号/流水号（`nextNo`）。
4. **`ProcessInvariantScanner.insertOpen` 改用 `IdempotencyGuard`**：并发体检不重复插记录。
5. **新增实验九**（`Experiment9MultiInstanceTest`，5 个对照）。

## 尚存不确定性（本次审计后仍然存在的）

完整清单在 `基线文档/可靠性设计.md` 10.3，这里列要点：

1. **验证方式仍是"单 JVM 内的多实例模拟"**：实验九用两个组件实例 + 并发线程覆盖了
   "共享数据库、各自持有组件"的多实例语义，**未覆盖**真实多进程/多主机、网络分区、
   负载均衡路由、进程崩溃恢复、数据库主从延迟。这几项需要真实多节点环境与混沌工具（3.2）。
2. **异步回调的发送仍在实例内**：处理"确认扣款"的实例用内存线程池做退避重试；
   该实例在重试期间崩溃则这次回调丢失——支付单已落库，对账（任意实例）可补偿，
   即"回调是尽力而为、对账才是保证"。若要求回调不丢，应改为持久化投递（事件表 + 消费者）。
3. **`notifyUrl` 默认值只适合单实例**（`http://127.0.0.1:8090/...`），多实例需指向负载均衡地址；
   否则回调全部失败、退化为纯对账补偿（数据仍正确，时效变差）。
4. **`ProcessPendingTaskJob` 的重复消费会让 `retry_count` 前进更快**，待办可能更早被放弃并转兜底通道。
   正确性不受影响，但收敛路径变了；严格单次消费需要 CAS 认领（新增"处理中"状态 + 超时回收），未做。
5. **体检闭环标记在并发下可能被覆盖为"未闭环"**（假阴性）：两个实例的修复一成功一失败时，
   最终标记取决于写入顺序。下一轮体检会通过"复检通过"自动闭合。
   实验九对照 D 实测为 1（已闭环），但**这不是可保证的结果**，因此测试不断言该标记。
6. **规则/参数变更最长 60 秒全局收敛**；**实例间时钟偏移未处理**（部署要求校时）。
7. **`wechat_pay_order` 会持续增长**（它同时是对账依据，不能随意清理）；长期运行需按
   "已对账 + 超过保留期"清理，当前未做。
8. 订单号/流水号的跨实例唯一性由"随机实例标识 + 唯一键兜底"保证，
   属于**概率上不会撞**而非数学保证；若需严格保证应改为数据库序列/号段服务。
