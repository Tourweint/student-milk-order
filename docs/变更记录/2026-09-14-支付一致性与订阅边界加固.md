# 2026-09-14 支付一致性与订阅边界加固（模拟支付状态校验 + 业务边界 + 状态机可配置化）

## 一、背景与目标

模拟支付虽然没有对接真实微信支付，但演示链路中依然存在**分布式调用异常场景**。本次改造围绕两条主线：

1. **模拟支付的状态一致性校验**：回调丢包/超时、重复回调幂等、支付超时自动取消、状态校验防乱改状态；
2. **订阅业务边界挖掘 + 工程优化**：暂停/恢复、缺货单期取消、重复订阅校验、禁止状态回退、终止时机选择，并把**状态迁移规则入库、管理端可配置**（不改代码）。

## 二、支付链路加固（四个分布式异常场景）

### 2.1 场景一：前端支付成功，回调丢包/请求超时

**三层兜底**（对应真实微信链路「重试通知 + 商户对账」）：

| 层 | 机制 | 实现 |
| --- | --- | --- |
| L1 回调重试 | 模拟微信失败后按指数退避重试（1s/2s/4s/8s/16s，默认 5 次） | `WechatPaySimulator.sendNotifyWithRetry`：非 HTTP 200 或应答非 `SUCCESS` 一律视为失败进入重试；重试耗尽后支付单仍保留在微信侧存储 |
| L2 查单补偿 | 商户主动查单：`GET /api/order/{id}/pay-result`（前端轮询兜底） | `OrderInfoService.queryPayResult`：待支付订单向微信侧查单，已扣款则走回调同路径补偿落账 |
| L3 对账任务 | 每 5 分钟扫描存在待支付流水且已过 2 分钟在途窗口的订单，逐单查单补偿 | `PaymentReconcileJob` → `reconcilePendingPayments`（可经系统参数 `order.pay.reconcile.enabled` 关闭） |

关键设计：**扣款结果先落微信侧存储（`paidStore`），再异步通知商户**——与真实链路一致，即使回调全部丢失，查单仍能拿到 `transactionId/payTime/amount`，补偿路径复用回调处理逻辑（`handleWechatPayNotify`），天然幂等。

### 2.2 场景二：重复回调（幂等）

- **快速幂等路径**：已支付/配送中/已完成订单收到回调直接返回成功（微信侧停止重试），不再扣配额、不再写流水；
- **CAS 串行化**：`markOrderPaid` 改为条件更新 `UPDATE order_info SET status=2,... WHERE id=? AND status=1`，并发双回调/回调与取消竞争时仅一方成功；失败方抛异常回滚本轮全部写入（含配额扣减），微信重试后走幂等快速路径；
- **状态机规则校验**：落账前校验 `ORDER/PAY/from_status` 规则，管理端禁用后回调拒绝（恢复规则后自动补齐）。

### 2.3 场景三：支付超时自动取消（定时任务）

- `OrderTimeoutCancelJob`（每 5 分钟）：扫描 `status=1 AND create_time < now-超时阈值` 的候选订单，逐单调 `cancelTimeoutOrder`；
- **超时锚点取最近一次待支付流水时间**（无流水回退订单创建时间）——用户刚重新发起支付的订单不会被误杀；
- **取消前先查单**：微信侧已扣款 → 补偿落账，绝不取消已付款订单；
- 超时阈值 `order.pay.timeout.minutes`（默认 15 分钟）存于 `sys_config`，管理端在线修改；
- 取消动作走 CAS（`WHERE status=1`），与并发到达的支付回调仅一方成功。

### 2.4 场景四：状态校验——只有待支付订单可接收支付成功回调

| 回调到达时订单状态 | 处理 |
| --- | --- |
| 待支付(1) | 校验金额 → 规则允许 → 扣配额 → 流水落账 → CAS 置已支付 → 展开配送任务 |
| 已支付(2)/配送中(3)/已完成(4) | 幂等应答 SUCCESS（不修改任何数据，防微信重试风暴） |
| 已取消(5) | **拒绝**（返回 FAIL），不将已取消订单置为已支付；真实链路对应「关单+退款」 |

全部状态变更（支付/取消/配送联动/完成）统一接入**状态迁移规则表**（白名单语义），且全部改为 CAS 条件更新，杜绝「查状态→更新」的 check-then-act 竞态。

## 三、订阅业务边界（五个 case 的设计决策）

### 边界1：订阅生效期间中途暂停，已生成的待配送子订单怎么办？

- 新增计划状态 `2-已暂停`（`pause_plan`/`resume_plan` 接口 + 小程序/管理端入口）；
- **决策：暂停只挡续订生成，不回收已支付权益**。默认「未配送任务保留照常送」；可选「暂停并取消未配送任务」（该期不送，家长主动选择）；
- 暂停中的计划被续订定时任务天然跳过（查询条件 `status=1`）+ 状态机 `RENEW from 2` 默认禁止，双保险。

### 边界2：配送前缺货——单期子订单取消，不影响主订阅

- 新增 `PUT /api/delivery/task/stockout-cancel`（仅 ADMIN）：按「配送日期 + 奶品」批量取消**待配送**任务（状态机 `STOCKOUT_CANCEL from 1`）；
- 已完成/已签收任务禁止任何回退；配送中任务不动（奶已出库在途）；
- **零散订单当日配额按台账精确回补**（`restoreForOrderProductDate`：订单×品种×日期三维定位，不影响同订单其他期次/品种）；学期套餐不占配额自然跳过；
- 主订阅计划不受影响：下期续订照常，任务由续订订单重新展开；
- 订单任务全部到达终态时自动完成（复用 `completeOrderIfAllTasksDone`）。

### 边界3：重复创建订阅的校验

- 原有「同订单不能重复开启」升级为 `status IN (1,2)`（暂停中也算占用）；
- **新增同一学生维度校验**：同一学生同时只允许一个生效计划（开启/暂停均算），防止并行扣款。

### 边界4：已完成配送的子订单，禁止任何状态回退

- 任务状态流转全部接入状态机规则表：`SIGN from 2`、`TASK_CANCEL from 1/2`、`STOCKOUT_CANCEL from 1`——已完成(3)/已取消(4)不在任何动作的来源白名单中；
- 全部改为 CAS 条件更新（`WHERE status=期望状态`），并发重复签收/取消仅一方生效；
- 订单侧同理：`PAY/CANCEL/DELIVER/AUTO_COMPLETE/COMPLETE` 均按规则表 + CAS 把关。

### 边界5：订阅终止的时机——立刻终止 vs 执行完当前配送周期再终止

- 关闭订阅（`DELETE /api/subscription/{id}?terminateNow=`）提供两种时机：
  - **默认（terminateNow=false）**：立即停止后续续订，当前已生成的配送任务照常送完（已支付权益不损失）；
  - **立即终止（terminateNow=true）**：同时取消当前周期未配送任务（剩余期次线下退款）；
- 小程序用 ActionSheet 二选一，管理端用 Radio 对话框，防误操作。

## 四、状态迁移规则入库 + 管理端可配置

- 新表 `state_transition_rule`（scene + action + from_status 唯一，allowed 0/1，说明文字），**白名单语义：未配置的迁移一律禁止**；
- 新表 `sys_config`（业务参数）：支付超时阈值、对账任务开关；
- `StateMachineService`：全量规则加载进内存缓存（60 秒 TTL 兜底 + 管理端修改后立即刷新），`assertAllowed(scene, action, fromStatus)` 业务侧一行接入；`SysConfigService` 同模式；
- 接入点全覆盖：订单（支付/取消/配送联动/自动完成/手动完成）、配送任务（送出/取消/签收/拒收/缺货取消）、续订计划（续订/暂停/恢复/关闭）；
- 管理端「系统管理」新增两个 Tab：**状态机规则**（场景筛选 + 开关切换，即刻生效）、**系统参数**（在线编辑）；
- 种子数据 = 现行硬编码行为（`data.sql` + 独立迁移脚本），上线即兼容，不改代码即可调规则。

## 六、已知边界与后续建议

1. **取消后到达的回调**：拒绝并让微信重试耗尽——真实链路需触发退款，本系统为模拟环境不涉及资金流，已在代码注释与本文档标注；
2. **模拟器内存态**：预支付单/支付单存内存，重启后未完成预支付单失效（重新发起支付即可，与既有文档一致）；对账任务在该场景下查不到单，订单会被超时任务正常取消；
3. **多实例部署**：状态机/参数缓存为进程内缓存（60s TTL 兜底），管理端修改在其他实例最长 60 秒生效；单机演示场景即刻生效；
4. 建议后续：`payment_record` 增加 `order_id + transaction_id` 唯一约束进一步兜底；对账任务接入告警通知。

## 七、2026-09-15 复核修订

对本次改造做代码复核后，修正了以下几处「文档声明与实现不一致」的问题（功能语义不变，均为加固）：

| # | 问题 | 修订 |
| --- | --- | --- |
| 1 | 支付查单端点实际映射为 `GET /api/order/pay-result/{id}`，与文档（及同文件注释）声明的 `/api/order/{id}/pay-result` 不一致 | 统一为 REST 风格 `GET /api/order/{id}/pay-result`（`OrderController`），三份文档无需再改 |
| 2 | L2「前端轮询兜底」实际未接通：小程序 `utils/pay.js` 轮询的是订单详情，不会触发查单补偿，`queryPayResult` 无调用方 | 小程序新增 `orderApi.getPayResult(id)`，支付轮询改为调查单接口——回调全部丢失时前端这一轮也能把订单推成已支付；并处理轮询期订单被取消（status=5）的提示 |
| 3 | 「配送任务流转全部改为 CAS」不成立：签收/拒收/取消任务仍是「读状态→判断→全量更新」，并发重复签收会生成重复营养摄入记录，取消任务还可能把已完成(3)回退成已取消(4) | `doSign` / `rejectRecord` / `cancelTask` / `cancelPendingTasksForOrder` 全部改为条件更新；`rejectRecord`、`cancelTask` 补 `@Transactional`；签收记录更新收敛为 `markRecordRejected`（仅 `sign_status=2` 生效） |
| 4 | `batchStartDelivery`（今日已送出）绕过 `DELIVERY_TASK/DISPATCH` 规则，管理端禁用后单条被拦、批量仍可执行 | 批量入口补状态机校验，与单条同口径 |
| 5 | `processDuePlans` 内部直调 `triggerRenewal` 属同类自调用，`@Transactional` 失效：续订订单与计划时间链非原子，计划更新失败会导致下一轮重复续订（重复扣款） | 注入自身代理 `self`，经代理调用 `triggerRenewal`（与 `OrderInfoServiceImpl` 既有做法一致） |
| 6 | 关闭订阅的备注无论 `terminateNow` 取值都写「当前周期任务送完为止」，立即终止时与事实相反 | `buildCloseRemark` 按终止时机分别写入备注 |
| 7 | `OrderTimeoutCancelJob` 把未取消（补偿落账/未到锚点/规则禁止）的候选订单也计入 `processed` 日志 | 仅在 `cancelTimeoutOrder` 返回 true 时计数，日志区分候选数与实际取消数 |
| 8 | 迁移脚本 `ALTER ... ADD COLUMN` 非幂等，与「幂等可重复执行」的说明矛盾；重复执行会在第 1 步中断，导致后续建表与种子不执行 | 改为先查 `information_schema` 再 `PREPARE/EXECUTE` 动态 `ADD COLUMN`，脚本可整体重复执行 |
