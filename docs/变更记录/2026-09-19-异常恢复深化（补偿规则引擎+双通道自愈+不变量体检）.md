# 2026-09-19 异常恢复深化：补偿规则引擎 + 双通道自愈 + 不变量体检

## 背景

在同日的「业务过程抽象与可靠执行层重构」之后做了一次自评，结论是：抽象方向成立，但有两处**结构性偏薄**：

1. **补偿是硬编码的**：`OrderInfoService.reconcileOrderAggregation` 把两类漂移写成两个 `if`，
   `已支付 + 有配送中任务 → 配送中` 这类补偿规则没有下沉到规则表，与状态迁移规则表（数据驱动）形成明显不对称；
   新增一类漂移必须改代码重新发布。
2. **验证是一次性的**：跨表不变量只在实验里被验证过一次，运行期没有任何持续检查；
   漂移检测是纯拉模式（10 分钟一轮全表扫），**不可检测窗口最长 10 分钟**。

本次按 `docs/论文/后续扩展方案.md` 的「第一档」实现三件事，并加一组结构性回归守卫：

- **2.1 补偿规则从硬编码下沉到规则表**（探测 / 决策 / 执行三层分离）；
- **2.2 不变量校验器：2 类 → 6 类跨表不变量**（分级处置 + 复检闭环）；
- **2.3 实时自愈 + 定时兜底双通道**（事件驱动待办 + 秒级消费者 + 兜底最后防线）；
- **2.4 状态机契约矩阵测试**（规则覆盖 / 安全关键禁止 / 台账可回放）。

第三档（嵌套状态机、规则引擎化、人工介入通道等）按约定**只写进 future work**，不实现。

## 主要改动

### 1. 过程层新增三个子域（`com.milk.order.process`）

```text
process/
  TransitionSpec / ProcessTransitionExecutor / ProcessTransitionLog   # 既有：统一迁移出口
  reconcile/   # ① 补偿规则引擎：ProcessReconcileEngine（探测）、ProcessReconcileRule（决策）、
               #    ProcessReconcileCoordinator（执行编排）、ParentProcessProbe/Aggregator（业务侧契约）
  pending/     # ② 实时通道：ProcessPendingTaskService（入队/领取/退避/放弃/清理）
  invariant/   # ③ 持续验证：ProcessInvariant（契约）、ProcessInvariantScanner、InvariantScanReport
  job/         # ProcessPendingTaskJob（5 秒）、ProcessInvariantJob（30 分钟）
  mapper/      # 4 张过程层表的 Mapper
```

过程层**不依赖任何业务 Service**：候选怎么查、子过程条件怎么判、补偿动作怎么落地，
全部由业务侧实现 `ParentProcessProbe` / `ParentProcessAggregator` / `ProcessInvariant` 注入。
新增一类父过程（如将来的续订计划）只需新增探测器 + 聚合器，过程层零改动。

### 2. 补偿规则引擎（第一档 2.1）

| 层 | 职责 | 落点 |
| --- | --- | --- |
| 探测 | 按规则表的 `parent_status` 取候选 → 求值子过程条件 → 产出决策（**只读**） | `ProcessReconcileEngineImpl` |
| 决策 | 「父状态 + 子条件 → 补偿动作 + 目标状态」，可在线启停 | 表 `process_reconcile_rule` |
| 执行 | 复用统一迁移出口做条件更新并留痕 | `OrderProcessAggregator` → `ProcessTransitionExecutor` |

- 规则种子 3 条：两条与重构前行为等价（默认启用），一条「全取消补偿」默认停用，
  并在描述里注明**启用前需同步放开 `state_transition_rule` 的 `ORDER/CANCEL/3`**；
- `OrderInfoService.reconcileOrderAggregation` **已删除**（避免两套判定口径并存），
  `OrderProcessReconcileJob` 改为调用 `ProcessReconcileCoordinator.reconcile`；
- 两处刻意的设计边界：① **同一主体一轮只补偿一次**（按规则 id 取首个命中），避免多规则叠加连跳两个状态；
  ② 条件语义**不配置化**（枚举 + 业务侧实现），规则表只决定「用哪个条件、补偿到什么状态」。

### 3. 双通道自愈（第一档 2.3）

- 新增表 `process_pending_task`：子过程状态变更**在同一事务内**入队一条「父过程待聚合」待办；
  去重键 `(scene, entity_id, trigger_action, status)`；
- 6 处入队点：批量/单条开始配送、签收、拒收、任务取消、缺货批量取消、退订联动作废任务；
- `ProcessPendingTaskJob` 每 5 秒消费：按父过程**最新状态**重新探测 → 补偿 → 标记完成；
  失败按指数退避（5s→300s）重试，超 5 次置「已放弃」并告警，交由兜底通道；
- 兜底通道（`OrderProcessReconcileJob`，10 分钟）保留，职责从「主责」降为「最后防线」；
- 顺带修复一处真实漂移来源：**单条开始配送原先没有联动订单状态**（只有批量路径有），
  已补齐为与批量同口径。

### 4. 不变量体检（第一档 2.2）

新增表 `process_invariant_violation` + 6 个检查项（探测用只读 SQL 表达，修复必须经业务出口）：

| 编码 | 不变量 | 处置 | 落点 |
| --- | --- | --- | --- |
| `INV_QUOTA_LEDGER` | 配额已售数 = 台账合计（限定 `deleted = 0`） | 自动修复 | `module/product/invariant` |
| `INV_TASK_RECORD` | 任务已完成 ⇒ 签收记录已签收 | 自动修复 | `module/delivery/invariant` |
| `INV_SIGN_INTAKE` | 已签收 ⇒ 存在营养摄入记录 | 自动修复 | `module/delivery/invariant` |
| `INV_ORDER_TASK` | 任务覆盖「品种 × 配送日」全网格 | 自动修复 | `module/delivery/invariant` |
| `INV_ORDER_AGGREGATION` | 父状态与子任务集合一致 | 自动修复 | `module/order/invariant` |
| `INV_PAYMENT_CONSISTENCY` | 订单状态与支付流水互证 | **仅告警** | `module/order/invariant` |

- 执行层通用：`ProcessInvariantScanner`（探测 → 记录 → 逐条修复 → 复检闭环 → 出报告）；
- 记录语义：每个（不变量 × 主体）**一行当前状态** + `reopen_count`（重复漂移计数，自愈有效性度量）；
- 假阳性控制：`INV_PAYMENT_CONSISTENCY` 的「流水成功但订单未落账」方向只检出自成功超过 5 分钟的记录，
  避免把支付对账任务的正常处理窗口误报为不一致。

### 5. 契约矩阵测试（第一档 2.4）

`src/test/java/com/milk/order/contract/StateMachineContractTest.java`，3 个用例：

- **矩阵 A · 规则覆盖**：白名单语义下漏配一行 = 该迁移静默被禁止，因此断言 35 个可达
  （场景/动作/来源状态）组合全部有规则行；
- **矩阵 B · 安全关键禁止**：12 项（已完成任务不可回退、已退订订单不可流转、配送中订单不可退订等）
  + 未配置组合默认禁止；
- **矩阵 C · 台账可回放**：用 `process_transition_log` 逐步重放订单生命周期，断言每步首尾相接、
  回放结果与真实状态一致。

## 数据库变更

```sql
-- 开发库与实验库均已执行（实验库由开发库结构重建）
CREATE TABLE process_reconcile_rule      (...);  -- 过程补偿规则（决策层）
CREATE TABLE process_invariant_violation (...);  -- 不变量体检记录
CREATE TABLE process_pending_task        (...);  -- 自愈待办（实时通道）
ALTER TABLE nutrition_intake ADD UNIQUE KEY uk_delivery_record (delivery_record_id);
-- 种子：process_reconcile_rule 3 条；sys_config 新增 process.pending.enabled、process.invariant.scan.enabled
```

> `process_pending_task` 的唯一键**必须包含 `status`**：否则逻辑删除的「已处理」行仍占用业务键，
> 会让同一业务键的新待办**静默入队失败**。这与之前 `daily_quota_usage` 的坑同源，属主动规避。
