# 2026-09-19 混沌注入（事务中间故障）与长稳对账度量

## 背景

第二档的第二项（后续扩展方案 3.2）。前面的实验验证的都是**完整的坏数据**（重复回调、状态漂移、
并发冲突），但真实系统最凶的故障是**事务做到一半被打断**。本次补上两块：

1. **混沌注入**：在真实事务的中间步骤注入失败，验证"中间失败不留半截数据"与"被打断的业务能被收敛"；
2. **长稳对账度量**：把"业务写入 + 人为漂移 + 三条自愈通道并发"压在持续负载下，度量三通道工作量与检测延迟。

### 注入语义（本次最关键的设计决定）

注入器在目标方法**执行完之后**抛异常，精确对应「这一步的写入已发生、外层事务尚未提交」：

- 因此**注入点必须位于某个外层事务内部**（扣配额、展开任务、签收事务内的父状态聚合）；
- 若注入点自身就是事务边界，`proceed` 已提交，"抛异常"会变成另一种现象——
  **调用方看到失败、实际已生效**（模糊失败/悬挂）。那是另一个课题，本实验刻意不混用。

### 两个实测踩坑（都写进了文档，避免后人重踩）

1. **切点写在接口上匹配不到**：Spring Boot 默认 `proxy-target-class`（CGLIB），
   方法签名的声明类型是**实现类**，因此 `execution(* XxxService.deduct(..))` 命中 0 次
   （最初实验里"注入次数 = 0 / 命中 = 0"）。改为 `execution(* ...service..*.deduct(..))` 后正常。
   教训：**实验"没反应"时先确认注入真的发生了，再解读数据。**
2. **秒精度时间列让延迟度量失去意义**：`DATETIME` 下「入队 → 处理完成」只会落在 0ms / 1000ms 两档。
   改为 `DATETIME(3)` 后才得到 p50 81ms / p95 216ms。
   结论：**时间列精度也是可观测性的一部分**，度量能力需要在建模时就设计。

## 验证结果

### 实验十（混沌注入）

| 对照 | 注入点 | 关键结果 |
| --- | --- | --- |
| A | 支付事务中的扣配额 | 失败后订单仍待支付、0 流水 / 0 任务 / 配额 0 / 台账 0 / PAY 台账 0；对账查单后补偿落账 1 次，各写一份 |
| B | 支付事务的最后一步（展开任务） | 状态抢占、配额扣减、支付流水**全部回滚**；撤防后重试完整成功、不产生重复 |
| C | 签收事务内的父状态聚合 | 记录 / 任务 / 营养 / 父状态全部回滚；重试后一次性完成，SIGN 台账恰好 1 条 |
| D | 全部注入点（60% 概率、最多 4 次） | 4 笔被打断的支付全部由对账补回；6 处人为漂移 2 轮收敛；最终零非法状态、零重复副作用、零不变量违规 |

### 实验十一（长稳度量，6 秒压缩负载）

```text
业务操作成功 36 / 并发冲突 0          人为注入漂移 624
实时通道 362 轮 / 补偿生效 10         兜底通道 75 轮 / 补偿生效 543
体检 33 轮 / 自动修复 71             停机后最终收敛 0 / 1 轮
待办 27 行 / 已处理 24 / 已放弃 0 / 到期未处理 0
体检记录 12 行 / 重复漂移合计 125
检测延迟 p50 81ms / p95 216ms / max 218ms
最终：12/12 已完成，0 非法状态，0 重复成功流水，0 重复 PAY 台账，12 条营养摄入，体检零检出/零未闭环
迁移台账：生效 24 / CAS 冲突 9（冲突体现为"未生效"，不是重复副作用）
```

**由此得到一条设计论证（已写入文档与术语表）**：624 次漂移里实时通道只处理了 10 次，
因为注入的漂移"没有任何子过程事件"——**事件驱动的实时通道对"没有事件发生的写入丢失"无能为力**，
而周期扫描的检测窗口又太长。**两条通道覆盖两类不同失效形态，双通道不是重复建设。**

## 发现的新问题（未修复，已记录）

**补偿规则覆盖盲区**：特征化测试构造「订单已支付(2) + 子任务已全部签收(3)」
（配送联动与聚合写入同时丢失），结果：

- 现有规则命中：**无**（规则表有 `(2,HAS_DISPATCHING_TASK→3)` 与 `(3,ALL_TASKS_TERMINAL→4)`，
  缺 `(2,ALL_TASKS_TERMINAL→4)`）；
- 双通道补偿生效数：0；通道跑完后订单仍为 2；
- 不变量体检检出：**0**（现有不变量也看不出问题）。

即这条漂移**既不被补偿、也不被判为违规**，静默停在"已支付"。
修复需补一条规则 **并** 放开 `ORDER/COMPLETE/2` 的迁移闸门（否则补偿会被闸门拒绝）——
"配了规则 ≠ 配对了规则"的又一个实例。已列入后续扩展方案 §3.4（0.5 人日）；
测试用例断言的是**当前行为**（用于固化该盲区），补齐后需同步翻转断言。

## 尚存不确定性

1. **长稳是"高密度压缩"**：6 秒负载能回答"持续负载下是否稳定收敛"，
   **不能**回答"运行数小时后是否缓慢退化"（缓存膨胀、表膨胀、连接泄漏）。需要小时级运行 + 资源曲线采集。
2. **混沌注入是白盒的**：注入点在代码里预先选定，覆盖"事务中间故障"一类；
   **未覆盖**进程被杀、网络分区、数据库不可用、磁盘满、时钟跳变。需要进程级/网络级故障工具。
3. **"模糊失败"语义未验证**：当注入点自身是事务边界时，会出现"调用方看到失败、实际已生效"，
   本实验刻意避开该形态；真要验证它需要另外设计（幂等查询 + 用户可重试的提示）。
4. **检测延迟只覆盖实时通道**：兜底通道与体检的"检测延迟"取决于调度周期（10 分钟 / 30 分钟），
   本次未对其做分布度量（口径上它们是窗口而不是延迟）。
5. **延迟度量依赖列精度**：已把 `process_pending_task` 改为毫秒精度；体检记录与迁移台账仍是秒精度，
   若要对它们做细粒度度量需同样升级。
6. **规则覆盖盲区仍未修**（见上）：这是本次主动发现的、可立即修但不该顺手改的问题
   （补规则会改变行为，需要先确认"已支付订单直接转已完成"在业务上可接受）。
