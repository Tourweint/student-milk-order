# 2026-09-19 业务过程抽象与可靠执行层重构

## 背景

毕业设计评审反馈「选题偏简单」。重新审视后确认：本项目真正的问题不是「做一个订奶系统」，
而是「一个现实业务对象会经历长期、多阶段、异步、可失败的执行过程，系统如何让这个过程在并发、
重复、超时和局部失败下仍然可控」。据此把系统从「订单管理系统」重新抽象为
**「周期性业务履约的状态管理与异常恢复」**，并把原本零散散落在各 Service 里的技巧
（幂等、CAS、锁、台账、对账、补偿、超时任务）统一为「业务过程的可靠执行机制」。

本次改动做了两件事：

1. **把抽象落成代码**（此前抽象只存在于文档，缺少可指认的工程产物）；
2. **补上验证层**（此前完全没有测试与实验，无法证明机制有效）。

## 主要改动

### 1. 新增过程层 `com.milk.order.process`

| 类 | 职责 |
| --- | --- |
| `ProcessTransitionExecutor` / `...Impl` | 状态迁移统一出口：规则校验 + CAS 条件更新 + 迁移留痕 |
| `TransitionSpec` | 迁移规格（场景/动作/主体/起止状态/冲突提示/是否受规则管控） |
| `ProcessTransitionLog` + `Mapper` | 迁移台账实体与持久化 |

提供两组语义：

- `require(...)`：规则禁止或 CAS 冲突都抛业务异常（用户直接发起的操作）；
- `attempt(...)`：两者都返回 false 不抛异常（批量流转、定时兜底、对账补偿，天然幂等）。

### 2. 新增可靠性层 `com.milk.order.reliability`

| 类 | 职责 |
| --- | --- |
| `IdempotencyGuard` | 把数据库唯一键冲突翻译为「已存在」，实现基于数据库约束的幂等 |

### 3. 三个业务模块迁移到统一出口

`OrderInfoServiceImpl`、`DeliveryTaskServiceImpl`、`SubscriptionPlanServiceImpl` 中
所有状态迁移（约 20 处）改为经 `ProcessTransitionExecutor` 执行，不再直接依赖
`StateMachineService`，也不再手写「规则判断 + 条件更新 + 抛异常」三件套。

具体迁移点：

- 订单：支付（模拟支付 / 微信回调）、退订、超时取消、配送联动、手动完成、全部终态自动完成；
- 配送任务：单条/批量开始配送、任务取消、签收、拒收、缺货批量取消、订单退订联动作废，
  以及配送记录子状态机（签收记录，未纳入规则表，只做 CAS 与留痕）；
- 续订计划：暂停、恢复、关闭、续订执行。

### 4. 新增父子状态聚合对账与兜底任务

- `OrderInfoService.reconcileOrderAggregation(limit)`：修复两类父状态漂移
  （已支付但子任务已配送 → 补配送中；配送中但子任务全终态 → 补已完成）；
- `OrderProcessReconcileJob`：每 10 分钟执行，可用 `order.process.reconcile.enabled` 关闭。

> **后续调整（同日晚）**：上述补偿规则已下沉到 `process_reconcile_rule` 规则表
> （探测 / 决策 / 执行三层分离），`reconcileOrderAggregation` 已随之删除，
> `OrderProcessReconcileJob` 改为调用 `ProcessReconcileCoordinator`。
> 详见 `2026-09-19-异常恢复深化（补偿规则引擎+双通道自愈+不变量体检）.md`。

## 接口与服务契约变更

`OrderInfoService` 两个方法由 `void` 改为 `boolean`（返回是否发生迁移），并新增一个方法：

```java
boolean markDeliveringIfPaid(Long orderId);
boolean completeOrderIfAllTasksDone(Long orderId);
int reconcileOrderAggregation(int limit);
```

HTTP 接口契约**新增一个只读接口**（其余不变）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/system/transition-log/list` | 过程迁移台账分页（仅管理员）：按场景/动作/主体/业务单号/结果/时间范围筛选 |

配套：`ProcessTransitionLogService` + `ProcessTransitionLogServiceImpl`（`module/system`）、
前端 `api/system.ts#getTransitionLogList` 与「系统管理 → 过程迁移台账」页签（只读）。
台账**不提供修改与删除**：它是已提交业务事实的记录，删改会破坏可追溯性。

## 实验暴露并修复的缺陷

本轮实验最有价值的产出：**5 个真实缺陷被暴露并修复**，其中 2 个只在并发下出现。

| 编号 | 缺陷 | 修复 |
| --- | --- | --- |
| D1 | 幂等靠应用层「先 `selectCount` 再 `insert`」，并发下重复生成任务 | 业务唯一键 + `IdempotencyGuard`；任务生成前先按品种合并需求 |
| D2 | `StateMachineServiceImpl` 用 `cache.clear()` + `putAll()` 刷新规则缓存，并发读取方在清空窗口内读到空表，白名单语义下**瞬时全禁** | 改为构造完整新表后一次性替换 `volatile` 引用；`@PostConstruct` 启动预热 |
| D3 | 同一事务内「先快照读、再加锁写」同一行：MariaDB 直接报 `Record has changed since last read` 拒绝（MySQL 静默取最新版本），并发扣减只成功 25/200 | 扣减改为一次性 `SELECT ... FOR UPDATE` 加锁读；统一隔离级别为 `READ_COMMITTED` |
| D4 | 副作用（扣配额、写流水）先于状态抢占（CAS）执行，落败方已做副作用才失败，并发下互撞唯一键 | `payOrder` / `handleWechatPayNotify` 调整为**先抢占状态、再执行副作用** |
| D5 | 「每一次状态迁移都写入台账」存在空洞：退订/缺货取消联动作废签收记录时无台账记录 | `markRecordRejected` 改为按任务查询未签收记录后**逐条经过程层执行器 `attempt` 提交**（宽松迁移 + 留痕）。由「统一论文与代码表述」时逐条核对不变量发现，回归守卫为实验五 |

实验数据与回归守卫详见 `docs/实验/实验设计与结果.md`。

- `mvn -DskipTests compile` 通过；
- `cd school-ui && npm run build` 通过；
- 台账接口端到端验证：启动后端 → `POST /api/auth/login`（admin）取 token →
  `GET /api/system/transition-log/list` 返回 `code=200`，场景/动作/主体/业务单号/起止状态/结果/操作人

## 尚存不确定性

- 实验只在 MariaDB 12.1 上实测；MySQL 8 为设计目标但未实测（预期统一隔离级别后行为一致）。
- 实验为单进程单库并发，未覆盖多实例部署与网络分区。
- 迁移台账写入为「尽力而为」（失败只告警），如需强审计需改为同事务强一致。
- `delivery_record` 子状态机未纳入规则表，只做 CAS 与留痕（属有意取舍，见设计文档）。
