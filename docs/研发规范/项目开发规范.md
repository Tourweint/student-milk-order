# 学生奶订购系统 - 项目开发规范

> 本规范是项目开发的总纲，所有人工编码和 AI 辅助编码均须遵守。
> 核心思想：**架构是钢筋，代码是混凝土。钢筋先定好，混凝土随便浇。**

---

## 一、总则

### 1.1 为什么需要规范（AI协作场景）

本项目大量使用 AI 辅助编码。AI 生成代码速度极快，但如果没有明确约束，会快速产生大量结构混乱、职责不清的代码。本规范的核心作用是：

- **给 AI 明确的约束条件**：文件怎么分层、数据怎么流动、什么能做什么不能做
- **防止单文件膨胀**：AI 倾向于把所有逻辑堆在一个文件里，规范强制拆分
- **保证架构一致性**：无论谁（人或AI）写代码，产出的结构都是一致的
- **降低后期维护成本**：前期 1 小时定规范，后期省 10 小时重构

### 1.2 核心设计原则

1. **高内聚、低耦合**
2. **分层隔离、单向依赖**
3. **单一职责：一个文件/类/组件只做一件事**
4. **上层易变、下层稳定；越抽象越稳定，越具体越灵活**
5. **能抽象绝不具体，能复用绝不重复**
6. **变动频繁的层尽量薄，核心稳定的层尽量纯**

### 1.3 文档驱动开发流程

所有功能开发遵循"先文档、后实现、再校验"：

1. **需求澄清**：明确目标、边界、影响范围
2. **文档先行**：先更新接口文档/架构文档，确认 API 路径、参数、返回结构
3. **代码实现**：按文档实现，保持结构一致
4. **验证与回写**：编译、测试、联调后回写文档结论
5. **变更沉淀**：大改动写入 `docs/变更记录/`

**大改动判定标准**（满足任一须写变更日志）：
- 目录结构或模块边界调整
- API 路径或返回结构变化
- 认证/权限模型变化
- 数据库表结构变化
- 端口、部署流程、运行方式变化

## 二、全局代码规范（前后端统一）

### 2.1 单一职责原则

- 一个文件、一个模块、一个类、一个组件 **只承担唯一核心职责**
- 功能重叠、职责混杂的代码必须拆分
- 禁止一个文件同时处理渲染、业务、数据存储、外部请求多种逻辑

### 2.2 文件行数约束

- **任意单文件代码行数严格不超过 500 行**
- 临近 400 行必须开始考虑拆分子文件、子模块、子组件
- 超过 500 行的文件在代码审查时直接打回

### 2.3 禁止硬编码

- 固定文本、固定标识、固定参数、固定配置不允许散落业务代码中
- 所有常量、配置、枚举统一集中管理
  - 后端：`common/constant/`、`common/enums/`
  - 前端：`utils/` 下的常量文件或 `stores/`
- 业务逻辑只读配置，不手写固定值

### 2.4 类型与数据规范

- 所有输入、输出、对象结构**明确约束类型与结构**
- 后端：DTO/VO/Entity 严格区分，禁止 Entity 直接作为接口返回
- 前端：TypeScript 严格模式，接口返回数据定义 interface/type
- 禁止隐式类型、模糊结构、`any` 滥用
- 数据结构统一定义，全局复用，不重复定义相似结构

### 2.5 依赖原则

- **单向依赖：外层依赖内层，内层绝不反向依赖外层**
- 稳定层不依赖易变层
- 通用基础层不依赖业务层
- 后端依赖方向：`controller → service → mapper → database`，禁止反向
- 前端依赖方向：`views → components → api/stores → utils`，禁止组件反向依赖页面

## 三、后端开发规范

### 3.1 分层架构

后端整体从**外层交互 → 中层业务 → 底层数据**逐级递进：

```
┌─────────────────────────────────────────┐
│  交互路由层 (Controller)                  │  最外层、高变动
│  接收请求、参数校验、调用Service、返回响应  │
├─────────────────────────────────────────┤
│  业务服务层 (Service)                     │  核心编排层
│  业务流程编排、规则调度、逻辑组装           │
├─────────────────────────────────────────┤
│  数据访问层 (Mapper)                      │
│  数据读写映射、SQL 操作                    │
├─────────────────────────────────────────┤
│  数据模型层 (Entity)                      │  最内层、稳定
│  数据库表结构映射                          │
└─────────────────────────────────────────┘
         ↑ 横切：common / config / security / exception
```

### 3.2 各层职责边界

#### Controller（交互路由层）

**允许做：**
- 接收外部请求与参数
- 统一参数合法性校验（`@Valid` + Bean Validation）
- 调用下层 Service 能力
- 统一封装对外响应格式（`ApiResponse`）

**禁止做：**
- 书写任何业务判断、流程逻辑
- 直接操作数据库（调用 Mapper）
- 直接调用外部第三方接口
- 掺杂定制化业务规则
- 一个 Controller 方法超过 30 行（超过说明业务逻辑泄露到 Controller 了）

#### Service（业务服务层）

**允许做：**
- 组装完整业务执行流程
- 调用 Mapper 完成数据读写
- 调用其他 Service 完成跨模块业务
- 抛出标准业务异常（`BusinessException`）
- 事务管理（`@Transactional`）

**禁止做：**
- 耦合前端展示、响应结构、页面相关概念
- 直接获取 HttpServletRequest/Response（应通过参数传入）
- 书写底层通用工具能力

#### Mapper（数据访问层）

**允许做：**
- 定义数据读写接口
- 复杂 SQL 编写（XML 或注解）
- 单表 CRUD（继承 MyBatis-Plus BaseMapper 自动获得）

**禁止做：**
- 承载业务逻辑、业务判断
- 编写流程、规则、计算逻辑

#### Entity（数据模型层）

**允许做：**
- 定义数据库表字段映射
- 定义表间关联关系

**禁止做：**
- 承载业务逻辑、业务方法
- 直接作为接口返回对象（必须转 VO/DTO）

### 3.3 模块划分规范

按业务模块划分包，每个模块内部统一六层：

```
module/
└── {模块名}/
    ├── controller/   # 控制器
    ├── service/      # Service 接口
    │   └── impl/     # Service 实现
    ├── mapper/       # Mapper 接口
    ├── entity/       # 数据库实体
    ├── dto/          # 请求数据传输对象
    └── vo/           # 响应视图对象
```

**当前模块清单**（与开题报告 9 大模块对应）：
- `auth` - 认证模块
- `user` - 用户与权限模块
- `clazz` - 班级与学生模块
- `product` - 奶品管理模块
- `order` - 订单核心模块
- `delivery` - 配送管理模块
- `nutrition` - 营养统计模块
- `stats` - 数据可视化模块
- `subscription` - 自动续订模块

**新增模块原则**：必须与开题报告功能模块对应，不随意新增无关模块。

### 3.4 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 包名 | 全小写，模块名用单数 | `com.milk.order.module.order` |
| Controller | 业务名 + Controller | `OrderController` |
| Service 接口 | 业务名 + Service | `OrderInfoService` |
| Service 实现 | 业务名 + ServiceImpl | `OrderInfoServiceImpl` |
| Mapper | 实体名 + Mapper | `OrderInfoMapper` |
| Entity | 表名驼峰，与表对应 | `OrderInfo` → `order_info` |
| DTO | 动作 + Request/DTO | `OrderCreateRequest` |
| VO | 动作 + Response/VO | `OrderDetailVO` |
| 常量类 | 业务名 + Constants | `OrderConstants` |
| 枚举类 | 业务名 + 类型 + Enum | `OrderStatusEnum` |

### 3.5 接口规范

- 统一前缀：`/api`
- 路径用名词复数，RESTful 风格：`/api/orders`、`/api/orders/{id}`
- HTTP 方法语义明确：GET 查询、POST 新增、PUT 修改、DELETE 删除
- 统一返回结构：`ApiResponse<T>` → `{ code, message, data }`
- 分页统一参数：`pageNum`（默认1）、`pageSize`（默认10）
- 接口必须写注释：方法用途、参数说明、返回说明

### 3.6 异常处理规范

- 业务异常统一抛出 `BusinessException`，禁止直接 `throw new RuntimeException()`
- 系统异常由 `GlobalExceptionHandler` 统一兜底，禁止在 Controller 里 try-catch 吞异常
- 异常消息必须对用户友好，禁止暴露堆栈信息
- 参数校验异常由 `@Valid` + 全局异常处理器统一处理

### 3.7 事务规范

- 写操作（新增/修改/删除）涉及多表操作时必须加 `@Transactional`
- 事务方法内禁止调用外部接口（HTTP/RPC），防止长事务
- 只读操作不加事务

## 四、前端开发规范

### 4.1 目录分层

```
src/
├── api/          # 接口封装层（按模块分文件）
├── components/   # 通用组件层（可复用 UI 组件）
├── router/       # 路由配置
├── stores/       # 状态管理（Pinia）
├── styles/       # 全局样式
├── utils/        # 工具函数（request、auth 等）
├── views/        # 页面层（按模块分目录）
├── App.vue
└── main.ts
```

### 4.2 各层职责边界

#### views（页面层）

**允许做：**
- 页面布局组装
- 调用 stores/api 获取数据
- 组合 components 渲染页面
- 页面级交互逻辑

**禁止做：**
- 直接写 axios 请求（必须通过 api 层封装）
- 堆砌大量业务数据处理逻辑（应抽到 utils 或 stores）
- 单文件超过 500 行

#### components（组件层）

**允许做：**
- 通用 UI 组件封装
- 接收 props、emit 事件
- 组件内部交互状态

**禁止做：**
- 直接调用 api（必须通过 props 传入数据或 emit 事件让父级处理）
- 依赖具体业务页面
- 组件内写业务逻辑

#### api（接口层）

**允许做：**
- 封装后端接口调用
- 请求参数组装
- 响应数据初步转换

**禁止做：**
- 书写业务判断逻辑
- 操作 DOM 或页面状态

#### stores（状态管理层）

**允许做：**
- 全局状态管理（用户信息、权限、全局配置）
- 跨页面共享数据
- 复杂业务状态逻辑

**禁止做：**
- 存储页面局部状态（用组件内 ref/reactive）
- 堆砌接口调用（接口调用放 api 层，store 只调用 api 层方法）

### 4.3 组件设计规范

- **单一职责**：一个组件只负责一块 UI/单一交互能力
- **大页面强制拆分**：页面容器组件 + 多个原子/业务子组件
- **通用组件与业务组件分层**：
  - `components/` 下放通用组件（不依赖具体业务）
  - 业务专属组件放在对应 `views/{模块}/components/` 下
- **组件输入输出明确**：props 定义类型和默认值，emit 事件命名清晰

### 4.4 逻辑与视图分离

- 纯 UI 文件只负责渲染、展示、基础交互
- 所有业务逻辑、数据处理、请求逻辑抽离独立模块（composables/utils/stores）
- 禁止页面组件内堆砌大量业务判断、数据处理逻辑
- 复杂逻辑用 `composables/` 下的组合式函数封装（如 `useOrderList.ts`）

### 4.5 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 页面组件 | 业务名 + 页面功能，PascalCase | `OrderManage.vue` |
| 通用组件 | 功能描述，PascalCase | `PageContainer.vue` |
| 组合式函数 | use + 功能名，camelCase | `useOrderList.ts` |
| API 文件 | 模块名，camelCase | `order.ts` |
| API 方法 | 动词 + 名词，camelCase | `getOrderList`、`createOrder` |
| Store | 业务名 + Store，camelCase | `useUserStore` |
| 工具函数 | 功能描述，camelCase | `formatDate` |
| 常量 | 全大写下划线 | `ORDER_STATUS_MAP` |
| 路由 path | 全小写连字符 | `/order-manage` |
| 路由 name | PascalCase | `OrderManage` |

### 4.6 样式规范

- 优先使用 Element Plus 组件和主题变量，不重复造轮子
- 全局样式放 `styles/`，组件内样式用 `scoped`
- 禁止在组件内写大量全局样式（会污染全局）
- 颜色、间距等设计变量统一在 `styles/variables.scss` 定义

## 五、核心数据处理规范

### 5.1 订单状态机

订单状态流转是系统核心，必须严格遵守状态机，禁止随意跳变：

```
待支付(1) ──支付成功──→ 已支付(2) ──开始配送──→ 配送中(3) ──签收完成──→ 已完成(4)
   │                       │                                            ↑
   └──取消/超时──→ 已退订(5) ←────────退订──────────────────────────┘
```

**状态变更规则：**
- 只能按箭头方向流转，禁止逆向（如已完成不能退回配送中）
- 每次状态变更必须记录变更时间和操作人
- 状态变更方法统一在 `OrderInfoService` 中，禁止在 Controller 或其他 Service 中直接修改 `status` 字段
- 状态变更前必须校验当前状态是否允许目标状态
- 配送任务开始配送（单条或"今日已送出"批量）通过 `OrderInfoService.markDeliveringIfPaid` 在同一事务内将已支付订单联动为配送中；该联动即退款闸门：开始配送后订单不可自助退订
- 订单下配送任务全部到达终态（已完成/已取消）时，系统自动将配送中订单流转为已完成（`OrderInfoService.completeOrderIfAllTasksDone`）；`PUT /order/complete/{id}` 保留为管理员手动提前完成入口

### 5.2 每日机动配额（替代传统库存）

- 本系统不存在传统仓库库存、入库出库、库存盘点逻辑；唯一的"余量"概念是【每日机动配额】
- 每日机动配额由学校管理员在后台**按日、按品种**手动设置（该品种当日可售机动盒数），仅用于单日零散订购（临时补订、换口味、插班临时订购），卖完即止
- 配额变动必须通过 `DailyQuotaService` 统一入口（原子扣减/回补），禁止直接修改 `daily_quota` 表
- 零散订购在支付成功事务内按品种扣减配额（任一品种不足则整单拒绝），退订按台账（`daily_quota_usage`）精确回补；余量不足时抛出业务异常
- **结转与保质期**：当日未售完的配额自动结转次日继续可售（牛奶不扔）；按 3 天保质期滚动，超出窗口的剩余自动作废（窗口内动态计算，无需定时任务）；扣减时先消耗最老的池子（最接近过期的先出）
- 学期套餐为全校统一预约定制订单，全生命周期与配额/库存无关

### 5.3 支付处理（模拟支付）

- 支付不接入真实渠道，使用模拟支付
- 支付成功后必须：
  1. 写入 `payment_record` 支付流水
  2. 更新订单状态为"已支付"
  3. 记录支付时间
  4. 展开整个配送周期的配送任务（`delivery_task`）与签收记录（`delivery_record`，每日每奶品一条）
- 以上操作必须在同一事务中完成；任务展开按"订单+奶品+日期"幂等，重复支付/重复回调不会重复生成
- 禁止重复支付（支付前校验订单状态）

### 5.4 营养计算

- 营养摄入量 = 奶品营养成分（每100ml） × 实际饮用量（ml） / 100
- 营养摄入记录由配送签收时自动生成，禁止手动修改；口径为"签收即视为当日饮用"（按签收记录估算）
- 营养统计接口只做聚合查询，不做实时计算（保证性能）

### 5.4.1 配送任务生成与签收

- 配送任务在订单支付成功时一次性展开，按订单配送日期表达两种模式：
  - **散订**（起止同日）：一次性配送，每奶品展开一条任务，任务数量=订购盒数；多笔散订订单各自展开各自的配送任务
  - **周期订**（起止区间，月度/学期套餐）：区间内每日配送，每奶品每天一条任务，任务数量=每日盒数；学期套餐仅是区间更长，展开规则相同
- 展开粒度以订单为准（"订单+奶品+日期"幂等），不按学生合并，支持"明天牛奶今天送"的提前配送场景
- 订购模式仅两种：学期套餐（主业务）与单日零散订购（辅助小众业务）
- 套餐内容（奶品与每日数量）由管理端在套餐上固定配置，仅学期套餐类型，家长下单不可自选；订单明细以服务端套餐配置为准
- 学期套餐：全校统一预约定制订单，配送周期固定约 5 个月，不参与任何配额/库存，不支持自动续订（一次性购买）
- 单日零散订购：起止同日、按盒数一次性配送，占用当日机动配额；学期套餐覆盖日内也允许散订（换口味/加购），仅受当日余量约束
- `POST /delivery/task/generate` 仅作为管理端手工补生成入口（历史订单/遗漏数据）
- **日常配送由配送站（DELIVERY 角色）执行**：在配送站面板点击"今日已送出"（按日期+可选班级批量开始配送，幂等），逐条记录派送人与派送时间（`delivery_task.dispatch_by`/`dispatch_time`），形成"谁在何时送出"的审计痕迹；单条开始配送同样记录。开始配送（单条/批量）仅管理员与配送站可操作，班主任不可；订单管理页不提供独立"开始配送"入口，订单进入配送中一律由配送任务联动触发
- **退款闸门**：订单一经开始配送（进入配送中或存在配送中任务）即不可自助退订，学期套餐与散订一致；开始配送后的退费一律走线下处理，系统不提供按天折算退费。退订回补配额只发生在尚未开始配送的订单上
- 签收仍由班主任按日进行（配送站对配送记录只读，不可签收）；管理端支持按"日期+班级"批量签收，班主任数据范围强制限定本班，管理员可代签全部班级
- **签收/拒收前置条件：任务必须已开始配送（配送中，即配送站已点"今日已送出"或单条送出）**；批量签收仅处理已送出任务的记录，未送出的不会被代签；单条签收/拒收对未送出任务直接拒绝
- 签收（单条/批量）在同一事务内完成：更新签收记录、完成任务、生成营养摄入记录；任务全部终态后自动完成订单
- 订单退订时联动作废其未签收的配送任务（任务→已取消，签收记录→拒收），防止退订后仍被签收

### 5.5 自动续订（已下线）

- 自动续订功能已随月度套餐一并下线：现行仅学期套餐（一次性购买）与单日零散订购，均无续订场景
- 续订相关代码保留但不可达；新学期预约届时以"提前开放学期套餐订购"的方式实现

### 5.6 数据安全

- 密码必须 BCrypt 加密存储，禁止明文
- 接口返回用户信息时不返回密码字段
- 家长只能查看自己孩子的数据，班主任只能查看本班数据，管理员可查看全部
- 数据权限校验在 Service 层完成，禁止依赖前端传参控制权限

## 六、AI 协作规范

### 6.1 让 AI 写代码前必须提供的信息

每次让 AI 写代码，必须在 prompt 中包含：

1. **本规范文件**（或关键章节）—— 告诉 AI 分层规则、命名规则、行数限制
2. **相关接口文档** —— 告诉 AI API 路径、参数、返回结构
3. **相关实体/DTO 定义** —— 告诉 AI 数据结构
4. **明确的功能范围** —— 告诉 AI 只做什么，不做什么

### 6.2 AI 产出代码的验收标准

AI 生成的代码必须通过以下检查才能合入：

- [ ] 文件行数不超过 500 行
- [ ] 分层正确（Controller 没有业务逻辑、Service 没有直接操作响应等）
- [ ] 命名符合规范
- [ ] 没有硬编码（常量/枚举已抽取）
- [ ] 类型定义完整（没有滥用 any）
- [ ] 接口路径和返回结构与文档一致
- [ ] 异常处理规范（业务异常用 BusinessException）
- [ ] 关键业务逻辑有注释

### 6.3 禁止让 AI 做的事

- 禁止让 AI 一次性生成整个模块（必须拆分为：先 entity → mapper → service → controller，逐步生成逐步验证）
- 禁止让 AI 修改架构/目录结构（架构变更必须人工讨论确认）
- 禁止让 AI 直接修改数据库表结构（表结构变更必须先更新文档，再执行 SQL）
- 禁止让 AI 写核心业务逻辑（订单状态流转、库存变动、支付）而不经过人工审核
