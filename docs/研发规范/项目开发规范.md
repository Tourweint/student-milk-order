# 学生奶订购系统 - 项目开发规范

> 本规范是项目开发的总纲，所有人工编码和 AI 辅助编码均须遵守。
> 核心思想：**架构是钢筋，代码是混凝土。钢筋先定好，混凝土随便浇。**

---

## 一、总则

### 1.1 为什么需要规范（AI协作场景）

本项目大量使用 AI 辅助编码。AI 生成代码速度极快，但如果没有明确约束，会快速产生大量结构混乱、职责不清的代码。本规范的核心作用是：

- **给 AI 明确的约束条件**：文件怎么分层、数据怎么流动、什么能做什么不能做
- **防止单文件膨胀**：AI 倾向于把所有逻辑堆在一个文件里，规范强制拆分
- **保证架构一致性**：无论谁（人或AI）写代码，产出的结构都是一致的
- **降低后期维护成本**：前期 1 小时定规范，后期省 10 小时重构

### 1.2 核心设计原则

1. **高内聚、低耦合**
2. **分层隔离、单向依赖**
3. **单一职责：一个文件/类/组件只做一件事**
4. **上层易变、下层稳定；越抽象越稳定，越具体越灵活**
5. **能抽象绝不具体，能复用绝不重复**
6. **变动频繁的层尽量薄，核心稳定的层尽量纯**

### 1.3 文档驱动开发流程

所有功能开发遵循"先文档、后实现、再校验"：

1. **需求澄清**：明确目标、边界、影响范围
2. **文档先行**：先更新接口文档/架构文档，确认 API 路径、参数、返回结构
3. **代码实现**：按文档实现，保持结构一致
4. **验证与回写**：编译、测试、联调后回写文档结论
5. **变更沉淀**：大改动写入 `docs/变更记录/`

**大改动判定标准**（满足任一须写变更日志）：
- 目录结构或模块边界调整
- API 路径或返回结构变化
- 认证/权限模型变化
- 数据库表结构变化
- 端口、部署流程、运行方式变化

## 二、全局代码规范（前后端统一）

### 2.1 单一职责原则

- 一个文件、一个模块、一个类、一个组件 **只承担唯一核心职责**
- 功能重叠、职责混杂的代码必须拆分
- 禁止一个文件同时处理渲染、业务、数据存储、外部请求多种逻辑

### 2.2 文件行数约束

- **任意单文件代码行数严格不超过 500 行**
- 临近 400 行必须开始考虑拆分子文件、子模块、子组件
- 超过 500 行的文件在代码审查时直接打回

### 2.3 禁止硬编码

- 固定文本、固定标识、固定参数、固定配置不允许散落业务代码中
- 所有常量、配置、枚举统一集中管理
  - 后端：`common/constant/`、`common/enums/`
  - 前端：`utils/` 下的常量文件或 `stores/`
- 业务逻辑只读配置，不手写固定值

### 2.4 类型与数据规范

- 所有输入、输出、对象结构**明确约束类型与结构**
- 后端：DTO/VO/Entity 严格区分，禁止 Entity 直接作为接口返回
- 前端：TypeScript 严格模式，接口返回数据定义 interface/type
- 禁止隐式类型、模糊结构、`any` 滥用
- 数据结构统一定义，全局复用，不重复定义相似结构

### 2.5 依赖原则

- **单向依赖：外层依赖内层，内层绝不反向依赖外层**
- 稳定层不依赖易变层
- 通用基础层不依赖业务层
- 后端依赖方向：`controller → service → mapper → database`，禁止反向
- 前端依赖方向：`views → components → api/stores → utils`，禁止组件反向依赖页面

## 三、后端开发规范

### 3.1 分层架构

后端整体从**外层交互 → 中层业务 → 底层数据**逐级递进：

```
┌─────────────────────────────────────────┐
│  交互路由层 (Controller)                  │  最外层、高变动
│  接收请求、参数校验、调用Service、返回响应  │
├─────────────────────────────────────────┤
│  业务服务层 (Service)                     │  核心编排层
│  业务流程编排、规则调度、逻辑组装           │
├─────────────────────────────────────────┤
│  数据访问层 (Mapper)                      │
│  数据读写映射、SQL 操作                    │
├─────────────────────────────────────────┤
│  数据模型层 (Entity)                      │  最内层、稳定
│  数据库表结构映射                          │
└─────────────────────────────────────────┘
         ↑ 横切：common / config / security / exception
```

### 3.2 各层职责边界

#### Controller（交互路由层）

**允许做：**
- 接收外部请求与参数
- 统一参数合法性校验（`@Valid` + Bean Validation）
- 调用下层 Service 能力
- 统一封装对外响应格式（`ApiResponse`）

**禁止做：**
- 书写任何业务判断、流程逻辑
- 直接操作数据库（调用 Mapper）
- 直接调用外部第三方接口
- 掺杂定制化业务规则
- 一个 Controller 方法超过 30 行（超过说明业务逻辑泄露到 Controller 了）

#### Service（业务服务层）

**允许做：**
- 组装完整业务执行流程
- 调用 Mapper 完成数据读写
- 调用其他 Service 完成跨模块业务
- 抛出标准业务异常（`BusinessException`）
- 事务管理（`@Transactional`）

**禁止做：**
- 耦合前端展示、响应结构、页面相关概念
- 直接获取 HttpServletRequest/Response（应通过参数传入）
- 书写底层通用工具能力

#### Mapper（数据访问层）

**允许做：**
- 定义数据读写接口
- 复杂 SQL 编写（XML 或注解）
- 单表 CRUD（继承 MyBatis-Plus BaseMapper 自动获得）

**禁止做：**
- 承载业务逻辑、业务判断
- 编写流程、规则、计算逻辑

#### Entity（数据模型层）

**允许做：**
- 定义数据库表字段映射
- 定义表间关联关系

**禁止做：**
- 承载业务逻辑、业务方法
- 直接作为接口返回对象（必须转 VO/DTO）

### 3.3 模块划分规范

按业务模块划分包，每个模块内部统一六层：

```
module/
└── {模块名}/
    ├── controller/   # 控制器
    ├── service/      # Service 接口
    │   └── impl/     # Service 实现
    ├── mapper/       # Mapper 接口
    ├── entity/       # 数据库实体
    ├── dto/          # 请求数据传输对象
    └── vo/           # 响应视图对象
```

**当前模块清单**（与开题报告 9 大模块对应）：
- `auth` - 认证模块
- `user` - 用户与权限模块
- `clazz` - 班级与学生模块
- `product` - 奶品管理模块
- `order` - 订单核心模块
- `delivery` - 配送管理模块
- `nutrition` - 营养统计模块
- `stats` - 数据可视化模块
- `system` - 系统管理模块（参数配置、状态迁移规则、过程迁移台账、操作日志）

**新增模块原则**：必须与开题报告功能模块对应，不随意新增无关模块。

### 3.4 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 包名 | 全小写，模块名用单数 | `com.milk.order.module.order` |
| Controller | 业务名 + Controller | `OrderController` |
| Service 接口 | 业务名 + Service | `OrderInfoService` |
| Service 实现 | 业务名 + ServiceImpl | `OrderInfoServiceImpl` |
| Mapper | 实体名 + Mapper | `OrderInfoMapper` |
| Entity | 表名驼峰，与表对应 | `OrderInfo` → `order_info` |
| DTO | 动作 + Request/DTO | `OrderCreateRequest` |
| VO | 动作 + Response/VO | `OrderDetailVO` |
| 常量类 | 业务名 + Constants | `OrderConstants` |
| 枚举类 | 业务名 + 类型 + Enum | `OrderStatusEnum` |

### 3.5 接口规范

- 统一前缀：`/api`
- 路径用名词复数，RESTful 风格：`/api/orders`、`/api/orders/{id}`
- HTTP 方法语义明确：GET 查询、POST 新增、PUT 修改、DELETE 删除
- 统一返回结构：`ApiResponse<T>` → `{ code, message, data }`
- 分页统一参数：`pageNum`（默认1）、`pageSize`（默认10）
- 接口必须写注释：方法用途、参数说明、返回说明

### 3.6 异常处理规范

- 业务异常统一抛出 `BusinessException`，禁止直接 `throw new RuntimeException()`
- 系统异常由 `GlobalExceptionHandler` 统一兜底，禁止在 Controller 里 try-catch 吞异常
- 异常消息必须对用户友好，禁止暴露堆栈信息
- 参数校验异常由 `@Valid` + 全局异常处理器统一处理

### 3.7 事务规范

- 写操作（新增/修改/删除）涉及多表操作时必须加 `@Transactional`
- 事务方法内禁止调用外部接口（HTTP/RPC），防止长事务
- 只读操作不加事务

## 四、前端开发规范

### 4.1 目录分层

```
src/
├── api/          # 接口封装层（按模块分文件）
├── components/   # 通用组件层（可复用 UI 组件）
├── router/       # 路由配置
├── stores/       # 状态管理（Pinia）
├── styles/       # 全局样式
├── utils/        # 工具函数（request、auth 等）
├── views/        # 页面层（按模块分目录）
├── App.vue
└── main.ts
```

### 4.2 各层职责边界

#### views（页面层）

**允许做：**
- 页面布局组装
- 调用 stores/api 获取数据
- 组合 components 渲染页面
- 页面级交互逻辑

**禁止做：**
- 直接写 axios 请求（必须通过 api 层封装）
- 堆砌大量业务数据处理逻辑（应抽到 utils 或 stores）
- 单文件超过 500 行

#### components（组件层）

**允许做：**
- 通用 UI 组件封装
- 接收 props、emit 事件
- 组件内部交互状态

**禁止做：**
- 直接调用 api（必须通过 props 传入数据或 emit 事件让父级处理）
- 依赖具体业务页面
- 组件内写业务逻辑

#### api（接口层）

**允许做：**
- 封装后端接口调用
- 请求参数组装
- 响应数据初步转换

**禁止做：**
- 书写业务判断逻辑
- 操作 DOM 或页面状态

#### stores（状态管理层）

**允许做：**
- 全局状态管理（用户信息、权限、全局配置）
- 跨页面共享数据
- 复杂业务状态逻辑

**禁止做：**
- 存储页面局部状态（用组件内 ref/reactive）
- 堆砌接口调用（接口调用放 api 层，store 只调用 api 层方法）

### 4.3 组件设计规范

- **单一职责**：一个组件只负责一块 UI/单一交互能力
- **大页面强制拆分**：页面容器组件 + 多个原子/业务子组件
- **通用组件与业务组件分层**：
  - `components/` 下放通用组件（不依赖具体业务）
  - 业务专属组件放在对应 `views/{模块}/components/` 下
- **组件输入输出明确**：props 定义类型和默认值，emit 事件命名清晰

### 4.4 逻辑与视图分离

- 纯 UI 文件只负责渲染、展示、基础交互
- 所有业务逻辑、数据处理、请求逻辑抽离独立模块（composables/utils/stores）
- 禁止页面组件内堆砌大量业务判断、数据处理逻辑
- 复杂逻辑用 `composables/` 下的组合式函数封装（如 `useOrderList.ts`）

### 4.5 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 页面组件 | 业务名 + 页面功能，PascalCase | `OrderManage.vue` |
| 通用组件 | 功能描述，PascalCase | `PageContainer.vue` |
| 组合式函数 | use + 功能名，camelCase | `useOrderList.ts` |
| API 文件 | 模块名，camelCase | `order.ts` |
| API 方法 | 动词 + 名词，camelCase | `getOrderList`、`createOrder` |
| Store | 业务名 + Store，camelCase | `useUserStore` |
| 工具函数 | 功能描述，camelCase | `formatDate` |
| 常量 | 全大写下划线 | `ORDER_STATUS_MAP` |
| 路由 path | 全小写连字符 | `/order-manage` |
| 路由 name | PascalCase | `OrderManage` |

### 4.6 样式规范

- 优先使用 Element Plus 组件和主题变量，不重复造轮子
- 全局样式放 `styles/`，组件内样式用 `scoped`
- 禁止在组件内写大量全局样式（会污染全局）
- 颜色、间距等设计变量统一在 `styles/variables.scss` 定义

## 五、核心数据处理规范

### 5.1 订单状态机

订单状态流转是系统核心，必须严格遵守状态机，禁止随意跳变：

```
待支付(1) ──支付成功──→ 已支付(2) ──开始配送──→ 配送中(3) ──签收完成──→ 已完成(4)
   │                       │                                            ↑
   └──取消/超时──→ 已退订(5) ←────────退订──────────────────────────┘
```

**状态变更规则：**
- 只能按箭头方向流转，禁止逆向（如已完成不能退回配送中）
- **所有状态变更必须经过程层统一出口 `ProcessTransitionExecutor`**（`com.milk.order.process`）：
  一次迁移同时完成「规则校验 + CAS 条件更新 + 迁移留痕」；禁止在 Controller 或业务 Service 中
  直接修改 `status` 字段，也禁止读状态后无条件下全量更新
- 迁移的合法性由 `state_transition_rule` 规则表（**白名单语义**）驱动，管理端可在线调整；
  新增状态或动作必须同步补 `src/main/resources/sql/data.sql` 的规则种子，否则该迁移会被拒绝
- 调用语义二选一：用户直接发起的操作用 `require`（失败抛业务异常）；批量流转、定时兜底、
  对账补偿用 `attempt`（返回 false 即跳过，天然幂等）
- 每次迁移写入 `process_transition_log`（起止状态、结果、操作人、时间），成功与 CAS 冲突可区分
- **顺序不变式**：同一动作同时涉及状态迁移与副作用（扣资源、写流水、展开任务）时，必须先 CAS 抢占状态，
  落败方立即中止；禁止「先做副作用、再迁移状态」
- **父子状态聚合**：父订单状态只能由子过程聚合决定。配送任务开始配送（单条或"今日已送出"批量）通过
  `OrderInfoService.markDeliveringIfPaid` 将已支付订单联动为配送中；该联动即退款闸门：开始配送后订单不可自助退订。
  订单下配送任务全部到达终态（已完成/已取消）时，`OrderInfoService.completeOrderIfAllTasksDone` 将配送中订单流转为已完成
  （`PUT /order/complete/{id}` 保留为管理员手动提前完成入口）；漂移的探测与补偿由过程层
  `ProcessReconcileEngine` + `ProcessReconcileCoordinator` 按 `process_reconcile_rule` 规则表执行，
  补偿动作经 `ParentProcessAggregator` 落回统一迁移出口——**禁止新增硬编码的补偿 `if`**
- **补偿规则**：`process_reconcile_rule` 决定「什么漂移补偿成什么状态」，可在线启停；启用新规则前必须确认
  `state_transition_rule` 放开了对应迁移（否则补偿会被闸门拒绝）；新规则默认设为停用
- **实时自愈**：子过程状态变更时必须在**同一事务内** `ProcessPendingTaskService.enqueue`
  一条父过程自愈待办；消费端 `ProcessPendingTaskJob` 按最新状态重新探测后补偿，失败退避、超限放弃
- **不变量体检**：新增跨表约束时登记为 `ProcessInvariant`（探测只读、修复必须走业务出口）；
  涉资金或需业务判断的一律 `ALERT_ONLY`，不得自动改数据
- 订单退订、超时取消、任务取消、签收/拒收等所有迁移点均同此规范

### 5.2 每日机动配额（替代传统库存）

- 本系统不存在传统仓库库存、入库出库、库存盘点逻辑；唯一的"余量"概念是【每日机动配额】
- 每日机动配额由学校管理员在后台**按日、按品种**手动设置（该品种当日可售机动盒数），仅用于单日零散订购（临时补订、换口味、插班临时订购），卖完即止
- 配额变动必须通过 `DailyQuotaService` 统一入口（原子扣减/回补），禁止直接修改 `daily_quota` 表
- 零散订购在支付成功事务内按品种扣减配额（任一品种不足则整单拒绝），退订按台账（`daily_quota_usage`）精确回补；余量不足时抛出业务异常
- **结转与计划顺延窗口**：当日未售完的配额自动结转次日继续可售（牛奶不扔）；按 3 天的计划顺延窗口滚动，超出窗口的剩余自动作废（窗口内动态计算，无需定时任务）；扣减时先消耗最老的池子（最接近窗口到期的先出）。
  > 口径校正（2026-09-21）：本系统配送的奶为常温奶，实际保质期六个月；配额池建模的是**供货计划**而非奶的实体，"3 天"的真实语义是**计划顺延窗口**（当日未售完的计划量几天后不再可顺延的商务约定，由与奶站的合同定），不是保质期。批号/批次追溯属奶站责任域，系统仅预留钩子（见 `docs/论文/后续扩展方案.md` §4.7 与 `docs/设计方案/2026-09-21-保质期语义校正与批次追溯-设计方案.md`）。周末并入日提前 2 天的约定仍在窗口内，结论不变。
- **批次追溯钩子（2026-09-21 实现）**：`product_batch` 批次档案 + `daily_quota.batch_no` 可选标注。批次**只作标注**——不参与扣减、结转、台账口径与任何状态流转，备货仍按计划进行；系统**不做**入库/出库/效期预警（属奶站 ERP 职责域）。唯一用途是召回反查：批号 → 配额池（日期×品种）→ 扣减台账 `daily_quota_usage` → 订单/学生/配送任务与签收状态（`GET /api/product/batch/trace`）。两条边界：① 批号**不要求先建档**（事故当场可直接标注并反查），建档只提供生产/到货日期；② **学期套餐不经配额池，反查只覆盖单日零散订购**，套餐用奶需按配送日与奶站人工对照。设定配额时若批号已建档且品种不一致会被拒绝（避免批号串到别的品种池子上）；删除批次只下线档案，池子上的批号字符串保留。见 `docs/论文/后续扩展方案.md` §4.7 与 `docs/变更记录/2026-09-21-批次追溯钩子.md`
- 学期套餐为全校统一预约定制订单，全生命周期与配额/库存无关

### 5.3 支付处理（模拟支付）

- 支付不接入真实渠道，使用模拟支付
- 支付成功的处理顺序（**顺序不可调换**）：
  1. **先抢占状态**：经 `ProcessTransitionExecutor` 做 CAS（待支付→已支付）并写迁移台账；
     并发支付/并发回调下只有一个执行者能过，落败方立即中止
  2. 零散订购按品种扣减当日机动配额（`DailyQuotaService.deduct`，行锁读 + 条件更新 + 写台账）
  3. 写入/更新 `payment_record` 支付流水，记录支付时间
  4. 展开整个配送周期的配送任务（`delivery_task`）与签收记录（`delivery_record`，每日每奶品一条）
- 以上操作必须在同一事务中完成；任务展开按"订单+奶品+日期"由业务唯一键 `uk_order_product_date` 幂等，
  重复支付/重复回调不会重复生成
- 禁止重复支付（支付前校验订单状态）；回调幂等由「已支付走快速路径 + CAS 只成功一次 + 唯一键」三重保证
- 顺序颠倒（先扣配额/写流水、再 CAS）会让落败方已做副作用才失败，并发下互撞业务唯一键，禁止这样写

### 5.4 营养计算

- 营养摄入量 = 奶品营养成分（每100ml） × 实际饮用量（ml） / 100
- 营养摄入记录由配送签收时自动生成，禁止手动修改；口径为"签收即视为当日饮用"（按签收记录估算）
- 营养统计接口只做聚合查询，不做实时计算（保证性能）

### 5.4.1 配送任务生成与签收

- 配送任务在订单支付成功时一次性展开，按订单配送日期表达两种模式：
  - **散订**（起止同日）：一次性配送，每奶品展开一条任务，任务数量=订购盒数；多笔散订订单各自展开各自的配送任务
  - **周期订**（起止区间，月度/学期套餐）：区间内每日配送，每奶品每天一条任务，任务数量=每日盒数；学期套餐仅是区间更长，展开规则相同
- 展开粒度以订单为准（"订单+奶品+日期"幂等），不按学生合并，支持"明天牛奶今天送"的提前配送场景
- 订购模式仅两种：学期套餐（主业务）与单日零散订购（辅助小众业务）
- 套餐内容（奶品与每日数量）由管理端在套餐上固定配置，仅学期套餐类型，家长下单不可自选；订单明细以服务端套餐配置为准
- 学期套餐：全校统一预约定制订单，配送周期固定约 5 个月，不参与任何配额/库存，一次性购买（系统不提供续订）
- 单日零散订购：起止同日、按盒数一次性配送，占用当日机动配额；学期套餐覆盖日内也允许散订（换口味/加购），仅受当日余量约束
- **配送开始日期不得早于今天**：下单时由服务端强制校验（`OrderInfoServiceImpl.doCreateOrder`），前端日期控件同步限制。理由是过去日期在支付成功后会一次性补造整段历史配送任务，这些任务随即被 `DeliveryAutoSignJob` 当作「超时未签收」自动签收，凭空产生签收记录与营养摄入；与配送日平移「不可改到已过去的日期」同一口径。管理端补录历史数据不走下单接口
- `POST /delivery/task/generate` 仅作为管理端手工补生成入口（历史订单/遗漏数据）
- **日常配送由配送站（DELIVERY 角色）执行**：在配送站面板点击"今日已送出"（按日期+可选班级批量开始配送，幂等），逐条记录派送人与派送时间（`delivery_task.dispatch_by`/`dispatch_time`），形成"谁在何时送出"的审计痕迹；单条开始配送同样记录。开始配送（单条/批量）仅管理员与配送站可操作，班主任不可；订单管理页不提供独立"开始配送"入口，订单进入配送中一律由配送任务联动触发
- **退款闸门**：订单一经开始配送（进入配送中或存在配送中任务）即不可自助退订，学期套餐与散订一致；开始配送后的退费一律走线下处理，系统不提供按天折算退费。退订回补配额只发生在尚未开始配送的订单上
- 签收仍由班主任按日进行（配送站对配送记录只读，不可签收）；管理端支持按"日期+班级"批量签收，班主任数据范围强制限定本班，管理员可代签全部班级
- **签收/拒收前置条件：任务必须已开始配送（配送中，即配送站已点"今日已送出"或单条送出）**；批量签收仅处理已送出任务的记录，未送出的不会被代签；单条签收/拒收对未送出任务直接拒绝
- 签收（单条/批量）在同一事务内完成：更新签收记录、完成任务、生成营养摄入记录；任务全部终态后自动完成订单
- 订单退订时联动作废其未签收的配送任务（任务→已取消，签收记录→拒收），防止退订后仍被签收
- **自动签收兜底**：配送站已送出、老师当日未签收且未拒收的配送记录，由 `DeliveryAutoSignJob` 定时任务在次日凌晨（00:30）自动签收，签收人标记「系统自动签收」（备注「超时未签收，系统自动签收」），复用签收共用流程（记录未签收→已签收 CAS、任务配送中→已完成、生成营养摄入、订单全终态自动完成）。兜底窗口为「配送日期早于当天」（当天送出的记录留给老师当天签收，不自动兜底）；逐条独立事务处理，单条失败不影响其余。拒收是老师当场的即时人工动作，自动兜底只处理「未签收且未拒收」记录，不误伤
- **家长端「当日豁免」（2026-09-21 实现）**：家长当天临时不要这份奶（病假/外出）时，可申请取消该学生**今天尚未送出（待配送）**的全部任务。硬约束：① 只豁免"今天 + 待配送"——已送出的奶在途，取消等于把已出库的奶从记录里抹掉；② 取消**复用统一迁移出口**（规则闸门 + CAS + 迁移台账留痕 + 父过程自愈待办 + 签收记录联动置拒收），**不另写一套取消逻辑**；③ 次数上限按「学生 × 自然月」计，落在 `delivery_parent_exemption`（学生×自然月一行计数器），用**行锁读 + `used_count + 1 <= limit` 条件更新**保证严格不超限（`COUNT(*)` 判定在并发下会超限），次数与取消在**同一事务**内（取消失败则次数自动回退）；④ 上限由 `sys_config` 的 `delivery.parent.exemption.monthly-limit` 控制（默认 3，**配 0 等于关闭该能力**）；⑤ 零散订购的配额按台账回补原池（与缺货取消同一口径，套餐不占配额故为 no-op）；⑥ 数据范围在 Service 层强制为本人绑定学生（接口层已限 PARENT）。机制细节见 `基线文档/可靠性设计.md` §十七，实测见 `实验/实验设计与结果.md` §6.15
- **当日未送达申报（自动签收的例外通道，2026-09-21 实现）**：兜底窗口用的是**信息态**（配送站点过「今日已送出」），而"奶是否真的到校"是**物理态**；两者不一致时（车辆故障/道路中断/未备齐）兜底会替老师签收并生成营养摄入，产出一条虚假签收。因此奶站（`DELIVERY`）可对「配送中」且配送日不晚于今天的任务发起 `POST /api/delivery/task/undelivered-report` 申报，该任务随即**排除出自动签收候选集**（候选集过滤 + `autoSignOne` 单条入口再判一次，两道闸门缺一不可——候选集分批取，两次取之间可能新增申报）。**申报只打标记与待办，不新增状态、不自动改任何状态**：任务保持「配送中」，人工处置仍走签收/拒收/取消出口，管理员在配送站面板「未送达申报」页跟进并可标记已跟进（只写说明）。一条任务只允许一条申报（`uk_task` 唯一键）；已知代价是无人处置时订单会长期停在「配送中」（比制造虚假签收可取）。机制细节见 `基线文档/可靠性设计.md` §十六，实测见 `实验/实验设计与结果.md` §6.14
- **待签收提醒与一键签收**：`GET /delivery/record/pending-sign` 提供某日期（默认今天）已送出未签收记录按班级聚合的待签收汇总（班主任限本班）；数据看板展示今日待签收指标，配送站面板展示未签收提醒（配送站与老师线下接触多，可口头提醒），配送记录页提供「今日待签收 + 一键签收」入口

### 5.4.2 配送日调整（平移 / 日历重排 / 期末摊平）

三种改期/改量手段**共用同一套落账骨架**（`DeliveryTaskServiceImpl.relocateTask`：CAS 作废 → 合并/新建到目标日 → 同步签收记录 → 入队父过程自愈待办），**禁止另写第二套**（两套逻辑必然漂移，参考缺陷 D7）：

| 手段 | 入口（均仅 ADMIN） | 定位 |
|---|---|---|
| 配送日平移 | `POST /delivery/task/shift`（勾选任务 + 目标日） | 临时改期，逐条指定 |
| 配送日历重排 | `POST /delivery/task/calendar-rebalance`（日期区间） | 学期初按日历批量改期（周末/停送日并入工作日） |
| 学期末摊平 | `POST /delivery/task/rebalance`（订单 + 截止日） | 学期末把剩余盒数按截止日重新分配 |

**周末停送与调休例外（配送日历）业务规则**：

1. **周末（周六、周日）不送奶**：任务仍按"每日 1 盒"照常生成（**不动展开逻辑、不动套餐定价**），由日历重排把周末的奶挪到工作日——**周六并入周四、周日并入周五**（各提前 2 天，仍在保质期内，周四/周五各约 2 盒）。
2. **调休以官方文件为准，系统不做任何节假日自动推算**：官方调休各地不同、每年发布（存在连放 13 天的极端情况），全部由管理员在 `delivery_exception` 手工维护，**该表是唯一权威**，系统不校验"官方日历"。
   - `type=1` **停送日**（工作日放假/调休）：该日任务并入**前一个有效配送日**；连续停送（长假）时继续向前回溯，如 5/1~5/5 连休都并入 4/30（假前最后一个工作日）起向前的工作日。
   - `type=2` **补课日**（周末调休上课）：该日**照常配送**，重排跳过。
3. **开关**：`sys_config.delivery.weekend.stop` 默认 `false`（＝周末照送、与现状完全一致）；为 `false` 时重排接口**拒绝执行**并提示，不静默跳过。
4. **顺序硬约束**：先维护例外 → 再日历重排 → 最后期末摊平（摊平晚于重排，否则两者互相覆盖）。
5. **例外表只允许维护今天及以后的日期**：历史已配送/已签收属"已提交业务事实"，不可改。
6. **营养不特殊处理**：摄入记录由签收生成（"签了就算"），周五签 2 盒即记 2 盒，周六/周日 0 盒属自然结果。

**三者共性硬约束**（机制细节与判定口径见 `../基线文档/可靠性设计.md` §十三、§十四）：

- **盒数守恒**：只改配送日与合并数量，不改订单金额、套餐盒数；**不得更新 `deliveryEndDate`**（改 end 会让网格不变量把空档日 `AUTO_REPAIR` 补造任务）。
- **CAS 即幂等闸门**：作废走 `attempt(1→4)`，重复执行不重复加量，**不需要批次表**。
- **合并/加量条件更新影响 0 行必须抛异常回滚**，不能静默跳过（否则"原任务已作废、目标日未加量"＝静默丢盒）。
- **单任务单日上限 3 盒**；重排合并超限时继续向前找未满的有效工作日，找不到才跳过并计入 `messages`。
- 服务端校验，不信任前端传入的任务/日期。

管理端页面：`school-ui/src/views/delivery/DeliveryCalendar.vue`（「配送日历」：例外维护 + 一键重排 + 周末停送开关 + 开学提醒条；路由 `/delivery-calendar`）。

  2026-09-19 **整体删除**，不再保留不可达代码

### 5.6 数据安全

- 密码必须 BCrypt 加密存储，禁止明文
- 接口返回用户信息时不返回密码字段
- 家长只能查看自己孩子的数据，班主任只能查看本班数据，管理员可查看全部
- 数据权限校验在 Service 层完成，禁止依赖前端传参控制权限

### 5.7 退款与毕业清算（资金侧）

**范围**：家长对已支付/配送中订单按**期次（配送任务）**申请退款；管理员审核后执行（模拟通道即时到账）；
退订联动补齐全额退款记录；毕业时一键清算名下未完成订单。
**不做**：真实微信退款联调（T+1/回调/原路退回，机制已预留）、金额自定义（属议价，走线下）、
日历日粒度退款（任务才是履约原子单位）、订单新增"部分退款中"状态。

**业务规则**：

| # | 规则 | 说明 |
|---|------|------|
| R1 | 可退期次 = 执行时刻的「待配送(1)」∪「缺货取消」 | 缺货取消判据 `task.status=4 AND record.sign_status=3 AND reject_reason_code IS NULL`（与 `INV_TASK_COMPENSATION` 同判据）；**已退订(5) 订单整体排除**（其联动作废任务同形，避免与退订全额退款重复）；配送中/已完成/真拒收（已补送）不退 |
| R2 | 金额：零散按明细单价精确、套餐按盒均摊 + 累计制 | 套餐 `本笔 = 实付 × 累计退盒数 / 合同总盒数 − 已退累计`，上限 `实付 − 已退金额`；分母用 `order_info.contract_total_boxes` **支付时快照**（不可实时汇总任务表）；分子扣除任务上的**补送免费盒**；零散 `pay_amount` 无优惠，用明细快照单价 × 盒数 |
| R3 | 订单状态零新增 | 退款是旁侧资金过程；作废期次后由既有聚合出口（`completeOrderIfAllTasksDone`）把订单自然推向已完成；部分退款后订单继续配送剩余期次 |
| R4 | 已支付未配送退订（2→5）同事务补一张全额退款记录（状态 3） | 只补记录、不改流程；建单即终态（规则表无"空状态→已退款"路径），退订本身的迁移已有台账留痕 |
| R5 | 退款单状态机 `1 待审核 → 2 已审核待退款 → 3 已退款`；`1 → 4 已拒绝`（可重新申请） | 全部经 `ProcessTransitionExecutor`（场景 `REFUND`），规则种子见 `data.sql` |
| R6 | 同一订单最多一张进行中（1/2）退款单 | 由生成列 `active_order_id` + 唯一索引 `uk_refund_active` 仲裁，冲突翻译为"已有进行中的退款单"；**禁止"先查再插"** |
| R7 | 金额以**执行时刻**为准；申请盒数仅参考 | 申请与执行之间任务可能继续配送；预览与执行必须共用同一计算方法 |
| R8 | 毕业清算：待支付单取消、已支付/配送中单整单退款 | 待支付走**专属路径**（`attempt(CANCEL, 1→5)` + 作废待支付流水），**不复用** `cancelTimeoutOrder`；逐单独立事务、单笔失败不阻塞其余；重复执行只会得到"无可清算订单" |
| R9 | 权限：家长申请/查看本人（服务层校验订单归属）；管理员审核/执行/查看全部；班主任与配送站不接触退款 | 接口级见 `接口文档.md` §10 与 SecurityConfig |
| R10 | 执行退款**必须回补配额**：本次实际作废成功的零散单任务按品种调 `restoreForOrderProductDate` | 缺货取消任务在取消时已回补过、**不重复回补**；套餐任务不占每日配额 |

**机制与判定口径**见 `../基线文档/可靠性设计.md` §十五；接口见 `../基线文档/接口文档.md` §10；

### 5.8 过敏/禁忌软警示（只提示，不拦截）

- **建模**：`student.allergy_tags`（学生禁忌）与 `product.allergen_tags`（奶品过敏原）**共用同一套受控编码**——
  `LACTOSE/NUTS/PEANUT/SOY/FLAVORING/EGG/OTHER`（`com.milk.order.common.enums.AllergenType`）。
  两侧文案分开（奶品侧"乳糖"、学生侧"乳糖不耐"），由 `GET /api/order/allergy-options` 统一下发。
- **为什么必须受控枚举**：命中判定是"两侧标签交集"。若允许自由文本，学生写"乳糖不耐"、奶品写"乳糖"，
  字符串永远匹配不上，警示会**静默永不命中**——这类"看起来配了、其实没生效"的配置比没有更危险。
  因此写入时经 `AllergenType.normalizeStrict` 统一大写/去空白/去重，**未知编码直接拒绝**（宁可保存报错）。
- **清空语义**：规范化的空输入返回**空串而不是 null**。MyBatis-Plus 默认只更新非 null 字段，
  用 null 表达"清空"会被静默跳过（界面提示保存成功但标签还在）；因此接口约定 `allergyTags/allergenTags`
  传空串=清空，前端也必须显式下传该字段。
- **警示优于拦截**：预检接口 `GET /api/order/allergy-check`（?studentId&productIds）只返回命中清单，
  由用户在提交前确认（小程序与管理端下单表单均接入）；**创建订单接口契约不变**（仍只回 orderId）。
  理由是禁忌档案由人工维护、可能滞后或不精确，家长也可能明知而仍要买——硬拦截等于用一份可能过期的
  档案阻断交易，而软警示既保住知情权，也留下"系统提示过"的事实。预检本身失败**不阻断下单**。
- 标签**不参与**计价、配额扣减、状态流转与任何不变量判定；数据范围与下单同口径（家长仅本人孩子、班主任仅本班）。
- 变更记录见 `docs/变更记录/2026-09-21-过敏与禁忌软警示.md`，实测见 `docs/实验/实验设计与结果.md` §6.16。

## 六、AI 协作规范

### 6.1 让 AI 写代码前必须提供的信息

每次让 AI 写代码，必须在 prompt 中包含：

1. **本规范文件**（或关键章节）—— 告诉 AI 分层规则、命名规则、行数限制
2. **相关接口文档** —— 告诉 AI API 路径、参数、返回结构
3. **相关实体/DTO 定义** —— 告诉 AI 数据结构
4. **明确的功能范围** —— 告诉 AI 只做什么，不做什么

### 6.2 AI 产出代码的验收标准

AI 生成的代码必须通过以下检查才能合入：

- [ ] 文件行数不超过 500 行
- [ ] 分层正确（Controller 没有业务逻辑、Service 没有直接操作响应等）
- [ ] 命名符合规范
- [ ] 没有硬编码（常量/枚举已抽取）
- [ ] 类型定义完整（没有滥用 any）
- [ ] 接口路径和返回结构与文档一致
- [ ] 异常处理规范（业务异常用 BusinessException）
- [ ] 关键业务逻辑有注释

### 6.3 禁止让 AI 做的事

- 禁止让 AI 一次性生成整个模块（必须拆分为：先 entity → mapper → service → controller，逐步生成逐步验证）
- 禁止让 AI 修改架构/目录结构（架构变更必须人工讨论确认）
- 禁止让 AI 直接修改数据库表结构（表结构变更必须先更新文档，再执行 SQL）
- 禁止让 AI 写核心业务逻辑（订单状态流转、库存变动、支付）而不经过人工审核
- 禁止用 PlantUML/Java 渲染或生成位图的方式新增图件；图统一用 draw.io（`*.drawio`），工具与风格约定见 `docs/基线文档/UML/README.md`
