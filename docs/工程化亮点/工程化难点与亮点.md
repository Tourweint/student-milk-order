## 二、七个亮点：先看例子，再下结论

### 亮点 1：一笔订单 → 78 条配送任务（一对多展开模型）

**例子（给老师讲这个故事）**：

> 2026 年 9 月 12 日 21:01:54，家长在微信小程序里支付了一笔**学期套餐**订单——比如"本学期每天 1 盒牛奶，从 9 月 13 日送到 11 月 29 日"。
>
> 支付成功的那一刻，系统自动把这一笔订单展开成了 **78 条独立的配送任务**，日期从 2026-09-13 一直排到 2026-11-29，**逐日一条，一条不落**（数据库备份 `backup-before-clean-20260913.sql` 中可查到任务号 `DT20260912210154081474` 起的连续 78 条）。
>
> 每条任务有自己的状态：今天送没送、谁送的、签没签收，互不影响。2 分钟后家长反悔退订，系统把这 78 条任务**全部作废**（数据库里备注：`订单已退订，任务作废`），不会漏掉任何一天。

**如果做简单了会怎样**：只在订单表上存一个"已支付"字段、不展开任务——那么配送站今天根本不知道"该送谁、送多少"，签收、缺货、退订的逐日处理全都无法进行。看起来"少做了很多"，实际上业务直接断掉。

**这个例子能推理出什么**：订单是"一次交易"，配送是"逐日发生"，两者是**一对多**关系。把一对多展开做成支付事务内的自动联动（代码 `DeliveryTaskServiceImpl`：`for (LocalDate date = start; ...; date = date.plusDays(1))`，且 `createTaskIfAbsent` 幂等），说明设计时把真实业务周期想清楚了，而不是只做了"能下单"的表单。

**证据**：`src/main/java/com/milk/order/module/delivery/service/impl/DeliveryTaskServiceImpl.java`、`backup-before-clean-20260913.sql`（真实任务数据）、`docs/变更记录/2026-09-12-配送任务整期生成与批量签收.md`。

### 亮点 2：同一笔支付被回调了两次（支付幂等与 CAS 原子落账）

**例子（给老师讲这个故事）**：

> 家长在小程序确认支付后，模拟的微信支付平台会**异步回调**商户后端通知"钱已到账"。真实微信网络不可靠，回调可能重复、可能乱序——模拟器也会按 1s/2s/4s/8s/16s **重试最多 5 次**。
>
> 假设没有做幂等：同一笔支付被处理两次，库存就会被扣两次（今天 30 盒的机动配额直接扣成负数），支付流水会写两条，订单金额对不上。
>
> 系统实际的做法：`markOrderPaid` 用**条件更新**（`UPDATE ... SET status=2 WHERE id=? AND status=1`，CAS），两个回调同时到达时只有一方成功，失败方整笔回滚。重复回调进来，直接返回 SUCCESS，不再重复扣库存。金额核对：回调金额必须等于订单应付金额，否则拒绝。
>
> 还有一层时序兜底：订单 15 分钟不支付会自动取消，但超时锚点取**最近一次待支付流水时间**——家长在 14:59 重新发起支付，15:00 的取消任务不会误杀这单；取消前还会先向微信侧查单，已扣款的订单绝不被取消。

**如果做简单了会怎样**：回调处理写成"先查状态再更新"，两个请求之间插一脚就出账实不符；或者干脆不做重试/对账——回调丢了，钱扣了订单还停在待支付，只能靠人工修数据。

**这个例子能推理出什么**：资金链路的正确性靠**幂等 + 原子 + 对账补偿 + 超时兜底**四层保证，而不是靠"微信不会出错"的假设。能写出这层代码，说明理解并发和分布式一致性问题，不是只会 CRUD。

**证据**：`docs/基线文档/支付链路.md`（完整时序 + 不变量清单）、`src/main/java/com/milk/order/module/order/pay/WechatPaySimulator.java`、`module/order/job/PaymentReconcileJob.java`（5 分钟对账）、`module/order/job/OrderTimeoutCancelJob.java`（超时取消）。

### 亮点 3：一行规则拦住退订（状态机规则表 + 退款闸门）

**例子（给老师讲这个故事）**：

> 配送站 9 月 18 日早上 7:30 在 Web 面板点了"今日已送出"，系统记录派送人和派送时间，订单联动进入"配送中"。
>
> 家长 9:00 在手机上看订单想退订——**被拒绝**，提示"已开始配送，请联系管理员线下处理"。奶已经装车送出去了，钱不能直接退。
>
> 这个"拒绝"不是写在某个 if 里，而是查一张规则表。打开 `state_transition_rule` 表可以看到这样一行：
>
> ```sql
> ('ORDER', 'CANCEL', 3, 0, '配送中订单禁止退订（奶已送出）')
> ```
>
> 意思是：订单状态 3（配送中）执行 CANCEL（退订）动作，**allowed=0，禁止**。整张表有 40+ 行，覆盖订单、配送任务、续订计划三个场景的所有迁移，比如"已取消订单拒绝支付回调，防止乱改状态""已完成任务禁止回退"。管理端"系统管理-状态机规则"页面可以**在线查看和启停**这些规则。

**如果做简单了会怎样**：退订逻辑写死在 service 里一个 if——改业务规则要改代码、重新编译、重新部署；而且状态怎么迁、哪里禁止回退，没有任何地方能审计。

**这个例子能推理出什么**：把"状态怎么变、哪些不允许变"从代码里抽出来做成**可配置、可审计的规则表**，是状态机治理的正规做法——不是把状态机画在文档里，而是真的在系统里执行。

**证据**：`src/main/resources/sql/data.sql`（state_transition_rule 全部规则数据）、`src/main/resources/sql/schema.sql`（建表）、`docs/基线文档/核心链路图.md`（订单/配送任务双状态机）。

### 亮点 4：班主任 A 打不开班主任 B 的班（多角色数据权限）

**例子（给老师讲这个故事）**：

> 系统有四种角色：管理员、配送站、班主任、家长。班主任 A 负责三年级 2 班（35 个学生），班主任 B 负责三年级 3 班。
>
> 班主任 A 登录 Web 管理端后，无论他查看学生列表还是签收配送，系统在接口层强制拼接 `WHERE class_id = A 所带班级`——他看不到 3 班的任何学生。如果 A 手工构造请求，传一个 3 班学生的 ID 去签收，接口返回 **403**。
>
> 家长同理：登录后只能看到**自己绑定的那个孩子**的订单、配送、营养数据，传别人的订单号也查不到。配送站角色则只开放配送相关接口（今日概览、今日已送出、签收情况只读），其他管理功能一律无权访问。

**如果做简单了会怎样**：只做"登录校验"不做"数据范围校验"——任何一个登录用户都能把全校学生的数据翻一遍，权限系统形同虚设。这在评审时是最容易被一眼看穿的"粗糙"。

**这个例子能推理出什么**：RBAC 解决"谁能进系统"，**数据权限**解决"进了能看什么"。两层都做了，才叫完整的权限设计；而且越权返回 403 而不是悄悄返回空数据，说明错误语义也是设计过的。

**证据**：`docs/基线文档/核心链路图.md`（角色与权限速查表）、`docs/变更记录/2026-09-12-权限管理收紧（数据范围+登录限制+接口角色+前端过滤）.md`、`2026-09-11-小程序接入后端增强（微信登录与数据权限）.md`。

### 亮点 5：牛奶不能扔——三天保质期结转 + 先到期先出 + 数据库行级防超卖

**例子（给老师讲这个故事）**：

> 学校每天早上给每个品种进一批新鲜奶，假设周一进 100 盒草莓奶，只卖了 70，剩 30。这 30 盒**不能扔**——还在保质期内。周二又进 100 盒。那周二家长下单，应该从这 130 盒里的哪一批扣？
>
> 系统的回答是：牛奶保质期 3 天，周一剩的 30 盒会自动"滚"到周二、周三的池子里继续卖，周四这 30 盒就过期、不再可售。剩多少**不靠定时任务每天去删过期记录**，而是查询时动态加总"最近 3 个池"的余量（`remaining()` 里 `for (k=0; k<SHELF_DAYS; k++)`）——过期的池自然不在窗口里，等于自动作废。
>
> 扣减顺序也有讲究：家长下单买 5 盒，系统从**最老的那个池**开始扣（代码里 `k` 从 `SHELF_DAYS-1` 往 0 走），临期的先喝掉。这在仓储里叫 **FEFO（First-Expired-First-Out，先到期先出）**，不是简单的先买先卖。
>
> 真正容易出事的是并发：两个家长同时下单，都看到"草莓奶还剩 5 盒"。如果代码写成"先查剩多少、再 update 减几"，两个请求查完都是 5，各扣 5，库存就变 -5。系统没用 Redis 分布式锁，而是在 SQL 里加了一道条件：`used_quota + 本次要扣 <= total_quota`——这行 WHERE 条件由 MySQL 行锁保证，两个事务抢同一行，只有一个能更新成功，另一个更新 0 行，直接抛"配额扣减冲突，请重试"。
>
> 退订也讲分寸：退订时不是简单地 `已售数 - 5`，而是按当初扣减时写的台账（`daily_quota_usage`：每笔扣到了哪一天的池子）**精确回补到原池**。因为如果把退掉的 5 盒回补到今天的新池，就等于把临期奶的额度"洗"成了新奶，下次扣减顺序又乱了。回补动作同样带 `used_quota >= 回补数` 的条件，防止减成负数。

**如果做简单了会怎样**：库存只存一个"剩余多少"的数字——要么并发下卖超了（今天 30 盒卖成 35），要么临期奶没人管最后全过期扔掉，要么退订回补把账加错池子。"库存管理"四个字人人都会说，但**保质期结转 + 先进先出 + 并发防超卖**三件套一起做，才叫真的把业务想透了。

**这个例子能推理出什么**：库存不是一个字段，是一个带时间维度的模型。而且一行 SQL 条件更新就解决了并发超卖，没有引入 Redis——说明懂得用数据库本身的事务和行锁，而不是一上并发问题就先上中间件。

**证据**：`src/main/java/com/milk/order/module/product/service/impl/DailyQuotaServiceImpl.java`（`SHELF_DAYS=3`、`remaining()` 窗口加总、`deduct()` 从老池往新池扣、`.apply("used_quota + {0} <= total_quota")`、`restore()` 按台账回补原池）、`daily_quota` / `daily_quota_usage` 两张表。

### 亮点 6：点一下"签收"，四件事在一个事务里完成

**例子（给老师讲这个故事）**：

> 配送站老师上午 10 点在面板点"批量签收三年级 2 班今天的 35 盒奶"。就点一下，系统在**同一个数据库事务**里连做四件事：
>
> 1. 把 35 条配送任务从"配送中"改成"已完成"——带 CAS 条件（必须还是"配送中"才改得动）；
> 2. 把 35 条签收记录改成"已签收"，记下签收人和签收时间；
> 3. 从奶品规格字符串（如"250ml"）里正则解析出 ml 数，乘以喝的盒数得到总量，再按奶品营养表（每 100ml 含多少蛋白质/钙/能量）折算，把这顿孩子实际摄入了多少克蛋白、多少毫克钙写进**营养摄入表**；
> 4. 顺手检查这一单的 78 条任务是不是全部到终态了，是就把订单自动标成"已完成"。
>
> 这一串任何一步失败，整个事务回滚——不会出现"签收成功了但营养没算"这种半截数据。
>
> 并发也想到了：老师手快，先点了某一条的单条签收，又点了整班批量签收，两个请求同时到达。因为任务状态更新带了 `WHERE status=2`，先到的那个把状态改成 3，后到的那个条件不匹配、更新 0 行，直接报错回滚——**营养摄入记录绝不会写两份**。
>
> 还有一层兜底：老师万一某天忘了签收，定时任务每天扫"配送日早于今天、仍在配送中、未签收"的记录，复用**同一个签收方法**补签，签收人写"系统自动签收"留痕；单批最多处理 200 条（`MAX_AUTO_SIGN_BATCH`），防止历史脏数据把定时任务跑死。

**如果做简单了会怎样**：签收就是 `update task set status=3` 一个字段。营养摄入让家长自己在小程序填、或者下次登录再异步算；批量签收和单条签收撞了就写两份营养；老师忘了签收，系统里那条任务就永远挂在"配送中"。每个"小功能"单看都能跑，拼在一起就是到处是半截数据。

**这个例子能推理出什么**：一个业务动作背后是**跨表事务 + 并发 CAS + 兜底补偿**三件套。而且自动签收不是另写一套逻辑，而是复用人工签收的同一个私有方法——说明设计时就把"谁来触发"和"怎么做"分开了，一致性靠复用保证，而不是靠抄两份代码。

**证据**：`src/main/java/com/milk/order/module/delivery/service/impl/DeliveryTaskServiceImpl.java`（`doSign()` 私有方法串起任务/记录/营养/订单完成四步、`generateNutritionIntake()` 按规格解析与折算、`autoSignOne()` 复用 `doSign`、`MAX_AUTO_SIGN_BATCH=200`）、`nutrition_intake` 表。

## 三、答辩演示路径（7 步，每步对应一个例子）

1. 启动后端 + 前端，管理员登录，打开仪表盘 → 看数据可视化；
2. 创建学期套餐订单 → 模拟微信支付（预下单 → 确认 → 异步回调）→ **打开数据库展示一笔订单展开成的 78 条配送任务**（对应亮点 1）；
3. 配送站点"今日已送出" → 家长端尝试退订被拒 → **现场打开 `state_transition_rule` 表指给老师看那行规则**（对应亮点 2、3）；
4. 用班主任 A 的账号访问 3 班数据，展示 403（对应亮点 4）；
5. 打开 `DailyQuotaServiceImpl.deduct()`，指 `used_quota + n <= total_quota` 那行条件更新，讲"两个家长同时抢最后几盒、数据库行锁只放一个过"（对应亮点 5）；
6. 配送站点"批量签收" → **打开营养摄入表展示自动算出的蛋白质/钙** → 看订单自动变"已完成"（对应亮点 6）；
7. 打开 `docs/变更记录/` 目录，翻几份带"缺陷修复"的记录（对应亮点 7）。

> 时间紧就挑 2、3、6 这三步现场演，其余口述代码位置即可。每讲完一个例子问自己："老师能从这个例子里推出我要说的道理吗？"——能，就讲到位了。

## 五、一句话总结

**先用例子证明，再讲道理。** 七个例子分别证明：一对多任务展开、支付幂等与原子性、状态机规则治理、数据权限收敛、带保质期的库存模型、跨表签收事务联动、文档驱动过程管理——每一处都有真实数据和代码可查，这就是完成度。
