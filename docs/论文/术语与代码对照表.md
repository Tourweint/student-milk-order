| 我做了一个可以在线修改状态机的功能 | 将业务状态转换规则**从程序控制逻辑中分离**，使业务流程具有**数据驱动**特征 |

## 四、术语的精度要求（答辩易被追问处）

| 说法 | 精度要求 |
| --- | --- |
| 「行锁」 | 不要笼统说「靠 MySQL 行锁保证」。准确说法：**先 `SELECT ... FOR UPDATE` 加锁读，再做条件更新**；条件更新本身也会加行锁，但本系统的原子性来自「加锁读 + 条件更新」的组合（实验一 D3 证明只靠条件更新在 MariaDB 上会失败） |
| 「幂等」 | 不要只说「加了幂等判断」。准确说法：**由数据库业务唯一键承担并发仲裁**，应用层把唯一键冲突翻译为「已存在」并跳过 |
| 「状态机」 | 不要只说「用状态机管理订单」。准确说法：**订单与配送任务构成父子状态机**，父状态由子过程聚合；迁移规则外置为**规则表**，白名单语义 |
| 「事务」 | 不要只说「放在一个事务里」。准确说法：**先 CAS 抢占状态、再执行副作用**，使落败方在产生副作用前中止（顺序本身是一致性设计的一部分） |
| 「对账补偿」 | 不要只说「有定时任务补偿」。准确说法：**发现不一致 → 对账 → 补偿 → 恢复合法状态**，补偿复用统一迁移出口因而幂等 |
| 「补偿规则可配置」 | 不要只说「规则可配置」。准确说法：**探测（只读）/ 决策（规则表）/ 执行（统一迁移出口）三层分离**；可配置的是「用哪个条件、补偿到什么状态」，条件的语义由枚举 + 业务侧实现（刻意的边界）。且**补偿仍受迁移闸门约束**——配置化不等于可绕过 |
| 「实时」 | 不要只说「实时自愈」。准确说法：**双通道**——实时通道把「处于错误状态而不自知」的**不可检测窗口**从 10 分钟压到约 5 秒（实测 5014ms vs 600000ms），瓶颈是轮询间隔而非修复耗时；但自愈本身会失败（实测重试 5 次后放弃），因此**不能替代**兜底通道。实时通道给收敛速度，兜底通道给最终一致 |
| 「不变量」 | 不要只说「做了校验」。准确说法：把主键外键表达不了的**跨表约束**登记为 `ProcessInvariant`，探测只读、修复分级（`AUTO_REPAIR` / `ALERT_ONLY`），由体检任务周期求值——**不变量只在被验证时才成立**，实验只能证明它某一次成立过 |
| 「自动修复」 | 不要只说「有问题自动修」。准确说法：**分级的判断标准是修复的可逆性与影响面**——能由既有台账唯一推导出正确值且重算幂等的才自动修；涉及资金流向或需业务判断的一律只告警、不改数据（实验七对照 B 验证） |
| 「隔离级别」 | 不要避而不谈。准确说法：数据源**显式统一为 `READ_COMMITTED`**，因为 MariaDB 与 MySQL 在 `REPEATABLE READ` 下对「快照建立后被并发修改的行」行为不一致（实验发现） |

## 五、论文与代码的对应检查清单

写作或答辩前逐条自查：

1. 论文里提到的每个机制，能否在代码中指出**唯一落点**（类 + 方法）？
2. 代码里的每个状态迁移，是否都能用「场景 / 动作 / 起止状态 / 结果」四元组描述？
3. 论文中的「实验结论」，是否都能在 `target/experiment-reports/` 找到对应的原始数据？
4. 论文中的「已知局限」，是否与 `实验设计与结果.md` 第 8 节的局限一致？
5. 是否出现了「功能清单式」表述（列举做了什么）而没有对应的「设计理由」？
6. 是否把「模拟实现」（如模拟微信支付）当成真实能力描述？（应明确标注为模拟）
