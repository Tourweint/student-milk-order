# 选题与章节结构

> 本文确定毕业设计的题目层次、核心问题、章节结构与图表清单，并给出「为什么这样定」的理由。
> 业务背景来自校园乳品配送系统，但研究对象是业务过程的建模与可靠执行。

## 一、题目

### 推荐题目

> **面向周期性业务履约的状态管理与异常恢复系统设计与实现**
>
> ——以校园乳品配送业务为例

三层正好对应论文的叙事主线：

| 层次 | 内容 | 回答 |
| --- | --- | --- |
| 现实业务（案例） | 校园乳品配送 | **为什么做？** |
| 问题（研究对象） | 周期性业务履约 | **做什么？** |
| 技术核心 | 状态管理与异常恢复 | **怎么解决？** |

### 备选题目

1. 面向长期业务过程的层级化状态管理与可靠执行机制研究与实现
2. 周期性履约业务的过程建模与最终一致性保障机制设计与实现
3. 校园乳品配送系统中业务过程可靠执行机制的设计与实现

> 选择建议：若导师更看重「系统实现」，用推荐题目；若更看重「机制研究」，用备选 1。

## 二、核心问题与贡献

### 2.1 核心问题

> 一个现实业务对象进入系统后，会经历长期、多阶段、异步、可失败的执行过程；
> 系统如何让这个过程在**并发、重复、超时、失败、部分成功**下仍然可控？

拆成两个子问题：

| 子问题 | 内容 |
| --- | --- |
| A. 过程如何被建模 | 复杂业务过程如何从一个业务对象分解成多个可执行状态与任务？ |
| B. 过程如何保证可靠 | 出现异常时如何保证系统不进入不可控状态，并能恢复？ |

### 2.2 主要工作（论文的「做了什么」）

1. **提出四层模型**：业务层 / 过程层 / 可靠性层 / 兜底层，把原本零散的十几个技巧
   （幂等、CAS、行锁、台账、对账、补偿、超时任务）统一到「业务过程的可靠执行机制」这一问题下。
2. **过程建模**：把订单的宏观状态与配送任务的微观状态分离，建立**父子状态机 + 状态聚合**模型；
   将状态迁移规则从代码中抽离为**规则表驱动**，使业务流程具备数据驱动特征。
3. **可靠执行机制**：以「唯一键幂等 + CAS 条件更新 + 行锁读 + 资源台账 + 先抢占状态再执行副作用」
   构成一组可复用的原语，并实现为统一迁移出口 `ProcessTransitionExecutor`。
4. **异常恢复机制**：以「对账 + 补偿 + 定时兜底」把目标从「绝对原子性」转为
   「可检测、可恢复的最终一致性」，覆盖支付对账、超时对账、**父子状态漂移对账**三类。
5. **实验验证**：设计 4 组可重复的并发实验（含无保护对照）与 1 个不变量检查用例，量化验证机制有效性；
   **并反向暴露 4 个真实缺陷**并修复，形成「问题 → 设计 → 实现 → 对照实验 → 发现缺陷 → 修复 → 回归守卫」
   的完整闭环。

### 2.3 与「加功能显得高级」的区别

论文明确**不**通过引入 AI 推荐、消息队列、Redis、微服务、容器编排来堆技术点。
理由是这些与本项目要解决的问题无因果关系；本项目的复杂度来自**业务过程本身的长期性与异常性**，
而不是吞吐量或部署规模。

## 五、可能被追问的问题与回答要点

| 追问 | 回答要点 |
| --- | --- |
| 这和普通订单系统有什么区别？ | 订单状态是宏观状态，配送任务是微观状态；一个订单展开为 N 个异步任务，父状态由子过程聚合成，这是层级化状态管理而不是单字段状态。 |
| 你的「抽象」在代码里体现在哪？ | 过程层 `com.milk.order.process`（统一迁移出口 + 迁移规格 + 迁移台账）、可靠性层 `com.milk.order.reliability`（幂等守卫）；所有状态迁移都收口到执行器。 |
| 为什么不直接上分布式事务 / MQ？ | 问题不在跨服务事务，而在单服务内的长期过程与异常分支；引入 MQ 不解决「父子状态漂移」与「重复回调副作用」。目标是可检测可恢复的最终一致性。 |
| 为什么不用 Redis 分布式锁？ | 单库场景下行级锁 + 条件更新已足够，且避免引入额外中间件与锁失效问题；机制的有效性由实验一量化验证。 |
| 怎么证明你的机制有效？ | 12 组实验含对照：无保护超卖 100 盒 / 有保护零超卖；20 次并发回调只落账一次；停用补偿规则后漂移不再被修；实时通道窗口 5.0 秒 vs 兜底 600 秒（119 倍）；两个实例并发跑同一任务只生效一次；事务中间注入异常后零半截数据；持续负载下 624 次漂移全部被三通道收敛、检测延迟 p95 216ms；热点单池 32 线程吞吐反低于 8 线程（0.89×）而分散多池 ×4。数据见实验文档。 |
| 实验是不是只证明了「理想情况」？ | 相反：实验过程暴露了 6 个真实缺陷（弱幂等、规则缓存非原子刷新、快照读与加锁读混用、副作用先于状态抢占、联动路径绕过统一出口、自调用导致事务失效），其中 2 个只在并发下出现，已全部修复并留下回归断言；实验七还**主动发现**了一个修复顺序缺口（诚实记录，未修复）。 |
| 工作量和创新点在哪？ | 工作量：9 个业务模块、完整前后端与小程序、15 个自动化用例；创新/改进点：四层模型 + 父子状态聚合 + 迁移规则表驱动 + **补偿规则引擎（探测/决策/执行三层）** + **双通道自愈** + **跨表不变量持续验证** + 量化验证。 |
| 为什么用 MariaDB 而不是 MySQL？ | 部署目标就是 MariaDB（`mysql-connector-j` 与 SQL 语法均兼容，用哪个都不构成限制）；实验正是利用了两者在 REPEATABLE READ 下的行为差异发现了缺陷 D3，最终统一 `READ_COMMITTED` 使两者行为一致——这是实验的收获之一。 |
| 为什么不用「行锁」这个词概括并发控制？ | 「行锁」太笼统。本系统的原子性来自「`SELECT ... FOR UPDATE` 加锁读 + 以原状态为条件的 CAS 更新」的组合，搭配业务唯一键承担幂等仲裁；只靠条件更新在 MariaDB 上会直接失败（缺陷 D3）。 |
