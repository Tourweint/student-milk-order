### 2.1 补偿规则从硬编码下沉到规则表

> **✅ 已实现（2026-09-19）**
> - 落点：`process/reconcile/`（`ProcessReconcileEngine`、`ProcessReconcileCoordinator`、
>   `ProcessReconcileRule`、`ParentProcessProbe`、`ParentProcessAggregator`）、
>   表 `process_reconcile_rule`、业务侧 `OrderProcessProbe` / `OrderProcessAggregator`；
> - 原 `OrderInfoService.reconcileOrderAggregation` 已删除（避免两套判定口径并存）；
> - 验证：实验四（链路端到端）、实验六（规则启停 + 迁移闸门）；
> - 文档：`docs/基线文档/业务过程与可靠执行模型.md` §3.6、`可靠性设计.md` §7.2。
>
> 实现时补上的两处设计细节（原方案未写）：① 同一主体一轮只补偿一次（按规则 id 取首个命中），
> 避免多规则叠加导致一次补偿连跳两个状态；② 新增补偿动作若未在聚合器实现，**快速失败**而不是静默跳过。

**现状**（`OrderInfoServiceImpl.reconcileOrderAggregation`）：

```java
// 场景一：已支付但子任务已开始配送 —— 补齐"配送中"联动
if (deliveryTaskService.hasDispatchingTask(order.getId()) && self.markDeliveringIfPaid(order.getId())) { ... }
// 场景二：配送中但子任务全部到达终态 —— 补齐"已完成"聚合
if (self.completeOrderIfAllTasksDone(order.getId())) { ... }
```

**问题**：
- 补偿规则（父状态 + 子过程条件 → 动作）**硬编码**，与状态迁移规则表（数据驱动）形成不对称；
- 想增加第三类漂移（如"配送中 + 子任务全取消 → 应退订"）必须改代码、重新发布。

**方案**：新增规则表 + 探测器/决策/执行三层分离。

```sql
CREATE TABLE IF NOT EXISTS process_reconcile_rule (
    id BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '规则ID',
    name VARCHAR(64) NOT NULL COMMENT '规则名',
    parent_scene VARCHAR(30) NOT NULL COMMENT '父过程场景，如 ORDER',
    parent_status INT NOT NULL COMMENT '父过程需满足的状态，如 2-已支付',
    child_condition VARCHAR(40) NOT NULL COMMENT '子过程条件编码，如 HAS_DISPATCHING_TASK',
    action VARCHAR(30) NOT NULL COMMENT '补偿动作（复用 StateTransitions 动作码）',
    target_status INT NOT NULL COMMENT '补偿后的父状态',
    enabled TINYINT NOT NULL DEFAULT 1 COMMENT '是否启用（1-启用，0-停用）',
    description VARCHAR(255) COMMENT '规则说明',
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    deleted TINYINT DEFAULT 0,
    UNIQUE KEY uk_reconcile (parent_scene, parent_status, child_condition, action)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='过程补偿规则表';
```

种子（前两条 = 当前硬编码行为，第三条是"配置出来"的新能力，默认关闭）：

```sql
('联动丢失补偿', 'ORDER', 2, 'HAS_DISPATCHING_TASK', 'DELIVER',        3, 1, '已支付且存在配送中子任务 → 补偿为配送中'),
('聚合丢失补偿', 'ORDER', 3, 'ALL_TASKS_TERMINAL',  'AUTO_COMPLETE',  4, 1, '配送中且子任务全部终态 → 补偿为已完成'),
('全取消补偿',   'ORDER', 3, 'ALL_TASKS_CANCELLED', 'CANCEL',         5, 0, '配送中且子任务全部取消 → 补偿为已退订（默认关闭，需线下退款配合）'),
```

三层结构：

| 层 | 职责 | 实现 |
| --- | --- | --- |
| 探测器 | 按规则表里出现过的 `parent_status` 分组取候选父过程（每组 `LIMIT n`），逐条求值子过程条件 | `ProcessReconcileEngine.detect(scene, limit)` |
| 决策器 | 命中的规则交给谁执行（规则里已写明 action 与 target_status） | 规则表 |
| 执行器 | 复用 `ProcessTransitionExecutor.attempt`，成功后写迁移台账（`remark` 标注"由规则 X 补偿"） | 已有 |

**关键设计点**：
- 子过程条件做成**显式枚举 + 求值器**（`HAS_DISPATCHING_TASK` / `ALL_TASKS_TERMINAL` / `ALL_TASKS_CANCELLED`），新增条件需要改代码——这是**有意的边界**：条件求值涉及业务语义，不适合纯配置化，配置化的对象是"**用哪个条件、补偿到什么状态**"；
- 每条规则独立开关，默认只开"与现有行为等价"的两条 → **行为可灰度、可回滚**；
- 单轮上限 + 迁移台账留痕 → 补偿放大可追溯。

**论文价值**：把"异常恢复"从代码里的两个 `if` 提升为**与状态迁移对称的可配置机制**，可以写"检测（探测）/决策（规则）/执行（统一出口）三层分离"，并讨论"哪些该配置化、哪些不该"。

**风险**：规则配错会放大问题 → 靠默认关闭 + 限批 + 台账回溯控制。

### 2.2 不变量校验器：从 2 类漂移到 6 类跨表不变量

> **✅ 已实现（2026-09-19）**
> - 落点：`process/invariant/`（`ProcessInvariant`、`ProcessInvariantScanner`、`InvariantScanReport`）、
>   表 `process_invariant_violation`、6 个业务侧检查项（`module.product.invariant`、
>   `module.delivery.invariant` × 3、`module.order.invariant` × 2）、`ProcessInvariantJob`；
> - 实现时的两处调整：① 接口签名由「批量修复返回条数」改为**逐条 `repair(violation)`**，
>   因为只有逐条才知道哪一条真的修好了、哪一条失败（体检记录要按条闭环）；
>   ② 记录表由「每次检出追加一行」改为**每个（不变量 × 主体）一行当前状态 + `reopen_count`**，
>   否则反复漂移会堆出多行，反而看不出当前是否一致；`reopen_count` 同时成为自愈有效性的度量；
> - 验证：实验七（对照 A 四类注入全修复 + 复检闭环；对照 B 资金项只告警）；
> - 文档：`业务过程与可靠执行模型.md` §3.8、`可靠性设计.md` §7.4。

**现状**：只有"父状态与子任务集合"这一类不一致被检测。其它跨表不变量（配额账实、签收与营养、任务与记录）**从未在运行期被检查过**。

**方案**：把不变量做成可注册的检查项，由 Job 周期执行"体检"。

```java
public interface ProcessInvariant {
    String code();                                   // 如 QUOTA_LEDGER_MISMATCH
    String description();
    InvariantSeverity severity();                    // 与修复策略绑定
    List<InvariantViolation> detect(int limit);      // 只探测，不改数据
    int autoRepair(List<InvariantViolation> v);      // 仅幂等、可逆的项支持自动修复
}
```

六类不变量（都不需要新表，全是既有表之间的约束）：

| 编号 | 不变量 | 检测口径 | 处置 |
| --- | --- | --- | --- |
| INV-1 | 配额账实一致 | `daily_quota.used_quota` 是否等于 `SUM(daily_quota_usage.boxes) WHERE deleted = 0`（同日期+品种） | 自动修：以台账为准重算 `used_quota` |
| INV-2 | 任务-记录一致 | 任务 `status=3`（已完成）但签收记录 `sign_status<>1` | 自动修：补签收记录 |
| INV-3 | 签收-营养一致 | 签收记录 `sign_status=1` 但无对应 `nutrition_intake` | 自动修：按签收记录补生成 |
| INV-4 | 订单-任务一致 | 任务数是否等于「订单品种数 × 配送天数」（按品种合并后） | 自动修：补生成缺失任务（幂等） |
| INV-5 | 父状态-子集合一致 | 现有两类漂移 | 自动修（并入 2.1 的引擎） |
| INV-6 | 支付一致 | 订单已支付但无成功流水 / 有成功流水但订单非已支付 | **只报警**：涉及资金，必须人工核 |

**关键设计点（这是最容易写错的地方）**：
- **口径要显式**：台账行回补后是**逻辑删除**（`deleted=1`），所以 INV-1 必须写 `deleted = 0`；否则会长期误报。这个口径本身就是可写进论文的一节"口径与假阳性"。
- **探测与修复分离**：探测只读、可随时跑；修复必须经统一出口（复用迁移出口/聚合出口），保证留痕与幂等；
- **严重度分级**：`AUTO_REPAIR`（幂等可逆）/ `ALERT_ONLY`（涉资金、需人工）。

**论文价值**：★★★ 最高。这正是本项目自己论证过的那句话——**"不变量只在被验证时才成立"**：实验里验证一次只是抽样，运行期周期校验才是持续保证。可以据此写"从一次性实验到运行期持续验证"。

**工作量**：1 张违规记录表（记录 code/violation/detected_at/handled_at，便于看板与统计）+ 6 个探测器 + 1 个 Job + 管理端只读页。

**风险**：低（以只读探测为主；自动修限定在幂等、可逆动作）。

### 2.3 实时自愈 + 定时兜底"双通道"（"实时推"的正确解法）

> **✅ 已实现（2026-09-19）**
> - 落点：`process/pending/`（`ProcessPendingTaskService`）、表 `process_pending_task`、
>   `ProcessPendingTaskJob`（每 5 秒消费）、6 处业务侧入队点（送出/签收/拒收/取消/缺货取消/退订联动作废）；
> - 实测：实时窗口 5014ms（轮询 5000 + 修复 14ms）vs 兜底 600000ms，缩短 119 倍。
>   值得写进论文的一点：**瓶颈是轮询间隔而不是修复**——「实时」的收益来自发现得早，不是修得快；
> - 实现时的两处细节：① 去重键含 `status`，否则逻辑删除的已处理行会阻塞同一业务键的新待办，
>   使其**静默入队失败**（详见 `可靠性设计.md` 第六节）；② 入队必须在子过程状态变更的同一事务内；
> - 验证：实验八（对照 A 窗口对比 / 对照 B 去重 / 对照 C 退避与放弃）；
> - 文档：`业务过程与可靠执行模型.md` §3.7、`可靠性设计.md` §7.3。

**现状**：`OrderProcessReconcileJob` 每 10 分钟全表扫两类订单。漂移的**不可检测窗口最长 10 分钟**，且全表扫随数据量增长而变慢。

**先说清楚"实时"到底解决什么**：它不是为了让界面更快，而是为了**把"系统处于错误状态而不自知"的窗口从分钟级压到秒级**。但自愈本身也会失败，所以实时通道**不能替代**兜底——两者必须是双通道。

**方案**：事务内落地待办（outbox 变体）+ 秒级消费者 + 定时兜底。

```sql
CREATE TABLE IF NOT EXISTS process_pending_task (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    scene VARCHAR(30) NOT NULL COMMENT '待补偿的过程场景，如 ORDER',
    entity_type VARCHAR(50) NOT NULL COMMENT '父过程表名',
    entity_id BIGINT NOT NULL COMMENT '父过程主键',
    biz_no VARCHAR(64) COMMENT '业务单号',
    trigger_action VARCHAR(30) NOT NULL COMMENT '触发动作（子过程终态动作），用于去重',
    status TINYINT NOT NULL DEFAULT 0 COMMENT '0-待处理，1-已处理，2-已放弃',
    retry_count INT NOT NULL DEFAULT 0 COMMENT '已重试次数',
    next_retry_time DATETIME COMMENT '下次可处理时间（指数退避）',
    last_error VARCHAR(255) COMMENT '最近一次失败原因',
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_pending (scene, entity_id, trigger_action, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='过程自愈待办（实时通道）';
```

流程：

```text
子过程状态变更成功（同一事务）
        ↓ 写入一条待办（唯一键去重，已存在则忽略）
        ↓
秒级消费者（每 5 秒，LIMIT n）
        ↓ 调用聚合/补偿出口（attempt，天然幂等）
   ┌────┴────┐
成功         失败
  ↓            ↓
置已处理   retry_count++、指数退避，超 5 次置「已放弃」并告警
                ↓
        定时兜底（10 分钟）扫「已放弃 + 漂移候选」，最后防线
```

**关键设计点**：
- 写入点在**事务内**，保证"副作用发生 ⇒ 待办存在"（不会因为进程崩溃而丢待办）；
- 唯一键 `(scene, entity_id, trigger_action, status)` 防止同一触发动作堆积多条待办；
- 消费者用 `attempt` 语义 → 重复消费不产生额外状态变更；
- **超限即降级**：重试 5 次仍失败就交给兜底通道 + 告警，避免消费者被单条脏数据拖死（与现有 `MAX_AUTO_SIGN_BATCH` 同一思路）；
- 兜底通道保留，职责从"主责"降为"最后防线"。

**论文价值**：★★★ 可以直接写"实时自愈 + 定时兜底双通道"，并论证"**为什么不能只有实时通道**（自愈会失败）"和"**为什么不能只有兜底通道**（窗口太长）"。这是一个完整的设计论证，而不是功能堆砌。

**风险**：中。事务内多一次 insert 有写放大；待办表会成为新的热点，需按 `next_retry_time` 建索引并限批。

### 2.4 状态机契约矩阵测试（防旁路回归）

> **✅ 已实现（2026-09-19）**
> - 落点：`src/test/java/com/milk/order/contract/StateMachineContractTest.java`；
> - 实现时的调整：矩阵 A 由「遍历全部组合做真实迁移」改为**断言规则表覆盖全部可达组合**
>   （因为白名单语义下漏配一行 = 该迁移静默被禁止，这是覆盖矩阵能抓到的最有价值的一类问题）；
>   矩阵 C 由「台账条数」升级为**台账可回放**（逐步断言 from 等于回放到此刻的状态，无缝隙、无跳跃）；
> - 验证：3 个用例全绿（35 个组合零缺失、12 项安全关键迁移均禁止、回放 1→2→3→4）;
> - 已知未覆盖：D6（自调用导致 `@Transactional` 失效）仍无自动化守卫。

**现状**：D5（联动路径绕过统一出口导致台账空洞）是"逐条核对不变量"发现的，**没有自动化守卫**；D6（自调用导致事务失效）同样没有守卫。

**方案**：把"状态机契约"做成参数化测试矩阵，而不是零散用例。

- **矩阵 A（迁移合法性）**：对每个主体（订单 5 状态 × 5 动作、配送任务 4 状态 × 5 动作）遍历全部组合，
  断言"规则表允许 → 迁移成功且台账恰有 1 条生效记录"、"规则表禁止 → 被拒绝且状态不变"；
- **矩阵 B（留痕完整性）**：任何一次状态变更后，断言台账条数 == 变更次数（实验五的全场景版）；
- **矩阵 C（事务边界）**：断言所有标注 `@Transactional` 的 public 方法都**经 Spring 代理**调用（可用 `AopUtils`/`ApplicationContext` 校验自调用黑名单），把 D6 变成"不可能悄悄回归"。

**论文价值**：★★ 把"经验教训"变成"可执行的契约"，也是"验证层"从实验扩展到测试的体现。

**风险**：低。

### 2.5 修复动作的依赖与顺序约束（🆕 本轮实验新发现）

**来源**：这不是事先设计出来的方案，而是**实验七对照 A 主动发现了自己的一个缺口**——
这是"验证层"真正价值的又一次体现，值得单独成节。

**现象**：对照 A 同时注入 4 类互不相关的违规，各条不变量的修复全部成功（4 检出 / 4 修复 /
次轮复检 0），但最后一个观察项显示：**修复后仍有 1 条未完成任务，而订单已经是已完成状态**。

**根因**：修复动作之间缺少依赖与顺序——
`INV_ORDER_TASK` 补回一条缺失的任务（状态=待配送）可能发生在 `INV_ORDER_AGGREGATION`
把订单聚合为已完成之后，于是得到「已完成订单 + 待配送任务」这种组合可疑状态。
**现有 6 条不变量都没有被违反**，因为没有任何一条覆盖「父过程已终态时不应存在非终态子过程」
这个组合约束。

**方案（候选）**：

1. **补一条组合不变量** `INV_PARENT_TERMINAL_CHILD_PENDING`：父过程已结束却存在非终态子过程时告警
   （或按规则补偿：把该子任务取消）。代价最小，先把问题变成可见的；
2. **给修复动作声明显式依赖**：例如"补子任务"必须在"父过程聚合"之前完成。
   可在 `ProcessInvariant` 上增加 `dependsOn()` 与执行序，体检器按拓扑序执行修复；
3. **更彻底的方向**：不变量之间本就是一个约束系统，理想形态是「一致性问题求解」——
   由约束集合推导出一个满足全部约束的修复计划，而不是逐条独立修复。
   这已超出毕设范围，适合作为"展望"里的深度方向。

**工作量**：候选 1 约 0.5–1 人日；候选 2 约 3 人日；候选 3 属于研究性问题。

**论文价值**：★★★ 这是一个**自己发现自己的缺口**的案例，非常适合写进"验证层的价值"与
"已知局限"两处：它说明「单个机制正确」不等于「机制组合正确」，
而**持续验证能发现设计者没想到的组合问题**。

**风险**：中。修复顺序本身会引入新的并发/顺序问题，需要与幂等性一起验证。

## 3. 第二档：可做（实现/实验章节加分）

### 3.1 多实例部署的正确性

**现状**：单实例部署。系统的并发安全依赖数据库（唯一键 + 条件更新 + 行锁），**原则上天然支持多实例**，但有两个真实障碍：

| 障碍 | 说明 | 方案 |
| --- | --- | --- |
| 定时任务无协调 | `@Scheduled` 在每个实例都会触发，对账/补偿/自动签收会**重复执行** | 先论证"所有 Job 都是幂等的"（`attempt` 语义），因此重复执行**只浪费不犯错**；再可选加轻量选主（`scheduler_lock` 表 + `SELECT ... FOR UPDATE` + 过期时间）降低浪费 |
| 预支付单在内存 | `WechatPaySimulator` 是内存态，多实例下回调可能落到**没有该预支付单**的实例 | 模拟器改为读写 `payment_record` 的待支付行（该行本就是预支付单），消除唯一的本地状态依赖 |

**论文价值**：★★★ 可以写一个很有力的小节：《为什么本设计能（也只有一个地方不能）天然支持多实例》——多实例的正确性来自"幂等 + 唯一键 + CAS"，而不是分布式协调；唯一的本地状态依赖（内存态模拟器）被明确指出并消除。

**风险**：中（需要把定时任务逐个再审计一遍幂等性）。

### 3.2 混沌注入实验 + 长稳对账度量

**方案**：
- **混沌注入**：用 AOP 在事务中间以概率抛异常 / 注入延迟 / 随机中断请求，运行混合负载后断言"系统最终收敛"（所有订单处于合法状态、所有不变量成立）；
- **长稳**：连续跑 2~24 小时混合负载，统计**对账命中数、补偿条数、检测延迟分布、台账冲突率、不变量违规数**——这些正是 2.2/2.3 之后才有的可观测量；
- 输出"自愈有效性"指标：漂移发生后被实时通道修复的比例 vs 被兜底通道修复的比例。

**论文价值**：★★★ 第 7 章从"正确性实验"扩成"**正确性 + 混沌 + 长稳**"三节，把"可靠性"从"正确"推进到"可度量"。

**风险**：低。

### 3.3 性能基准（TPS/P99 + 热点行争用）

**方案**：JMeter/k6 压测下单、支付、签收；重点测**同一配额池的热点争用**。

预期结论（有价值）：行锁读把同一池子的扣减**串行化**，吞吐上限 ≈ `1 / 单次事务时长`；因此热点品种会成为瓶颈。
由此自然引出对比实验：**单池 vs 按班级/批次分段池** 的吞吐差异 → 既是性能结论，也是"一致性 vs 吞吐"的权衡讨论。

**论文价值**：★★ 补上"性能测试"这一常被问到的环节。

**风险**：低。

## 4. 第三档：写进 future work 即可

> 按约定**本轮不实现**（除 4.6 可视化为可选演示增强）。下面各项的价值在于「写清楚边界与代价」，
> 而不是做出来——尤其是 4.1 与 4.2，论文里讲清「为什么刻意不做」比做出来更有说服力。

### 4.1 嵌套/层次化状态机（三级）

**现状**：两级——订单（父）/ 配送任务（子），另有"签收记录"作为**不纳入规则表**的挂载子状态（判定标准：是否可被外部独立发起）。

**可以升级为三级**：把 `delivery_record` 提升为正式的第三级状态机并纳入规则表（需补 3 条种子规则）。

**我的建议：暂不做，写进 future work。** 理由：
- 收益主要是**表达层面的完整性**，而不是解决新的问题；
- 成本与风险不成比例：第三级纳入规则表后，"任务签收"与"记录签收"会形成**两份描述同一件事的规则**，管理员关掉一个忘了另一个就自相矛盾（这正是当初 D5 与本设计的耦合点）；
- 论文里**把它作为一个设计决策讨论反而更有价值**：写清"哪一级该纳入规则表"的判定标准（可被外部独立发起），比"全都能配"更专业。

若确实要做，正确做法是**父子联动规则**：规则表增加 `parent_scene/parent_action` 列，用"级联规则"表达"任务签收 ⇒ 记录签收"，而不是并列两份独立规则。

### 4.2 规则表升级为轻量规则引擎（守卫条件 + 副作用声明）

**现状**：`state_transition_rule` 是**布尔白名单**（scene/action/from_status → allowed），没有"条件"维度。

**可扩展**：增加 `guard_expr`（守卫：金额上限、时间窗、角色、业务开关）与 `effect`（副作用声明：写台账/发通知/扣资源）。

**建议**：作为 future work 并在论文里明确"**当前是白名单而非规则引擎**"这一事实边界（诚实反而加分），同时论证"为什么毕设阶段刻意不做条件维度"——它会引入表达式求值的安全性与可测试性问题，收益与复杂度不匹配。

### 4.3 人工介入通道（补偿升级）

自动补偿失败 N 次后，把主体标记为「需人工处理」，在管理端形成待办列表（可指派、可备注、可关闭）。
**价值**：★★ 这是"异常处理分类学"的最后一环：检测 → 决策 → 执行 → **升级人工**。当前链路止于"重试"。工作量小（1 张表 + 1 个页面），性价比高，也可升级进第一档。

### 4.4 失败事件表 + 显式重试（死信语义）

现状：失败即抛异常，依赖上游隐式重试（微信重试、定时任务下一轮），**重试过程不可观测**。
可改为显式"失败事件表 + 指数退避 + 死信状态"，与 2.3 的待办表可合并设计。

### 4.5 配额预占（下单占货）

现状：**支付成功时才扣配额**，因此存在"付了钱才发现当日配额不足"的体验问题（会产生一次失败回调 + 订单保持待支付）。
可改为下单时预占、超时释放。这是**业务侧**改进，与可靠性机制正交，工作量小但要处理"预占泄漏"（泄漏本身就是新的异常分支，需要新的兜底任务）。

### 4.6 过程回放可视化

把 `process_transition_log` 做成"单订单时间轴 + 状态变迁图"，管理端可点开任意订单看它的完整经历（含补偿记录）。
**价值**：★★ 论文配图与答辩演示效果极好，且是"可观测性"的直观体现。工作量小（前端为主，后端接口已有）。
