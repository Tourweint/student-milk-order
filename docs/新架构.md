# 一、先把“牛奶”完全拿掉

你的真实业务可以抽象成：

```text
现实业务需求
     ↓
业务订单
     ↓
执行计划
     ↓
多个执行任务
     ↓
任务逐个完成
     ↓
业务对象最终完成
```

但现实世界不是理想流程。

实际上是：

```text
                    ┌── 重复
                    ├── 并发
业务执行 ───────────┼── 超时
                    ├── 失败
                    ├── 部分成功
                    └── 数据不一致
```

所以系统真正需要解决的是：

> **如何管理一个长期业务过程的状态，以及如何让这个过程在异常条件下最终回到一个合法状态。**

这个抽象就比“订单管理系统”高了一层。

# 五、第二层才是你真正值得讲的东西：业务过程

## 1. 一个订单不是一个状态

这是你系统第一个真正的抽象。

普通订单：

```text
创建 → 支付 → 完成
```

你的订单：

```text
创建
 ↓
支付
 ↓
生成 N 个执行任务
 ↓
任务逐个执行
 ↓
任务状态不断变化
 ↓
最终聚合
 ↓
订单完成
```

所以：

> **订单状态是长期过程的宏观状态，配送任务状态是过程执行的微观状态。**

两者不能混在一起。

---

# 六、这就自然产生“父子状态机”

这是我建议你重点做成论文图的地方。

```text
                 Order
                   │
        ┌──────────┼──────────┐
        ↓          ↓          ↓
      Task 1     Task 2     Task 3
        ↓          ↓          ↓
      完成        完成        配送中
                             
                   ↓
              Order = 配送中
```

当：

```text
Task 1 = 完成
Task 2 = 完成
Task 3 = 完成
...
Task N = 完成
```

才：

```text
Order = 完成
```

这实际上是一个：

> **层级化业务状态管理模型。**

而不是单纯的订单状态字段。

# 七、“状态机靠表”就放到这里

你的 `state-rule` 不应该被描述成：

> “我做了一个可以在线修改状态机的功能。”

那样还是功能。

应该描述成：

> **将业务状态转换规则从程序控制逻辑中分离，使业务流程具有数据驱动特征。**

也就是：

```text
传统：

代码
 ↓
if status == X
 ↓
允许 Y


你的设计：

状态 + 操作 + 条件
       ↓
    规则表
       ↓
 状态机执行器
```

于是：

```text
状态规则
    ↑
数据库配置
    ↑
管理员调整
```

程序本身不需要重新发布。

这才是设计思想。

# 八、第三层：可靠执行

这里你原来的那些“零碎技巧”突然全部串起来了。

## 幂等

解决：

> **同一个动作执行多次怎么办？**

例如：

```text
微信回调
微信回调
微信回调
```

系统最终只能：

```text
一次有效落账
```

---

## CAS

解决：

> **两个执行者同时试图改变同一个状态怎么办？**

例如：

```text
A：支付
B：支付

status = 1
```

只有一个能够：

```text
1 → 2
```

另一个发现：

```text
WHERE status = 1
```

不成立，于是失败。

---

## 行锁

解决：

> **多个请求同时消耗有限资源怎么办？**

```text
库存 = 10

A 买 8
B 买 5
```

不能让数据库最终出现：

```text
库存使用 = 13
```

---

## 台账

解决：

> **资源究竟从哪里被消耗，又从哪里恢复？**

这就是你 `daily_quota_usage` 真正的价值。

它不是：

> 一个库存表。

而是：

> **资源变动的可追踪记录。**

所以退订的时候：

```text
原来从哪个池子扣掉
        ↓
现在精确回哪个池子
```

而不是简单：

```text
stock++
```

---

# 九、然后是你最值得保留的“对账 + 补偿”

因为它把问题又提升了一层。

假设：

```text
支付系统
    ↓
成功

但

订单系统
    ↓
没更新
```

那么：

```text
支付 = 成功
订单 = 待支付
```

系统出现了：

> **跨边界状态不一致。**

这时候你没有追求：

> 所有事情必须同时成功。

而是采用：

```text
发现不一致
     ↓
对账
     ↓
补偿
     ↓
恢复合法状态
```

这个思想非常重要。

它实际上是：

> **从“绝对原子性”转向“可检测、可恢复的最终一致性”。**

你的系统里已经有这个雏形了。

# 十、第四层：为什么还需要“兜底”？

因为：

> **可靠系统不能假设所有执行机会都会正常发生。**

例如：

```text
任务应该被处理
       ↓
但某个请求没有来
```

如果系统只是：

> “等下一次请求。”

那么它可能永远卡住。

所以：

```text
正常路径
   ↓
人工 / API / 回调
```

之外增加：

```text
兜底路径
   ↓
定时扫描
   ↓
发现异常状态
   ↓
执行恢复
```

你的系统里已经有：

```text
15 分钟未支付 → 自动取消

5 分钟 → 支付对账

配送日结束 → 自动签收
```

这三个东西放在一起后，意义就出来了：

> **系统不是只有正常执行路径，还具有基于状态的异常恢复路径。**

# 十一、于是你整个系统可以浓缩成一张图

我认为这张图甚至可以成为你答辩 PPT 的核心。

```text
                  业务请求
                     │
                     ↓
             ┌──────────────┐
             │  业务过程模型 │
             └──────┬───────┘
                    ↓
              状态机 / 任务
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
       正常执行             异常执行
          │                   │
          ↓                   ↓
     事务 / CAS / 锁       超时检测
     幂等 / 台账            对账 / 补偿
          │                   │
          └─────────┬─────────┘
                    ↓
                合法状态
```

这里最重要的是最后四个字：

> **合法状态。**

你的系统真正想保证的不是：

> “每一步都成功。”

现实系统做不到。

而是：

> **即使中间发生异常，系统最终也能识别问题，并将业务过程恢复到一个可解释、可继续执行的合法状态。**

这就是你整个毕设可以站住的理论核心。



* 失败数
* 库存最终值
* 是否出现超卖

## 实验二：重复支付


```text

```
